 1. Purpose
 This rewritten DD is the developer-facing version of the module contract DD_NOT-01-Notification_Service-v1.3.md.

 Verdict: ■ New | Wave: 1 | Group: Cross-cutting Foundation Services | Version: v1.3 Cross-cutting service consumed by
 many DDs. Owns three concerns: (1) artifact rendering — producing rendered output (PDFs, email bodies, SMS texts,
 future formats) from templates with placeholder substitution; (2) channel delivery — dispatching notifications through
 pluggable channel adapters (initial scope: email and SMS; architecture extensible to add WhatsApp, Telegram, push, or any
 other channel by adding a new adapter); (3) routing and preferences — deciding which event triggers which channels using
 which template, respecting per-customer preferences and per-operator regulatory rules. Version history: see
 CHANGELOG_NOT-01-Notification_Service.md in the same directory.

 The goal of this rewrite is to make the DD easier for a mid-level developer to implement without losing the detailed source
 contract.

 This DD should be implemented as part of the owning SOPHIX capability, not as an isolated service unless the deployment
 architecture explicitly separates that capability.

 Implement this DD with these rules:

   - Use the owning module APIs/repositories for authoritative writes.

   - Use approved internal APIs/client wrappers when reading another module's data.

   - Do not query another module's database tables directly from business flow code.

   - Treat worker names as logical Camunda external-task topics, not separate deployments.

   - One worker application may handle multiple topics, but metrics, retries, and logs must remain visible per topic.

   - Emit success events only after the authoritative state commit succeeds.

   - Use outbox publishing for Kafka events.

  Channel adapter                                                A pluggable implementation that knows how to send through one specific

                                                                 channel's API. One adapter per channel; per-operator configuration.

  Routing rule                                                   A per-operator mapping: when event X happens, send through channels [A, B,

 1. What this process is about
 NOT-01 is the service that turns events from across the platform into something a customer or admin actually sees — a PDF
 stored for later download, an email in their inbox, an SMS on their phone. It has three internal concerns that work together:

 Concern A — Artifact rendering. When an event arrives, NOT-01 looks up the templates configured for that event +
 operator + locale + channel, fills the placeholders with values from the event payload (plus supporting data like the customer
 snapshot and operator branding), and produces the rendered output. PDFs (invoices, credit/debit notes, tax invoices, dunning
 letters) are stored in MinIO per FOUNDATION_FILE_STORAGE.md and the URL is written back to the source entity's
 metadata. Email bodies and SMS texts are rendered in-memory and passed straight to the channel adapter.

 Templates are just text with placeholders. The templating engine is a deployment choice — Handlebars, Mustache,
 Thymeleaf, HTML-to-PDF tools, or plain string substitution all work. NOT-01 doesn't mandate one engine; it provides a
 TemplateEngine interface and selects the implementation based on the template's format (PDF templates use a
 PDF-capable engine; email and SMS use a text/HTML engine).

 Concern B — Channel delivery. When events require pushing a message to a customer or admin, NOT-01 dispatches
 through configured channels. Initial scope: email and SMS. The architecture uses pluggable channel adapters — adding
 WhatsApp, Telegram, in-app push, voice, or any other channel later is implementing a new adapter (and adding its template
 format) without changing routing, preferences, audit, or anything else in NOT-01.

 Concern C — Routing and preferences. "Which channels do I use, which templates, in what order, respecting which
 preferences" is configuration, not code. Per-operator routing rules map event types to channel + template lists. Per-customer
 notification preferences override defaults (customer opted out of SMS but accepts email). Per-operator regulatory rules
 enforce constraints (no SMS after 21:00 in some markets; transactional vs marketing distinction).

 #### How rendering and channel delivery relate

 For an event like InvoiceIssued, NOT-01 typically does both:

   1. Renders the PDF first (using the operator's PDF template) — produces the artifact, stores it in MinIO, gets a URL

   2. Renders channel artifacts (email subject + body, SMS text) using their respective templates

   3. Dispatches through channels — sends email with the PDF attached or linked, sends SMS with a link to the PDF (the
     URL points to BIL-02-READ-01's PDF endpoint, which proxies the stored artifact)

 For an event like PtpRegistered that doesn't need a PDF:

   1. PDF rendering is skipped

   2. NOT-01 renders the email/SMS templates and dispatches a confirmation ("We've registered your promise to pay
     6,402.50 KES by 25 May")

 For an admin action like PdfRerenderRequested (admin asked READ-01 to retry a failed render):

   1. Only PDF rendering runs — produces a new PDF, replaces the URL in invoice.metadata.pdf_url

   2. Channel dispatch may or may not run depending on whether a re-notification is requested

 #### Extensibility — adding a channel later

 Adding a channel (WhatsApp, Telegram, in-app push, voice, paper mail, anything else) is a contained change:

   1. Implement a new ChannelAdapter for that channel

   2. Define template format(s) for that channel (e.g., WHATSAPP_TEMPLATE_REF for pre-approved WhatsApp templates;
     PUSH_PAYLOAD for push)

   3. Add per-operator channel config row (credentials, identifiers)

   4. Operators add routing rules that include the new channel

   5. Customer preference table gets a new opt-in field

 The routing engine, the preferences engine, the failure handling, the audit, the admin operations all remain unchanged. The
 DD's design separates "what the channel is" from "how routing and preferences work" precisely to make this extension
 cheap.

 Channels NOT in initial scope: WhatsApp, Telegram, in-app push, voice/IVR, paper mail, in-app messages (notification feed
 within the portal/app — those are owned by the consuming UI, not NOT-01).

 #### What NOT-01 explicitly does not own

   - Event sources — invoice issuance, payment events, subscription lifecycle, etc. are owned by their respective DDs;
     NOT-01 just consumes events

   - Customer master — CRM owns customer identity, contact details (email, phone), language preference at the customer
     level. NOT-01 reads these via a service call when composing notifications

   - Dunning policy — BIL-04 Collections decides "step 1 reminder at D+3, step 2 at D+7, etc." and emits events to NOT-01;
     NOT-01 doesn't decide the schedule

   - Marketing campaigns — separate marketing system owns campaign creation, segmentation, scheduling. May piggyback
     on NOT-01's channel adapters for actual sending, but the campaign logic is elsewhere

   - In-app message rendering — owned by the UI (portal, mobile app)

   - Voice / IVR notifications — out of scope for initial release; if needed later, added as a new channel adapter

   - Long-running customer support conversations — out of scope; NOT-01 handles transactional/notification messages,

 Technical design
 Module placement
 New notification module deployed on its own cluster (cluster N). Cluster choice rationale: notification traffic has different
 scaling characteristics from billing (spiky around cycle close + dunning waves) and different external dependencies (SMTP,
 SMS gateways, etc.) that benefit from network isolation. Cluster N has independent CPU/memory/network capacity from
 cluster C.

 Adds the following new tables: template, notification_routing_rule, channel_operator_config,
 customer_notification_preference, notification_log, notification_delivery_attempt,
 render_failure_queue. All on cluster N. (When new channels are added later, they may need additional tables — e.g., a
 token store for push, a chat-link store for messaging-app channels — added at that time.)

 End-to-end flow — InvoiceIssued
          Step 1 — Event consumed
            RenderEventConsumer reads InvoiceIssued from billing topic
            Extracts: invoice_id, customer_id, operator_code, invoice_type_code, payload

          Step 2 — Idempotency check (Redis)
            Key: notification:processed:{event_id}
            If exists → skip (already processed); ack event and return
            If not → set key with 24h TTL, continue

          Step 3 — Route resolution
            - RoutingResolverService.resolve("InvoiceIssued", operator_code, payload)
              → [{channel: EMAIL, priority: 1, urgency: NORMAL, purpose: INVOICE_CYCLE_POSTPAID},
                 {channel: SMS,   priority: 2, urgency: NORMAL, purpose: INVOICE_CYCLE_POSTPAID}]
            - PreferenceFilterService.apply(customer_id, channels)
              → customer opted out of SMS marketing → SMS is transactional so kept; if it were marketing, dropped
            - RegulatoryFilterService.apply(operator_code, channels, now)
              → no restrictions → list unchanged

          Step 4 — Render PDF (if any channel needs it)
            - TemplateLookupService.resolve(operator_code, PDF, "INVOICE_CYCLE_POSTPAID", customer.locale)
              → Template row, OR null
            - If null → render_failure_queue + RenderFailed event + skip PDF-dependent channels
            - TemplateEngineRegistry.engineFor(PDF).render(template, payload, customer_snapshot)
              → byte[] PDF
            - PdfStorageService.store(operator, "invoices/2026/05/inv_01HZ...pdf", bytes)
              → MinIO key
            - Update invoice.metadata.pdf_url via the billing API (or direct DB write if same cluster — TBD)
            - Emit PdfReady

          Step 5 — Render channel artifacts per channel and dispatch
            For each remaining channel:
              For each template format the channel needs (e.g., EMAIL needs SUBJECT + HTML + TEXT):
                Resolve template + render
              DispatchService.queue(channel, RoutingDecision, rendered_artifacts, pdf_url_if_applicable)
              → internal Kafka topic: notification.dispatch.{channel}

             EmailAdapter consumer:
               - Resolve customer's email from CRM
               - Compose with rendered subject + HTML + text + PDF attachment (or link)
               - Send via SMTP
               - On 2xx: notification_delivery_attempt row with status=SENT
               - On 4xx/5xx: notification_delivery_attempt row with status=FAILED + category
               - If TRANSIENT failure: retry scheduler queues retry
               - If PERMANENT_RECIPIENT: fallback to next channel in priority order

             SmsAdapter consumer (in parallel):
               - Resolve customer's phone from CRM
               - Send rendered SMS text via SMSC API (truncate or split if needed)
               - Track DLR if supported

          Step 6 — Audit and downstream


SOPHIX BSS Design Documents                                                                                         Page 12
               - notification_log aggregate row written (final status across all channels)
               - Emit NotificationDispatched (or NotificationFailed if all channels failed)


 Retry flow
             RetryScheduler runs every 1 minute
               Queries notification_delivery_attempt WHERE status = 'PENDING_RETRY' AND next_attempt_at <= NOW()
               For each:
                 BEGIN TRANSACTION
                   SELECT FOR UPDATE
                   If still PENDING_RETRY:
                     DispatchService.retry(attempt)
                     Update attempt: increment attempt_count, set next_attempt_at based on backoff schedule
                     After max attempts: set status = ESCALATED, emit NotificationEscalated
                 COMMIT

 Channel adapter contract
 The ChannelAdapter interface is the contract that makes NOT-01 extensible. Adding a new channel means writing one
 new adapter; nothing else in NOT-01 changes. This section documents the contract precisely enough that a developer can
 implement a new adapter from this DD alone.

 #### Java interface
          package com.sophix.notification.dispatch.adapter;

          import java.time.Duration;
          import java.util.Map;
          import java.util.Optional;

          /**
           * Channel adapter contract. One implementation per channel (email, SMS, future channels).
           *
           * Lifecycle: instantiated once per (channel, operator_code) pair at application startup,
           * cached by the dispatcher, and reused for all dispatches on that channel + operator.
           * Adapter instances are SHARED across threads and MUST be thread-safe.
           *
           * The adapter does NOT decide who to send to, what template to use, or whether to send —
           * those decisions are owned by the routing module. The adapter receives a fully-resolved
           * Dispatch and produces a DeliveryResult.
           */
          public interface ChannelAdapter {

               /**
                * Channel this adapter handles. Used by the dispatcher to route Dispatch instances
                * to the correct adapter implementation.
                */
               Channel channel();

               /**
                * Called once when the adapter instance is created. Receives the per-operator config
                * row for this (channel, operator_code) and the resolved credentials from the secret
                * store. The adapter validates the config and prepares any reusable resources
                * (SMTP connection pool, HTTP client, etc.).
                *
                * Throws AdapterConfigurationException if the config is invalid or required credentials
                * are missing — caught by the dispatcher, which marks the adapter UNUSABLE and emits
                * an operational alert. The dispatcher does NOT retry initialization automatically.
                *
                * @param config the row from channel_operator_config + decrypted credentials
                */
               void initialize(ChannelOperatorConfig config) throws AdapterConfigurationException;

               /**
                * Send one dispatch through the channel. MUST be idempotent on the adapter's side:
                * if the dispatcher retries the same Dispatch (same dispatch_id), the adapter MUST
                * either (a) re-send accepting that the recipient may receive a duplicate, or
                * (b) detect the duplicate via the channel's deduplication mechanism if available
                * and return a SENT result without re-sending. Most channels don't have native
                * deduplication, so (a) is the default — the dispatcher's idempotency layer (Redis
                * key per source event) prevents most duplicates at a higher level.



SOPHIX BSS Design Documents                                                                                                 Page 18
                *
                * MUST respect the timeout parameter — return TRANSIENT failure if the channel
                * doesn't respond within the timeout rather than blocking indefinitely.
                *
                * MUST NOT mutate any shared state visible outside the adapter.
                * MUST NOT log PII at INFO level (recipient address / phone are PII).
                *
                * @param dispatch the resolved dispatch — rendered artifacts, recipient, metadata
                * @param timeout max time to wait for channel response
                * @return result with status (SENT or FAILED), failure category if failed, and
                *         channel-specific response data for audit
                */
               DeliveryResult send(Dispatch dispatch, Duration timeout);

               /**
                * Called once when the application is shutting down. Releases resources (connection
                * pools, file handles). MUST complete within 10 seconds; otherwise the JVM terminates
                * forcibly.
                */
               void shutdown();
          }

 #### Contract rules

 A new adapter implementation MUST satisfy:

  Rule                                                             What it means

  Thread-safe                                                      send() is called from multiple threads concurrently. The adapter must not have
                                                                   shared mutable state without synchronization. Connection pools, HTTP clients,
                                                                   and similar resources are fine — they're designed for concurrent use.

  No side effects beyond the channel call                          The adapter MUST NOT write to the database, emit Kafka events, update
                                                                   caches, or modify any state outside its own internal resources. The dispatcher
                                                                   owns audit and event emission.

  Categorize failures correctly                                    A TRANSIENT failure incorrectly marked as PERMANENT means the customer
                                                                   never receives the message even though a retry would have worked. A
                                                                   PERMANENT failure marked TRANSIENT means 8 hours of pointless retries.
                                                                   Each adapter MUST document its category mapping from the channel's error
                                                                   codes in a comment block.

  Respect the timeout                                              If the channel doesn't respond within timeout, return TRANSIENT failure with
                                                                   detail "timeout after Xs". Do not block indefinitely; that blocks the dispatcher
                                                                   thread.

  No PII in logs at INFO                                           Recipient address, phone number, and message content are PII. At INFO level,
                                                                   log only dispatch_id, notification_id, status, category. PII may
                                                                   appear at DEBUG (operator-controlled).

  Idempotent at the dispatcher contract                            The dispatcher may call send() more than once with the same dispatch_id
                                                                   (during retry, after restart). The adapter sends each time unless the channel
                                                                   itself supports deduplication. The dispatcher's higher-level idempotency (Redis
                                                                   key per source event) prevents most duplicates; the adapter doesn't need its
                                                                   own dedup layer.

  Capture externalReference                                        If the channel returns a message ID, tracking ID, or similar reference, populate
                                                                   externalReference in the result. This enables later DLR (delivery receipt)
                                                                   correlation and customer-support troubleshooting.

  Truncate channelResponse to 4KB                                  Some channel responses are large (full HTTP response bodies). Adapters
                                                                   MUST truncate to 4KB before returning so the audit table doesn't bloat.


 #### Worked example: EmailAdapter skeleton
           package com.sophix.notification.dispatch.adapter;

           import jakarta.mail.*;
           import jakarta.mail.internet.*;
           import java.time.Duration;
           import java.util.Properties;

           public final class EmailAdapter implements ChannelAdapter {

                 private Session smtpSession;
                 private String senderAddress;
                 private MinioClient minioClient;   // injected for PDF attachment fetch
                 private boolean attachPdf;          // operator config: attach vs link

                 @Override
                 public Channel channel() {
                     return Channel.EMAIL;
                 }

                 @Override
                 public void initialize(ChannelOperatorConfig config) throws AdapterConfigurationException {
                     Map<String, String> creds = config.getCredentials();
                     if (!creds.containsKey("smtp_host") || !creds.containsKey("smtp_user")) {
                         throw new AdapterConfigurationException(
                             "EmailAdapter requires 'smtp_host' and 'smtp_user' credentials"



SOPHIX BSS Design Documents                                                                                                                Page 20
                        );
                   }

                   Properties props = new Properties();
                   props.put("mail.smtp.host", creds.get("smtp_host"));
                   props.put("mail.smtp.port", creds.getOrDefault("smtp_port", "587"));
                   props.put("mail.smtp.starttls.enable", "true");
                   props.put("mail.smtp.auth", "true");

                   this.smtpSession = Session.getInstance(props, new Authenticator() {
                       @Override protected PasswordAuthentication getPasswordAuthentication() {
                           return new PasswordAuthentication(
                               creds.get("smtp_user"),
                               creds.get("smtp_password")
                           );
                       }
                   });

                   this.senderAddress = config.getSenderIdentifier();
                   this.attachPdf = Boolean.parseBoolean(
                       config.getAdditionalConfig().getOrDefault("attach_pdf", "true").toString()
                   );
               }

               @Override
               public DeliveryResult send(Dispatch dispatch, Duration timeout) {
                   try {
                       MimeMessage msg = new MimeMessage(smtpSession);
                       msg.setFrom(new InternetAddress(senderAddress));
                       msg.addRecipient(Message.RecipientType.TO, new InternetAddress(dispatch.getRecipient()));
                       msg.setSubject(dispatch.getRenderedArtifacts().get(TemplateFormat.EMAIL_SUBJECT));

                        Multipart multipart = new MimeMultipart("alternative");

                        // Text part
                        MimeBodyPart textPart = new MimeBodyPart();
                        textPart.setText(
                            dispatch.getRenderedArtifacts().get(TemplateFormat.EMAIL_TEXT),
                            "UTF-8"
                        );
                        multipart.addBodyPart(textPart);

                        // HTML part
                        MimeBodyPart htmlPart = new MimeBodyPart();
                        htmlPart.setContent(
                            dispatch.getRenderedArtifacts().get(TemplateFormat.EMAIL_HTML),
                            "text/html; charset=UTF-8"
                        );
                        multipart.addBodyPart(htmlPart);

                        // PDF attachment (if configured and present)
                        if (attachPdf && dispatch.getPdfStorageKey().isPresent()) {
                            MimeBodyPart pdfPart = new MimeBodyPart();
                            byte[] pdfBytes = minioClient.getObject(
                                dispatch.getOperatorCode(),
                                dispatch.getPdfStorageKey().get()
                            );
                            pdfPart.setContent(pdfBytes, "application/pdf");
                            pdfPart.setFileName(dispatch.getPdfStorageKey().get().split("/")[3]);
                            multipart.addBodyPart(pdfPart);
                        }

                        msg.setContent(multipart);

                        // Send with timeout (SMTP transport blocks; would wrap in executor in practice)
                        Transport.send(msg);

                        return DeliveryResult.sent(
                            msg.getMessageID(),
                            Map.of("smtp_message_id", msg.getMessageID())
                        );

                   } catch (SendFailedException e) {
                       return DeliveryResult.failed(
                           categorize(e),
                           e.getMessage(),
                           Map.of("error_class", e.getClass().getSimpleName())
                       );
                   } catch (MessagingException e) {
                       return DeliveryResult.failed(
                           FailureCategory.TRANSIENT,
                           e.getMessage(),

                              Map.of("error_class", e.getClass().getSimpleName())
                        );
                   }
               }

               /**
                 * Category mapping for SMTP errors.
                 *
                 * SMTP 5xx codes (permanent):
                 *    550, 553 — invalid recipient                   -> PERMANENT_RECIPIENT
                 *    552       — message size exceeds limit          -> PERMANENT_TEMPLATE
                 *    554       — transaction failed (often spam-flag) -> PERMANENT_TEMPLATE
                 *
                 * SMTP 4xx codes (transient):
                 *    421 — service not available                     -> TRANSIENT
                 *    450 — mailbox unavailable                       -> TRANSIENT
                 *    451 — local error                               -> TRANSIENT
                 *    452 — insufficient storage                      -> TRANSIENT
                 *
                 * Connection-level errors (timeout, refused)         -> TRANSIENT
                 */
               private FailureCategory categorize(SendFailedException e) {
                    int code = parseSmtpCode(e);
                    if (code >= 500) {
                          if (code == 550 || code == 553) return FailureCategory.PERMANENT_RECIPIENT;
                          return FailureCategory.PERMANENT_TEMPLATE;
                    }
                    return FailureCategory.TRANSIENT;
               }

               private int parseSmtpCode(SendFailedException e) {
                   // implementation extracts the SMTP code from the exception message
                   return 0;
               }

               @Override
               public void shutdown() {
                   // jakarta.mail Session has no explicit close; SMTP connections are per-send
               }
          }

 #### Adding a new channel — checklist for the implementer

 When adding a new channel (e.g., WhatsApp) later:

   1. Add the enum value to Channel (e.g., WHATSAPP)

   2. Add template format(s) to TemplateFormat if needed (e.g., WHATSAPP_TEMPLATE_REF)

   3. Implement a new ChannelAdapter for the channel

   4. Register the adapter implementation in the dispatcher's adapter registry

   5. Add a column to customer_notification_preference for the new opt-in (additive migration)

   6. Add per-operator rows to channel_operator_config for operators that enable the channel

   7. Operators add routing rules that reference the new channel

   8. Document the channel's adapter implementation reference in the channel-specific notes section

 Nothing else in NOT-01 changes. The routing engine, the preferences engine, the failure handling, the retry scheduler, the
 audit tables, the admin operations — all unaffected.

 B — Target operator coverage
 Each operator deploys their own per-channel configuration, templates, and routing rules. The four target operators (Wananchi
 KE, Wananchi UG, Wananchi TZ, Yas SN) will each set up:

   - SMTP / email service contract → EmailAdapter config

   - SMS gateway / aggregator → SmsAdapter config

   - Per-operator templates per (template_format, template_purpose_code, locale)

   - Per-operator routing rule set

 When additional channels are added in future phases (e.g., WhatsApp, in-app push), each operator that wants them sets up
 the corresponding external service contract and adapter config; existing email/SMS deployments are unaffected.

 The DD describes the platform capability; per-operator setup is per-operator implementation work outside this DD.



 C — Current TZ and gap
 Workshop materials do not describe a unified notification service in TZ Sophix. Various per-DD notification mechanisms likely
 exist (email triggers in billing, SMS triggers in subscription, etc.) but there is no documented service to compare against.

 NOT-01 is entirely new functionality as a unified service. It introduces:

   - Single notification surface across channels (initial scope: email, SMS)

   - Channel-agnostic adapter contract enabling future channel additions without changing routing or preferences

   - Per-operator template management with versioning, format-agnostic (PDF, email parts, SMS text — same template
     model)

   - Per-customer preference management

   - Centralized routing rules

   - Comprehensive audit

   - Artifact rendering separated from event sources

   - Failure handling with retries and channel fallback
