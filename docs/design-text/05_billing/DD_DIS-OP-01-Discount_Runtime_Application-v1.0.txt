 DD_SIP-03, DD_SIP-05, DD_BIL-01, DD_BIL-02-GEN-01, DD_BIL-05, DD_BIL-CFG-01, DD_EM-CFG-04,

 MVP simplification baseline: DIS-OP-01 starts with deterministic billing-time discount application for active assignments and
 simple campaign eligibility. Keep high-volume runtime logic efficient and testable; use Drools only for operator-configurable
 policy, not fixed arithmetic or invoice-line validation.



 1. Purpose
 DIS-OP-01 defines how SOPHIX applies configured discounts during billing, order charging, invoice generation, and
 wallet-credit operations.

 The catalog and assignment modules answer these questions:

  Question                                                                            Owning DD

  What is this discount and how is it calculated?                                     PLM-CFG-04

  Who has been granted this discount?                                                 SIP-03

  Which campaign may create discount assignments?                                     SIP-05

  Which charge event is being billed?                                                 BIL-CFG-01 and BIL-01

  How is the discount applied at runtime?                                             DIS-OP-01


 DIS-OP-01 is therefore the runtime calculation and audit layer. It receives a charge context from Billing, retrieves eligible
 active assignments from SIP-03, loads discount definitions from PLM-CFG-04, applies ordering/stacking/cap rules, returns
 discount lines to Billing, and records what happened.

 Use this DD when:

   - a recurring MRC charge must be reduced by a percentage or fixed amount;

   - an installation charge must be waived during an acquisition campaign;

   - a prorated invoice line must include discount impact;

   - a prepaid wallet needs to receive a promotional credit;

   - support must explain why a discount did or did not apply;

   - a failed or disputed discount decision must be replayed without double-applying money.

 Do not use DIS-OP-01 to create discounts or assign discounts to customers. That remains PLM-CFG-04 and SIP-03.

 4. Terminology
  Term                                                                    Meaning

  Charge context                                                          Runtime payload describing the customer, subscription, package, event code,
                                                                          base amount, tax context, and date being charged.

  Candidate assignment                                                    Active SIP-03 discount assignment that may apply to the charge context.

  Discount definition                                                     PLM-CFG-04 record that defines amount, calculation type, validity, caps, event
                                                                          applicability, and stacking metadata.

  Runtime decision                                                        Auditable decision showing candidates, accepted discounts, rejected discounts,
                                                                          and reasons.

  Discount application                                                    The persisted result of applying discounts to one charge context.

  Discount line                                                           One monetary effect returned to Billing or Wallet.

  Stacking                                                                Whether multiple discounts can apply to the same charge context.

  Cap                                                                     Maximum discount amount allowed per event, period, customer, assignment, or
                                                                          campaign.

 8. Integration Contracts
 8.1 Calls To SIP-03
 DIS-OP-01 calls:
           GET /api/discount-assignments/effective?operatorCode=WIK&subscriptionId=SUB-700045&eventCode=RECURRING_MRC&onDate=2026-06-

 The response identifies assignments. DIS-OP-01 still validates the runtime charge context because the same assignment
 may be eligible for one event and not another.

 8.2 Calls To PLM-CFG-04
 DIS-OP-01 loads discount definitions by code/id. The definition must include:

   - calculation type;

   - value/rate;

   - max amount and cap scope;

   - allowed billable event codes;

   - allowed package/service/category constraints;

   - stacking group;

   - rounding rule;

   - wallet-credit behavior, if applicable.

 8.3 Calls To BIL-05
 For WALLET_CREDIT discount lines, DIS-OP-01 does not write wallet ledger rows itself. It calls BIL-05:
           POST /api/wallets/{wallet_id}/credit
           Idempotency-Key: wallet-credit-dapp-001-dal-001
           Content-Type: application/json

           {
               "amount": 500.00,
               "currency": "KES",
               "transactionType": "PROMOTIONAL_CREDIT",
               "reference": "dapp-001/dal-001",
               "reasonCode": "CAMPAIGN_WALLET_CREDIT"
           }


 8.4 Return To BIL-01/BIL-02
 BIL-01 uses netAmount and lines to create charge results. BIL-02 uses returned lines to show invoice-level discount details.
 Tax calculation order must follow PLM-CFG-02 and BIL-02 tax rules.

 11. Rule Engine Guidance
 Use Drools for operator-variable decisions:

  Rule file                                                                Purpose

  discount-runtime-eligibility.drl                                         Decide if candidate assignment is eligible for the runtime context.

  discount-runtime-stacking.drl                                            Select which candidates survive stacking conflict checks.

  discount-runtime-cap-policy.drl                                          Choose cap scope and cap period when policy differs by
                                                                           operator/channel/product.

  discount-runtime-replay-approval.drl                                     Decide if a replay/override should call EM-CFG-04.



SOPHIX BSS Design Documents                                                                                                                           Page 9
 Do not use Drools for fixed validations such as JSON shape, required fields, date parsing, DB uniqueness, or idempotency
 hash comparison.

 Example:
              package com.sophix.discount.runtime

              rule "Manual replay above threshold requires finance approval"
              when
                $r : DiscountReplayFact(expectedFinancialImpact >= 1000.00, currencyCode == "KES")
                $d : ReplayDecision()
              then
                $d.setApprovalRequired(true);
                $d.setApprovalPolicyCode("DISCOUNT_RUNTIME_REPLAY_FINANCE");
                $d.addReason("REPLAY_FINANCIAL_IMPACT_ABOVE_THRESHOLD");
              end




 12. Worker Model
 DIS-OP-01 does not require a dedicated worker per action. For a budget-conscious medium deployment, consolidate these
 jobs inside the billing worker deployment:

  Worker job                                  Purpose                                                 Frequency

  discount-cap-reconcile                      Reconcile cap usage with application lines.             Nightly.

  discount-application-outbox-publish         Publish outbox events.                                  Continuous/short interval.

  discount-wallet-credit-retry                Retry failed BIL-05 wallet-credit calls.                Every 5 minutes.

  discount-replay-runner                      Execute approved replays.                               On demand / queue.


 Operational rule: one worker process can handle multiple job types if metrics and retry queues are separated.

 14. Infrastructure Recommendations
 For a medium budget deployment, implement DIS-OP-01 inside the billing API/service deployment rather than a separate
 pod. Keep the database tables in the billing schema.

 16. Testing Guidance
  Test                                                              Expected result

  No active assignment                                              Application status REJECTED, no lines.

  One active percentage discount                                    Correct amount and net amount returned.

  Full fee waiver                                                   Discount equals base amount, net zero.

  Two discounts same stacking group                                 Highest priority accepted, other rejected with reason.

  Two compatible stacking groups                                    Both accepted in configured order.

  Cap reached                                                       Candidate rejected with REJECTED_CAP_REACHED.

  Concurrent applies near cap                                       Cap usage not exceeded.

  Same idempotency key/context                                      Same response returned.

  Same idempotency key/different context                            409.

  Wallet credit discount                                            BIL-05 credit called once with idempotency.

  Preview request                                                   No cap update, no wallet credit.

  Replay requiring approval                                         EM-CFG-04 request created; no recompute until approved.




 17. Acceptance Criteria
   - Runtime preview and apply APIs exist.

   - DIS-OP-01 reads effective assignments from SIP-03 and definitions from PLM-CFG-04.

   - Billing apply is idempotent and records application, lines, decisions, and cap usage.

   - Stacking, eligibility, cap, and replay approval rules are configurable through Drools where operator-variable.

   - Wallet-credit discounts are posted through BIL-05, not direct DB writes.

   - Replay/override financial changes use EM-CFG-04 when configured.

   - Backoffice can explain why each candidate discount was accepted or rejected.

   - Events are emitted through an outbox.

   - Tests cover idempotency, cap concurrency, stacking, preview side effects, and wallet-credit integration.
