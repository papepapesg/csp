 1. What this process is about
 A subscription workflow (ACTIVATE, RESUME, UPGRADE, DOWNGRADE, RELOCATION, MIGRATION) reaches its
 fulfillment step. The workflow's BPMN dispatches a worker (ful-call-activate or ful-call-modify) which calls
 FUL-03's REST endpoint synchronously. FUL-03 then:

   1. Loads the subscription's current Package + the Package's Services from SIP-01 + PLM-CFG-01.

   2. For MODIFY_SERVICE: also loads the target Package composition (carried in envelope).

   3. Loads the HomePass + service_management_endpoints from RLM-CFG-01.

   4. For each Service to dispatch:

   - Resolves target via homepass.service_management_endpoints[service.serviceManagementKey] →
     {nodeCode, port}.

   - If serviceManagementKey is null (partner-fulfilled service), passes (null, null) to the adapter.

   - Looks up Provisioner adapter by service.provisionerKey.

   - Invokes the verb matching intent:

   - ACTIVATE_SERVICE → Provisioner.activateService(...)

   - MODIFY_SERVICE for an added class → Provisioner.activateService(...)

   - MODIFY_SERVICE for a dropped class → Provisioner.deactivateService(...)

   - MODIFY_SERVICE for a modified class (same class, different profile params) →
     Provisioner.modifyService(oldParams, newParams, ...)



SOPHIX BSS Design Documents                                                                                                                 Page 4
   - RESUME_SERVICE → Provisioner.resumeService(...)

   - For ACTIVATE_SERVICE calls, also runs per-customer network-side setup specific to the service class — e.g., for IPTV:
     provision IGMP-snooping on the port, join the customer's chosen multicast groups, register STB serial in IPTV middleware
     AAA.

   5. Aggregates per-Service outcomes into a terminal state (FULLY_PROVISIONED / PARTIALLY_PROVISIONED /
     FAILED_AT_FIRST_SERVICE / FAILED_AND_ROLLED_BACK).

   6. On PARTIALLY_PROVISIONED or FAILED_AND_ROLLED_BACK: runs compensation by invoking the inverse Provisioner
     verb on each previously-succeeded Service.

   7. Returns to the caller synchronously within the 60-second time budget.

 The HomePass is not mutated by FUL-03. RLM-CFG-01 is read-only. HomePass-side bookkeeping (counter + binding row) is
 owned by FUL-07, called by the workflow separately.

 #### 2.3 MODIFY_SERVICE diff computation

  Rule                                      Description

  R-FUL-03-MO-1                             For intent = MODIFY_SERVICE, FUL-03 computes three sets by comparing
                                            source Package composition (serviceRefs[]) to target Package composition
                                            (targetPackageRef.serviceRefs[]): (a) addedServices[] — Services
                                            in target but not in source; (b) droppedServices[] — Services in source but
                                            not in target; (c) modifiedServices[] — Services in both, BUT with different
                                            network_profile_shape.params (e.g., same INET class, different speed
                                            tier).

  R-FUL-03-MO-2                             Dispatch per class: (a) addedServices[] →
                                            Provisioner.activateService(...) per Service; (b)
                                            droppedServices[] → Provisioner.deactivateService(...) per

                                            Provisioner.modifyService(oldParams, newParams, ...) per

  R-FUL-03-MO-3                             Equipment-binding deltas are NOT handled by FUL-03. The caller
                                            (UPGRADE-01 / DOWNGRADE-01) is responsible for: (a) ensuring required

                                            carries the post-modification bindings, which FUL-03 passes to Provisioners but
                                            does not validate.

  R-FUL-03-MO-4                             Dispatch order for MODIFY_SERVICE: (a) added classes first (so customer sees
                                            new functionality during the change window even if a dropped class is still up);
                                            (b) modified classes next; (c) dropped classes last. The Package owner may
                                            declare a different order in Package.modificationOrder; FUL-03 honors it.

  R-FUL-03-MO-5                             If both source and target Service lists are identical (no diff), FUL-03 returns

 #### 2.5 Compensation

  Rule                          Description

  R-FUL-03-CO-1                 Compensation invoked when terminal state is FAILED_AND_ROLLED_BACK.
                                For each previously-successful Service, FUL-03 calls the inverse Provisioner
                                verb: activateService → deactivateService; modifyService →
                                modifyService(oldParams = newParams, newParams = oldParams)
                                (reverse-direction modify); deactivateService → activateService;
                                resumeService → suspendService. Order: reverse of original dispatch.

  R-FUL-03-CO-2                 If compensation itself fails for any Service: terminal compensation state
                                recorded as COMPENSATION_FAILED in the ledger; emit
                                CompensationFailed Kafka event; manual NOC recovery required. The
                                fulfillment ledger row is the audit anchor.

  R-FUL-03-CO-3                 A failed MODIFY_SERVICE rollback returns the subscription's network state to
                                its pre-modification configuration. The caller (UPGRADE-01 /
                                DOWNGRADE-01) is responsible for reverting its own state changes
                                (package_ref, equipment bindings, billing).


 #### 2.6 Outcome aggregation

  Rule                          Description

  R-FUL-03-OA-1                 Terminal state = FULLY_PROVISIONED when all dispatched Services succeed.

  R-FUL-03-OA-2                 Terminal state = PARTIALLY_PROVISIONED when some Services succeed
                                and some fail BUT the failure mode is policy = TOLERATE_PARTIAL. The
                                caller decides whether to accept partial or revert.

  R-FUL-03-OA-3                 Terminal state = FAILED_AT_FIRST_SERVICE when the first Service fails
                                AND policy = ABORT_ON_FIRST_FAIL (the default). No compensation
                                needed (no prior successes).

  R-FUL-03-OA-4                 Terminal state = FAILED_AND_ROLLED_BACK when a Service fails AFTER
                                prior successes AND policy requires rollback. Compensation runs per §2.5.

  R-FUL-03-OA-5                 Per-Service outcomes are recorded in fulfillment_service_outcome
                                (one row per Service per fulfillment). Carries service_ref, outcome
                                (SUCCEEDED / FAILED / SKIPPED_NOT_ADDRESSABLE / COMPENSATED /
                                COMPENSATION_FAILED), adapter_refs (vendor-system IDs),
                                failure_reason, failure_detail, target_node_code, target_port,
                                duration_ms.

 10:35:38 — ful-call-modify worker invokes FUL-03 (same request body as §4.2).

 policy=ABORT_ON_FIRST_FAIL, terminal state = FAILED_AT_FIRST_SERVICE (not FAILED_AND_ROLLED_BACK — no
 prior successes to roll back).

 But wait: the adapter DID partially apply state — IGMP-snooping is enabled on the port and the multicast group is joined.
 Even though the AAA registration failed, the network plane has partial state. The adapter's contract requires it to self-roll-back
 its own intermediate state on failure (the adapter should call its own teardown on the IGMP enable + multicast join when it
 knows the AAA registration won't complete). The adapter does this internally; FUL-03 doesn't see it.

 If for some reason the adapter cannot self-roll-back (e.g., the OLT is also unreachable now), the adapter returns
 failure_reason=ADAPTER_ERROR with compensationState=ADAPTER_INTERNAL_ROLLBACK_FAILED. FUL-03
 records this and emits CompensationFailed to NOC.

 doesn't return non-200 — the BPMN catches the failure via the response body's terminalState).

 FULLY_PROVISIONED and enters its own compensation: (a) osr-equipment-unbind for the STB (it's no longer in use);

 UPGRADE_FAILED_REVERSAL_INTENT to refund the proration delta; (d) emit SubscriptionUpgradeRejected with

 Failure with prior successes — alternative path: Imagine a more complex case where Njeri's upgrade also changed her

 addedServices=[svc_IPTV_BASIC]. Per dispatch order (§2.3 R-MO-4), added classes first → IPTV first. If IPTV failed,
 no rollback needed (no prior successes). But if the order were modified first: INET modify succeeds (1.5s), then IPTV fails

 newParams=oldINET, ...) to reverse the INET speed change. If that succeeds, INET back to 50Mbps and terminal state
 = FAILED_AND_ROLLED_BACK. If the rollback also fails, terminal state = COMPENSATION_FAILED and NOC alert fires.

 This is why FUL-03's dispatch order matters: added-classes-first (the default) minimizes the rollback surface area in failure
 cases.

 7.1 Build order
 This DD (v1.1) deploys after:

   1. FUL-03 v1.0 (already deployed; v1.1 is a backwards-compatible extension)

   2. PLM-CFG-01 v1.0 (declares the 5-method Provisioner interface; pending)

   3. SIP-01 v1.0 (Package + Package Version pinning)

   4. RLM-CFG-01 v1.0 (HomePass + service_management_endpoints)

 Callers depending on v1.1 verbs:

   - UPGRADE-01 / DOWNGRADE-01 (require MODIFY_SERVICE)

   - RELOCATION-01 / MIGRATION-01 (use ACTIVATE_SERVICE against target HomePass — already in v1.0, no change
     needed for them)

   - RESUME-01 (requires RESUME_SERVICE)

 7.2 Stub debt + open coordination items
   - PLM-CFG-01 v1.0 Provisioner interface declaration — pending. The 5-method interface (activateService /
     modifyService / deactivateService / resumeService / suspendService) needs to be formally specified in
     PLM-CFG-01 v1.0 before adapter implementations can target it.

   - v1.0 endpoint deprecation — POST /api/activation/execute remains as an alias for
     intent=ACTIVATE_SERVICE. Marked deprecated; removal planned for v2.0. Existing ACTIVATE-01 callers continue
     without code change.

   - Equipment-binding validation — FUL-03 does not validate that equipmentBindings[] covers all
     equipment_requirement Services. The caller (UPGRADE-01 / DOWNGRADE-01 / ACTIVATE-01 / RELOCATION-01
     / MIGRATION-01) is responsible. If FUL-03 needs to enforce this in a future version, it would require reading
     PLM-CFG-01's equipment_requirement field per Service and rejecting on mismatch.
