 Sophix V3 MVP Runtime Simplification Baseline
 Date: 2026-06-01

 Status: Binding implementation baseline for first build wave

 Purpose: convert the performance/complexity assessment into concrete implementation rules that squads must follow unless
 architecture governance approves an exception.


 1. Binding Principles
   1. A DD is a capability contract, not a deployment boundary.

   2. A worker topic is a logical task contract, not a pod name.

   3. A BPMN process is used only when the work is long-running, asynchronous, human-approved, retryable, or
     compensating.

   4. Drools is used only for configurable business policy, not fixed validation.

   5. Reporting dashboards and exports use REP-01.

   6. No frontend or backend component reads another module's database directly.

   7. Cache is acceleration only; current transactional truth comes from the owning module.

   8. Dense frontend screens must use panelized reads, lazy loading, timeouts, and optional read aggregation.

   9. The first release implements revenue-critical journeys before advanced commercial/assurance/audit scope.


 2. Approved Deployment Groups
 The first production build should target these deployable groups:

  Group                                                              Capabilities

  Edge/API gateway                                                   Routing, auth enforcement, rate limits, correlation headers.

  Customer/catalog API                                               ILM, PLM, SIP, RLM, tech regions, lightweight config APIs.

  Subscription API/workflow                                          SUB-LM, SUB-WF APIs, subscription lifecycle worker group.

  Billing API/jobs                                                   Charging, payment application, invoices, wallet, dunning, tax, rating batch
                                                                     interfaces.

  Fulfillment API/workflow                                           FUL-02/03/04/05/07/08/09/10 and provisioning orchestration.

  Field operations API                                               WO, EM-02 contractor/staff, field audit process types.

  Equipment/stock API                                                OSR stock, equipment instance, RMA/swap, procurement, inventory audit.

  CRM/commercial API                                                 TCK, ASR type flows, SALES, EM-01, campaigns, discounts, CVM.

  Integration workers                                                Payment gateway, provisioning, tax gateway, mediation/rating ingestion,
                                                                     external callbacks.

  Reporting API                                                      REP-01 mart, dashboards, exports, reconciliation APIs.

  Shared workers                                                     Consolidated low-volume task handlers with per-topic metrics.


 Splitting a group later requires a reason: throughput, security isolation, release independence, scaling profile, or separate
 team ownership.

 4. Communication Rules
  Scenario                                               Required pattern

  Command                                                Frontend calls one owning module API. That module calls only required
                                                         participants or starts workflow.

  Long-running work                                      API returns accepted/operation id; Camunda/events track completion. Do not
                                                         hold HTTP calls open for minutes.

  Dashboard                                              REP-01 only for aggregate totals.

  Customer 360                                           Panelized reads with independent errors; optional read aggregator.

  Gateway callback                                       Dedicated integration module validates/dedupes, then calls owning module.

  Event reaction                                         Outbox/inbox, idempotent consumers, no cross-module DB writes.

 5. Architecture Exception Process
 Any exception must state:

   - which baseline rule is being broken;

   - why the simpler pattern is insufficient;

   - expected throughput/latency/security reason;

   - how observability and rollback will work;

   - whether the exception is temporary or permanent.

 Without an approved exception, this baseline overrides DD wording that appears to imply more deployments, more workers,
 or broader first-release scope.
