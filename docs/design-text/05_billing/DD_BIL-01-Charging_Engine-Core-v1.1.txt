 architecture explicitly separates that capability.

   - Emit success events only after the authoritative state commit succeeds.

 1. What this DD owns
   1. The bil01-emit-intent worker contract — canonical request/response envelope.

   2. Catalog resolution — for a given intent (or lifecycle event, or direct admin action), resolve matching BillableEvents from
     BIL-CFG-01 filtered by operator scope + trigger metadata + filter rules.

   3. Amount computation — formulas for proration, ETF, fixed fees, signed deltas. Runtime sign resolution per
     amount_sign_policy.

   4. cycleAnchorPolicy + effectiveTiming interpretation — for package-change intents.

   5. Line item aggregation — multi-event invocations produce a single envelope.

   6. Settlement — PREPAID wallet path + POSTPAID invoice path.

   7. State callback invocation — post-settlement SUB-LM-01 calls per matched event's state_callback.

   8. Domain Kafka events — BillableEventCharged, BillableEventStateCallbackFailed.

 What this DD does NOT own
   - BillableEvent catalog — BIL-CFG-01 v1.0.

   - Service catalog — PLM-CFG-01 v1.0.

   - Package + Package Version catalog — SIP-01.

   - Tax computation — PLM-CFG-02 (BIL-01 applies but doesn't define).

   - Wallet operations — PLM-CFG-03 + BIL-01-PAY-01.

   - Invoice generation — BIL-02-GEN-01.

   - Credit note flow — BIL-02-ADJ-01.

   - Collections / dunning — BIL-04.

   - Subscription state transitions — SUB-LM-01 (BIL-01 invokes callbacks, doesn't own transitions).

   - Cycle accrual for CONTINUOUS Packages — BIL-02-GEN-01 (recurring billing). BIL-01 handles one-shot events only.

 3. Rules
 3.1 Catalog resolution
  Rule                                                      Description

  R-BIL-01-CR-1                                             For SAGA_INTENT calls, BIL-01 queries BIL-CFG-01 with (operatorCode,
                                                            triggerType='SAGA_INTENT', triggerIntentCode=<from
                                                            envelope>, status='ACTIVE'). The query uses the
                                                            idx_billable_event_trigger_intent partial index.

  R-BIL-01-CR-2                                             For each candidate, BIL-01 evaluates the candidate's trigger_filter_drl
                                                            rule (if non-null) against the intentContext facts. The rule votes
                                                            accept/reject. NULL filter = always accept.

  R-BIL-01-CR-3                                             Eligibility filters (eligibility_franchise_refs,
                                                            eligibility_package_refs) are evaluated post-filter-rule. Subscription's
                                                            HomePass franchise + Package ref are read from the intent context (or fetched
                                                            if absent). Empty/NULL = no restriction.

  R-BIL-01-CR-4                                             Applicability is enforced: PREPAID_ONLY rejects subscriptions whose
                                                            billingMode = POSTPAID; vice versa.

  R-BIL-01-CR-5                                             Surviving candidates are ordered by (display_order ASC, code ASC) for
                                                            deterministic dispatch.



 3.2 Amount computation
  Rule                                                      Description

  R-BIL-01-AC-1                                             Each matched BillableEvent has its amount computed by a pricing formula. The
                                                            formula is selected from a registry keyed by (billableEventCode,
                                                            operatorCode). KE seed formulas: prorateDelta, migrationFee,
                                                            relocationFee, etfResidential, firstCycleCharge,
                                                            oldCycleCredit, etc. New formulas register via the same registry.

  R-BIL-01-AC-2                                             Pricing formulas receive the intent context + subscription snapshot + cycle
                                                            window as inputs. They return {amount, sign?, metadata}. For
                                                            amount_sign_policy = POSITIVE_ONLY events, the formula's sign is
                                                            forced positive; for NEGATIVE_ONLY, forced negative; for SIGNED, the
                                                            formula's computed sign is honored.

  R-BIL-01-AC-3                                             Signed proration delta (for MIGRATION_PRORATE_DELTA with
                                                            amount_sign_policy = SIGNED): formula computes priceDelta =
                                                            (targetPackagePrice - sourcePackagePrice) × (daysRemaining /
                                                            cycleLengthDays). Positive → charge; negative → credit. The sign is
                                                            reflected in the line item's amount (signed) and the
                                                            metadata.computedSign.

  R-BIL-01-AC-4                                             cycleAnchorPolicy = PRESERVE: BIL-01 computes the signed proration
                                                            delta for cycle-days-remaining at the price difference. One line item per
                                                            matched event (e.g., UPGRADE_PRORATE_DELTA,
                                                            MIGRATION_PRORATE_DELTA, DOWNGRADE_PRORATE_CREDIT —
                                                            whichever the catalog match resolves to per filter rules).

  R-BIL-01-AC-5                                             cycleAnchorPolicy = RESET_TO_OPERATION_DATE: BIL-01 returns two
                                                            line items per matched-event-pair: OLD_CYCLE_CREDIT (NEGATIVE — credits
                                                            the source-price portion of cycle-days-already-paid) + FIRST_CYCLE_CHARGE
                                                            (POSITIVE — charges the target Package price for one full cycle starting at the
                                                            operation date). Filter rules on these events match on cycleAnchorPolicy
                                                            == RESET_TO_OPERATION_DATE per BIL-CFG-01 v1.0 §2.2 KE seed.

  R-BIL-01-AC-6                                             effectiveTiming = END_OF_CURRENT_CYCLE + cycleAnchorPolicy =
                                                            PRESERVE: BIL-01 returns zero proration delta (the current cycle finishes on
                                                            source price/Package; next cycle starts on target). Migration fee + other
                                                            non-proration fees may still apply.

 3.3 Aggregation
  Rule                        Description

  R-BIL-01-AG-1               totals.gross = SUM(lineItems[].amount) (signed). totals.tax =
                              SUM(lineItems[].taxAmount) (signed, follows the line amount sign for
                              credits). totals.net = totals.gross + totals.tax. All in the same
                              currency (per R-CR-6).

  R-BIL-01-AG-2               If line items span multiple currencies, the call is rejected with
                              MIXED_CURRENCY_LINE_ITEMS (400). All matched events SHOULD share
                              the subscription's currency (enforced upstream by BIL-CFG-01 R-B-4 + the
                              subscription's Package currency).

  R-BIL-01-AG-3               payFirstRequired on the response = OR(line.payFirstRequired)
                              across matched events. If any matched event requires pay-first, the workflow
                              waits.



 3.4 Settlement
  Rule                        Description

  R-BIL-01-SE-1               PREPAID settlement: BIL-01 calls POST /api/wallet-debit on
                              BIL-01-PAY-01 with {customerId, subscriptionId, amount:
                              totals.net, currency, chargeAttemptId}. Positive net → debit.
                              Negative net → wallet credit (top-up). Zero net → no-op (settlementStatus =
                              NOT_APPLICABLE).

  R-BIL-01-SE-2               PREPAID wallet debit may fail with INSUFFICIENT_FUNDS. BIL-01 returns
                              settlementStatus = FAILED with reasonCode =
                              INSUFFICIENT_FUNDS. The workflow's payment-await message catch then
                              fires the operator-configured payment-timeout. Customer-initiated top-up via
                              portal / USSD / agent triggers the payment-confirmed message back to the
                              workflow when the wallet rises to sufficient.

  R-BIL-01-SE-3               POSTPAID settlement: positive totals.net → BIL-01 calls POST
                              /api/invoice-lines on BIL-02-GEN-01 with {customerId,
                              subscriptionId, chargeAttemptId, lines: [...], currency,
                              dueDate, originIntent}. Negative totals.net (net credit) is NOT
                              settled here — the call is rejected with settlementStatus = REJECTED,
                              reasonCode = REQUIRES_CREDIT_NOTE_WORKFLOW, and the caller is
                              directed to use BIL-02-ADJ-01 (credit note flow). For POSTPAID, BIL-01 does
                              NOT check credit limit at charge time — that's BIL-04 Collections's job at cycle
                              close.

  R-BIL-01-SE-4               A single intent call settles as a single transaction per billing mode: PREPAID
                              → one wallet debit of net total; POSTPAID → one batch invoice-lines call
                              attached to the same invoice. Partial settlement is not supported. If settlement
                              fails, the entire decision rolls back; the workflow receives settlementStatus
                              = FAILED.

  R-BIL-01-SE-5               The decisionId is recorded in bil01_charge_ledger (one row per
                              decision) with status PENDING at issue, transitioning to SETTLED / FAILED /
                              REJECTED upon outcome. Idempotency: same (subscriptionId,
                              fulfillmentCorrelationId) retried within 24h returns the prior decision
                              row with HTTP 200.

  R-BIL-01-SE-6               When the canonical envelope contains multiple BillableEvents (e.g.,
                              MIGRATION_INTENT yielding migration fee + signed proration delta),
                              aggregation runs across all events; settlement is a single transaction per the
                              rules above.

  R-BIL-01-SC-1                                                  After successful settlement, BIL-01 invokes each matched BillableEvent's
                                                                 state_callback (if non-null) via SUB-LM-01's transition endpoint. Per-event
                                                                 basis — multiple events may each invoke their own callback. Order: same as
                                                                 line item order (display_order, code).

  R-BIL-01-SC-2                                                  Callback invocation result is recorded in the response's
                                                                 stateCallbackInvocations[] array — one entry per invocation with
                                                                 transitionCode, outcome (SUCCEEDED / FAILED), failureReason.

  R-BIL-01-SC-3                                                  Callback failure does NOT roll back the charge. The charge is recorded as
                                                                 SETTLED; the callback failure is recorded;
                                                                 BillableEventStateCallbackFailed Kafka event fires for alerting. Per
                                                                 BIL-CFG-01 v1.0 R-SC-5.

  R-BIL-01-SC-4                                                  For SAGA_INTENT calls where the WORKFLOW itself drives the subscription
                                                                 transition (e.g., UPGRADE-01 commits package_ref change via SUB-LM-01
                                                                 directly, not via callback), the BillableEvent has state_callback = null.
                                                                 State callbacks are used for events where BIL-01 is the trigger of the transition
                                                                 (e.g., RECONNECTION_FEE_AFTER_DUNNING calls back to flip
                                                                 SUSPENDED_NP → ACTIVE; EQUIPMENT_BUYBACK_ONT calls back to
                                                                 unbind equipment).



 3.6 Operator scoping
  Rule                                                           Description

  R-BIL-01-OP-1                                                  Every envelope MUST carry operatorCode. Catalog resolution is scoped to
                                                                 the operator. Cross-operator catalog matches are not possible.

  R-BIL-01-OP-2                                                  Filter rules live in operator-scoped KJAR packages
                                                                 (billing-rules-<operator>). The KJAR is selected by operatorCode at
                                                                 decision time. Cross-operator rule references are not possible.

  R-BIL-01-OP-3                                                  Pricing formulas are registered per (billableEventCode,
                                                                 operatorCode). Same billableEventCode may have different formulas
                                                                 across operators (e.g., RELOCATION_FEE_CROSS_FRANCHISE may use
                                                                 different distance-based formula in WUG vs WIK).
