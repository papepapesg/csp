 FOUNDATION_FILE_STORAGE - Binary Artifact Storage
 Developer implementation guide: FOUNDATION_FILE_STORAGE_DEV_IMPL_GUIDE.md.


 1. Purpose
 This foundation defines how SOPHIX stores and serves binary artifacts: PDFs, images, signed documents, exports,
 attachments, KYC files, installation photos, and generated letters.

 Use this document when implementing:

   - Invoice PDF storage.

   - KYC document upload.

   - Work order or equipment photos.

   - Signed agreement storage.

   - Export file generation.

   - Download APIs.

   - Retention/lifecycle policies.


 2. Ownership
 FOUNDATION_FILE_STORAGE owns:

   - Object storage technology choice.

   - Bucket naming.

   - Object key conventions.

   - Access model.

   - Retention/lifecycle defaults.

   - Backup expectations.

   - AWS S3 mapping.

 FOUNDATION_FILE_STORAGE does not own:

   - Document rendering. See NOT-01 and relevant billing DDs.

   - API authorization rules for downloads. Each module owns its own access check.

   - Database metadata schema. Each owning DD defines metadata fields.

   - Virus scanning pipeline unless a later security DD introduces one.


 3. Core Principle
 Binary files live in object storage. Business tables store references to object keys.

 Do not store large binary files in PostgreSQL.

 Do not expose object storage directly to customers. Downloads must go through an application service that authenticates,
 authorizes, audits, and streams the object.

 6. Object Key Convention
 Pattern:
              {domain_prefix}/{yyyy}/{mm}/{further_partition}/{filename}.{ext}

 Examples:
              invoices/2026/05/inv_01HZQX8N5V8KJEC9M3T2A4DPYW.pdf
              invoices/2026/05/tax/taxinv_01HZQX8N5V8KJEC9M3T2A4D.pdf
              invoices/2026/05/credit/cn_01HZQX8N5V8KJEC9M3T2A4D.pdf
              kyc/cust_01HX4P5R6S7T8U9V/id_front_2026-03-15.jpg
              equipment/2026/05/cpe_01HZ/install_front.jpg
              agreements/cust_01HX/sub_01HY/signed_2026-04-01.pdf
              exports/reconciliation/2026/05/wik_recon_2026-05-15.csv.gz
              dunning/2026/05/dunning_01HZ.pdf

 Rules:

  Rule                                                                     Description

  FILE-KEY-1                                                               Keys are lowercase except platform IDs if case-sensitive.

  FILE-KEY-2                                                               Include year/month for lifecycle and browsing.

  FILE-KEY-3                                                               Use platform IDs, not customer names, phone numbers, ID numbers, or email
                                                                           addresses.

  FILE-KEY-4                                                               File extension must match content type.

  FILE-KEY-5                                                               Store relative object keys in DB metadata, not presigned URLs.

  FILE-KEY-6                                                               Object key must be immutable after published unless the owning DD defines a
                                                                           replacement/versioning flow.

 7. Access Pattern
 Customer/admin download path:
            sequenceDiagram
                participant User as User/Browser
                participant API as SOPHIX API
                participant DB as Module DB
                participant OBJ as Object Storage

                 User->>API: GET /api/invoices/{id}/pdf
                 API->>API: Authenticate and authorize
                 API->>DB: Load invoice metadata and object key
                 API->>OBJ: Fetch object with service credentials
                 API->>API: Audit download
                 API-->>User: Stream file

 Rules:

  Rule                                                              Description

  FILE-ACCESS-1                                                     No direct customer access to MinIO/S3.

  FILE-ACCESS-2                                                     No public buckets.

  FILE-ACCESS-3                                                     No customer-facing presigned URLs by default.

  FILE-ACCESS-4                                                     Application service must enforce ACL before fetching object.

  FILE-ACCESS-5                                                     Every successful download must be audit logged.

  FILE-ACCESS-6                                                     Each service gets scoped object-storage credentials.




 8. Service Credentials
 Use one object-storage IAM identity per service, scoped to minimum required buckets/actions.

  Service                                    Buckets                                           Permissions

  BIL-02 READ                                invoices                                          Read

  NOT-01                                     invoices, dunning                                 Read/write

  ILM/KYC                                    kyc                                               Read/write

  WO/Equipment                               equipment                                         Read/write

  Subscription service                       agreements                                        Read/write

  Billing/Finance exports                    exports                                           Read/write

  Customer service                           attachments                                       Read/write


 Credential rules:

   - Store credentials in the platform secret manager.

   - Do not share credentials across services.

   - Rotate credentials through an ops runbook.

   - Log access by service identity.

 10. Metadata Pattern
 Owning modules store object metadata in their own tables.

 Example:
            ALTER TABLE invoice
              ADD COLUMN pdf_bucket TEXT NULL,
              ADD COLUMN pdf_object_key TEXT NULL,
              ADD COLUMN pdf_content_type TEXT NULL,
              ADD COLUMN pdf_size_bytes BIGINT NULL,
              ADD COLUMN pdf_sha256 TEXT NULL,
              ADD COLUMN pdf_rendered_at TIMESTAMPTZ NULL;

 Rules:

  Rule                                                               Description

  FILE-META-1                                                        Store bucket and object key separately.

  FILE-META-2                                                        Store content type.

  FILE-META-3                                                        Store size and checksum for critical legal documents.

  FILE-META-4                                                        Store render/upload timestamp.

  FILE-META-5                                                        Store object version ID if the backend supports versioning and the DD needs
                                                                     immutable versions.




 11. Retention and Lifecycle
 Default retention:

  Bucket                            Hot period                       Archive/warm period                        Delete after

  invoices                          2 years                          Years 2-10                                 10 years

  kyc                               Active customer lifetime         7 years after closure                      7 years post-closure

  equipment                         Equipment in service             2 years after retirement                   2 years post-retirement

  agreements                        Active subscription lifetime     10 years after termination                 10 years post-termination

  exports                           90 days                          None                                       90 days

  attachments                       5 years                          None                                       5 years

  dunning                           7 years                          None                                       7 years


 Operator legal/regulatory requirements override these defaults.

 Lifecycle rules:

  Rule                                                               Description

  FILE-LIFE-1                                                        Lifecycle policies should delete/archive automatically where supported.

  FILE-LIFE-2                                                        Manual delete requires privileged storage admin role and audit log.

  FILE-LIFE-3                                                        Legal/tax document retention must be reviewed per operator before production.

  FILE-LIFE-4                                                        If hard immutability is required, enable object lock/versioning for the specific
                                                                     bucket/prefix.




 12. Backup and Recovery
 On-prem MinIO medium baseline:

   - 2-node distributed MinIO gives single-node failure tolerance.

   - Snapshot object storage to separate backup storage.

   - Keep daily incremental, weekly full, monthly archive by operator policy.

   - Test restore of representative files before go-live.

 Rules:

  FILE-BACKUP-1                                                        Backups must leave the MinIO nodes.

  FILE-BACKUP-2                                                        Backup scope is per operator; no cross-operator backups unless explicitly
                                                                       approved.

  FILE-BACKUP-3                                                        Restore tests must include legal PDFs and KYC images.

                                                                       references.




 13. Failure Behavior
  Failure                                                              Behavior

  One MinIO node down                                                  Cluster continues in degraded mode. Restore node and let MinIO heal.

  Both MinIO nodes down                                                File uploads/downloads fail. Business workflows that require files must pause or
                                                                       retry.

  Object missing but DB metadata exists                                Return controlled 404/ops error; create recovery ticket.

  DB metadata missing but object exists                                Object is orphaned; reconciliation job reports it.

  Lifecycle deletes too much                                           Restore from backup if within backup retention.




 14. Monitoring
 Alert on:

  Signal                                                               Threshold

  Node down                                                            Any

  Disk usage                                                           Warning at 80 percent, critical at 90 percent

  Failed PUT/GET rate                                                  Sustained increase

  p99 read latency                                                     More than 500 ms sustained

  Healing queue                                                        Large or not decreasing

  Lifecycle backlog                                                    Sustained growth

  IAM auth failures                                                    Spike

  Backup failure                                                       Any

           /              40 GB
           /opt/minio     20 GB
           /var/log       60 GB
           /data        3700 GB
           /tmp           30 GB

 Partition rules:

   - Store objects under /data or dedicated data mount.

   - Do not store object data on /.

   - Alert at 80 percent disk usage.

   - Use xfs or ext4.

   - Keep backup target separate from /data.

 16.2 Bucket Mapping
 AWS bucket naming pattern:
              sophix-{env}-{operator}-{bucket}

 Examples:
              sophix-prod-wik-invoices
              sophix-prod-wik-kyc
              sophix-prod-wik-equipment
              sophix-prod-wik-agreements

 Alternative: one operator bucket with domain prefixes. Separate buckets give cleaner IAM and lifecycle boundaries, but more
 objects to administer.

 Recommended for production: separate buckets for at least:

   - invoices

   - kyc

   - agreements

   - exports

   - attachments/equipment/dunning as separate or grouped depending on ops preference

 16.3 S3 Security
 Required:

   - Block Public Access enabled.

   - Bucket policies deny public access.

   - Server-side encryption enabled.

   - IAM roles scoped per service and bucket/prefix.

   - Access through VPC endpoint where possible.

   - No long-lived AWS keys on application servers; use IAM roles.

 Encryption:

  Bucket                                                                     Recommendation

  invoices                                                                   SSE-S3 minimum; SSE-KMS if legal/compliance requires key audit.

  kyc                                                                        SSE-KMS recommended.

  agreements                                                                 SSE-KMS recommended.

  exports                                                                    SSE-KMS if finance/tax exports contain sensitive data.

  Other buckets                                                              SSE-S3 minimum.

 16.6 AWS Operational Notes
   - Do not generate public presigned URLs unless a DD explicitly approves that user flow.

   - Prefer application streaming downloads for audit and access control.

   - Enable versioning/Object Lock only for buckets that require immutability; this increases operational complexity.

   - Use S3 Inventory or reconciliation jobs to detect orphaned/missing objects.

   - Use replication to another region only if DR requirements justify cost.
