 Handles cancellation of an in-flight order, from any phase prior to ACTIVATED. Triggered by customer-initiated request, ops
 decision, or payment-timeout. Owns the cascade logic — cleaning up downstream artifacts (subscription, install work order,
 payments) that may have been created during the journey, in reverse order, and emitting events that finance and the
 customer can act on. Phase: CANCELLED.



 1. What this step does
 A customer's order can be cancelled at any time before the order reaches ACTIVATED. The trigger can come from:

   - Customer-initiated cancellation — the customer calls support and asks to cancel, and a support agent issues the cancel
     from the BO UI.

   - Payment timeout — the PT7D boundary timer on wait-payment fires (STEP-PAYMENT).

   - Ops escalation — an ops user manually cancels an order via the admin UI (e.g., to resolve a fraud case).

 The cancellation entry point varies (REST API call vs Camunda timer fire), but they all converge on the same
 order-cascade-cancellation worker. That worker walks the order's current state to figure out what's been created so
 far, cleans each up in reverse creation order, then order-mark-cancelled finalizes the order with phase CANCELLED.

 The reverse-creation order matters because each cleanup depends on the previous one not being in a half-state:

   1. Cancel the install WO (if work_order_id IS NOT NULL and the order is in INSTALLING or beyond). Calls the WO
     module to set the WO to CANCELLED — contractor is no longer dispatched, equipment is no longer needed. v1.0 routes
     to the install_wo_stub admin cancel endpoint.

   2. Terminate the subscription (if subscription_id IS NOT NULL). Calls SUB-WF-TERMINATE-01 to walk the
     subscription from CREATED (or PENDING_ACTIVATION, in race scenarios) to TERMINATED.
     SUB-WF-TERMINATE-01 owns its own saga (calls BIL-01 to close any open invoices, NMS to deactivate any
     provisioning, etc.).

   3. Request refund (if payment_received_amount > 0). Emits OrderRefundRequested for BIL-02-ADJ-01 to
     process. Same refund cascade as STEP-INSTALL / STEP-ACTIVATION failures. FUL-02 doesn't issue the refund itself
     — Finance does, on the refund queue.

 Each cleanup is conditional: if a step never ran, its artifacts don't exist, no cleanup needed. The worker checks NULL on each
 column on customer_order before invoking the relevant cleanup.

     (REJECTED/CANCELLED/ACTIVATED/INSTALL_FAILED/ACTIVATION_FAILED → 409 with
     ORDER_ALREADY_TERMINAL).

   2. Verifies the order isn't ACTIVATED — if it is, the customer should use the terminate-subscription flow instead (different
     code path, different refund rules, etc.). Returns 409 ORDER_ALREADY_ACTIVATED_USE_TERMINATE pointing at
     SUB-WF-TERMINATE-01.

   3. Sends a Camunda message correlation directly (no Kafka — this is a synchronous control plane action):
               POST /engine-rest/message HTTP/1.1
               {
                 "messageName": "OrderCancellationRequested",
                 "businessKey": "ord_01HZ...",
                 "processVariables": {
                   "cancellationReason": { "value": "CUSTOMER_REQUESTED",                                  "type": "String" },
                   "cancellationDetail": { "value": "Customer changed mind — moving to a different ISP", "type": "String" },
                   "cancellationActor": { "value": "cust_01HX...",                                         "type": "String" }
                 }
               }

 The BPMN's top-level interrupting boundary message event (FRAMEWORK §1.8) catches
 OrderCancellationRequested and interrupts whatever subprocess the order was in — be it wait-payment, the L1
 KYC user task, the Team Leader KYC user task, or the install wait. Control routes to order-cascade-cancellation.

 For audit, the cancellation request itself is recorded in a side table customer_order_cancellation_requests BEFORE
 the Camunda call (so it survives even if Camunda 5xxs).

 Entry path: Camunda message, not Kafka
 The cancel entry uses Camunda's REST message API directly, not Kafka. Reason: cancellation is a control-plane action that
 needs to be confirmed synchronously to the caller (support agent expects an immediate "yes, your order was cancelled" or
 "couldn't cancel because X"). Kafka would add eventual-consistency delay and remove the ability to return a meaningful error
 code. Note that the *outcome* events (OrderCancelled, OrderRefundRequested) ARE emitted on Kafka — those are
 downstream notifications, not control-plane handshakes.

 What the customer journey looks like during cancellation
 When order-cascade-cancellation and order-mark-cancelled complete, the customer receives a DD_NOT-01
 notification:

   - If money was received and refund was requested: "Your order has been cancelled. You'll receive a refund of {amount}
      within 5 business days."

   - If no money was received: "Your order has been cancelled. No refund needed."

   - If the cancellation was system-initiated (payment timeout): "Your order was cancelled because we did not receive payment
      within 7 days. {refund text if applicable}."

 What this step deliberately doesn't do
   - Doesn't cancel an ACTIVATED order. Once the order has reached ACTIVATED, the subscription is live; cancelling it is a
     subscription-termination operation (SUB-WF-TERMINATE-01), not a FUL-02 concern. The cancel API returns 409.

   - Doesn't issue the actual refund. That's BIL-02-ADJ-01 (consumes OrderRefundRequested events into a Finance
     queue). FUL-02's job is to declare that a refund is owed.

   - Doesn't roll back the customer record. The customer_stub row (v1.0) or ILM-CFG-01 record (future) survives — the
     customer can re-submit a new order with the same identity.

 4. Worked example — auto-cancellation from PT7D payment timer
 The boundary timer on wait-payment fires at 2026-05-25T09:00:03Z. Camunda routes the flow to
 order-cascade-cancellation directly (no API call, no audit row in customer_order_cancellation_requests —
 auto-triggered).

 after the timer fires). Cleanup: subscription was created at STEP-SUBSCRIPTION, so it gets terminated.
 payment_received_amount = 0 → no refund. work_order_id is NULL → no WO cleanup.

 order-mark-cancelled runs with cancellationReason = PAYMENT_TIMEOUT, cancelledFromPhase =
 AWAITING_PAYMENT. The OrderCancelled event's cancellationActor is set to system_timer to distinguish from
 human-initiated cancellations.

 Failure modes:

   - WO module unreachable during install WO cancel → retry; if persistent, log the failure into
     cascadeOutcome.installWoCancelled = false and continue. The order still ends in CANCELLED phase; ops
     gets a NOC alert from the OrderCancelled event payload's cascadeOutcome flags.

   - SUB-WF-TERMINATE-01 4xx (e.g., subscription already TERMINATED — race with another path) → treat as success;
     subscriptionTerminated = true.

   - SUB-WF-TERMINATE-01 5xx → retry. After exhaustion: cascadeOutcome.subscriptionTerminated = false,
     log, continue. Ops gets alerted.

 9. Step-pinned rules




SOPHIX BSS Design Documents                                                                                                            Page 11
  ID                          Rule

  R-FUL-02-CAN-1              POST /api/orders/{id}/cancel correlates Camunda's
                              OrderCancellationRequested message directly via POST
                              /engine-rest/message — NOT through Kafka. Cancellation is a
                              control-plane action that returns synchronous error codes to the caller (404,
                              409, 403, etc.); Kafka would lose this. Downstream notification events
                              (OrderCancelled, OrderRefundRequested) ARE emitted on Kafka.

  R-FUL-02-CAN-2              The cancel API rejects orders already ACTIVATED with 409
                              ORDER_ALREADY_ACTIVATED_USE_TERMINATE. Cancelling an activated
                              subscription is a SUB-WF-TERMINATE-01 operation (different code path,
                              different refund/proration rules, different audit chain). FUL-02 stops covering an
                              order once current_phase = ACTIVATED.

  R-FUL-02-CAN-3              order-cascade-cancellation cleans up in REVERSE creation order:
                              install WO → subscription → refund. Each cleanup is conditional on the
                              corresponding customer_order column being non-NULL. Skipping vs running
                              is decided by NULL-check, not by phase — works regardless of which step
                              interrupted the order.

  R-FUL-02-CAN-4              Subscription termination via SUB-WF-TERMINATE-01 is async (its own saga).
                              The cascade worker accepts the 202 and continues; doesn't wait for the saga to
                              complete. The customer's OrderCancelled notification fires after the cascade
                              returns (subscription terminate may still be running). Rationale: customer should
                              see "cancelled" promptly; underlying cleanup completes async.

  R-FUL-02-CAN-5              Refund request is emitted as a separate OrderRefundRequested event from
                              OrderCancelled, even though both fire from the same worker. The split lets
                              BIL-02-ADJ-01 subscribe only to refund events without filtering.

  R-FUL-02-CAN-6              Auto-cancellations (PT7D payment timer fire) do NOT write to
                              customer_order_cancellation_requests — no API call was made.
                              They're visible in customer_order.failure_reason and the
                              OrderCancelled event's cancellationActor = system_timer only.
                              The table audits human-initiated requests.

  R-FUL-02-CAN-7              When the BPMN's main subprocess is interrupted by
                              OrderCancellationRequested, any pending message correlations (e.g., a
                              late WorkOrderCancelled from the WO module canceling our install WO
                              during the cascade) find no active subprocess. Camunda returns 400; the
                              corresponding consumer DLQs the event. The cascade in progress is already
                              handling the cleanup — no double-processing.

  R-FUL-02-CAN-8              Cascade failure modes (e.g., WO module unreachable,
                              SUB-WF-TERMINATE-01 5xx) do NOT block the order's transition to
                              CANCELLED. The cascade worker logs the failure into cascadeOutcome flags
                              and continues; the order is marked CANCELLED, the OrderCancelled event
                              carries the partial-cleanup flags so NOC can alert. Manual cleanup happens
                              out-of-band.

  R-FUL-02-CAN-9              Phase-history rows during cancellation are appended by PhaseProjector like
                              any other transition. The metadata field on the CANCELLED transition
                              includes the full cancellationReason, cancellationActor, and
                              cascadeOutcome for audit.
