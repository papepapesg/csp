 Glossary
 Plain definitions for terms used across BIL-02 and satellite DDs.

  Term                                                               Meaning

  Invoice                                                            Customer-facing bill listing what was billed, for which period, the amount due,
                                                                     and the payment deadline. May have tax authority weight depending on
                                                                     deployment.

  Pro forma                                                          Informational preview of the next invoice. Not a legal/tax document. Tells the
                                                                     customer "this is what you'll owe next cycle so you can prepare to pay."
                                                                     Handled by BIL-02-GEN-01.

  Tax invoice                                                        A signed proof-of-payment document required by tax authorities in some
                                                                     deployments. Generated after a payment is received. Handled by
                                                                     BIL-02-TAX-01.

  Gap-free numbering                                                 Legal invoices are numbered sequentially. The system must never silently skip
                                                                     a number. If issuance fails after a number is reserved, the gap is recorded in an
                                                                     audit table for reconciliation with the tax authority — never silently lost.

  Change history table                                               A parallel table that records every change to a record (status change, payment
                                                                     applied, cancellation, etc.). Each row in the history table captures: who made
                                                                     the change, when, what the field value was before, what it is after. The history is
                                                                     append-only — rows are never edited or deleted. Used by compliance auditors,
                                                                     operations, and customer care to reconstruct exactly what happened to an
                                                                     invoice. Named with _history suffix (e.g., invoice_history).

  Per-operator configuration                                         Wananchi operates in 3 countries (KE/UG/TZ), Yas in Senegal, plus future
                                                                     deployments. Each may need different invoice formats, due-date grace periods,
                                                                     tax-gateway endpoints, etc. Settings live in
                                                                     invoice_type_operator_config.

  Wallet type                                                        Operators define their wallet structure via the PLM-CFG-03 Wallet Configuration
                                                                     catalog. Each operator may have one or multiple wallet types. Wallet type codes
                                                                     are operator-configurable, not hardcoded.

  Grouping policy                                                    Per-operator config that defines how charges are distributed across invoices at
                                                                     cycle close. The policy has a dimension (WALLET, PACKAGE,
                                                                     SERVICE_CATEGORY, or SINGLE) and a list of groups. Each group lists which
                                                                     keys belong together (e.g., a wallet group lists wallet types; a package group
                                                                     lists package refs). Number of invoices generated per cycle per customer =
                                                                     number of groups in the policy that have non-zero charges. The dimension lets
                                                                     operators decide whether grouping is by wallet, by package, by service
                                                                     category, or none (single combined invoice).

  Customer snapshot                                                  A JSONB object stored on the invoice (and pro forma) at issuance, capturing
                                                                     customer name, billing address, email, phone, language preference, tax
                                                                     identifier, and customer type. The snapshot is immutable for that invoice — if
                                                                     the customer's address changes 6 months later, the historical invoice still shows
                                                                     the address as it was at issuance. Used for legal compliance (a 2026 tax invoice
                                                                     must show the customer info as of 2026, not as of when it's re-rendered) and for
                                                                     self-contained PDF rendering by the notification service (no need to call CRM at
                                                                     render time).

  Summary vs detailed view                                           An invoice has a summary page showing top-level totals per service grouping
                                                                     and a detailed page (or pages) showing per-package consumption breakdown.

  Billing mode                                                       When the customer pays relative to their service cycle. Two modes: POSTPAID
                                                                     (customer pays AFTER cycle close; receives a regular invoice with a due date)
                                                                     and PREPAID (customer pays BEFORE cycle close; receives a pro forma in
                                                                     advance, and at cycle close the cycle is settled).

  POSTPAID                                                           Customer uses service during the cycle, gets a regular invoice at cycle close,
                                                                     has a grace period (typically 14 days) to pay. If unpaid by the due date, the
                                                                     invoice goes OVERDUE and dunning starts. Example operator: Wananchi
                                                                     POSTPAID customers.

  PREPAID                                                            Customer pays before the cycle begins. The system issues a pro forma in
                                                                     advance (default 5 days before cycle end) telling the customer how much will be
                                                                     settled. At cycle close, the operator settles the cycle — depending on the
                                                                     operator's PLM-CFG-03 Wallet Configuration, this is either a debit from the
                                                                     customer's wallet (Wananchi-style: customer tops up wallet, system debits at
                                                                     cycle) or a direct per-cycle payment (Yas SN-style: customer pays the cycle
                                                                     amount as a standalone transaction). BIL-02 doesn't care which — it just knows
                                                                     the customer pays before cycle. The wallet-vs-direct-pay choice is owned by
                                                                     BIL-05 Wallet and Topup and is invisible to BIL-02 Core.

 1. What this process is about
 BIL-02 core owns the invoice entity and the shared infrastructure that all 5 satellite DDs depend on: the data model, the
 type catalog, the lifecycle state machine, sequence number allocation, per-operator configuration, multi-tax summary
 structure, wallet isolation strategy, the REST + Kafka contract, and the scanner framework that satellite scanners plug into.

 Core does NOT generate invoices itself — that's BIL-02-GEN-01. Core does NOT issue tax invoices — that's BIL-02-TAX-01.
 Core does NOT handle adjustments — that's BIL-02-ADJ-01. Core does NOT serve PDFs or the read API — that's
 BIL-02-READ-01. Core does NOT run the overdue scanner or PTP/dispute logic — that's BIL-02-STA-01.

 Core provides the chassis. The satellites bolt on.

 #### What core owns

   - Invoice entity: the invoice table, immutability rules, lifecycle states, and transitions.

   - Pro forma entity: the pro_forma table (separate from invoice for legal-compliance query separation).

   - Line items: the shared invoice_line_item table with two-level (summary + detail) structure. Each line item references
     a wallet_type_code (FK to PLM-CFG-03 wallet type catalog) — operator-configurable.

   - Type catalog: invoice_type_definition + invoice_type_operator_config for extensibility (new types added
     by config + a generator class).

   - Sequence allocation: gap-free per-(operator, fiscal_year, type) for legal invoices; non-gap-free for pro forma.

   - Per-operator config: wallet isolation strategy, formats, grace days, fiscal year start, etc. Number and types of wallets per
     operator come from PLM-CFG-03 (separate catalog).

   - Multi-tax summary: structured tax_summary JSONB at invoice level for arbitrary tax stacks.

   - Scanner framework: pattern + audit table for the daily scanners that satellites implement (overdue, pre-due, pro forma,
     tax retry).

   - REST contract: read endpoints exposed to admin console and customer portal. Satellites add their endpoints.

   - Kafka contract: invoice lifecycle events emitted on transitions. Satellites consume + emit their own.

   - Subscription state interaction: gating on PENDING_* Subscriptions (skip + retry), reading master fields for invoice
     generation, writing pro forma ID back.

 #### Out of scope (handled in satellite DDs)

   - Invoice generation logic (which charges to include, how to compute, idempotency on triggers) → BIL-02-GEN-01

   - Tax invoice signing flow → BIL-02-TAX-01

   - Credit/debit notes and adjustments → BIL-02-ADJ-01

   - PDF retrieval, caching, read API → BIL-02-READ-01

   - Overdue scanner, pre-due reminder, PTP, dispute, late fee → BIL-02-STA-01

 #### Out of scope entirely

   - Charging logic and amount computation — BIL-01

   - Tax computation rules — PLM-CFG-02 Tax Configuration

   - Payment recording — BIL-01

   - PDF rendering, channel dispatch, template management — DD_NOT-01 Notification Service

   - Dunning state machine — BIL-04

   - Refund execution (outbound payouts) — V3.2 / payout module

 Generator framework — developer guide
 BIL-02 Core provides a generator framework that satellite DDs (and future deployments) plug into. This section explains
 how it works concretely for a developer who will write a generator class.

 #### What the framework provides

 The framework consists of four pieces that live in BIL-02 Core:

   1. InvoiceGenerator interface — what every generator must implement.

   2. InvoiceGenerationService — the central entry point that receives triggers and dispatches to the right generator.

   3. InvoiceGeneratorRegistry — at module startup, scans for classes implementing InvoiceGenerator and
     registers them indexed by getTypeCode(). Looks them up by
     invoice_type_definition.generator_class_ref.

   4. Shared services that generators use to do their work: InvoiceSequenceService, InvoiceLineBuilder,
     InvoiceWriter, ProFormaWriter, CustomerSnapshotService, InvoiceEventPublisher.

 Each generator is responsible for ONE invoice type. The framework dispatches to it; the generator does its specific work; the
 framework's shared services handle the cross-cutting concerns (sequence, writing, events).

 #### The InvoiceGenerator interface
          public interface InvoiceGenerator {

               /**
                * Returns the invoice_type_code this generator handles.
                * Must match a row in invoice_type_definition.type_code.
                * Used by InvoiceGeneratorRegistry to dispatch.
                */
               String getTypeCode();

               /**
                * Produces zero or more invoices for the given context.
                * Returns a list because grouping policies may produce N invoices per trigger
                * (e.g., Wananchi KE WALLET dimension with 2 groups produces 2 invoices per cycle).
                * Returns empty list when the trigger results in no invoices (e.g., zero-charge cycle).
                * Returns existing invoice(s) when idempotency check finds previous match.
                */
               List<Invoice> generate(InvoiceGenerationContext context);
          }

 In Laravel/PHP the equivalent is an interface with the same contract; the rest of this section uses Java syntax for
 concreteness.

 #### How a generator gets discovered and called

 The lifecycle has three phases:

 Phase 1 — Module startup (one-time at boot):

 The Spring container scans the classpath for @Component-annotated classes implementing InvoiceGenerator. For each
 one found, it calls getTypeCode() and registers the bean in InvoiceGeneratorRegistry indexed by that code. After
 startup, the registry has a map like:
          "CYCLE_POSTPAID" → CyclePostpaidInvoiceGenerator instance
          "ONE_OFF_INVOICE" → OneOffInvoiceGenerator instance
          "PRO_FORMA_CYCLE" → ProFormaCycleGenerator instance
          "TAX_INVOICE"     → TaxInvoiceGenerator instance
          "CREDIT_NOTE"     → CreditNoteGenerator instance
          "DEBIT_NOTE"      → DebitNoteGenerator instance

 The same generator classes are listed in invoice_type_definition.generator_class_ref. If a row in the catalog
 references a generator class that's NOT registered at startup, the system logs a configuration error and refuses to generate
 that type — protecting against half-deployed code.

 Phase 2 — Trigger arrives:


SOPHIX BSS Design Documents                                                                                               Page 26
 A Kafka event consumer (e.g., CycleClosedConsumer for cycle invoices, PaymentAppliedConsumer for tax invoices), a
 scheduled scanner (e.g., ProFormaScanner for daily pro forma generation), or an admin REST endpoint receives a trigger.
 It builds an InvoiceGenerationContext and calls:
            List<Invoice> invoices = invoiceGenerationService.generate(context);

 InvoiceGenerationService.generate() looks up the right generator by context.getInvoiceTypeCode(),
 delegates, and returns the result.

 Phase 3 — Generator execution:

 The generator's generate() method is called. It uses framework services to do its work (see below). The returned Invoice
 objects are already written to the database and have lifecycle events published.

 #### Skeleton — the canonical generator shape

 The actual generator classes (CyclePostpaidInvoiceGenerator, OneOffInvoiceGenerator,
 ProFormaCycleGenerator, CreditNoteGenerator, DebitNoteGenerator) and their per-class flows live in
 BIL-02-GEN-01 Invoice Generation. Core only defines the framework shape; the satellite owns the concrete
 implementations.

 Every generator follows the same canonical structure when using the framework services Core provides. The skeleton below
 is a shape sketch — not a real class — illustrating how a generator orchestrates the shared services:
            @Component
            @Transactional
            public class SomeInvoiceGenerator implements InvoiceGenerator {

                // Inject framework services from BIL-02 Core
                private final InvoiceSequenceService sequenceService;
                private final InvoiceLineBuilder lineBuilder;
                private final CustomerSnapshotService snapshotService;
                private final InvoiceWriter invoiceWriter;
                private final InvoiceEventPublisher eventPublisher;
                private final IdempotencyChecker idempotency;

                @Override
                public String getTypeCode() { return "..."; }

                @Override
                public List<Invoice> generate(InvoiceGenerationContext ctx) {
                    // 1. Subscription state gate (skip if PENDING)
                    // 2. Capture customer_snapshot via snapshotService
                    // 3. For each group in ctx.getGroupingPolicy():
                    //    a. Idempotency check via idempotency.findExisting(...)
                    //    b. Filter charges/inputs for this group
                    //    c. Build line items via lineBuilder.build(...)
                    //    d. Build invoice header (set fields from ctx + snapshot + group)
                    //    e. Allocate sequence number via sequenceService
                    //    f. Write atomically via invoiceWriter.write(invoice, lines)
                    //    g. Publish event via eventPublisher
                    // 4. Return list of persisted invoices
                }
            }

 Each of the 5 concrete generators in BIL-02-GEN-01 Invoice Generation specializes this shape with type-specific logic: cycle
 generator fetches charges from BIL-01 Charging Engine; one-off generator uses the fee descriptor directly from the event; pro
 forma generator runs from a scanner with projected charges; credit/debit note generators receive their inputs from
 BIL-02-ADJ-01 Invoice Adjustments. See that DD for the full step-by-step flow of each generator.

 #### How a future deployment plugs in a new generator

 A future deployment wanting to add a new invoice type does these steps:

   1. Write the generator class — implement InvoiceGenerator, annotate with @Component. Follow the canonical shape
     sketched above and the worked examples in BIL-02-GEN-01 Invoice Generation. Use existing framework services for
     sequence, line items, snapshot, write, events.

   2. Insert a row in invoice_type_definition — register the new type code, set generator_class_ref to the
     fully-qualified class name of the new generator, choose legal_nature, trigger_type, requires_signing,

SOPHIX BSS Design Documents                                                                                                           Page 28
     legal_sequence_required, customer_deliverable, active.

   3. Insert rows in invoice_type_operator_config — one per operator that will use the new type, with their specific
     settings (grace days, format, signing endpoint if applicable).

   4. Insert rows in invoice_grouping_config — define how charges are grouped for the new type per operator (which
     dimension, which groups). For most non-cycle types (one-offs, tax invoices, notes), often a single SINGLE-dimension
     group is enough.

   5. Add a trigger source — either subscribe to an existing Kafka topic, register a new scheduled scanner, or expose a new
     admin endpoint. The trigger source builds the InvoiceGenerationContext and calls
     InvoiceGenerationService.generate(context).

 That's the whole extension surface. No changes to:

   - invoice table schema (the new type uses the same columns)

   - invoice_line_item table schema

   - InvoiceSequenceService (just allocates per new type_code automatically)

   - InvoiceWriter, CustomerSnapshotService, InvoiceEventPublisher (same code, same events)

   - Other generators (each is independent)

   - DD_NOT-01 Notification Service (it already handles the standard event payload; only needs new template if the operator
     wants a different layout)

 Tax invoice nuance: When BIL-02-TAX-01 produces a tax invoice, it captures a fresh customer_snapshot at payment
 moment, not the snapshot from the original cycle invoice. The tax invoice reflects customer state at tax declaration time. If the
 customer changed their tax identifier or address between cycle and payment, the tax invoice shows the new state — which is
 what the tax authority expects.

 Subscription / wallet model (confirmed)
 A Subscription holds a package or bundle. The package or bundle itself owns one or more wallets (per PLM-CFG-03 Wallet
 Configuration catalog). For Wananchi, a typical bundle holds three wallets (Internet, TV, Voice); the customer's Subscription
 thus has three wallets associated through its bundle. For Yas SN, packages have a single wallet (or zero, depending on the
 operator's configuration — PREPAID customers without a wallet pay per cycle directly via BIL-05 Wallet and Topup).

 BIL-02 Core uses wallet_type_code per line item and per invoice (when grouping_dimension=WALLET) to identify which
 wallet a charge belongs to. The grouping policy then determines how those wallet-tagged charges are distributed across
 invoices. BIL-05 Wallet and Topup owns the wallet entity itself, including the relationship between Subscription →
 bundle/package → wallets.
