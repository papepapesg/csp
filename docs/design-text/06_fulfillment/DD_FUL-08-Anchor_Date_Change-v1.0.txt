 1. Purpose
 FUL-08 defines how SOPHIX changes a subscription's billing anchor date.

 The billing anchor date is the day used to compute cycle windows, recurring charge timing, invoice period boundaries,
 prepaid wallet cycle debit timing, dunning expectations, and customer communication dates.

 Use FUL-08 when:

   - customer asks to move billing date from the 1st to the 15th;

   - operator aligns anchor date after relocation, corporate account change, or manual correction;

   - care agent needs to correct a wrong anchor date created during onboarding;

   - billing team needs an auditable operation before BIL-03 cycle close uses the new date.

 FUL-08 is not the billing engine. It orchestrates the change, validates policy, asks Billing to preview/compute financial impact,
 obtains approval where needed, updates subscription lifecycle state through SUB-LM-01, and emits events for Billing and
 reporting.



 2. Scope And Boundaries
  Capability                                                         Owner

  Anchor change request, validation, approval, operation audit       FUL-08

  Subscription master anchor field update                            SUB-LM-01

  Billing impact preview and proration charge/credit                 BIL-01 / BIL-02-ADJ

  Cycle close use of new anchor date                                 BIL-03

  Billable event codes for anchor change fee/proration               BIL-CFG-01

  Configurable approval policy                                       EM-CFG-04

  Operator-variable eligibility/fee/approval policy                  Drools


 Boundary rules:

   - FUL-08 must not directly generate invoices.

   - FUL-08 must not directly edit Billing ledger, invoice, wallet, or adjustment rows.

   - FUL-08 must not directly update subscription DB fields if SUB-LM-01 exposes an owning API/service; call the owner.

   - EM-CFG-04 owns approval tasks and policy. FUL-08 stores approval references and applies final outcome.

   - Camunda is used for the anchor-change process itself if the operator wants async approval/payment/timer orchestration.
     EM-CFG-04 starts Camunda only for approval policies in BPMN mode.

 6. APIs
 6.1 Preview Anchor Change
           POST /api/subscriptions/{subscription_id}/anchor-date-change/preview
           Content-Type: application/json

           {
               "operatorCode": "WIK",
               "requestedAnchorDay": 15,
               "effectiveMode": "NEXT_CYCLE",
               "reasonCode": "CUSTOMER_REQUEST",
               "sourceChannel": "BACKOFFICE"
           }

 FUL-08 validates subscription state, runs Drools policy, then calls Billing preview.

 6.2 Create Anchor Change Request
           POST /api/subscriptions/{subscription_id}/anchor-date-change
           Idempotency-Key: adc-sub-700045-202607-anchor15
           Content-Type: application/json

           {
               "operatorCode": "WIK",
               "requestedAnchorDay": 15,
               "effectiveMode": "NEXT_CYCLE",
               "reasonCode": "CUSTOMER_REQUEST",
               "sourceChannel": "BACKOFFICE",
               "confirmedPreviewRef": "bil-prev-adc-001"
           }


 6.3 Approval Evaluation
 FUL-08 calls EM-CFG-04 when rule/policy requires approval:
           POST /api/approvals/evaluate
           Content-Type: application/json

           {
               "operatorCode": "WIK",
               "moduleCode": "FUL-08",
               "actionCode": "ANCHOR_DATE_CHANGE_APPROVAL",
               "subjectType": "ANCHOR_DATE_CHANGE",
               "subjectId": "adc-001",
               "context": {
                 "subscriptionId": "SUB-700045",
                 "currentAnchorDay": 1,
                 "requestedAnchorDay": 15,
                 "financialImpactType": "CHARGE",
                 "prorationAmount": 1400.00,
                 "currencyCode": "KES",
                 "sourceChannel": "BACKOFFICE"
               }
           }


 6.4 Approval Outcome Callback
           POST /internal/anchor-date-change/{request_id}/approval-outcome
           Content-Type: application/json

           {
               "approvalRequestId": "apr-adc-001",
               "outcome": "APPROVED",
               "decisionComment": "Approved customer billing date alignment."
           }


 6.5 Apply Anchor Change
           POST /api/anchor-date-change/{request_id}/apply
           Idempotency-Key: apply-adc-001
           Content-Type: application/json

 Apply behavior:

   1. call SUB-LM-01 to update anchor day/effective date;

   2. call Billing to apply fee/proration if preview requires it;

   3. emit AnchorDateChanged.

 7. Business Rules
  Rule                                        Description                                             Reason

  R-FUL-08-01                                 Subscription must be active or in an allowed state.     Avoid changing closed subscriptions.

  R-FUL-08-02                                 Anchor day must be between 1 and 28 in v1.0.            Avoid month-length edge cases.

  R-FUL-08-03                                 Only one pending anchor change per subscription.        Prevent conflicting cycle windows.

  R-FUL-08-04                                 Billing preview is required before request              Customer/finance transparency.
                                              confirmation.

  R-FUL-08-05                                 Approval must go through EM-CFG-04 when policy          Governance.
                                              requires it.

  R-FUL-08-06                                 Customer payment must clear before apply if Billing     Revenue protection.
                                              marks paymentRequired=true.

  R-FUL-08-07                                 Apply must be idempotent.                               Prevent double proration.

  R-FUL-08-08                                 BIL-03 must use the new anchor only after               Cycle consistency.
                                              successful apply event/state.




 8. Rule Engine Guidance
 Use Drools for configurable policy:

  Rule file                                                               Purpose

  anchor-date-change-eligibility.drl                                      Decide if requester/source/subscription may change anchor.

  anchor-date-change-approval.drl                                         Decide whether EM-CFG-04 approval is required.

  anchor-date-change-payment-policy.drl                                   Decide payment-first behavior where operator policy differs from Billing default.


 Example:
              package com.sophix.fulfillment.anchor

              rule "Backoffice anchor change with large proration requires approval"
              when
                $f : AnchorChangeFact(sourceChannel == "BACKOFFICE", prorationAmount >= 1000.00)
                $d : AnchorChangeDecision()
              then
                $d.setApprovalRequired(true);
                $d.setApprovalPolicyCode("ANCHOR_CHANGE_SUPERVISOR");
              end

  Database                                                       Fulfillment/subscription workflow schema.

 AWS notes: use existing ECS/EKS workflow services, RDS PostgreSQL, MSK/Kafka, Secrets Manager, and
 CloudWatch/Prometheus alerts for stuck requests and failed apply retries.



 12. Acceptance Criteria
   - Anchor change request/preview/apply tables exist.

   - Preview calls Billing and stores financial impact.

   - Approval uses EM-CFG-04 when policy requires.

   - Apply updates subscription anchor through SUB-LM-01 and financial impact through Billing APIs.

   - Apply is idempotent and retryable.

   - BIL-03 can consume/apply the new anchor after successful event/state.

   - Backoffice can preview, submit, approve, and apply anchor change.
