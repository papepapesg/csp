 1. What this process is about
 A Discount is a configured reduction of what a customer pays, either as a PriceRebate (reduces a billable amount —
 recurring invoice line, installation fee, MACD fee, or any other charge) or as a WalletCredit (credits a customer wallet). The
 Discount catalog stores the definitions; assignment of a discount to a specific customer/package and the actual application at
 any billable event are operational processes covered by later DDs (assignment by DIS-OP-01, application at recurring cycle
 close by BIL-01, application at onboarding/installation by SIP-03 and FUL-03, application at top-up by BIL-06, in campaigns
 by EM-04).

 This DD covers the configuration of Discounts by an admin user: create, read, update, soft-delete, plus an INACTIVE /
 ACTIVE / RETIRED lifecycle (with automatic ACTIVE/INACTIVE flipping driven by the validity window) and audit. There is no
 business workflow here — this is administrative CRUD on catalog data with rules.

 PLM-CFG-04 scope. This DD covers:

   - The Discount entity (catalog)

   - Discount lifecycle (INACTIVE / ACTIVE / RETIRED) with automatic activation/deactivation based on
     startDate/endDate

   - Eligibility filters (per-Package, per-Franchise)

   - Validity window (Start Date / End Date)

   - Two flavors: PriceRebate (any billable charge — recurring invoice line, installation fee, MACD fee, one-off charge) and
     WalletCredit (credits a wallet)

   - Type (PERCENTAGE / AMOUNT) and value

 PLM-CFG-04 NOT in scope (handled in later DDs):

   - Customer-to-discount assignment (the customer_discount table and assignment APIs) → DIS-OP-01

   - Batch assignment via file upload → DIS-OP-01

   - Application at recurring cycle close (postpaid invoice) → BIL-01

   - Application at onboarding / installation fees → SIP-03, FUL-03

   - Application at prepaid top-up → BIL-06

   - Application at MACD events → FUL-04 and related

   - Campaign attachment (Discount linked to a marketing campaign) → EM-04

   - Cancellation of an assigned discount per customer → DIS-OP-01

 Downstream modules (billing, cvm, search index) consume Discount catalog data via Kafka events.

 Module placement. Discount catalog is owned by billing, not plm. The PLM family in the code organization holds
 product catalog (Service, Package, Bundle — what the customer buys); discounts are a revenue/billing concept alongside
 Tax, Wallet, Charge type, Penalty type, and Adjustment type. The "PLM-CFG-XX" ID prefix is historical (inherited from the

 Lifecycle semantics (no rule ID — these are state machine invariants):

   - The Discount has two underlying stored fields and one derived field:

   - adminEnabled : boolean — admin's intent ("I want this Discount to be applicable when in date window"). Default
     false on create.

   - retiredAt : timestamp NULL — set when admin manually retires the Discount. Terminal.

   - effectiveStatus : enum {INACTIVE, ACTIVE, RETIRED} — derived (or cached and refreshed by a daily job;
     see Sequence diagrams):

   - RETIRED if retiredAt IS NOT NULL

   - ACTIVE if retiredAt IS NULL AND adminEnabled = true AND startDate ≤ today ≤ endDate (with
     endDate = null treated as +∞)

   - INACTIVE otherwise

   - Initial state on creation: effectiveStatus = INACTIVE (because adminEnabled defaults to false).

   - Manual transitions (admin actions):

   - Toggle adminEnabled (true ↔ false) — recomputes effectiveStatus. Triggers R-PLM-CFG-04-7 and -8 when going
     to true.

   - Retire (retiredAt = now) — terminal. Triggers R-PLM-CFG-04-9. Once retired, cannot return to ACTIVE or INACTIVE.

   - Automatic transitions (driven by time, not by admin action):

   - When startDate is reached and adminEnabled = true: effectiveStatus becomes ACTIVE automatically (no
     admin action needed).

   - When endDate passes: effectiveStatus becomes INACTIVE automatically. The Discount is NOT retired — it can be
     reactivated by extending endDate.

 What's missing for Wananchi KE / Sophix V3:

   1. No flavor distinction. A Promo in TZ always behaves as a PriceRebate on the bill. Wananchi V3 needs WalletCredit
     for prepaid customers.

   2. No INACTIVE / ACTIVE / RETIRED lifecycle with automatic date-driven flipping. TZ has only an active flag — a
     Promo with active=true and endDate already passed still appears active in queries. V3 separates admin intent
     (adminEnabled) from current effect (effectiveStatus), and a daily job (plus inline recomputation at decision time)
     ensures effectiveStatus always reflects today's reality.

   3. No application beyond cycle close. TZ's PromoController is wired only to the cycle-close apply engine. V3 surfaces
     the catalog via /api/discounts/applicable so onboarding (SIP-03, FUL-03), upgrades (FUL-04), top-ups (BIL-06)
     can all apply discounts at the right billable event.

   4. No per-Franchise eligibility. TZ has per-Offer eligibility (PromoInfo) but no franchise dimension. Wananchi has 6
     franchises and assigns staff/loyalty discounts per franchise.

   5. No cross-module ref validation at enable. TZ doesn't verify Package + Franchise + Wallet refs exist when toggling
     active; it just toggles. Bad data surfaces later as runtime failures during apply.

   6. No structured DRL rules. Validation lives inline in Java controllers and service classes; not in a rules engine. Adding
     new validations requires code change + deploy.

   7. No standard event envelope. TZ uses internal Java events between the billing and onboarding monoliths; no Kafka
     publishing for downstream consumers (cache invalidation, search index, CVM, SIP-03, BIL-06) to react to discount
     changes.

   8. BulkPromoUploadController mixes catalog and assignment. In V3 these are separated: catalog in PLM-CFG-04
     (this DD), assignment in DIS-OP-01.

   9. No soft-delete with assignment-count gate. Today, an ops user can disable a Promo regardless of in-flight
     assignments; effect on running customers is ambiguous.



 C — Gap & bridge
 Migration approach: strangler-fig per discount catalog
 The Discount catalog is low-frequency admin data. Strangler-fig is cleanest:

   1. Build the new discount-catalog sub-area in V3 billing module with the schema, rules, events, APIs from this
     DD.

   2. Initial seed from TZ: one-off Liquibase data migration imports existing TZ Promo rows into the new discount table:

   - flavor = PRICE_REBATE for every imported row (TZ has no WalletCredit concept)

   - type mapped 1:1 (PERCENTAGE / AMOUNT)

   - value carried over

   - creditWalletRef = null

   - adminEnabled = (Promo.active = true) (mirror existing intent)

   - effectiveStatus computed at migration time from adminEnabled + startDate + endDate (so ACTIVE Promos
     in-window come in as ACTIVE; expired ones come in as INACTIVE; manually-deactivated come in as INACTIVE)

   - hasBeenActive = (Promo.active was ever true) (best-effort; can be inferred from PromoInfo attachment
     history, else default true to be safe — locks code/flavor as if it had been ACTIVE)

   - retiredAt = null initially; admins retire explicitly post-migration if a Promo should be terminal

   - eligiblePackageRefs[] derived from PromoInfo attachments (mapped via Package ref derived from TZ Offre
     codes)

   - eligibleFranchiseRefs[] empty (all franchises) since TZ has no franchise eligibility

   3. TZ PromoController retired once all consumers (Wananchi-V3 BIL-01, CVM, SIP-03, etc.) read from the new
     endpoints.

 What's deferred to other DDs
   - Customer-to-discount assignment (drag-drop UI, batch upload, schedule-for-future) → DIS-OP-01

 Risks
   - Migration of TZ PromoInfo → V3 eligiblePackageRefs: depends on a stable mapping from TZ Offre.code to V3
     Package code. To be confirmed against the SIP-01 import.

   - Multiple discounts stacking on the same invoice line: rules for "which discounts compose, which conflict" are NOT in
     scope of PLM-CFG-04 (that's an application-time concern, lives in BIL-01). PLM-CFG-04 only ensures each discount is
     well-formed.

   - Backdating activation: a Discount activated today with startDate in the past — should it auto-apply retroactively at
     next cycle close? This is a BIL-01 decision; PLM-CFG-04 allows the configuration but doesn't impose semantics.
