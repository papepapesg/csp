 The terminal step that hands the activation off to SUB-WF-ACTIVATE-01. Once activation completes, the order is done — the
 customer is live, billing has charged, the network is configured. Phases: ACTIVATING → ACTIVATED (success terminal) or
 ACTIVATION_FAILED (failure terminal).



 1. What this step does
 The order has reached its final hurdle. Equipment is physically installed (STEP-INSTALL captured the serial numbers); the
 customer has paid; KYC has cleared; the subscription exists in CREATED status. Now we have to actually turn the service on
 — charge the installation fees and first cycle, push the customer's profile to the AAA, configure the OLT port + VLAN, finalize
 the subscription's status as ACTIVE.

 We don't do any of that work ourselves. SUB-WF-ACTIVATE-01 owns the activation saga. Our job in this step is to hand off to
 it cleanly:

   1. Trigger the activation saga (order-trigger-activation worker). POSTs to SUB-WF-ACTIVATE-01's trigger
     endpoint with the subscription ID, the activation date, the operator's cycle-anchor overflow policy, and the equipment
     bindings STEP-INSTALL captured. The saga responds 202 Accepted with a processInstanceId and the topics where
     it'll publish its outcome.

   2. Wait for the activation to finish, via Kafka. Camunda parks at wait-activation-outcome — a message catch
     event listening for either ActivationSucceeded or ActivationFailed. Two of our Kafka consumers
     (SubscriptionActivatedConsumer for the success topic, SubscriptionActivationFailedConsumer for the
     failure topic) correlate the right outcome back to the parked order.

   3. Finalize the order. Success → order-notify-success worker marks the order ACTIVATED, emits
     OrderActivated Kafka event. Failure → order-mark-activation-failed marks ACTIVATION_FAILED, emits
     OrderActivationFailed + OrderRefundRequested (refund cascade if money was taken).

 Async handoff via 202 + Kafka outcome
 SUB-WF-ACTIVATE-01 responds 202 because the activation legitimately passes through PENDING_ACTIVATION as a
 committed intermediate state — the row is visible in subscription table during the saga, before BIL-01 and FUL-03 have
 finished. Pretending the call was synchronous would be misleading. So FUL-02 accepts the 202 and waits on Kafka.

 There is a long-poll convenience endpoint (GET /api/subscriptions/{subscription_id}/wait-for-terminal-s
 tate?processInstanceId=...&timeout=60s) but the SUB-WF-ACTIVATE-01 DD discourages its use ("blocks a


SOPHIX BSS Design Documents                                                                                                                  Page 3
 server-side connection per pending activation"). We use Kafka instead — same outcome, no held connections.

 Idempotency via deterministic correlationId
 Because the trigger is async and our worker might be re-fetched after a Camunda lock expiry (e.g., worker crash between
 POST and /complete), we need to be sure that re-triggering doesn't kick off two activation sagas. SUB-WF-ACTIVATE-01
 accepts a correlationId in the request body for exactly this reason — if it sees the same correlationId twice for the same
 subscription, it returns the existing processInstanceId rather than starting a fresh saga.

 We use a deterministic correlationId: act_{orderId} — derived from orderId, the same on every re-trigger of the same
 order. The worker computes it, posts it, accepts the 202 whether the saga is fresh or pre-existing.

 Equipment binding translation
 STEP-INSTALL captures equipment as an array shape: [{equipmentRequirement, equipmentRef,
 serialNumber}]. SUB-WF-ACTIVATE-01 wants a named-slot map: {ontSerial: "...", stbSerials: ["..."],
 ...}. The worker translates between the two using a static mapping per equipmentRequirement → SUB-WF-ACTIVATE-01
 slot name (e.g., GPON_ONT → ontSerial; ATA → ataSerial; STB → stbSerials[]). The mapping table lives in
 ful_02_config (one row per operator, with equipment_slot_mapping_jsonb per FRAMEWORK §5.3 future
 extension; v1.0 ships with a hardcoded default).

 Refund cascade on activation failure
 If activation fails after the customer has paid, the customer is owed a refund — same pattern as STEP-INSTALL's failure
 path. order-mark-activation-failed emits OrderRefundRequested alongside OrderActivationFailed when
 payment_received_amount > 0. BIL-02-ADJ-01 queues the refund.

 What this step deliberately doesn't do
   - Doesn't charge billing. BIL-01 charging happens inside SUB-WF-ACTIVATE-01 — that workflow's responsibility (per its
     R-WF-2). FUL-02 just triggers; the saga handles the charging.

   - Doesn't provision the network. FUL-03 owns network provisioning. SUB-WF-ACTIVATE-01 calls FUL-03 synchronously
     from its own service task; FUL-02 doesn't see FUL-03 in this step.

   - Doesn't roll back the subscription on failure. SUB-WF-ACTIVATE-01 owns its own rollback logic — on failure, it reverts
     the subscription to CREATED and writes last_failure onto the subscription row. FUL-02 just marks
     ACTIVATION_FAILED on its own customer_order row; the subscription stays alive in CREATED for ops to investigate
     (or terminate via SUB-WF-TERMINATE-01 if the activation can't be retried).

 8. Step-pinned rules
  ID                                                               Rule

  R-FUL-02-ACT-1                                                   order-trigger-activation POSTs to SUB-WF-ACTIVATE-01 POST
                                                                   /api/subscriptions/{subscription_id}/activate with deterministic
                                                                   correlationId = act_{orderId}. Re-trigger of the same order receives
                                                                   the existing processInstanceId rather than starting a fresh saga.

  R-FUL-02-ACT-2                                                   Equipment bindings are translated from STEP-INSTALL's array shape
                                                                   ([{equipmentRequirement, equipmentRef, serialNumber}]) to
                                                                   SUB-WF-ACTIVATE-01's named-slot map ({ontSerial, ataSerial,
                                                                   stbSerials, ...}) using
                                                                   ful_02_config.equipment_slot_mapping_jsonb. v1.0 ships the WIK
                                                                   default mapping (GPON_ONT → ontSerial, ATA → ataSerial, STB →
                                                                   stbSerials[]).

  R-FUL-02-ACT-3                                                   SubscriptionActivatedConsumer and
                                                                   SubscriptionActivationFailedConsumer correlate primarily via
                                                                   activation_correlation_id. Fallback: subscription_id. On neither
                                                                   matching, log DEBUG and skip — the activation is for a subscription not
                                                                   originating in FUL-02 (e.g., admin direct activation).

  R-FUL-02-ACT-4                                                   Trigger worker uses lock duration 95 sec (saga can take up to 90 sec per
                                                                   SUB-WF-ACTIVATE-01 R-WF-3; +5 sec margin for the worker to receive the
                                                                   202 and /complete).

  R-FUL-02-ACT-5                                                   Activation failure with payment_received_amount > 0 triggers refund
                                                                   cascade — order-mark-activation-failed emits both
                                                                   OrderActivationFailed and OrderRefundRequested. The subscription
                                                                   remains in CREATED status (SUB-WF-ACTIVATE-01 reverted it); FUL-02 does
                                                                   NOT terminate the subscription from this step. Ops decides whether to retry
                                                                   activation or to terminate the subscription via SUB-WF-TERMINATE-01.

  R-FUL-02-ACT-6                                                   FUL-02 does NOT roll back BIL-01 charges or FUL-03 provisioning on
                                                                   activation failure — SUB-WF-ACTIVATE-01 owns its own rollback (per its R-A-5
                                                                   / R-WF-* family). FUL-02 just reflects the outcome in its own customer_order
                                                                   row.

  ID                          Rule

  R-FUL-02-ACT-7              No boundary timer on wait-activation-outcome in v1.0.
                              SUB-WF-ACTIVATE-01 has its own 90-second timeout that emits
                              SubscriptionActivationFailed with reasonCode =
                              BILLING_TIMEOUT or FULFILLMENT_TIMEOUT; FUL-02 receives that via
