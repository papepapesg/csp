 MVP simplification baseline: FA-01, FA-02, and FA-03 must be implemented as one field-audit capability in the first release,
 with audit_type driving type-specific rules, checklists, and routing. Do not create three services or three independent
 databases.



 1. Purpose
 FA-01 defines a controlled equipment field audit process for verifying that equipment recorded in SOPHIX exists in the
 expected field/customer location, has the expected serial identity, and is in an acceptable condition.

 Use FA-01 when:

   - operations wants to verify equipment installed at a customer premises;

   - a contractor or field team must prove custody of assigned customer equipment;

   - support suspects serial mismatch, damaged CPE, missing ONT/modem/STB, or wrong equipment location;

   - internal audit needs evidence that equipment state in OSR-INSTANCE matches real-world field state;

   - a discrepancy must be routed to support, recovery, RMA, write-off, or manual correction.

 FA-01 is not the same as OSR-05 inventory audit. OSR-05 audits stock locations such as warehouse and contractor vans.
 FA-01 audits equipment in the field/customer context and uses technician/mobile evidence.

 FA-01 is also not a replacement for normal WO completion evidence. Normal installation, shifting, support, and swap WOs
 already capture equipment bindings/photos in their own flows. FA-01 is used when the business needs a standalone audit
 campaign or an exception-driven verification after the normal job has already completed.

 Boundary rules:

   - FA-01 does not directly update OSR stock balances or equipment instance lifecycle.

   - FA-01 routes approved corrections to OSR-INSTANCE, OSR-05, or OSR-RMA.

   - FA-01 does not create purchase orders and does not call OSR-02 procurement.

   - FA-01 can create a WO with kind=FIELD_AUDIT when technician scheduling/evidence is needed.

 3. Process Overview
            flowchart LR
              A["Backoffice creates audit campaign/task"] --> B["FA-01 loads expected equipment from OSR-INSTANCE"]
              B --> C["WO or audit task assigned to field user"]
              C --> D["Mobile app scans serial and captures evidence"]
              D --> E["FA-01 compares expected vs observed"]
              E --> F{"Discrepancy?"}
              F -- "No" --> G["Close audit task"]
              F -- "Yes" --> H["Open discrepancy"]
              H --> I["Drools selects severity and route"]
              I --> J["Create ticket, RMA/recovery, OSR correction, or approval"]

 7. Rules And Drools
 Use Drools for operator-variable scope, severity, and routing.

 Recommended packages:

   - rules.field_audit.equipment.scope

   - rules.field_audit.equipment.severity

   - rules.field_audit.equipment.routing

   - rules.field_audit.equipment.approval

 Examples:
          package rules.field_audit.equipment.severity

          rule "Missing installed customer equipment is high severity"
          when
            $f : EquipmentFieldAuditFact(discrepancyType == "MISSING",
                                         expectedLocationType == "CUSTOMER_PREMISES")
            $d : EquipmentFieldAuditDecision()
          then
            $d.setSeverity("HIGH");
          end

          package rules.field_audit.equipment.routing

          rule "Missing equipment creates recovery RMA"
          when
            $f : EquipmentFieldAuditFact(discrepancyType == "MISSING",
                                         equipmentRecoverable == true)
            $d : EquipmentFieldAuditDecision()
          then
            $d.route("CREATE_RMA_RECOVERY");
          end

          rule "Damaged customer equipment creates support ticket"
          when
            $f : EquipmentFieldAuditFact(discrepancyType == "DAMAGED")
            $d : EquipmentFieldAuditDecision()
          then
            $d.route("CREATE_TICKET");
          end

          package rules.field_audit.equipment.approval

          rule "Write-off requires approval"
          when
            $f : EquipmentFieldAuditFact(routeAction == "REQUEST_WRITE_OFF")
            $d : EquipmentFieldAuditDecision()
          then
            $d.requireApproval("EQUIPMENT_FIELD_AUDIT_WRITE_OFF");
          end

 Fixed validation such as allowed enum values, required evidence files, and duplicate offline references belongs in application
 code.

 Frontend must show expected source clearly:

   - expected serial and binding come from OSR-INSTANCE snapshot stored in FA-01;

   - WO state comes from WO-01 if the task is WO-backed;

   - discrepancy route action comes from FA-01 and target module references.



 10. Infrastructure Recommendations
 For a medium deployment:

   - Run FA-01 APIs in the operations/field service API deployment or a shared operations module.

   - Run logical handlers in an existing operations worker deployment.

   - Store evidence files in the foundation file storage service and reference only file ids in FA-01 tables.

   - Support mobile offline idempotency because field technicians may submit after connectivity returns.

   - Use PostgreSQL for audit/task/discrepancy state.

   - Use Kafka/outbox for audit events and reporting feed.

 Recommended logical worker handlers:

  Handler                                                              Purpose

  fa01-generate-expected-items                                         Reads OSR-INSTANCE and freezes expected item snapshot.

  fa01-create-wo                                                       Creates WO-01 field audit work order when needed.

  fa01-compare-observations                                            Compares expected items and submitted observations.

  fa01-route-discrepancy                                               Runs Drools and creates ticket/RMA/approval actions.

  fa01-close-task                                                      Closes tasks after discrepancies are resolved or no discrepancy exists.


 These are logical handlers. One worker process may implement multiple handlers.

 12. Implementation Notes
   - Use FA-01 only for standalone audit campaigns or exception-driven verification. Do not force every normal WO completion
     through FA-01.

   - Keep OSR-INSTANCE as the authoritative source of expected customer equipment.

   - Keep WO-01 as the owner of technician assignment and field execution when the audit requires dispatch.

   - Do not directly mutate equipment state from FA-01. Route corrections through the owning module.

   - Design mobile APIs for offline use: deterministic client refs, duplicate-safe uploads, and resumable task submission.

   - Preserve evidence and snapshots because audit findings may be reviewed weeks later.
