 configuration-compatible but phased after the first provider is stable.



 1. Purpose
 PAY-GW-01 defines how SOPHIX receives, validates, stores, reconciles, and routes payments coming from external
 payment providers.

 This includes mobile money, bank transfer notifications, card processors, retail-agent payment systems, and future regional
 payment channels.

 For the Kenya-first deployment, the first provider class is expected to be M-Pesa-style payment callbacks, with bank transfer
 and card channels added as operator configuration requires. The design must remain configurable enough to support other
 regions with different mobile-money or bank providers.

 This DD exists because payment gateway integration is not the same thing as payment application:

 3. Design Decision
 PAY-GW-01 is the integration boundary between external payment providers and the internal billing modules.

 The module must first persist the provider callback durably, then route it asynchronously to the correct internal target. This
 prevents provider retry behavior, network latency, or internal billing outages from losing payments.

 Preferred callback ownership:
          External provider
            -> PAY-GW public callback endpoint
            -> gateway_callback_event
            -> gateway_transaction
            -> routing worker
            -> BIL-01-PAY-01 or BIL-05

 BIL-05 currently mentions gateway-specific callback URLs for wallet topups. Those URLs should be treated as a legacy or
 compatibility shape. New implementation should expose provider callbacks under PAY-GW-01 and route wallet topups into
 BIL-05 using internal authenticated APIs.

 Compatibility wrappers may remain if already implemented:

  Legacy shape                                                      Preferred shape

  POST /api/gateway/mpesa/callback in BIL-05                        POST /api/payment-gateways/mpesa/callback in PAY-GW-01

  GET /api/gateway-reconciliations in BIL-05                        GET /api/payment-gateways/reconciliation-runs in PAY-GW-01

 5. Core Concepts
 5.1 Provider
 A provider is an external payment system integrated with SOPHIX.

 Examples:

   - MPESA_KE

   - BANK_TRANSFER_KE

   - CARD_PROCESSOR_KE

   - RETAIL_AGENT_KE

   - Future region-specific mobile-money providers

 5.2 Channel
 A channel is a customer-visible or operational payment route under a provider.

 Examples:

   - M-Pesa Paybill for customer invoice payment.

   - M-Pesa STK Push for self-care payment.

   - Bank transfer to operator account.

   - Retail-agent cash collection.

 5.3 Callback Event
 A callback event is the exact inbound message received from the provider. It is stored for audit and idempotency, with
 sensitive fields redacted or encrypted.

 5.4 Gateway Transaction
 A gateway transaction is SOPHIX's normalized representation of money received or reversed through an external provider.

 One provider callback may produce one gateway transaction. For batch settlement files, one settlement row may also
 produce or update one gateway transaction.

 5.5 Routing
 Routing decides which internal module must receive the money:

  Target                                                          Route to

  Customer invoice or account payment                             BIL-01-PAY-01

  PREPAID wallet topup                                            BIL-05

  Unknown customer/reference                                      Hold in PAY-GW queue

  Suspected duplicate conflict                                    Hold in PAY-GW queue

 6.2 Important Callback Rule
 PAY-GW returns success to the provider only after the callback is durably stored.

 Routing to BIL-01 or BIL-05 should normally happen asynchronously, because provider callbacks often have short timeout
 windows. If internal routing fails after storage, the routing worker retries and operations can repair the transaction from
 Backoffice.

 6.3 Duplicate Callback Rule
 If the same provider transaction arrives again with the same normalized provider transaction id and same
 amount/currency/payment date, PAY-GW must return 200 and not route a second payment.

 If the same provider transaction id arrives with a different amount, currency, payer, or paid date, PAY-GW must hold the
 transaction as DUPLICATE_CONFLICT and require operations review.



 7. Payment Routing Rules
 7.1 Route To Payment Application
 Use this route when the payment is meant to pay a POSTPAID invoice, account balance, activation charge, or other
 invoice-like receivable.

 PAY-GW calls:
          POST /api/payments/receive

 Target module:
          BIL-01-PAY-01

 Required normalized payload:
          {
              "operatorCode": "WIK",
              "customerId": "CUS-100045",
              "accountId": "ACC-900045",
              "invoiceId": "INV-2026-00001234",
              "paymentReference": "MPESA-QL91ABCD",
              "paidAmount": 2500.00,
              "currency": "KES",
              "paymentMethod": "MOBILE_MONEY",
              "gatewayProviderCode": "MPESA_KE",
              "gatewayTransactionId": "GTX-20260529-000001",
              "paidAt": "2026-05-29T09:42:00Z"
          }

 invoiceId may be null if the reference maps only to a customer account. In that case, PAY-01 uses its own allocation rules.

 8. Status Model
 8.1 Gateway Transaction Status
  Status                                                                  Meaning

  RECEIVED                                                                Callback or settlement row has been stored.

  VALIDATED                                                               Signature, payload, amount, and provider rules passed.

  ROUTING_PENDING                                                         Transaction is ready for routing worker.

  ROUTING_RETRY                                                           Last routing attempt failed due to recoverable issue.

  APPLIED                                                                 Target module accepted and posted the payment/topup.

  HELD                                                                    Human or configured repair action is required.

  REJECTED                                                                Invalid callback or non-recoverable provider payload.

  DUPLICATE                                                               Same payment already processed successfully.

  DUPLICATE_CONFLICT                                                      Same provider id with conflicting values. Requires review.

  REVERSED                                                                Provider sent reversal and internal reversal was completed.

  SETTLED                                                                 Provider settlement confirms the transaction.

  RECONCILED                                                              Provider settlement and internal records match.

 13. Frontend Usage

SOPHIX BSS Design Documents                                                              Page 11
 13.1 FE-APP-01 Backoffice
 Backoffice uses PAY-GW-01 for:

   - Payment gateway transaction search.

   - Held payment repair queue.

   - Provider/channel configuration.

   - Gateway reconciliation run and discrepancy resolution.

   - Retry routing action.

 Backoffice does not use PAY-GW-01 to apply payments directly unless resolving a held gateway transaction. Normal manual
 offline payments remain in PAY-01.

 13.2 FE-APP-02 Outdoor Sales App
 Outdoor sales app uses PAY-GW-01 channel configuration to show payment instructions during sales or activation flows.

 It should not hardcode Kenya-specific labels. It should request active channel instructions for the operator and context.

 13.3 FE-APP-04 Customer Self Care
 Self-care app uses PAY-GW-01 channel configuration to show payment instructions and available methods.

 If STK push or payment initiation is later implemented, PAY-GW-01 should own the provider initiation endpoint and still route
 successful provider confirmation back to PAY-01 or BIL-05.

 15.2 Recommended Partitions
 Partition high-volume tables by month:

 17. Testing Requirements
 17.1 Unit Tests
   - Provider parser normalizes valid callback payloads.

   - Invalid signature is rejected.

   - Duplicate callback returns existing transaction.

   - Duplicate conflict creates held transaction.

   - Redaction removes sensitive fields.

   - Routing payload mapping to PAY-01 is correct.

   - Routing payload mapping to BIL-05 is correct.

 17.2 Integration Tests
   - Provider callback creates gateway transaction and returns 200 after durable store.

   - Routing worker calls PAY-01 once for POSTPAID payment.

   - Routing worker calls BIL-05 once for wallet topup.

   - PAY-01 temporary outage triggers retry without duplicate application.

   - BIL-05 rejection creates held resolution.

   - Reconciliation run creates expected discrepancy items.

 17.3 End To End Tests
   - Customer pays invoice via provider callback, invoice becomes paid through PAY-01.

   - Customer tops up PREPAID wallet, wallet balance increases through BIL-05.

   - Unknown reference payment appears in Backoffice held queue.

   - Operations routes held payment to account, transaction becomes applied.

   - Provider settlement file with one missing row creates an open reconciliation item.



 18. Implementation Notes
   1. Implement provider adapters behind a common interface:
           PaymentProviderAdapter
             verifySignature(request)
             parseCallback(request)
             buildIdempotencyKey(parsedPayload)
             parseSettlementRow(row)

   2. Keep provider-specific code isolated from core routing logic.

   3. Store callbacks and transactions in one database transaction where possible.

   4. Return provider acknowledgement only after durable write.

   5. Make routing workers idempotent by checking gateway_transaction.application_reference_id before calling
     target modules.

   6. Use target module idempotency keys:

   - PAY-01: paymentReference = provider_transaction_id or stable gateway payment reference.

   - BIL-05: gatewayReference = provider_transaction_id.

   7. Do not route invalid signatures.

   8. Do not reject valid but unresolved money. Hold it for operations.

   9. The frontend must read channel display configuration from PAY-GW-01, not hardcode M-Pesa or bank text.

 20. Definition Of Done
 PAY-GW-01 is complete when:

   - Provider and channel configuration APIs are implemented.

   - At least one provider callback adapter is implemented.

   - Callback events and gateway transactions are durably stored.

   - Duplicate and duplicate-conflict handling is tested.

   - Routing to PAY-01 and BIL-05 works with idempotency.

   - Held payment repair queue works in Backoffice.

   - Daily reconciliation run can import or fetch provider settlement data.

   - Security controls for callback endpoints are active.

   - Metrics and alerts are configured.

   - FE apps can read active payment channel instructions by operator and context.
