 DEV_IMPL_GUIDE - SUB-WF-ACTIVATE-01 Subscription
 Activation
 1. Purpose
 This guide explains activation implementation as the flow executes at runtime.

 Use it with:

   - DD_SUB-WF-ACTIVATE-01-Subscription_Activation-v1.0.md

   - DD_SUB-WF-ACTIVATE-01-FLOW-WIK-v1.0.md

   - DD_SUB-WF-FRAMEWORK-01-Subscription_Workflow_Framework-v1.0.md

   - DD_SUB-WF-FRAMEWORK-01-WORKERS-v1.0.md

 The sequence below is the implementation path a developer should follow.


 2. Runtime Actors
  Runtime component                                               What it does

  subscription-workflow-api pod                                   Receives activation API request, validates, starts operation.

  subscription-workflow-worker pod/app                            Handles SUB-WF framework topics and cross-cutting topics.

  subscription-state-worker pod/app                               Handles SUB-LM worker topics. May be consolidated with workflow worker in
                                                                  budget deployment.

  billing-worker pod/app                                          Handles BIL-01 worker topics.

  fulfillment-worker pod/app                                      Handles FUL/OSR worker topics.

  Camunda                                                         Stores and executes BPMN state.

  Drools/KIE                                                      Executes activation rules and returns decisions.

  Kafka outbox dispatcher                                         Publishes outbox rows to Kafka.


 pod/app means deployment can vary. A Laravel command, Java process, or container can handle multiple worker topics.

 5. Step 2 - Request Lands On subscription-workflow-api
 The subscription-workflow-api pod receives the request.

 It validates request shape first:

  Field                                                           Validation

  operatorCode                                                    Required.

  activationTrigger                                               Required; allowed: BACKOFFICE_OPERATOR, CALL_CENTER,
                                                                  CUSTOMER_SELF_SERVICE, SALES_FIELD, SCHEDULED_ACTIVATION.

  intendedActivationDate                                          Required valid date.

  cycleAnchorOverflowPolicy                                       Optional; if present, allowed: ROUND_TO_28, ROUND_TO_1_NEXT_MONTH,
                                                                  PRORATE_PARTIAL_CYCLE.

  equipmentBindings                                               Array; no duplicate equipmentRequirement.

  equipmentBindings[].equipmentRequirement                        Required.

  equipmentBindings[].equipmentRef                                Required.


 If shape validation fails, return 400.

 Example:
          {
              "code": "VALIDATION_ERROR",
              "message": "equipmentBindings[0].equipmentRef is required."
          }

 7.3 Subscription Summary
 Load this from the SUB-LM source of truth, not from cache.

 How to load it depends on deployment:

  Deployment                                                       How activation reads subscription

  SUB-LM and SUB-WF in same application                            Call the SUB-LM application service/read repository in-process, for example
                                                                   SubscriptionReadService.getSummary(...).

  SUB-LM and SUB-WF split into separate services                   Call SUB-LM internal API, for example GET
                                                                   /internal/subscriptions/{id}/summary.


 Do not let activation code issue random SQL against the subscription table unless that SQL is inside a SUB-LM-owned
 repository/service. Activation can consume the summary; SUB-LM owns how the row is read.

 Do not use cache for this check. Activation needs authoritative current status because it is about to start a state-changing
 operation.

 7.4 Package Snapshot
 Load this from the package/catalog module, not from SUB-LM.

 Activation needs package and product/service composition because it must validate:

   - Package exists.

   - Package is ACTIVE.

   - Package version to pin on activation.

   - Required equipment for the package services.

   - Minimum contract term, if applicable.


SOPHIX BSS Design Documents                                                                                                               Page 4
 Runtime call:
           GET /internal/packages/{packageRef}/activation-snapshot?operatorCode=WIK HTTP/1.1
           Authorization: Bearer <subscription-workflow-service-token>

 The target pod/module is the SIP/package-management API. If SIP delegates service composition to PLM-CFG, SIP can call
 PLM internally and return one activation snapshot. Activation should not call many catalog tables directly.

 Who may call cache:

   - Preferred: SIP/package-management owns its own cache and returns authoritative-enough activation snapshots through
     its API.

   - Also acceptable: the subscription workflow service uses an approved PackageCatalogClient wrapper that implements
     read-through cache internally.

   - Not allowed: activation business logic directly reads Redis/cache keys.

 Read-through cache inside SIP or the approved client wrapper is allowed only as an optimization if:

   - Cache entry includes package status/version/equipment requirements.

   - Cache TTL is short.

   - Cache miss falls back to SIP.

   - If SIP is unavailable and no valid cache exists, activation fails safely.

 Example response:
           {
               "packageRef": "pkg_INET_VOIP_RES",
               "packageVersionId": "pkgver_003",
               "status": "ACTIVE",
               "requiredEquipment": ["GPON_ONT", "ATA"],
               "contractMinimumTermMonths": 12
           }


 7.5 HomePass Snapshot
 Load this from the RLM/HomePass module, not from SUB-LM.

           Authorization: Bearer <subscription-workflow-service-token>

 The target pod/module is the RLM-CFG/HomePass API.

 Who may call cache:

   - Preferred: RLM/HomePass owns its own cache and returns authoritative-enough activation snapshots through its API.

   - Also acceptable: the subscription workflow service uses an approved HomePassClient wrapper that implements
     read-through cache internally.

   - Not allowed: activation business logic directly reads Redis/cache keys.

 Read-through cache inside RLM or the approved client wrapper is allowed only as an optimization if:

   - Cache entry includes sellability/current status.

   - Cache TTL is short.

   - Cache miss falls back to RLM.

   - If RLM is unavailable and no valid cache exists, activation fails safely.

 Example response:
           {
               "homepassId": "hp_01HZ_NRB",
               "sellable": true,
               "technology": "GPON"

 9. Drools Rules To Configure
 The implementation should provide rules equivalent to the following.

 9.1 Subscription Must Be CREATED
          rule "activation requires subscription created"
          when
               $facts : ActivationFacts(subscription.statusCode != "CREATED")
               $decision : ActivationDecision()
          then
               if ($facts.subscription.statusCode == "ACTIVE") {
                   $decision.reject("ALREADY_ACTIVE", "Subscription is already ACTIVE.");
               } else if ($facts.subscription.statusCode == "TERMINATED") {
                   $decision.reject("SUBSCRIPTION_TERMINATED", "Terminated subscription cannot be activated.");
               } else {
                   $decision.reject("INVALID_STATE_FOR_ACTIVATION", "Subscription must be CREATED before activation.");
               }
          end


 9.2 Package Must Be Active
          rule "activation package must be active"
          when
               $facts : ActivationFacts(packageInfo.status != "ACTIVE")
               $decision : ActivationDecision()
          then
               $decision.reject("PACKAGE_RETIRED", "Package is not ACTIVE at activation time.");
          end


 9.3 HomePass Must Be Sellable
          rule "activation homepass must be sellable"
          when
               $facts : ActivationFacts(homepass.sellable == false)
               $decision : ActivationDecision()
          then
               $decision.reject("HOMEPASS_NOT_SELLABLE", "HomePass is not sellable.");
          end


 9.4 Trigger Role Rules
          rule "sales field activation role"
          when
               $facts : ActivationFacts(
                   request.activationTrigger == "SALES_FIELD",
                   actor.role != "SALES_AGENT"
               )
               $decision : ActivationDecision()
          then
               $decision.reject("ROLE_NOT_AUTHORIZED_FOR_TRIGGER", "SALES_FIELD activation requires SALES_AGENT role.");
          end

          rule "customer self service activation disabled"
          when
               $facts : ActivationFacts(
                   request.activationTrigger == "CUSTOMER_SELF_SERVICE",
                   config.customerSelfServiceEnabled == false
               )
               $decision : ActivationDecision()
          then
               $decision.reject("CUSTOMER_SELF_SERVICE_ACTIVATION_DISABLED", "Customer self-service activation is disabled for this o
          end


 9.5 Cycle Anchor Overflow Rules
          rule "calendar anchor overflow prorate partial cycle"
          when



SOPHIX BSS Design Documents                                                                                          Page 7
                $facts : ActivationFacts(
                    subscription.cycleModel == "CALENDAR_ANCHOR",
                    activationDayOfMonth in (29, 30, 31),
                    effectiveOverflowPolicy == "PRORATE_PARTIAL_CYCLE"
                )
                $decision : ActivationDecision(rejected == false)
          then
                $decision.setResolvedActivatedAt($facts.request.intendedActivationDate.atStartOfDay());
                $decision.setResolvedCycleAnchorDay(1);
                $decision.setCycleAnchorOverflowApplied("PRORATE_PARTIAL_CYCLE");
                $decision.setPartialCycleDays(daysUntilFirstOfNextMonth($facts));
          end

          rule "calendar anchor normal day"
          when
               $facts : ActivationFacts(
                   subscription.cycleModel == "CALENDAR_ANCHOR",
                   activationDayOfMonth >= 1,
                   activationDayOfMonth <= 28
               )
               $decision : ActivationDecision(rejected == false)
          then
               $decision.setResolvedActivatedAt($facts.request.intendedActivationDate.atStartOfDay());
               $decision.setResolvedCycleAnchorDay(activationDayOfMonth($facts));
               $decision.setCycleAnchorOverflowApplied(null);
               $decision.setPartialCycleDays(0);
          end


 9.6 Equipment Rules
          rule "activation required equipment must be supplied"
          when
               $facts : ActivationFacts(missingRequiredEquipment not empty)
               $decision : ActivationDecision()
          then
               $decision.reject("EQUIPMENT_MISSING", "Required equipment is missing: " + $facts.missingRequiredEquipment);
          end

          rule "activation strict equipment validation failed"
          when
               $facts : ActivationFacts(
                   config.equipmentBindingValidationStrict == true,
                   invalidEquipmentRefs not empty
               )
               $decision : ActivationDecision()
          then
               $decision.reject("EQUIPMENT_BINDING_INVALID", "One or more equipment references cannot be bound: " + $facts.invalidEqu
          end


 9.7 Backdating Rules
          rule "activation backdating disabled"
          when
               $facts : ActivationFacts(
                   intendedActivationDateBeforeToday == true,
                   config.backdatingAllowed == false
               )
               $decision : ActivationDecision()
          then
               $decision.reject("BACKDATING_NOT_ALLOWED", "Backdated activation is disabled for this operator.");
          end

          rule "activation future date rejected"
          when
               $facts : ActivationFacts(intendedActivationDateAfterToday == true)
               $decision : ActivationDecision()
          then
               $decision.reject("FUTURE_ACTIVATION_DATE_NOT_ALLOWED", "Future activation must use scheduled activation.");
          end

 Drools must not call databases, APIs, Kafka, SUB-LM, BIL, FUL, or OSR. It receives facts and returns decisions only.

 19. Manual Smoke Test
   1. Create test subscription in CREATED.

   2. Seed subscription_activation_config.

   3. Seed subscription_operation_config.

   8. Confirm Camunda process instance exists.

   9. Confirm subscription moves to PENDING_ACTIVATION.

   10. Simulate payment-confirmed.

   12. Confirm subscription becomes ACTIVE.

   13. Confirm SubscriptionActivated outbox row exists.

   14. Confirm operation final state is COMPLETED.


 20. Common Mistakes
   - Updating subscription status directly from activation API.

   - Trusting actor role from request body.

   - Starting Camunda before idempotency/concurrency reservation.

   - Letting Drools call external APIs.

   - Treating worker topic names as shell commands.

   - Creating one worker deployment per topic by default.

   - Publishing Kafka directly instead of writing outbox.

   - Emitting SubscriptionActivated before SUB-LM commits ACTIVE.

   - Dropping unmatched payment or fulfillment messages.
