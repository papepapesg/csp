 This DD should be implemented as part of the owning SOPHIX capability, not as an isolated service unless the deployment
 architecture explicitly separates that capability.

 Implement this DD with these rules:

   - Use the owning module APIs/repositories for authoritative writes.

   - Use approved internal APIs/client wrappers when reading another module's data.

   - Do not query another module's database tables directly from business flow code.

   - Treat worker names as logical Camunda external-task topics, not separate deployments.

   - One worker application may handle multiple topics, but metrics, retries, and logs must remain visible per topic.

   - Emit success events only after the authoritative state commit succeeds.

   - Use outbox publishing for Kafka events.

 A — Target
 1. What this process is about
 When a customer pays — through any channel — the money needs to be recorded, allocated to invoices (POSTPAID) or
 wallet (PREPAID), and the resulting status changes propagated. PAY-01 owns this flow end-to-end:

 Receipt: gateway adapters or admin tools call POST /api/payments/receive with the payment details (account,
 customer identity reference, amount, currency, method, reference, optional target invoice). PAY-01 deduplicates on
 (account_id, payment_reference) — gateways may retry the same notification.

 Allocation: PAY-01 determines the customer's billing mode. PREPAID → credit the wallet via BIL-05. POSTPAID → allocate
 across open invoices, either to the customer-specified target invoice or per the operator's auto-allocation policy (FIFO by due
 date, by issue date, by largest amount, or by smallest amount).

 Overpayment: if a POSTPAID payment exceeds total outstanding, the surplus goes to: (a) account_credit_balance for
 use against future invoices on the same account (default), (b) a designated overflow wallet, or (c) held for admin manual
 review.

 Audit: every payment writes to payment_ledger; every allocation against an invoice writes to
 payment_invoice_allocation. All in one DB transaction.

 Downstream notification: PAY-01 emits one PaymentApplied event per allocation. STA-01 consumes these to transition
 invoice status (PENDING → PAID / PARTIALLY_PAID; OVERDUE → PAID / PARTIALLY_PAID; etc.).

 Reversal: admin or gateway-driven reversal undoes allocations and restores outstanding amounts. Emits
 PaymentReversed.

 #### What PAY-01 explicitly does not own

   - Charging (outbound) — owned by BIL-01 Core. A charge debits the customer; a payment credits. Different flows, different
     ledgers, different entry points.

   - Credit / debit note application — owned by BIL-01-CN-01. Notes arrive via Kafka events from GEN-01; payments arrive
     via REST or other gateways.

   - Payment gateway integration — owned by adapter DDs (M-Pesa adapter, Visa adapter, bank transfer adapter).
     Adapters call PAY-01's REST; the wire-level integration with each payment provider is the adapter's responsibility.

   - Invoice status transitions — owned by BIL-02-STA-01. PAY-01 emits PaymentApplied; STA-01 consumes and
      transitions.

   - Wallet balance / top-up mechanics — owned by BIL-05. PAY-01 calls BIL-05 for wallet credits.

   - Invoice generation — owned by BIL-02-GEN-01. PAY-01 reads invoice.outstanding_amount for allocation
      decisions.

   - Refunds initiated by operator policy (different from gateway chargebacks) — typically handled via BIL-02-ADJ-01 credit
     note workflow, which feeds back through CN-01.

 B — Current TZ
 Workshop materials do not describe a unified payment application service in TZ Sophix as a separate concern. Payment
 receipt is likely tied into TZ's gateway-specific code paths with direct DB writes against invoice tables and wallet tables; no
 formal allocation policy, no credit balance entity, no payment reversal workflow.



 C — Gap & bridge
 PAY-01 is new functionality. It introduces:

   - Unified payment receipt entry point across all gateways and admin tools

   - Configurable allocation policy (FIFO by due date / by issue date / largest first / smallest first)

   - Configurable overpayment policy (apply to next open / wallet topup / manual review)

   - First-class account_credit_balance with auto-application on new invoices for the same account

   - Formalized event contracts (PaymentApplied, PaymentReceivedUnallocated, PaymentReversed,
     OverpaymentPendingReview, CreditBalanceAdjusted) consumed by STA-01, BIL-04, NOT-01, analytics

   - Payment reversal as a structured operation

   - Full audit in payment_ledger + payment_invoice_allocation with 10-year retention
