 1. What this is
 The Service Catalog. Two entities: service_class (the classes the operator sells — Internet, Voice, IPTV, ...) and
 service (the specific leaf products within a class — Internet 100Mbps GPON, VoIP standard, ...). Services are bundled into
 Packages by SIP-01.

 Who reads from PLM-CFG-01:

   - SIP-01 — reads Service definitions when validating a Package's serviceRefs[].

   - FUL-03 / FUL-04 / FUL-05 — read Service definitions to resolve service_management_key → HomePass endpoint,
     dispatch to Provisioner adapter via provisioner_key, apply network_profile_shape.params.

   - UPGRADE-01 / DOWNGRADE-01 / MIGRATION-01 — read service_class.requires_equipment to compute
     equipment-delta when comparing source vs target Package compositions.

   - BIL-01 / BIL-CFG-01 — read Service consumption_model to enforce that CONTINUOUS Services are referenced by
     Packages and ONE_SHOT Services by BillableEvents.

   - CVM / Reporting — read revenue_category for finance/analytics revenue stream separation.

 What this DD owns:

   1. The service_class and service tables.

   2. The Provisioner adapter interface declaration (5 methods).

   3. The rules governing addressability + consumption model + equipment requirement.

   4. CRUD APIs for admin-managed catalog entries.

   5. Kafka events on catalog changes (consumed by SIP-01 + downstream).

 What this DD does NOT own:

   - Package composition — owned by SIP-01.

   - Service pricing — pricing lives in BIL-CFG-01 (BillableEvents for ONE_SHOT) and SIP-01 Package Versions (for
     CONTINUOUS Package prices). PLM-CFG-01 carries default tax group and default wallet refs for revenue allocation, but
     never a price.

   - Provisioner adapter implementations — those are code beans in the fulfillment module, registered per
     provisioner_key. PLM-CFG-01 declares the interface contract; the beans live in code.

   - HomePass service_management_endpoints map — owned by RLM-CFG-01. PLM-CFG-01 only declares which
     keys Services consult.

   - Equipment binding to subscriptions — owned by OSR-INSTANCE-01 (the equipment inventory module). PLM-CFG-01
     declares the requirement; OSR-INSTANCE-01 tracks the binding.

 Adapters register a bean in the fulfillment module's Spring context with @ServiceProvisioner(key = "gpon-res") (or
 hfc-docsis, voip-sip, etc.). FUL-03 / FUL-04 / FUL-05 look up the bean by provisioner_key from the Service's

 3.4 Provisioner restrictions (FUL-04-only methods)
 FUL-04 (Restriction Fulfillment) requires two additional methods on the adapter: applyRestriction and
 liftRestriction. These are not on the ServiceProvisioner interface — they're on a separate
 RestrictionCapableProvisioner extension interface. Adapters that support restrictions (e.g., AAA-capable adapters)
 implement both; adapters that don't (e.g., partner-fulfilled OTT bundle adapters) implement only ServiceProvisioner.
          public interface RestrictionCapableProvisioner extends ServiceProvisioner {
            ProvisionerOutcome applyRestriction(String fulfillmentAction, String restrictionCode, Map<String,Object> params, Custome
            ProvisionerOutcome liftRestriction(String fulfillmentAction, String restrictionCode, Map<String,Object> params, Customer
          }

 FUL-04 checks the adapter implements RestrictionCapableProvisioner before invoking restriction methods; if not,
 returns RESTRICTION_NOT_SUPPORTED_BY_PROVISIONER for that Service.

                                                                FUL-05). A Service may be created with an unregistered provisioner_key
                                                                (e.g., pre-deployment); attempts to activate will fail at runtime with
                                                                UNKNOWN_PROVISIONER_KEY.

  R-PLM-CFG-01-PR-2                                             The 5-method ServiceProvisioner interface (§3.1) is the canonical
                                                                contract. All adapters MUST implement all 5 methods (may return
                                                                success=false, failureReason=NOT_SUPPORTED for methods they
                                                                cannot perform — e.g., a partner-fulfilled adapter may not support
                                                                modifyService).

  R-PLM-CFG-01-PR-3                                             The RestrictionCapableProvisioner interface (§3.4) is optional.
                                                                Adapters implement it only when they support restrictions.



 4.4 Equipment requirement
  Rule                                                          Description

  R-PLM-CFG-01-EQ-1                                             service_class.requires_equipment is the authoritative class-level flag.
                                                                Used by UPGRADE-01 / DOWNGRADE-01 / MIGRATION-01 when computing
                                                                equipment-delta between source and target Package compositions.

  R-PLM-CFG-01-EQ-2                                             Per-Service equipment_requirement_ref declares the SPECIFIC
                                                                equipment type. The class-level requires_equipment is a quick filter ("does
                                                                this class need ANY equipment?"); the Service-level ref tells the workflow which
                                                                equipment-type to look for in existing bindings or request from inventory.

  R-PLM-CFG-01-EQ-3                                             Multi-Service equipment retention: when
                                                                UPGRADE/DOWNGRADE/MIGRATION drops a class, the customer's existing
                                                                equipment is retained if it ALSO fulfills another retained class (e.g., ATA fulfilling
                                                                both VOIP and a future fax service; if VOIP class is dropped but fax class is
                                                                retained, ATA stays). The workflow checks equipment_requirement_ref
                                                                per class to determine multi-service overlap.
