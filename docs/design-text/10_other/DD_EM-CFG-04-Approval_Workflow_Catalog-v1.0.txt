 1. Purpose
 This DD defines the shared Approval Workflow Catalog for SOPHIX BSS.

 Many modules need human approval:

   - KYC L1/L2 approval;

   - invoice adjustments, write-offs, credit notes, reversals;

   - wallet manual adjustment;

   - tax invoice cancellation;

   - HomePass sensitive status transition;

   - franchise activation/retirement;

   - stock write-off and procurement approval;

   - discount/campaign approval;

   - dunning override or clear-without-payment;

   - future CVM, field audit, and service-assurance compensation decisions.

 EM-CFG-04 does not own those business objects. The owning module still owns the request, state, final apply/reject logic,
 and audit of its domain record.

 EM-CFG-04 owns the reusable catalog that tells a module:

   - whether approval is required;

   - which approval workflow applies;

   - which roles/permissions can approve;

   - how many steps are needed;

   - what thresholds and conditions apply;

   - how user tasks should be routed;

   - how approval outcome is reported back.

 4. Ownership Pattern
 EM-CFG-04 is a catalog and orchestration helper. It is not the owner of every approval request's business state.

 Standard pattern:

   1. Owning module receives a high-risk command.

   2. Owning module validates the business request and creates its own pending request record.

   3. Owning module calls EM-CFG-04 to evaluate approval policy.

   4. If no approval is required, owning module applies request immediately.

   5. If approval is required, EM-CFG-04 starts a configured approval process and creates approval tasks.

   6. Approvers act through Backoffice/API.

   7. EM-CFG-04 records decision audit and completes workflow step.

   8. On final approved/rejected/revision outcome, EM-CFG-04 calls the owning module callback or emits an event.

 5. Core Concepts
  Concept                                                            Meaning

  Approval subject                                                   The business object or request needing approval, for example adjustment
                                                                     request, KYC review, stock write-off.

  Approval policy                                                    Configuration that determines if approval is required and which process applies.

  Approval step                                                      One human decision point in the policy.

  Approver rule                                                      Role/permission/scope condition for who can act on a step.

  Threshold                                                          Numeric or categorical condition that changes routing.

  Segregation of duties                                              Rule preventing requester and approver from being the same person or team.

  Approval request                                                   Runtime instance of an approval process started for one business subject.

  Approval task                                                      Runtime user task assigned to eligible approver(s).

  Approval outcome                                                   APPROVED, REJECTED, REVISION_REQUESTED, CANCELLED, EXPIRED.

 10. Business Rules
  Rule                                                            Description

  APR-1                                                           Owning module must create and validate its pending business request before
                                                                  starting approval.

  APR-2                                                           EM-CFG-04 must not directly mutate owning module business records.

  APR-3                                                           Approval policy selection is by operator, module, action, status, effective date,
                                                                  and conditions.

  APR-4                                                           Active non-auto policy must have at least one step.

  APR-5                                                           Approver eligibility is checked through EM-CFG-03 permission and scope.

  APR-6                                                           If allow_requester = false, requester cannot approve their own task.

  APR-7                                                           Every approval action must create immutable approval_decision.




SOPHIX BSS Design Documents                                                                                                                 Page 8
  Rule                                                            Description

  APR-8                                                           Final outcome must be delivered to owning module through callback and/or
                                                                  event with retry.

  APR-9                                                           If callback fails, approval request remains in final approval state but callback log
                                                                  remains retryable until delivered or manually repaired.

  APR-10                                                          Retired policies remain readable for historical approval requests.

  APR-11                                                          Modules must support idempotent approval outcome callbacks.




 11. Camunda And Worker Model
 EM-CFG-04 can run simple single-step approvals without Camunda, but BPMN is recommended for:

   - multi-step approvals;

   - timer escalation;

   - request revision loops;

   - parallel approvals;

   - operator-specific routing.

 Reference BPMN service tasks:

  Task/topic                                                      Purpose

  approval-load-request                                           Load approval request context.

  approval-create-task                                            Create EM-CFG-04 task row and ICN notification.

  approval-wait-user-action                                       Human user task.

  approval-complete-step                                          Record step completion.

  approval-deliver-outcome                                        Call owning module callback or emit final outcome event.

  approval-expire-task                                            Mark timed-out task expired and escalate/reject per policy.


 Worker names are logical topics. One worker deployment can handle multiple topics if metrics remain visible per topic.

  Reject step                                                          Final rejected outcome delivered to owning module.

  Request revision                                                     Revision outcome delivered, request no longer open.

  Callback failure                                                     Callback log retryable; approval state preserved.

  Duplicate approval request idempotency key                           Same response, no duplicate request.

  Retired policy remains readable for historical request               Historical detail still works.
