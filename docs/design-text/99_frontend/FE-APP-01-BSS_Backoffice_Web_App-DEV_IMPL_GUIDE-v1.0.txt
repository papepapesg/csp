 DEV_IMPL_GUIDE - FE-APP-01 BSS Backoffice Web App
 1. Implementation Objective
 Implement the internal Backoffice web app as the main operational surface for customer care, subscription operations, billing
 operations, fulfillment monitoring, work orders, stock/equipment, ticketing, reporting links, and platform operations.

   5. DD_API-00-API_Catalog_and_Gateway_Standards-v1.0.md


 3. Build Order
   1. Implement shell, menu, auth guard, and role visibility.

   2. Implement customer search and Customer 360 header.

   3. Implement Customer 360 core panels: identity, active subscriptions, balance/debt summary, open tickets, recent timeline.

   4. Add lazy-loaded panels: invoices, wallet, dunning, work orders, equipment, notifications, audit.

   5. Implement ticket creation and ticket detail using TCK/ASR rules.

   6. Implement subscription operation actions only when owning module APIs exist.

   7. Implement order/fulfillment monitoring after FUL-02 APIs are ready.

   8. Implement billing and stock operational screens in their owning module areas.

   9. Add platform operations screens through approved admin proxies only.


 4. Customer 360 Performance Rule
 Customer 360 must not block on every module at once.

   - Initial load: identity, active subscriptions, balance/debt, open tickets, recent timeline.

   - Other panels lazy-load on tab open.

   - Each panel has independent loading, stale, error, and retry state.

   - Use a Backoffice BFF/read aggregator only for reads if direct gateway fan-out becomes slow.

   - The BFF must not own business state or execute writes across modules.


 5. Tests
   - Customer 360 partial failure.

   - Role-based menu/action visibility.

   - Idempotency header on commands.

   - Ticket creation from Customer 360.

   - Subscription command accepted and operation status shown.

   - Panel lazy loading and retry.

 Load order:

   1. Route enters with customer_id.

   2. Load ILM customer header and account list.

   3. Select default account from ILM if the customer has one account; otherwise ask the agent to choose an account.

   4. Load core panels for the selected account_id.

   5. Lazy-load heavy panels only when opened.

 Do not query billing, work order, or equipment by customer_id when an account_id is available. Customer-level search
 can find the customer; operational panels must be account-scoped.

 8. Command Flow Example - Pause Subscription
   1. Agent opens Customer 360 and selects the correct account.

   2. UI loads subscriptions for account_id.

   3. Agent clicks pause on subscription_id.

   4. UI displays reason/date form using config from the pause DD where exposed.

   5. UI submits:
          POST /api/subscriptions/{subscription_id}/pause
          Idempotency-Key: bo-pause:{subscription_id}:{formAttemptId}
          Content-Type: application/json

          {
              "reasonCode": "CUSTOMER_REQUEST",
              "requestedPauseDate": "2026-06-10",
              "notes": "Customer travelling for two months"
          }

   6. UI receives operation id/status from SUB-WF.

   7. UI shows operation status and polls or subscribes to operation status updates.

   8. UI does not manually mutate subscription status; SUB-LM state refresh confirms the result.


 9. Backoffice BFF Rule
 A Backoffice BFF/read aggregator is allowed only for read composition such as Customer 360. It may cache short-lived
 projections and normalize panel payloads. It must not own business state, execute multi-module writes, or hide which module
 owns each command.
