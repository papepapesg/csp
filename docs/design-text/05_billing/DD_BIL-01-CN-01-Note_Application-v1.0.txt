 Glossary
  Term                                                           Meaning

  Credit note                                                    A document issued by BIL-02-ADJ-01 / GEN-01 that reduces what the customer
                                                                 owes. Source events: dispute resolved in customer's favor, billing error
                                                                 correction, SLA compensation, goodwill credit.

  Debit note                                                     A document issued by BIL-02-ADJ-01 / GEN-01 that increases what the
                                                                 customer owes. Source events: under-billing correction, late fees added to a
                                                                 paid invoice, recovery from a previously-issued over-credit.

  Note application                                               The act of applying a credit or debit note to a customer's balance. For
                                                                 POSTPAID: reduces or increases invoice.outstanding_amount (the
                                                                 actual status change is owned by STA-01). For PREPAID: credits or debits the
                                                                 wallet via BIL-05.

  Target invoice                                                 When a note is scoped to a specific invoice (typical for line-level corrections,
                                                                 billing errors, late-fee additions). The note event payload from GEN-01 includes
                                                                 target_invoice_id in this case.

  Auto-allocation                                                When a credit note has no specific target invoice (e.g., a goodwill credit not tied
                                                                 to one specific invoice), CN-01 applies it across the customer's open invoices
                                                                 using the same allocation policy as PAY-01.

  Surplus                                                        When a credit note's amount exceeds the target invoice's outstanding (or the
                                                                 account's total outstanding for auto-allocated credits), the remaining amount
                                                                 goes to account_credit_balance per the operator's overpayment policy
                                                                 (reused from PAY-01's pay_01_config).

  Failed application                                             A debit note against a PREPAID wallet that doesn't have sufficient balance.
                                                                 CN-01 cannot make a wallet negative; the application is logged with status =
                                                                 FAILED, an event is emitted, and admin must reconcile manually.




 A — Target
 1. What this process is about
 When BIL-02-ADJ-01 approves an adjustment, BIL-02-GEN-01 issues the corresponding credit note or debit note (this is
 BIL-02 family business). At the moment of issuance, GEN-01 emits a Kafka event (CreditNoteIssued or
 DebitNoteIssued) carrying the note's identity, target, amount, and reason. CN-01 consumes that event and applies the

SOPHIX BSS Design Documents                                                                                                                 Page 3
 note — meaning it actually moves the money:

   - POSTPAID credit note: reduces invoice.outstanding_amount. If the credit exceeds outstanding, surplus goes to
     account_credit_balance (managed by PAY-01).

   - POSTPAID debit note: increases invoice.outstanding_amount. May take a previously-PAID invoice back to
     PENDING/OVERDUE.

   - PREPAID credit note: calls POST /api/wallets/credit on BIL-05. Customer's wallet balance grows.

   - PREPAID debit note: calls POST /api/wallets/debit on BIL-05. If insufficient balance, the application fails and
     admin must reconcile.

 The application is recorded in note_application_ledger. An event (CreditNoteApplied / DebitNoteApplied) is
 then emitted, which STA-01 consumes to transition invoice status (credit note clearing outstanding → PAID; debit note adding
 outstanding → PENDING/OVERDUE depending on due date).

 #### What CN-01 explicitly does not own

   - Adjustment workflow (proposal → approval) — owned by BIL-02-ADJ-01

   - Note generation / issuance — owned by BIL-02-GEN-01. The credit note / debit note document and its note_id are
     issued by GEN-01 BEFORE CN-01 sees the event.

   - Charging (outbound) — owned by BIL-01 Core

   - Payment receipt — owned by BIL-01-PAY-01

   - Invoice status transitions — owned by BIL-02-STA-01

   - Wallet balance / top-up — owned by BIL-05

   - account_credit_balance table — owned by BIL-01-PAY-01. CN-01 calls into PAY-01's CreditBalanceService
     when credit note surplus needs to be held as account balance.

   - Refund to gateway — out of scope for CN-01. If an operator wants to actually return money to the customer's payment
     method, that's a separate refund flow handled by the gateway adapter, not CN-01's application logic.

 B — Current TZ
 Workshop materials do not describe a structured credit / debit note application service in TZ Sophix. Adjustments are likely
 handled by direct DB updates against invoice tables or wallet logs with no centralized ledger or event emission.



 C — Gap & bridge
 CN-01 is new functionality. It introduces:

   - Event-driven application of credit / debit notes from ADJ-01 / GEN-01

   - Configurable surplus handling (reuses PAY-01's overpayment policy for credit note surplus)

   - Per-target audit in note_application_ledger with split rows for surplus

   - Formalized event contracts (CreditNoteApplied, DebitNoteApplied, DebitNoteApplicationFailed,
     NoteApplicationFailed) consumed by STA-01, BIL-04, NOT-01, analytics

   - Safe handling of PREPAID debit notes against insufficient wallets (no negative balances)
