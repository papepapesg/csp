 1. What this module is
 The four OSR-RMA-01 satellites all need the same plumbing: a swap-request root entity that tracks who/what/when, an
 append-only history of every state change, a set of Camunda service-task workers that operate on equipment_instance
 rows (per OSR-INSTANCE-01), a shared FOUNDATION_AUTH group set for dispatch / approval / vendor handoff, and a
 uniform way to fire Kafka events for downstream consumers. This DD is that shared layer.

 The four flows are technology- and trigger-divergent but share 80% of the orchestration mechanics:

 What they all share:

   1. A swap-request created in a DRAFT state.

   2. Eligibility checks (warranty status, subscription state, customer billing status, slot/port availability).

   3. Slot reservation against EM-02 contractor availability.

   4. Source-instance lookup (the old device — for SWAP/EQP) and target-instance reservation (the new device — for
     SWAP/EQU).

   5. Camunda BPMN that orchestrates field visit OR remote action OR mixed.

   6. Lifecycle event recording on each equipment_instance involved (via OSR-INSTANCE-01 API).

   7. Contractor-stock routing on recovered unit (THE Wananchi 40+ stale-equipment fix).

   8. Cross-system provisioning calls: serial unbind/rebind in Broadhub for HFC; ONT remote unassign in NMS for GPON;
     subscription state update; billing trigger.

   9. Customer + internal notifications.

   10. Completion or failure recording in the history ledger; final state on the swap-request row.

 The four satellites differ in: the BPMN process definition (different sequence of user tasks vs service tasks vs message
 catches), the eligibility rules, the provisioning calls (HFC = Broadhub double-config with slot/port preservation; GPON = NMS
 remote unassign with no slot/port preservation), and the customer-facing message templates.

 What this module owns
   1. equipment_swap_request — the workflow root entity. One row per swap request. Carries discriminator swap_kind to
     indicate which flow it belongs to.

   2. equipment_swap_request_history — append-only ledger of every state change on a swap-request.

     v1.0 captures the handoff but no SLA tracking, no return-batch matching.

   4. Shared Camunda workers (operator-agnostic Java beans, registered with the Camunda engine per
     FOUNDATION_CAMUNDA): instance-lookup, instance-state-transition, eligibility-check,
     contractor-slot-reserve, contractor-slot-release, contractor-stock-route,

 What this module does NOT do
   - Doesn't define per-flow BPMN. SWAP_HFC.bpmn, SWAP_GPON.bpmn, EQP.bpmn, EQU.bpmn live in the respective
     satellites. This DD only catalogs the workers + messages + user tasks they reuse.

   - Doesn't define per-flow REST endpoints. Each satellite owns its POST /api/swap-requests/... shape with its
     own discriminator fields. The framework only declares the base equipment_swap_request schema; satellites extend
     via the JSONB flow_payload column.

   - Doesn't own equipment_instance. Owned by OSR-INSTANCE-01. This DD's workers call OSR-INSTANCE-01 APIs.

   - Doesn't own stock movements. Owned by OSR-01. When a swap recovers a unit and routes it back to a contractor van,
     the framework's contractor-stock-route worker calls OSR-01 POST /api/stock-movements AND
     OSR-INSTANCE-01 POST /api/equipment-instances/{id}/lifecycle-events in the same business
     transaction.

   - Doesn't perform vendor-side RMA workflows. Outbound shipment to vendor, vendor repair SLA tracking, return-batch
     matching — all deferred. The stub captures the handoff timestamp + reference; that's all v1.0 provides.

   - Doesn't define charging rules. Whether a swap is free (warranty / system fault) vs charged (customer-caused damage)
     is decided by BIL-01 charge codes referenced from the eligibility-check worker; not by this framework.

   - Doesn't decide tech-region routing. The contractor for a given customer's swap is decided by reading
     account.tech_region_id (ILM-CFG-01) and looking up contractor_region_scope (EM-02). The framework
     calls EM-02's assign-contractor Drools rule; it does not redefine that logic.

 Regional flexibility
 KE is the v1.0 seed; schema designed for WUG/WTZ/YASSN variants:

   - Different tech mixes per operator. WIK has both HFC + GPON; WUG/WTZ/YASSN may have GPON-only. Schema's
     swap_kind is operator-agnostic; satellites are deployed selectively per operator.

   - Different Broadhub / NMS versions. WIK uses Broadhub with Clearcable NOMS for static-IP HFC; other operators have
     different OSS topologies. Workers like serial-unbind-broadhub-stub are STUBs in v1.0 — they call into an
     abstraction layer (provisioning-adapter) per operator that's configured by ops, not hardcoded into the worker.

   - Different vendor RMA SLAs. WIK uses Huawei + FiberHome (different SLA windows from Free Sénégal's vendors for
     YASSN). The vendor_rma_stub row carries vendor name + reference; per-vendor SLA is out of v1.0 scope.

   - OSR-INSTANCE-01 Equipment Instance Registry — the framework's workers (instance-lookup,
     instance-state-transition, contractor-stock-route) operate on equipment_instance rows by calling
     OSR-INSTANCE-01 APIs. Every swap step that changes an instance's state emits one
     EquipmentInstanceLifecycleTransition event via OSR-INSTANCE-01.

     contractor-stock-route calls OSR-01 POST /api/stock-movements (for the SKU+qty rollup) AND
     OSR-INSTANCE-01 POST /api/equipment-instances/{id}/lifecycle-events (for the per-serial detail) in the
     same transaction.

   - EM-02 Contractor & Staff Registry — the framework calls EM-02's POST /api/contractor-availability (to find
     eligible contractor) and POST /api/contractor-slot-commitments (to reserve a slot). Slot release on
     swap-request cancellation calls EM-02's PATCH /api/contractor-slot-commitments/{id} with
     status=RELEASED.

   - WO-01 Work Order Module — flows that require a field visit (SWAP-HFC, SWAP-GPON field-fallback, EQP, EQU) create
     a WO via POST /api/work-orders with wo_kind=EQUIPMENT_SWAP / EQUIPMENT_PICKUP /
     EQUIPMENT_UPGRADE. The WO carries swap_request_id in its origin_ref. WO finalization fires a message event back
     into the swap-request BPMN.

   - ILM-CFG-01 Customer Service Catalog — the framework reads account.account_id, account.tech_region_id,
      account.payment_account_number, subscription.subscription_id to identify the customer + drive
      tech-region-based contractor selection. Account is the binding anchor (Customer is identity-only).

   - PLM-CFG-06 Equipment Type Catalog — the framework validates that the source and target instances reference SKUs
     of compatible equipment_kind (e.g., source ONT can be replaced by target ONT but not by target STB). Eligibility
     worker reads PLM-CFG-06.

   - BIL-01 Charging Engine — eligibility-check worker calls BIL-01 to (a) check the customer's billing state (suspended? in
     dunning?), (b) determine if the swap is chargeable (warranty status + reason code → charge code mapping), (c) trigger
     the charge on completion if applicable.

   - NOT-01 Customer Notifications — flows send customer-facing notifications (swap appointment confirmation, technician
     en route, completion confirmation, EQR equipment-return-required reminder) via NOT-01.

   - ICN-01 Internal Communications — flows fan out notifications to internal candidate groups: swap dispatchers, field
      techs, NOC team, vendor RMA coordinators, finance warranty approvers.

 Notes:

   - AWAITING_PAYMENT is the pay-first gate for chargeable swaps (workshop 2026-04-28 wallet funding gate). Free
     swaps (under warranty, system fault, operator-paid like Shifting) skip this state and go ELIGIBILITY_CHECK →
     AWAITING_SLOT directly. Chargeable swaps go ELIGIBILITY_CHECK → AWAITING_PAYMENT → AWAITING_SLOT
     only after BIL-01 confirms payment. No slot is reserved before payment is confirmed; no contractor is dispatched; no truck
     rolls. Payment timeout (default 7 days) cancels the swap-request.

   - REMOTE_UNASSIGN_IN_PROGRESS is reached only by GPON_REMOTE (no field visit). Successful remote unassign +
     customer self-swap path: REMOTE_UNASSIGN_IN_PROGRESS → SOURCE_RECOVERED →
     PROVISIONING_IN_PROGRESS (remote-bind-new) → COMPLETED. Failed remote path falls back to creating a
     WO; transition is REMOTE_UNASSIGN_IN_PROGRESS → SLOT_RESERVED → WO_CREATED →
     FIELD_VISIT_IN_PROGRESS → .... Or, alternative: REMOTE_UNASSIGN_IN_PROGRESS → FAILED if no field
     fallback is configured for that operator.

   - EQP flow skips TARGET_PLACED (no replacement device): SOURCE_RECOVERED → PROVISIONING_IN_PROGRESS
     (subscription closure, BIL-01 deposit refund) → COMPLETED.

   - EQR sub-state (customer refuses return): FIELD_VISIT_IN_PROGRESS → COMPLETED_WITHOUT_RECOVERY directly.
     The source instance stays in IN_FIELD_DEFECTIVE or transitions to DECOMMISSIONED per BIL-01 forfeiture path.

   - SLOT_RESERVED → AWAITING_SLOT is the slot-release path: when a swap is rescheduled, the original slot is released
     and a new slot is requested.

   - HomePass network_path update is a side effect of TARGET_PLACED for GPON swaps only. See R-OSR-RMA-16.
     The homepass-network-path-update worker runs synchronously on the transition; its failure aborts the swap to
     FAILED.

  R-OSR-RMA-1                 Exactly one open swap-request per (account_id, source_instance_id) —

  R-OSR-RMA-4                 recovery_contractor_id MUST be set before current_state advances
                              past AWAITING_SLOT. Same row, same transaction, atomic with
                              slot_commitment_id.

                              free the contractor's capacity. Idempotent — if the slot is already past or already
                              released, the call is a no-op.

                              FIELD_VISIT_IN_PROGRESS → COMPLETED_WITHOUT_RECOVERY. The
                              source instance is NOT transitioned to RECOVERED_BY_CONTRACTOR; it stays
                              in IN_FIELD_DEFECTIVE (or transitions to DECOMMISSIONED once BIL-01
                              writes off the deposit).

                                                                When the eligibility worker determines the swap is chargeable (warranty void /
                                                                customer-caused damage / EQU upgrade fee / EQR forfeiture pre-charge), it

                                                                customer_charge_amount, calls BIL-01 POST /api/billable-events to

                                                                swap-request to AWAITING_PAYMENT. The bil01-charge-pre-authorize
                                                                worker drives this. The swap-request does NOT advance past
                                                                AWAITING_PAYMENT until BIL-01 confirms the customer wallet covers the
                                                                charge — confirmation arrives via the payment-confirmed Kafka message
                                                                catch on the BPMN. Until then, no slot is reserved, no contractor is dispatched,
                                                                no truck rolls. This codifies workshop 2026-04-28 rule "tech is dispatched only
                                                                after the customer wallet is topped up". Free swaps (under warranty / system
                                                                fault / Shifting-style operator-paid) set chargeable=FALSE and skip
                                                                AWAITING_PAYMENT entirely.

  R-OSR-RMA-11b                                                 Payment timeout: if AWAITING_PAYMENT exceeds the operator-configured
                                                                timeout (default 7 days), the swap-request transitions to CANCELLED with

                                                                swap_kind=GPON_REMOTE or GPON_FIELD and the source instance is bound

           package com.sophix.osr.rma.rules;

           import com.sophix.osr.rma.facts.SwapEligibilityRequest;
           import com.sophix.osr.rma.facts.RoutingDecisionRequest;

           rule "swap-eligibility-account-must-be-active"
           when
             $req: SwapEligibilityRequest($req.accountStatus != "ACTIVE" && $req.swapKind != "EQP_TERMINATION")
           then
             $req.setEligible(false);
             $req.setFailureCode("ACCOUNT_NOT_ACTIVE");
           end

           rule "swap-eligibility-source-instance-must-be-in-field"
           when
             $req: SwapEligibilityRequest($req.sourceInstanceCurrentState not in ("IN_FIELD_ACTIVE","IN_FIELD_DEFECTIVE"))
           then
             $req.setEligible(false);
             $req.setFailureCode("SOURCE_INSTANCE_NOT_IN_FIELD");
           end

           rule "swap-eligibility-hfc-target-must-match-equipment-kind"
           when
             $req: SwapEligibilityRequest($req.swapKind == "HFC_FIELD" && $req.sourceEquipmentKind != $req.targetEquipmentKind)
           then
             $req.setEligible(false);
             $req.setFailureCode("EQUIPMENT_KIND_MISMATCH");
           end

           rule "routing-decision-recovered-instance-routes-to-recovering-contractor"
           when
             $req: RoutingDecisionRequest($req.transitionReason == "CONTRACTOR_RECOVERED_FROM_FIELD")
           then
             $req.setTargetLocationKind("CONTRACTOR_VAN");
             $req.setTargetContractorId($req.recoveryContractorId);
           end

           rule "routing-decision-main-warehouse-fallback"
           when
             $req: RoutingDecisionRequest($req.transitionReason == "CONTRACTOR_RECOVERED_FROM_FIELD" && $req.recoveryContractorId ==
           then
             $req.setTargetLocationKind("MAIN_WAREHOUSE");
             $req.setWarning("RECOVERY_CONTRACTOR_MISSING_FALLBACK_MAIN");
           end

 The "routing-decision-recovered-instance-routes-to-recovering-contractor" rule is the formal codification of the Wananchi 40+

 8. Workshop sources
 Workshop sources for v1.0 (KE Zuku 2026-04-27+; no fabricated TZ baselines — TBD pending cartography):

   - BP-08 Equipment Swap (RMA) GAP analysis — technology-divergent swap mechanics (HFC = field pickup, GPON =
     remote unassign + new bind), device authorization slot/port mandatory (UC-PR4), serial unbind/rebind (UC-PR9),
     contractor-stock traceability gap (default routes to main warehouse — broken; documented as 40+ stale items). G-08-1
     (workflow) + G-08-2 (contractor stock traceability) — both addressed by this framework + satellites.

   - Workshop 2026-04-30 (Provisioning deep dive) — HFC modem authorization bound to slot/port (UC-PR4 KE-specific);
     static-IP HFC double config (Broadhub + Clearcable NOMS); static-IP GPON manual via DHCP console; voice MTA/IAD
     ports.

   - Workshop 2026-04-30 (Customer Management deep dive) — Equipment-routing gap: unassigned equipment
     auto-returns to main warehouse instead of recovering contractor team's warehouse (~40+ stale items). Wananchi target:
     SOPHIX must trace contractor team that recovered + route there. THIS FRAMEWORK'S recovery_contractor_id
     on equipment_swap_request + the
     routing-decision-recovered-instance-routes-to-recovering-contractor Drools rule + the
     contractor-stock-route worker collectively close this gap.

   - Workshop 2026-04-29 (Work Order & Field Operations deep dive) — WO Job Types EQU (Equipment Upgrade), EQP
     (Equipment Pickup), EQR (Equipment Recovery — closes EQP when customer paid for CPE & refuses return). These
     map to the four satellites' BPMN kinds.

   - Workshop 2026-04-30 (Service Termination) — Equipment dismantle is a separate retrieval WO if customer doesn't
     bring CPE back. Agent contractor dispatched. Refund processed via Invoice Adjustments (BIL-01 + PLM-CFG-05
     adjustment codes). Drives EQP satellite + EQR sub-state.

 TZ codebase coverage today: to be filled in after codebase review. No equivalent of multi-state swap-request workflow has
 been confirmed in the TZ codebase yet; assessment pending cartography.

 Gap & V3 design rationale: The OSR-RMA-01 family introduces an explicit Camunda-orchestrated swap workflow (replacing
 ad-hoc ticket-revamp + on-site action flow) with per-tech BPMN variants, formal slot/port preservation for HFC, formal
 contractor-stock-routing for recovered units (closing the documented 40+ stale-equipment gap), and an outbound-RMA stub
 for future expansion.
