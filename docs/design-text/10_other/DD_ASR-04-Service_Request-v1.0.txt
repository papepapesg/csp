 APIs where needed. It is not a separate request engine, database, or deployment in the first release.



 1. Purpose
 ASR-04 defines how SOPHIX handles customer service requests.

 A service request is a customer-initiated operational action that is not primarily a fault, complaint, or neutral information
 question. The customer is asking SOPHIX to do something.

 Examples:

   - reset customer service credentials or SIP profile;

   - request package upgrade/downgrade;

   - request relocation/address change;

   - request equipment swap;

   - request contact detail correction;

   - request installation appointment change;

   - request ownership/contact-person update;

   - request cancellation of an open non-critical request;

   - request account document/reference re-send;

   - request bucket/benefit transfer when the operator supports it.

 This DD does not create a new ticketing engine and does not replace owning workflows. Service requests are implemented
 as configured TCK tickets with ASR-specific request capture, validation, approval, dispatch, and completion tracking. The
 owning module still executes the business action.

 Rule: ASR-04 owns request intake and tracking. It must call the owning workflow/module to execute the requested action and
 store the returned external reference. It must not bypass those modules with direct table updates.

 Approval rule: ASR-04 does not define approval steps locally. If a service request category requires approval, ASR-04 calls
 EM-CFG-04 to evaluate and run the configured approval policy. EM-CFG-04 may execute the approval as auto-approval,
 single-step DB-driven approval, multi-step approval, or Camunda BPMN depending on operator policy.

 7.2 Create Structured ASR Request
          POST /api/asr/service-requests
          Content-Type: application/json

          {
              "ticketId": "tck-20260605-000014",
              "operatorCode": "WIK",
              "categoryCode": "PACKAGE_UPGRADE_REQUEST",
              "requestPayload": {
                "subscriptionId": "SUB-700045",
                "targetPackageRef": "pkg-fiber-200m",
                "requestedEffectiveDate": "2026-06-06",
                "customerConfirmedPrice": true
              }
          }

 This API validates config, required fields, self-care permission, and basic eligibility.

 7.3 Get Request Guidance
          GET /api/asr/service-requests/{ticket_id}/guidance

 Response:
          {
              "ticketId": "tck-20260605-000014",
              "categoryCode": "PACKAGE_UPGRADE_REQUEST",
              "owningModule": "SUB-WF-UPGRADE-01",
              "requiredFields": ["subscriptionId", "targetPackageRef", "requestedEffectiveDate"],
              "approvalPolicyCode": "NONE",
              "selfcareAllowed": true,
              "waitForExternalCompletion": true,
              "allowedActions": ["VALIDATE", "DISPATCH", "CANCEL"]
          }


 7.4 Validate Request
          POST /api/asr/service-requests/{service_request_id}/validate

 Validation calls the owning module's preview/eligibility APIs where available. For package upgrade, call SUB/SIP eligibility.
 For equipment swap, call OSR/WO eligibility. For appointment change, call WO availability.

 7.5 Approve Request
 Normal approver action happens through EM-CFG-04 task APIs:
          POST /api/approvals/tasks/{approval_task_id}/approve
          Content-Type: application/json

          {
              "decisionComment": "Customer confirmed price and relocation fee."
          }

 When EM-CFG-04 finalizes the approval request, it calls ASR-04:
          POST /internal/asr/service-requests/{service_request_id}/approval-outcome
          Content-Type: application/json

          {
              "approvalRequestId": "apr-sr-001",
              "outcome": "APPROVED",
              "decisionComment": "Customer confirmed price and relocation fee."
          }

 ASR-04 then marks asr_service_request_approval.status = APPROVED and permits dispatch. If the outcome is
 REJECTED, ASR-04 marks the service request REJECTED and does not dispatch.

 7.6 Dispatch Request
          POST /api/asr/service-requests/{service_request_id}/dispatch
          Idempotency-Key: asr-sr-001-dispatch-v1

 For package upgrade, ASR calls:
          POST /api/subscriptions/SUB-700045/upgrade-requests
          Idempotency-Key: asr-sr-001-dispatch-v1
          Content-Type: application/json

          {
              "source": "ASR-04",
              "sourceTicketId": "tck-20260605-000014",
              "targetPackageRef": "pkg-fiber-200m",
              "requestedEffectiveDate": "2026-06-06",
              "customerConfirmedPrice": true
          }

 ASR stores the returned operation id in asr_service_request_dispatch.owning_ref_id.

 7.7 Receive Or Sync Result
 Owning modules may publish result events or expose status APIs. ASR supports both.
          POST /api/asr/service-requests/results
          Content-Type: application/json

          {
              "owningModule": "SUB-WF-UPGRADE-01",
              "owningRefId": "subop-20260605-000019",
              "resultStatus": "COMPLETED",
              "resultCode": "UPGRADE_COMPLETED",
              "customerMessage": "Your package upgrade to Fiber 200M has been completed.",
              "resultPayload": {
                "subscriptionId": "SUB-700045",
                "newPackageRef": "pkg-fiber-200m"
              }
          }


 7.8 Resolve Ticket
 After successful result, ASR adds a customer-visible TCK comment and resolves the ticket using TCK:
          POST /api/tickets/{ticket_id}/resolve
          Content-Type: application/json

          {
              "resolutionCode": "SERVICE_REQUEST_COMPLETED",
              "resolutionSummary": "Package upgrade request completed by SUB-WF-UPGRADE-01."
          }

 10. Rule Engine Guidance
 Not every ASR-04 rule needs Drools. Fixed structural checks should remain normal application validation:

   - required field exists;

   - ticket/category exists;

   - self-care allowed flag;

   - external operation is open/closed.

 Use Drools when the decision is operator-variable, combines multiple facts, or changes often without code deployment.
 Recommended ASR-04 Drools rule sets:

  Rule file                                                                Purpose

  asr-service-request-eligibility.drl                                      Decide whether the request is eligible from category, customer/subscription
                                                                           state, requester role, channel, and request payload.

  asr-service-request-approval.drl                                         Decide whether ASR-04 should call EM-CFG-04 and which
                                                                           approval_policy_code to request.

  asr-service-request-dispatch.drl                                         Decide whether dispatch is allowed now or must wait for approval/customer
                                                                           confirmation.


 Example Drools fact:
              ServiceRequestFact {
                operatorCode = "WIK",
                categoryCode = "EQUIPMENT_SWAP_REQUEST",
                sourceChannel = "BACKOFFICE",
                requesterRole = "CARE_AGENT",
                subscriptionStatus = "ACTIVE",
                swapReasonCode = "CUSTOMER_REQUEST",
                customerConfirmedFee = false
              }

 Example rule:
              rule "Equipment swap requires technical approval when fee not confirmed"
              when
                $r : ServiceRequestFact(
                   categoryCode == "EQUIPMENT_SWAP_REQUEST",
                   customerConfirmedFee == false
                )

 11. Frontend Usage
 11.1 FE-APP-01 Backoffice
 Backoffice must support:

   - create service request from customer 360, subscription, invoice, WO, and ticket screens;

   - show request guidance and required fields from ASR API;

   - show eligibility preview from owning module;

   - request approval when required;

   - dispatch request;

   - display external operation status/reference;

   - show final customer-safe result;

   - resolve through TCK.

 11.2 FE-APP-04 Customer Self-Care
 Self-care must support only enabled request categories. It should show:

   - eligible request types for the logged-in customer/subscription;

   - required fields and confirmation checkboxes;

   - submitted request status;

   - final result or rejection reason.

 Self-care must not show internal dispatch errors, stack traces, supervisor notes, or raw workflow variables.



 12. Infra Recommendation
 ASR-04 should run inside the TCK service/module for a medium budget deployment. No separate ASR service-request pod is
 required initially.

  Component                                                            Recommendation

  API                                                                  Existing TCK API pods expose /api/asr/service-requests/....

  DB                                                                   Existing TCK schema/database with ASR service request tables.

  Workers                                                              Existing TCK worker pool handles dispatch retry, result sync, SLA scan.

  Events                                                               Existing Kafka/MSK topics.

  Cache                                                                Optional cache for request type config only.


 AWS deployment follows TCK deployment: same ECS/EKS service, RDS schema, MSK/Kafka cluster, CloudWatch
 logs/metrics, and IAM policies. Add alarms for dispatch failures, stuck approvals, open requests past SLA, and repeated
 downstream rejection by category.

 14. Definition Of Done
   - Service request categories are seeded in TCK.

   - ASR service request config exists per operator/category.

   - APIs support guidance, create, validate, approval, dispatch, result sync, and closure validation.

   - EM-CFG-04 is used for configurable approval policies; ASR-04 does not hardcode approver steps.

   - Drools rule files exist for configurable eligibility/approval/dispatch decisions where operator policy requires them.

   - Dispatch uses owning module APIs with idempotency.

   - Backoffice can process service requests end to end.

   - Self-care can submit only allowed request types.

   - Events are emitted for reporting and timeline.

   - Tests cover package, relocation, equipment, appointment, and failed dispatch paths.
