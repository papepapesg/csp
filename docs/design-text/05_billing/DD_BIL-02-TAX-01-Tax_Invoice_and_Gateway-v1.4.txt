 1. What this process is about
 In most jurisdictions where these operators run, the tax authority requires that for every payment received from a customer,
 the operator must produce a separate legal document called a tax invoice that proves tax (VAT, excise, etc.) was declared
 on the payment. The customer's payment is tax-inclusive: a portion of every payment they make is tax that the operator
 collects and remits to the authority. The tax invoice is how the operator declares that collected tax.

 This is distinct from the regular cycle invoice — the cycle invoice tells the customer "you owe X for cycle Y"; the tax invoice
 tells the authority "we received payment of Z, of which T is tax."

 The tax invoice carries a signed reference number issued by the tax authority's electronic invoicing platform where one
 exists. To get this reference, the operator submits the tax invoice payload to the authority's API; the authority validates, signs,
 and returns a unique reference plus QR code data. The customer's tax invoice PDF displays the signed reference and QR
 code so anyone can verify it with the authority.

 TAX-01 is built to support both deployment types: operator countries that require electronic tax invoice signing, and operator
 countries that do not. Where signing is required, the per-operator signer integrates with the local authority's platform. Where it
 is not, the operator simply disables tax invoice generation.

 Tax invoice is triggered by every customer payment. Tax is collected at the moment money moves from customer to
 operator, regardless of what that payment is for (cycle invoice, wallet topup, direct per-cycle pay) and regardless of billing
 mode. Three payment moments fire three different events that TAX-01 consumes:

   - Regular cycle invoices and one-off invoices — BIL-02-GEN-01 Invoice Generation

 Tax invoice end-to-end flow
 The canonical happy path from customer payment to signed tax invoice. Three flows depending on payment source:
 POSTPAID payment-applied, PREPAID wallet topup, PREPAID direct-pay. After generation, the signing flow is the same for
 all three.

 #### Flow A — POSTPAID payment applied (full or partial)
          Step 1 — Payment event arrives
            Customer pays a cycle/one-off invoice via M-Pesa, bank, card, cash, etc.
            BIL-01 Charging Engine records the payment, applies it to the invoice, and emits:
            sophix.billing.payment.applied with:
            { subscription_id, invoice_id, payment_id, paid_amount, payment_method,
              payment_timestamp, operator_code, currency }

          Step 2 — TAX-01 consumes the event (R-TAX-01-T-1)
            PaymentAppliedConsumer:
              - Validates event payload
              - Looks up invoice_type_operator_config for (operator_code, TAX_INVOICE); if disabled → ack and stop
              - Loads the parent invoice row to get its line items, totals, grouping context
              - Builds InvoiceGenerationContext and calls InvoiceGenerationService.generate(ctx)

          Step 3 — TaxInvoiceGenerator runs (R-TAX-01-G-*)
            - Idempotency check on triggering_event_ref (the PaymentApplied event ID)
            - Capture fresh customer_snapshot via CustomerSnapshotService
            - Compute payment ratio = paid_amount / parent_invoice.total_amount
            - For each parent invoice line item, build a corresponding tax invoice line:
                same service_category_code, package_ref, wallet_type_code, description
                subtotal = parent.subtotal × payment_ratio
                tax_breakdown = scale each component proportionally (parent.tax_breakdown × payment_ratio)
                total = parent.total × payment_ratio
            - Aggregate per-line tax breakdowns into invoice-level tax_summary
            - Build invoice header:
                billing_mode = POSTPAID (copied from parent invoice)
                customer_snapshot = fresh
                triggering_event_ref = PaymentApplied event ID
                original_invoice_id = parent invoice ID
                grouping_config_ref = parent's grouping_config_ref (preserved)
                grouping_dimension, grouping_key_values = copied from parent
                due_date = NULL
                status = GENERATED, payment_status = PAID
            - Allocate TAX_INVOICE sequence number atomically
            - Write invoice + line items + outbox event (TaxInvoiceIssued with full payload)
            Result: tax invoice row in status GENERATED, ready for signing.

             Note: a subsequent partial payment against the same parent invoice produces a SECOND tax invoice
             with its own triggering_event_ref (different payment_id). Customer ends up with two tax invoices
             for the parent invoice, each declaring the tax on its own paid portion.

          Step 4-6 — Signing, retries, downstream — see "Signing flow (all three flows)" below.

 #### Flow B — PREPAID wallet topup
          Step 1 — Topup event arrives
            Customer tops up their wallet via M-Pesa / bank / card / cash. BIL-05 Wallet and Topup processes
            the payment, credits the wallet, and emits:
            sophix.billing.wallet.toppedup with:
            { subscription_id, wallet_id, wallet_type_code, service_category_code (resolved from PLM-CFG-03),
              topup_amount, topup_method, payment_ref, topup_timestamp, operator_code, currency }

          Step 2 — TAX-01 consumes the event (R-TAX-01-T-2)
            WalletToppedUpConsumer:
              - Validates event payload
              - Looks up invoice_type_operator_config for (operator_code, TAX_INVOICE); if disabled → ack and stop
              - Builds InvoiceGenerationContext (no parent invoice lookup needed — topup is self-contained)
              - Calls InvoiceGenerationService.generate(ctx)

          Step 3 — TaxInvoiceGenerator runs (R-TAX-01-G-*)
            - Idempotency check on triggering_event_ref (the WalletToppedUp event ID)
            - Capture fresh customer_snapshot
            - Build ONE line item for the topup:


SOPHIX BSS Design Documents                                                                                          Page 11
                 description = "Wallet top-up — {service_category_label}" (localized)
                 package_ref = synthetic value like "TOPUP_{WALLET_TYPE}"
                 service_category_code = wallet's service category (e.g., INTERNET, TV, VOICE)
                 wallet_type_code = topup'd wallet's type
                 total = topup_amount (tax-inclusive)
                 Call PLM-CFG-02 Tax Configuration TaxService.computeTax(total, customer_location, service_category)
                   → returns tax_breakdown decomposing the inclusive total into base + tax components
                   per the operator's tax rules for that service category
                 subtotal = the decomposed pre-tax base
                 tax_total = total - subtotal
             - Build invoice header:
                 billing_mode = PREPAID
                 customer_snapshot = fresh
                 triggering_event_ref = WalletToppedUp event ID
                 original_invoice_id = NULL
                 metadata.topup_event_id, topup_payment_ref, topup_method
                 grouping_config_ref = SINGLE-dimension group for TAX_INVOICE (or per operator config)
                 due_date = NULL, status = GENERATED, payment_status = PAID
             - Allocate TAX_INVOICE sequence number atomically
             - Write invoice + line items + outbox event
             Result: tax invoice row in status GENERATED.

          Step 4-6 — Signing, retries, downstream — see "Signing flow (all three flows)" below.

 #### Flow C — PREPAID direct-pay (no wallet)
          Step 1 — Payment event arrives
            PREPAID customer (operator doesn't use wallets) pays for an upcoming cycle directly via
            M-Pesa / bank / card / cash. BIL-01 Charging Engine records the payment and emits:
            sophix.billing.payment.received with:
            { subscription_id, payment_id, target_cycle_start, target_cycle_end, paid_amount,
              payment_method, payment_timestamp, operator_code, currency }

          Step 2 — TAX-01 consumes the event (R-TAX-01-T-3)
            PaymentReceivedConsumer:
              - Validates event payload
              - Looks up invoice_type_operator_config for (operator_code, TAX_INVOICE); if disabled → ack and stop
              - Resolves the subscription's package and service category via PLM-CFG-01 Package Catalog
              - Optionally looks up the corresponding pro forma (if one exists) for traceability
              - Builds InvoiceGenerationContext and calls InvoiceGenerationService.generate(ctx)

          Step 3 — TaxInvoiceGenerator runs (R-TAX-01-G-*)
            - Idempotency check on triggering_event_ref (the PaymentReceived event ID)
            - Capture fresh customer_snapshot
            - Build ONE line item for the direct payment:
                description = "Cycle pre-payment — {package_name}" (localized)
                package_ref = subscription's package
                service_category_code = subscription's service category
                total = paid_amount (tax-inclusive)
                Call PLM-CFG-02 Tax Configuration TaxService.computeTax(total, customer_location, service_category)
                  → returns tax_breakdown decomposing the inclusive total
            - Build invoice header:
                billing_mode = PREPAID
                customer_snapshot = fresh
                triggering_event_ref = PaymentReceived event ID
                original_invoice_id = pro forma ID (if exists) or NULL
                metadata.payment_received_event_id, payment_method
                grouping_config_ref = SINGLE-dimension group for TAX_INVOICE (or per operator config)
                period_start = target_cycle_start, period_end = target_cycle_end
                due_date = NULL, status = GENERATED, payment_status = PAID
            - Allocate TAX_INVOICE sequence number atomically
            - Write invoice + line items + outbox event
            Result: tax invoice row in status GENERATED.

          Step 4-6 — Signing, retries, downstream — see "Signing flow (all three flows)" below.

 #### Signing flow (common to all three flows)
          Step 4 — SigningScanner picks up the tax invoice
            Every 1 minute per operator, scanner queries:
              SELECT * FROM invoice
              WHERE invoice_type_code = 'TAX_INVOICE'
                AND status = 'GENERATED'
                AND operator_code = :operator
            For each row:
              Step 4a — Transition status to PENDING_SIGNATURE (atomic compare-and-swap)
              Step 4b — Look up signer implementation via invoice_type_operator_config.signing_service_implementation_ref
              Step 4c — Call signer.sign(taxInvoice):
                          - Signer builds gateway-specific payload (proprietary format per authority)
                          - Submits over HTTPS with appropriate auth (mTLS / OAuth / signed JWT / etc.)
                          - Waits for response (timeout from operator config, default 30s)
                          - On success: parses response into TaxSignaturePayload
                          - On failure: throws TaxSigningException with category (TRANSIENT / VALIDATION)


SOPHIX BSS Design Documents                                                                                            Page 12
                   Step 4d — On success:
                               - Update invoice.metadata.tax_signature_data, signed_invoice_number, signed_at
                               - Transition status to SIGNED
                               - Emit TaxInvoiceSigned event
                   Step 4e — On failure:
                               - Transition status to SIGNING_FAILED
                               - Insert tax_invoice_signing_failure row
                               - Set next_retry_at per failure category (transient → exponential backoff; validation → NULL)
                               - Emit TaxInvoiceSigningFailed event

             Step 5 — RetryScanner picks up transient failures (R-TAX-01-F-2)
               Every 5 minutes per operator: re-submits SIGNING_FAILED with transient failure_type and next_retry_at <= NOW.
               After 8 transient failures: transitions to GAVE_UP_AUTO and emits TaxInvoiceSigningGaveUp event.

             Step 6 — Downstream consumers
               TaxInvoiceSigned → DD_NOT-01 Notification Service: renders PDF, sends to customer
               TaxInvoiceSigningGaveUp → ops alerting
               TaxInvoiceSigningFailed (VALIDATION) → admin queue: human action required

 The pluggable signer pattern
 Every operator's tax authority has its own protocol. To support this without polluting the shared TAX-01 code with
 per-jurisdiction conditionals, TAX-01 uses an interface-based signer pattern.

 The interface:
             public interface TaxInvoiceSigner {

                   /**
                    * Returns the operator code this signer is registered for.
                    * Used by the registry to select the right signer for a given operator.
                    */
                   String getOperatorCode();

                   /**
                    * Submit the tax invoice to the operator's tax authority gateway.
                    * Returns a normalized payload containing the signed reference,
                    * QR signature data, and gateway-specific metadata.
                    * Throws TaxSigningException with category (TRANSIENT / VALIDATION) on failure.
                    */
                   TaxSignaturePayload sign(Invoice taxInvoice) throws TaxSigningException;

                   /**
                    * Submit a cancellation request for an already-signed tax invoice.
                    * Returns the gateway's cancellation reference on success.
                    * Throws TaxSigningException on failure.
                    */
                   String cancel(Invoice signedTaxInvoice, String cancellationReason) throws TaxSigningException;
             }

 Concrete implementations: one Java class per operator. The implementation knows:

   - The gateway's URL and credentials (loaded from environment-specific config, NOT hardcoded)

   - The wire protocol (REST, SOAP, fiscal device proxy, etc.)

   - The payload schema (each authority has its own JSON or XML format)

   - The authentication mechanism (mTLS client certs, OAuth client credentials, signed JWTs, etc.)

   - Response parsing (extract signed reference number, QR data, timestamp)



SOPHIX BSS Design Documents                                                                                                                           Page 13
   - Error code mapping (each authority returns errors differently; the signer normalizes them to the TaxSigningException
     categories)

 Signer registration: each implementation is a Spring @Component. At startup, the TaxInvoiceSignerRegistry scans
 for all TaxInvoiceSigner beans, indexes them by getOperatorCode(). At runtime, TaxInvoiceSigningService
 looks up the right signer based on the tax invoice's operator code.

 What this means for adding a new operator: write a new signer class, annotate with @Component, deploy. No changes to
 the scanner, the retry framework, the data model, or other operators' signers. The pattern is the same as the
 InvoiceGenerator framework from BIL-02 Core.

 Signer implementations at deployment time
 Each operator that enables tax invoicing has one TaxInvoiceSigner implementation registered as a Spring @Component.
 The specific authority, protocol, payload format, and credentials are provided by the operator's tax team at deployment time.
 The TAX-01 framework supports any authority that fits the TaxInvoiceSigner contract; adding a new operator means
 writing one new class and deploying it — no changes to the scanner, retry framework, data model, or other operators' signers.

 Operators whose deployment country does not require electronic tax invoice signing leave the tax invoice capability disabled
 (invoice_type_operator_config.enabled = false for TAX_INVOICE). For those operators, no signer is needed.
