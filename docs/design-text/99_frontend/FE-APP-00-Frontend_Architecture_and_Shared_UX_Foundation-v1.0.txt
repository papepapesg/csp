 1. Purpose
 This DD defines the shared frontend foundation for SOPHIX V3.

 It explains how all frontend applications should be built so that they are consistent, secure, operator-flexible, and practical to
 maintain. It does not design every screen. Each application-specific DD will define screens and flows for its own users.

 SOPHIX is deployed in Kenya first, but the frontend must support future deployment into other regions with minor
 configuration changes. The same codebase must support different operators, countries, languages, currencies, logos, color
 themes, feature availability, and local compliance text.

 Every frontend app DD must also satisfy DD_CROSS-00-System_Traceability_and_Implementation_Map-v1.0:
 each feature/screen must identify the owning module API, supporting read APIs, role source, events/polling behavior, and
 E2E test scenario.

 3. Design Principles
  Principle                                  Meaning

  One codebase, many operators               Avoid country forks. Operator differences must be configuration, translations,
                                             theme tokens, and feature flags.

  Module ownership remains backend-owned     UI screens call owning module APIs. Frontend does not create hidden
                                             ownership rules.

  Role-driven navigation                     Users see only actions allowed by their roles and operator configuration.
                                             Backend still enforces authorization.

  Explicit process state                     Long-running operations show current state, next expected action, owner,
                                             timers, and failure reason.

  Mobile workflows survive weak networks     Sales and contractor apps need drafts, offline queues, retry, and conflict
                                             handling.

  Operational density for backoffice         Backoffice is a work tool. Use compact, scannable screens rather than
                                             marketing-style layouts.

  Customer clarity for frontoffice           Customer-facing screens use simpler language and hide internal workflow
                                             complexity.

  Accessibility by default                   Support keyboard navigation, readable contrast, labels, focus states, and
                                             responsive layouts.

 4.3 Language And Translation Rules
 All user-visible text must come from translation keys, except dynamic values returned by APIs.

 Translation key convention:
           <app>.<domain>.<screen>.<element>

 Examples:
           backoffice.customer360.title
           sales.orderCapture.homepassNotEligible
           contractor.workOrder.finalizeButton
           selfcare.invoice.payNow
           reports.billing.dunningAtRisk

 Rules:

   - Do not concatenate translated strings with variables in a way that breaks grammar.

   - Use ICU-style messages for pluralization and interpolation.

   - Store dates, money, and numbers as raw values; format in the UI using locale/currency config.

   - Backend error codes must map to localized frontend messages.

   - Support left-to-right layouts initially; do not block future RTL support with hardcoded alignment assumptions.


 5. Authentication And Authorization
 All frontend apps use Keycloak/OIDC from FOUNDATION_AUTH.

 Required behavior:

   1. User opens app.

   2. App loads public runtime config.

   3. App redirects to Keycloak if no valid session exists.

   4. App receives access token and refresh token.

   5. App calls APIs with Authorization: Bearer <token>.

   6. App renders navigation/actions from token claims, role matrix, and feature flags.

   7. Backend enforces authorization again on every API.

 6. Application Shell
 Each frontend application must share a consistent shell pattern while adapting to its device and user context.

 6.1 Backoffice Shell
 Backoffice is a dense operational web app.

 Required shell areas:

   - top bar with operator switch/context if user has multi-operator access;

   - left navigation grouped by module/process;

   - global customer/subscription/work-order search;

   - notifications/task inbox;

   - profile/session menu;

   - environment indicator for non-production;

   - breadcrumb for deep operational screens.

 6.2 Mobile Shells
 Sales and contractor apps are mobile-first.

 Required shell areas:

   - bottom navigation for main daily actions;

   - offline/connectivity indicator;

   - sync status indicator;

   - compact task/order/job queue;

   - camera/file capture entry points where relevant;

   - local draft recovery prompt.

 7. API Integration Pattern
 Frontend apps must call backend APIs through a shared API client layer.

 Required client behavior:

  Concern                                                                    Rule

  Auth                                                                       Attach bearer token automatically. Refresh token before expiry.

  Operator context                                                           Send selected operator/country context where backend contract requires it.

  Correlation                                                                Send X-Correlation-Id for every command and important query.

  Idempotency                                                                Send Idempotency-Key for every create/command that may be retried.

  Error mapping                                                              Convert backend error code to localized user message and support details.

  Retry                                                                      Retry safe reads with backoff. Do not blindly retry non-idempotent commands.

  Timeouts                                                                   Use explicit timeouts and show actionable pending state.

  Pagination                                                                 Use backend paging; do not load huge operational lists into browser memory.



 7.1 Error Model
 Backend errors should be displayed using a consistent frontend model.

  Backend field                                                              Frontend use

  errorCode                                                                  Translation key and support reference.

  message                                                                    Developer/support fallback, not always customer-safe.

  fieldErrors                                                                Field-level validation display.

  correlationId                                                              Show in details/copy button for support.

  retryable                                                                  Controls retry button or wait message.

  nextAction                                                                 Suggests user action where backend can provide it.


 Frontend display rules:

   - Use field-level errors near the field.

   - Use page-level alerts for business rule rejections.

   - Use modal confirmations only for irreversible or high-risk actions.

   - Show correlation id in expandable details for support users.

   - For customer-facing screens, avoid exposing internal module names unless needed.

 9. Forms And Validation
 Frontend validation improves UX. Backend validation remains authoritative.

 Required form behavior:

   - validate required fields before submit;

   - use backend enum/catalog APIs for select options;

   - format phone numbers, IDs, dates, and money by country/operator config;

   - preserve drafts for long forms;

   - prevent double submit;

   - attach idempotency key on create/command;

   - display backend field errors without losing user input.

 High-risk actions need explicit confirmation:

  Action type                                                         Confirmation requirement

  Subscription termination                                            Required, show impact summary.

  Billing adjustment/write-off/refund                                 Required, role-gated, show audit reason.

  Work order cancellation                                             Required, show downstream impact.

  Equipment swap/RMA finalization                                     Required when serial/state changes.

  Customer data deletion/anonymization                                Required and likely supervisor-approved.

   - incident: failure needing operational support.


 12. UX Standards
 12.1 Backoffice UX
 Backoffice screens should be dense, scannable, and operational.

 Use:

   - tables with filters, saved views, pagination;

   - timeline panels for customer/subscription/work order history;

   - status chips with consistent color semantics;

   - split view for list + detail where workflows require fast triage;

   - audit panels for high-risk records;

   - role-gated action menus.

 Avoid:

   - marketing-style hero layouts;

   - oversized cards for operational data;

   - hiding important state behind decorative UI;

   - actions that are visible but always fail due to permissions.

 12.2 Mobile UX
 Mobile apps should prioritize daily field tasks.

 Use:

   - clear current task/job/order state;

   - large touch targets;

   - camera-first upload flows;

   - offline status;

   - step-by-step checklists for work execution;

   - background sync with visible outcome.

 13. Accessibility And Responsive Rules
 Minimum requirements:

   - WCAG AA contrast for text and interactive controls.

   - Keyboard navigation for web apps.

   - Visible focus states.

   - Labels for all inputs.

   - Error text associated with fields.

   - No color-only status indicators.

   - Responsive layout for desktop, tablet, and mobile where app requires it.

   - Tables must have responsive alternatives for narrow screens.


 14. Security Rules
 Frontend must not:

   - store secrets in source code;

   - rely on hidden buttons for authorization;

   - expose service tokens to browsers/mobile apps;

   - log access tokens, refresh tokens, ID numbers, passwords, or payment secrets;

   - cache sensitive documents longer than approved;

   - send customer PII to third-party analytics without approval.

 Frontend must:

   - use HTTPS only;

   - validate file type/size before upload;

   - clear local state on logout;

   - handle token expiry gracefully;

   - display session timeout warnings where appropriate;

   - include correlation id on command requests.
