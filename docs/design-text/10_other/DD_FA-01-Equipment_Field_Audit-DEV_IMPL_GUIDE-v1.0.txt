 DD_FA-01 - Equipment Field Audit - Developer
 Implementation Guide
 Version: v1.0 Bundle: 10_other Companion DD: DD_FA-01-Equipment_Field_Audit-v1.0



 1. Goal
 Implement the standalone equipment field audit process.

 The implementation must let operations create audit tasks, freeze expected equipment from OSR-INSTANCE, let field users
 capture observations from the mobile app, compare expected vs observed state, and route discrepancies to the correct
 module.

 Do not use FA-01 as a replacement for every normal work order. Installation, shifting, support, and swap flows keep their own
 WO evidence. FA-01 is for planned audits and exception-driven verification.

 3. Step 1 - Database Migrations
 Create:

   - equipment_field_audit_campaign

   - equipment_field_audit_task

   - equipment_field_audit_expected_item

   - equipment_field_audit_observation

   - equipment_field_audit_discrepancy

 Implementation details:

   - Add a unique index for mobile offline submissions: (operator_code, offline_client_ref) on observations.

   - Store expected state snapshots as JSON so the audit remains explainable even if OSR-INSTANCE changes later.

   - Store only file ids in observations, not binary photo content.

   - Add indexes for assigned user task lists and discrepancy work queues.

   3. Emits EquipmentFieldAuditCampaignCreated.

 Campaigns are optional. A support user may create one direct audit task without a campaign.



 5. Step 3 - Create Audit Task And Freeze Expected Items
 Backoffice or another module calls:
           POST /api/equipment-field-audits/tasks
           Idempotency-Key: efat-CUS-100045-202608
           Content-Type: application/json

           {
               "operatorCode": "WIK",
               "campaignId": "efac-001",
               "taskType": "CUSTOMER_PREMISES",
               "customerId": "CUS-100045",
               "accountId": "ACC-900045",
               "subscriptionId": "SUB-700045",
               "homepassId": "HP-GPON-0440",
               "assignedToUserId": "usr-tech-010",
               "dueAt": "2026-08-12T17:00:00Z",
               "createWorkOrder": true
           }

 FA-01:

   1. Validates request and idempotency key.

   2. Creates equipment_field_audit_task in CREATED.

   3. Calls OSR-INSTANCE to load expected equipment:
           GET /api/equipment-instances?operatorCode=WIK&customerId=CUS-100045&subscriptionId=SUB-700045&state=INSTALLED

   4. For each returned equipment instance, inserts equipment_field_audit_expected_item.

   5. If no expected item exists, task can still be created for investigation, but mark it with a warning.

   6. Emits EquipmentFieldAuditTaskCreated.

 Expected item sample from OSR-INSTANCE:

 FA-01:

   5. Does not compare or route until task submit, unless the operator wants immediate discrepancy preview.



 9. Step 7 - Submit Task And Compare
 Mobile app calls:
          POST /api/equipment-field-audits/tasks/efat-001/submit
          Content-Type: application/json

          {
              "submittedByUserId": "usr-tech-010",
              "submittedAt": "2026-08-12T10:30:00Z"
          }

 FA-01 comparison logic:

   1. Load expected items.

   2. Load observations.

   3. For each expected item:

   - no matching observation means MISSING;

   - different serial means WRONG_SERIAL;

   - conditionStatus=DAMAGED means DAMAGED;

   - GPS too far from expected location may mean WRONG_LOCATION.

   4. For each observation without expected match, create FOUND_EXTRA.

   5. If no discrepancy, set task CLOSED and emit EquipmentFieldAuditTaskClosed.

   6. If discrepancies exist, set task DISCREPANCY_OPEN and emit EquipmentFieldAuditDiscrepancyOpened.

 Do not change OSR-INSTANCE state during comparison.



 10. Step 8 - Route Discrepancies
 Run Drools for every discrepancy:
          public record EquipmentFieldAuditFact(
               String operatorCode,
               String discrepancyType,
               String expectedLocationType,
               String observedCondition,
               boolean equipmentRecoverable,
               boolean customerServiceImpacted,
               boolean serialBelongsToAnotherCustomer,
               String technologyFamily
          ) {}

 Severity rules:

          package rules.field_audit.equipment.severity

          rule "Wrong serial assigned to another customer is critical"
          when
            $f : EquipmentFieldAuditFact(discrepancyType == "WRONG_SERIAL",
                                         serialBelongsToAnotherCustomer == true)
            $d : EquipmentFieldAuditDecision()
          then
            $d.setSeverity("CRITICAL");
          end

          rule "Missing customer premises equipment is high severity"
          when
            $f : EquipmentFieldAuditFact(discrepancyType == "MISSING",
                                         expectedLocationType == "CUSTOMER_PREMISES")
            $d : EquipmentFieldAuditDecision()
          then
            $d.setSeverity("HIGH");
          end

 Routing rules:
          package rules.field_audit.equipment.routing

          rule "Damaged equipment with customer impact creates ticket"
          when
            $f : EquipmentFieldAuditFact(discrepancyType == "DAMAGED",
                                         customerServiceImpacted == true)
            $d : EquipmentFieldAuditDecision()
          then
            $d.route("CREATE_TICKET");
          end

          rule "Recoverable missing equipment creates RMA recovery"
          when
            $f : EquipmentFieldAuditFact(discrepancyType == "MISSING",
                                         equipmentRecoverable == true)
            $d : EquipmentFieldAuditDecision()
          then
            $d.route("CREATE_RMA_RECOVERY");
          end

          rule "Unrecoverable equipment requests write off approval"
          when
            $f : EquipmentFieldAuditFact(discrepancyType == "MISSING",
                                         equipmentRecoverable == false)
            $d : EquipmentFieldAuditDecision()
          then
            $d.route("REQUEST_WRITE_OFF");
            $d.requireApproval("EQUIPMENT_FIELD_AUDIT_WRITE_OFF");
          end

 13. Step 11 - Tests
 Build tests in this order:

   1. Create task and freeze expected items from OSR-INSTANCE.

   2. Same idempotency key returns same task.

   3. Mobile observation duplicate offline ref returns same observation.

   4. Matching observation closes the task.

   5. Missing expected item creates MISSING discrepancy.

   6. Extra serial creates FOUND_EXTRA discrepancy.

   7. Wrong serial belonging to another customer becomes CRITICAL.

   8. Damaged equipment with service impact creates a ticket.

   9. Missing recoverable equipment creates OSR-RMA recovery.

   10. Write-off route calls EM-CFG-04 and waits for approval.

   11. FA-01 never calls OSR-02 procurement.



 14. Operational Notes
   - Mobile app uploads may arrive after the field visit because connectivity can be poor. Use offline refs everywhere.

   - Keep evidence immutable after submission. If a reviewer adds notes, create review comments instead of changing field
     evidence.

   - Do not let field users directly mark equipment written off or corrected.

   - Keep discrepancy routing visible in backoffice so audit managers can see the downstream ticket/RMA/approval reference.

   - Reporting should use FA-01 events and discrepancy tables, not screenshots from the mobile app.
