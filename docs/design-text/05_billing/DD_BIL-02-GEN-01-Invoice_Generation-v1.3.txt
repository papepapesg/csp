 1. What this process is about
 GEN-01 owns producing invoices and pro forma documents. The triggers come from elsewhere: BIL-03 Cycle Close
 emits a CycleClosed event when a subscription's cycle window has elapsed; the subscription workflow modules emit
 OneOffChargeRequested events when a workflow incurs a one-off fee (relocation, equipment swap, package change); a
 scheduled scanner wakes up daily to generate pro forma for upcoming PREPAID cycles; BIL-02-ADJ-01 Invoice Adjustments
 calls credit/debit note generators after approving an adjustment.

 For each trigger, GEN-01 instantiates the right generator class via the framework in BIL-02 Invoicing (Core), passes a
 generation context, and writes one or more invoices (one per group in the operator's grouping policy). The generator does the
 orchestration work: subscription state checks, charge computation calls to BIL-01 Charging Engine, tax computation calls to
 PLM-CFG-02 Tax Configuration, customer snapshot capture, line item building, sequence allocation, and event emission.

 GEN-01 also owns operational features tied to generation: idempotency on every retry path, bulk reversal/re-bill when whole
 batches need correction, and a generation failure queue for recoverable errors.

 #### Shared rule group Q — Generation failure queue (used by all generators)

 Invoice generation can fail partway through for reasons that are temporary rather than permanent — a downstream service is
 briefly unreachable, the customer master has a stale lock, the subscription is mid-workflow and can't be billed yet. These
 failures are recoverable: if we retry in 15 minutes, the problem is usually gone.

 Without a retry queue, the only options would be: (a) lose the invoice (the cycle close event was consumed and
 acknowledged, but no invoice exists for that customer that cycle — bad), or (b) keep retrying inline forever blocking the
 consumer thread (bad), or (c) fail loud and require manual intervention every time (bad at scale — a 5-minute BIL-01 outage
 could create 10,000 manual tickets).

 The generation failure queue is the fourth option: persist the failure with full context (what was being generated, for which
 subscription, why it failed, what payload to retry with), let the Kafka consumer commit and move on, and have a separate
 scanner pick up the queue every 15 minutes to retry. Exponential backoff means transient issues self-heal without operator
 involvement; persistent issues eventually escalate to admin review.

 Concrete scenarios this handles:

   - A subscription is in PENDING_UPGRADE state when its cycle closes — can't bill until the upgrade workflow finishes. Queue
     with reason SUBSCRIPTION_PENDING; retry every 15 minutes; succeeds once workflow completes (usually within an
     hour).

   - BIL-01 Charging Engine has a 20-minute outage during a cycle close batch — instead of losing 5,000 invoices, all 5,000
     land in the queue; BIL-01 comes back; next scanner tick regenerates all of them successfully.

   - PLM-CFG-02 Tax Configuration times out on a specific customer's tax computation due to an exemption rule edge case —
     queued; admin reviews after 8 retries (~3 days) and sees the underlying tax config bug that needs fixing.

   - CRM is unreachable during pro forma generation — queued; pro forma is informational, so deferred generation has no
     customer impact; succeeds on retry.

 The queue is admin-visible: after 8 retries (~3 days) the entry moves to GAVE_UP_AUTO for human review, and operators can
 monitor what's failing in real time (a spike of TAX_SERVICE_FAILED reasons in one hour is a tax service incident, not 200
 isolated failures).

 What the failure queue is NOT for:

   - Permanent errors (malformed event payload, invalid subscription ID, code bug throwing IllegalStateException) — those go
     to the Kafka dead-letter topic for engineering, not the failure queue. The queue is only for failures where "retrying later" is
     a sensible response.

   - Successful generation (the queue only has rows when something went wrong; successful generation leaves no trace
     here).

 #### Shared rule group R — Bulk reversal (operator-driven, affects already-generated invoices)

 Sometimes an entire batch of invoices needs to be cancelled and re-issued because they were all generated with a systemic
 error — the wrong tax rate, the wrong package price, the wrong grouping policy, a buggy charging computation. The invoices
 already exist in the system. Many of them have already been sent to customers by email. Some may have been notified to the
 tax authority. The operator needs a clean, auditable way to cancel them all and (optionally) re-issue corrected versions,
 without writing one-off SQL scripts or clicking through admin UI 10,000 times.

 That's bulk reversal. It is always initiated by a human — a billing admin in the operator's admin console. It is never triggered
 by an automatic system event. The mechanism: define a scope (operator + invoice type + date range + optional filters),
 preview the impact (how many invoices, what total amount), get dual approval (Billing Admin proposes, Finance Head
 approves), execute the reversal one invoice at a time in transactional batches with full audit trail, optionally re-invoke the
 generators to produce corrected replacements.

 Concrete scenarios that require bulk reversal:

   - An operator's tax team realizes that VAT was applied at 16% when it should have been 15% for September cycle invoices
     in Wananchi KE — 12,000 invoices need to be cancelled and re-issued with the right rate.

   - A package price catalog update was committed with a typo (KES 3,500 became KES 35,000 due to a missing decimal) —
     affected cycle invoices have totals 10x too high, customers complained, all need to be re-issued.

   - The grouping policy was misconfigured for one operator and a batch of cycle invoices was issued with the wrong wallet
     grouping (Internet and TV invoiced separately when they should have been grouped) — re-issue with corrected policy.

   - BIL-01 Charging Engine had a regression for 24 hours causing usage charges to be doubled for postpaid customers —
     entire 24-hour batch needs reversal and re-issue.

 Why this needs to be a first-class capability, not just SQL or stored procedures:

   - Scale: 10,000+ invoices in a single batch. Manual UI cancellation impractical.

   - Atomicity at invoice level: each invoice's reversal must be its own transaction (cancel + outstanding balance update +
     event emission). A bulk SQL UPDATE can't do this.

   - Protected states: signed tax invoices can't simply be cancelled — tax authority reconciliation required. Already-cancelled
     invoices shouldn't be re-cancelled. Invoices linked to credit/debit notes need to be reversed as a coherent group. SQL
     doesn't enforce this.

   - Dual approval audit: Finance regulators expect to see "who initiated, who approved, when, why" for any mass financial
     adjustment. The bulk_reversal_batch table captures this.

   - Per-invoice failure visibility: when 12,000 invoices are processed, some will fail (linked to credit notes, in protected state,
     etc.). The admin needs to see which ones failed and why, with the ability to resolve them individually.


SOPHIX BSS Design Documents                                                                                                       Page 8
   - Optional re-issue: cancellation alone leaves the customers with no invoice; the operator usually wants corrected versions
     issued automatically. The batch can re-invoke the appropriate generator with fresh inputs (fresh tax computation, fresh
     charges from BIL-01).

   - Downstream events: every cancellation emits InvoiceCancelled consumed by BIL-01 Charging Engine (outstanding
     balance update), BIL-04 Dunning Engine (stop dunning), DD_NOT-01 Notification Service (notify customer). Doing this via
     SQL would miss the event emission and break consumers.

 What bulk reversal is NOT:

   - Not for cancelling a single invoice — that's a routine operation owned by BIL-02-STA-01 Status Management &
     Recovery through standard admin UI.

   - Not for correcting just the amount on an invoice — that's an adjustment, owned by BIL-02-ADJ-01 Invoice Adjustments,
     which issues a credit or debit note rather than cancelling the original.

   - Not for handling individual customer disputes — that's STA-01 (dispute hold) and ADJ-01 (adjustment if dispute upheld).

   - Not for cancelling pro forma documents — pro forma supersession is automatic when the next pro forma is generated.
     There's no bulk reversal of pro forma.

 Source / who initiates: Always a Billing Admin user via the admin console REST endpoints listed later in this DD. The flow:

   1. Billing Admin defines scope and clicks "Preview" — system computes how many invoices match, what the total amount
     affected is, which would be rejected due to protected state.

   2. Billing Admin reviews preview, adds operator notes explaining why, clicks "Submit for approval" — batch row created with
     status PENDING_APPROVAL.

   3. Finance Head receives notification (typically via operator email/Slack), reviews in the admin console, clicks "Approve" —
     batch transitions to IN_PROGRESS.

   4. Worker thread executes the batch one invoice at a time; admin can monitor progress in real time.

   5. On completion: COMPLETED if all in-scope invoices processed successfully; PARTIALLY_FAILED if some failed.
     Per-invoice failures viewable in the failure detail screen.

               - Match against original invoice's line item (by original_line_id reference)
               - Compute credit amount (negative subtotal)
               - Call PLM-CFG-02 TaxService.computeTax with the negative amount → returns negative tax
               - Build a single DETAIL line referencing the original via metadata.original_line_id
             Build a SUMMARY line per affected wallet/package per the original's grouping dimension.
             Aggregate tax_summary from per-line negative tax breakdowns.

           Step 7 — Build credit note header
             invoice.original_invoice_id = original.id
             invoice.subscriptionId, customerId, operatorCode, currency: from original
             invoice.billing_mode: copied from original
             invoice.grouping_config_ref + grouping_dimension + grouping_key_values: copied from original
             invoice.customer_snapshot: from step 5 (fresh)
             invoice.triggering_event_ref: `adjustment_{adjustmentId}`
             invoice.issue_date: now()
             invoice.due_date: NULL (credit note is not "due" — it's a balance reduction)
             invoice.subtotal_amount, tax_amount_total, total_amount: negative
             invoice.status: GENERATED
             invoice.metadata: { adjustment_id, original_invoice_number, approved_by, approval_timestamp }

           Step 8 — Allocate CREDIT_NOTE sequence + write atomically (R-GEN-01-F-7)
             Sequence service allocates from CREDIT_NOTE sequence.
             Single DB transaction:
               - sequence row update
               - invoice row insert (negative amounts)
               - invoice_line_item bulk insert
               - outbox event row (InvoiceIssued with metadata.adjustment_id)
             Failure → invoice_sequence_gap row + throw exception back to ADJ-01.

           Step 9 — Return the persisted credit note invoice to ADJ-01
             ADJ-01 stores credit_note.id in invoice_adjustment.adjustment_invoice_id within its own transaction.

 Output:

SOPHIX BSS Design Documents                                                                                          Page 16
   - 1 row in invoice table with negative amounts and original_invoice_id set

   - N rows in invoice_line_item with negative line subtotals and negative tax

   - 1 InvoiceIssued event with metadata.adjustment_id populated

   - BIL-01 Charging Engine consumes the event and reduces outstanding balance against the original invoice

   - BIL-04 Dunning Engine consumes the event and may stop dunning if the credit note fully clears the original's balance

   - DD_NOT-01 Notification Service consumes the event and sends the credit note to the customer

 Failure paths: identical to cycle generator's, except failures are thrown back to ADJ-01 synchronously (since this is a
 synchronous Java call, not a Kafka consumer path). ADJ-01 decides what to do — retry inline, or queue its own adjustment
 for re-processing. ADJ-01 owns that decision.


 #### Generator 5 — DebitNoteGenerator

 Purpose: produce a debit note that increases a customer's outstanding balance on a previously-issued invoice. Used for
 under-charges discovered after the fact (missed line items, tax under-applied, regulatory adjustments increasing tax
 retroactively, etc.).

 Trigger: In-process Java method call from BIL-02-ADJ-01 Invoice Adjustments. Same mechanism as credit note but with
 positive amounts.

 Specific rules: same group N rules as credit note (shared between the two generators).

 End-to-end flow: identical to credit note's, with these differences in step 6:

   - adjustmentLine.amount is positive (debit means "customer owes more")

   - TaxService returns positive tax on the positive base

   - Resulting line subtotals and tax amounts are positive

   - Aggregated invoice total is positive

 In step 7, the debit note header has:

   - invoice.due_date = now() + grace_days (debit note IS due — customer owes more, has time to pay)

   - total_amount positive

   - metadata: same structure as credit note but adjustment_type = DEBIT

 Output: 1 row in invoice with positive amounts, original_invoice_id set, due date set. BIL-01 increases outstanding
 balance. BIL-04 may start dunning if the debit note isn't paid by due date.

 Failure paths: identical to credit note's.

 In TZ Sophix, invoice generation is embedded in the billing-engine cron job — a single monolithic procedure that on a
 schedule queries due cycles, computes charges, applies tax, and writes invoices. There is no formal separation of generators
 per invoice type; everything goes through the same code path. Pro forma is implemented as ad-hoc database queries
 rendered by an analytics tool rather than as a first-class document with sequence numbering and lifecycle. One-off invoices
 for relocation and equipment swap exist but are issued by direct database inserts from the workflow handlers, bypassing the
 cron — so they have inconsistent sequence numbering, inconsistent tax treatment, and no idempotency.

 Bulk reversal exists as a manual stored-procedure that an operator runs from a database client; there is no preview, no
 approval flow, no per-invoice audit, and re-issuance is a separate manual step. The reversal procedure is invoked perhaps
 2-3 times per year, always followed by a multi-hour cleanup of inconsistencies.

 There is no generation failure queue. When the cron job fails partway through a cycle close — usually because the tax
 microservice is unresponsive or BIL-01's predecessor times out — the operations team manually identifies missing invoices
 via spreadsheet comparison against the subscription list and triggers a partial re-run of the cron. This process loses 1-2
 invoices per quarter to operational errors.

 Idempotency is partial. The cron uses a "last processed cycle timestamp" to avoid re-processing the same cycle, but
 mid-cycle Kafka retries (the cron does consume some Kafka events) sometimes produce duplicate invoices that have to be
 manually cancelled.
