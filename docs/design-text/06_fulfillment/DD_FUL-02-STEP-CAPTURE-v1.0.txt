 Verdict: ■ New | Wave: 1 | Group III: Fulfillment | Version: v1.0 | Satellite of: DD_FUL-02-Order_Capture-v1.0.md

 The first step in the order journey: a channel UI (Field Agent PWA, Backoffice UI, Call Center UI, self-service portal) hands
 FUL-02 the customer's intent to subscribe; FUL-02 turns that into a durable order row and starts the operator's workflow
 running in Camunda. Phase: CAPTURED.



 1. What this step does
 A customer at a known HomePass wants to subscribe to a Package. The capturing channel — the screen the human (agent
 or self-service customer) is interacting with — sends an HTTP POST to POST /api/orders. This step's job is to turn that
 single HTTP call into two durable things, atomically from the channel's point of view:

   1. A row in customer_order (the DB table where the order lives for its whole lifetime, holding identifiers, status, audit).
     This row is what the rest of the system reads when it needs to know about this order: the BO UI, finance reports, NOC
     dashboards, ops investigations.

   2. A live workflow execution in Camunda for this order. Camunda is the workflow engine — it lives in its own server
     outside our module and runs the operator's BPMN flowchart that defines what happens to an order from capture to
     activation. The execution is called a process instance — one running execution of a recipe. Starting it is how the rest of
     the journey is launched: from this moment on, Camunda will drive the order through validation, payment, install, activation,
     by handing work to FUL-02's workers as the flow advances.

 The two things are bound together. The DB row knows about the Camunda process instance via the
 process_instance_id column; the Camunda process instance knows about the DB row via its businessKey
 (Camunda's way of tagging an instance with the domain entity it belongs to — here, the orderId). If a Kafka consumer or
 REST call later needs to wake the Camunda instance — for example, when a payment arrives — it'll look up the order by
 some external reference, get the process_instance_id or businessKey, and call Camunda's REST API.

 If either of the two writes fails after the other succeeded, the step rolls back: if Camunda fails to start, the DB row is deleted.
 The channel sees a 5xx and can retry safely thanks to the idempotency key — a string the channel generates per
 submission (e.g., from the device ID + timestamp) so that re-sending the same request never creates two orders.

 Why a separate "capture" step at all
 The other steps in FUL-02 are Camunda-driven: Camunda decides when they run and hands them work. Capture is the
 *only* step that runs before Camunda is involved — it's the bootstrap. It's the bridge between HTTP-from-a-channel and a
 running Camunda instance. Once capture completes, the rest of the journey is Camunda-orchestrated.

 Customer-side
 The customer record already exists in the customer service when the agent is at the door (KYC and identity were captured
 during the sales conversation). In v1.0 the customer service is stubbed by the customer_stub table (the ILM-CFG-01
 Customer Service DD is pending). The channel passes the customerId of the existing record. customer_stub is a
 deliberate v1.0 placeholder — its columns are documented in FRAMEWORK §6.1; it will be retired when ILM-CFG-01 lands.

 4. Service flow inside FUL-02
 OrderCaptureService runs the entry transaction. The numbered steps below are what the worked example in §2 walks
 concretely.

   1. Authenticate. Verify JWT, extract role. Channel-role pairing per FRAMEWORK R-FUL-02-FW-1 (ORDER_FIELD_AGENT
     ↔ FIELD_AGENT_PWA, ORDER_BACKOFFICE ↔ BACKOFFICE, ORDER_CALL_CENTER ↔ CALL_CENTER). Mismatch →
     403.


SOPHIX BSS Design Documents                                                                                                                                 Page 7
   2. Validate envelope. Required fields present; operatorCode ∈ {WIK, WUG, WTZ, YASSN} (KE v1.0 deployment
     accepts WIK only at runtime — see step 5; the schema allows others for forward-compat); capturedAt not in future;
     idempotencyKey non-empty. Fails → 400 INVALID_ENVELOPE with detail field.

   3. Idempotency check. SELECT FROM customer_order WHERE (operator_code, sales_channel,
     idempotency_key) matches. Hit → return existing order with idempotencyHit: true (409). The existing order's
     phase is returned as-is — if the customer's first submission already activated, the channel sees currentPhase:
     "ACTIVATED".

   4. Resolve customer. customerId is required (channel-supplied). Verified to exist in customer_stub (v1.0); future-state
     verified against ILM-CFG-01.

   5. Verify BPMN is deployed. GET /engine-rest/process-definition/key/OrderCapture_{operatorCode}.
     404 → return 400 BPMN_NOT_DEPLOYED_FOR_OPERATOR. Critical: do NOT write the order row if the BPMN is missing.
     The order would be orphaned (no flow to run it through).

   6. Generate orderId; INSERT customer_order. ULID for order_id. payment_reference = order_id (a convention
     used by STEP-PAYMENT's PaymentAppliedConsumer to correlate inbound PaymentApplied events back to the
     order — the customer types order_id as the M-Pesa account number when paying). current_phase = CAPTURED,
     current_activity_id = main-start. process_instance_id left NULL for now.

   7. Start the Camunda process instance. POST
     /engine-rest/process-definition/key/OrderCapture_{operatorCode}/start with businessKey =
     orderId and process variables. See FRAMEWORK §1.1 for the full call shape.

   8. UPDATE customer_order.process_instance_id. The Camunda response carries the new instance id; store it on the
     row.

   9. Emit sophix.orders.created on Kafka. See §6 below.

   10. Return 201.

 Compensating transaction on partial failure
 If step 7 fails after step 6 succeeded (Camunda 500, network error, etc.), the order row exists but no process instance does.
 OrderCaptureService issues a DELETE on the row, then returns 5xx to the channel. The channel retries with the same
 idempotencyKey; the second attempt's idempotency check (step 3) won't match because the row was deleted, so it
 proceeds fresh.

 If step 8 fails (the Camunda call succeeded but the UPDATE failed), there's a brief inconsistency — Camunda has an
 instance whose businessKey doesn't appear on any DB row. A startup reconciler in OrderCaptureService scans for
 process_instance_id IS NULL AND created_at < NOW() - INTERVAL '5 minutes' rows and queries
 Camunda by businessKey to backfill.



 5. DB tables touched
 customer_order (FRAMEWORK §5.1) — INSERT then UPDATE

 7. Step-pinned rules



SOPHIX BSS Design Documents                                                                                                               Page 10
  ID                          Rule

  R-FUL-02-CAP-1              Idempotency unique on (operator_code, sales_channel,
                              idempotency_key). Hit → return the existing order (with whatever phase it
                              has now) and idempotencyHit: true. Channels are expected to dedupe
                              network retries via this key.

  R-FUL-02-CAP-2              The customer_order row is written *before* Camunda is asked to start;
                              process_instance_id is UPDATEd onto the row after Camunda confirms.
                              businessKey = orderId links the two.

  R-FUL-02-CAP-3              If OrderCapture_{operatorCode} is not deployed in Camunda, return 400
                              and do NOT write the order row. An order without a flow to run would be
                              orphaned.

  R-FUL-02-CAP-4              payment_reference is initialized to order_id at capture.
                              STEP-PAYMENT's PaymentAppliedConsumer uses this convention to
                              correlate inbound PaymentApplied events to the order: the customer is
                              instructed to type order_id as the M-Pesa account number; BIL-01 echoes
                              that as targetReference in the PaymentApplied event; FUL-02's
                              consumer matches it against payment_reference.

  R-FUL-02-CAP-5              intendedActivationDate interpretation is BPMN-defined. WIK BPMN v1.0
                              ignores it (immediate activation). A future operator BPMN supporting scheduled
                              activations would set a timer firing install creation at
                              intendedActivationDate -
                              ful_02_config.future_activation_lead_days. WIK v1.0 BPMNs treat
                              the date as advisory metadata only.

  R-FUL-02-CAP-6              The channel passes an existing customerId (KE v1.0 flow). v1.0 verifies it
                              exists in customer_stub; future-state verifies against ILM-CFG-01 with same
                              customerId semantics. Customer creation is out of v1.0 FUL-02 scope.

  R-FUL-02-CAP-7              DB-write-then-Camunda-start is a compensating-transaction pair. If Camunda
                              start fails after the row was written, the row is DELETEd; channel retries with
                              the same idempotencyKey and succeeds fresh. A startup reconciler covers
                              the rare case where the row was UPDATEd partially (Camunda started, but the
                              process_instance_id UPDATE failed).

  R-FUL-02-CAP-8              The OrderCreated event is emitted only after both writes succeed (row +
                              Camunda). Consumers can trust the event: when they see it, both DB and
                              Camunda are consistent.
