 FOUNDATION_DB - PostgreSQL Database Foundation
 Developer implementation guide: FOUNDATION_DB_DEV_IMPL_GUIDE.md.


 1. Purpose
 This foundation defines how SOPHIX modules use PostgreSQL: cluster layout, module database placement, connection
 pooling, replication, migrations, outbox/inbox storage, and recovery rules.

 Use this document when implementing:

   - A module database.

   - A database migration.

   - Business tables that emit Kafka events.

   - Outbox and inbox storage.

   - Database connection configuration.

   - Read-replica routing.


 2. Ownership
 FOUNDATION_DB owns:

   - PostgreSQL cluster topology.

   - Module-to-cluster placement.

   - PgBouncer usage.

   - Replication model.

   - Migration conventions.

   - Database naming and schema conventions.

   - Outbox/inbox database placement.

   - Cluster-level failure behavior.

 FOUNDATION_DB does not own:

   - Module table schemas. Those are owned by each DD.

   - Kafka event payloads. See FOUNDATION_KAFKA.md.

   - Binary file storage. See FOUNDATION_FILE_STORAGE.md.

   - Secrets. Use the platform secret manager.

 7. Replication
 All clusters use PostgreSQL streaming replication via WAL.

 Common primary settings:
            wal_level = replica
            max_wal_senders = 5
            max_replication_slots = 5
            wal_keep_size = 1024
            archive_mode = on
            archive_command = 'rsync %p /var/lib/postgresql/wal_archive/%f'
            hot_standby = on
            hot_standby_feedback = on

 Cluster A and B:
            synchronous_commit = local
            synchronous_standby_names = ''

 Cluster C:
            synchronous_commit = on
            synchronous_standby_names = 'FIRST 1 (pg-c-replica)'

 Cluster C write rule: writes return only after primary and replica persist WAL. This gives zero RPO for committed revenue and
 lifecycle transactions.

 10. Outbox and Inbox Storage
 Each module stores outbox and inbox tables in its own database, in schema messaging.
             CREATE SCHEMA IF NOT EXISTS messaging;

 Producer outbox:
             CREATE TABLE messaging.outbox_event (
                event_id     TEXT PRIMARY KEY,
                topic        TEXT NOT NULL,
                message_key  TEXT NOT NULL,
                envelope     JSONB NOT NULL,
                created_at   TIMESTAMPTZ NOT NULL DEFAULT NOW(),
                published_at TIMESTAMPTZ NULL,
                attempts     INTEGER NOT NULL DEFAULT 0,
                last_error   TEXT NULL
             );

             CREATE INDEX idx_outbox_pending
               ON messaging.outbox_event (created_at)
               WHERE published_at IS NULL;

 Consumer inbox:
             CREATE TABLE messaging.inbox_event (
                event_id     TEXT PRIMARY KEY,
                topic        TEXT NOT NULL,
                message_key  TEXT NOT NULL,
                envelope     JSONB NOT NULL,
                received_at  TIMESTAMPTZ NOT NULL DEFAULT NOW(),
                processed_at TIMESTAMPTZ NULL,
                attempts     INTEGER NOT NULL DEFAULT 0,
                last_error   TEXT NULL
             );

             CREATE INDEX idx_inbox_pending

 11. Transaction Pattern
 When a business write emits an event, write both records in the same database transaction.
            BEGIN;

            INSERT INTO invoice (...);

            INSERT INTO messaging.outbox_event (
               event_id,
               topic,
               message_key,
               envelope
            ) VALUES (
               'billing:invoice:inv_01HX:evt_01HY',
               'sophix.billing.invoice.issued',
               'billing:invoice:inv_01HX',
               '{...}'::jsonb
            );

            COMMIT;

 If the transaction commits, the event is durable even if Kafka is unavailable.


 12. Read Replica Usage
 Use replica reads only for queries that tolerate staleness.

 Good candidates:

   - Reporting pages.

   - Admin dashboards.

   - Reconciliation previews.

   - Historical invoice lists.

 Do not use replicas for:

   - Payment posting.

   - Wallet debit/credit.

   - Subscription status commit.

   - Workflow state transition.

   - Idempotency checks.

 Example read-only datasource:
            spring:
              datasource-replica:
                url: jdbc:postgresql://pgbouncer-c-replica.sophix.internal:6432/billing_ro

  Signal                                                         Alert threshold

  Replication lag, async clusters                                More than 5 seconds

  Replication lag, sync cluster                                  More than 1 second

  PgBouncer pool usage                                           More than 80 percent

  Disk usage                                                     More than 75 percent warning, 90 percent critical

  WAL archive failure                                            Any failure

  Primary unreachable                                            Any failure

  Backup verification                                            Any failure

  Slow query rate                                                Sustained growth

  Pending outbox rows older than 1 minute                        Any sustained count

  Pending inbox rows older than 5 minutes                        Any sustained count




 15. Medium Budget Infrastructure
 This section defines the recommended starting infrastructure for a medium deployment with limited budget. The sizing is
 conservative, but the topology remains six PostgreSQL nodes because the database layer is critical.

 15.1 Target vs Budget Phase
 Required production architecture:
            Cluster A: primary + replica
            Cluster B: primary + replica
            Cluster C: primary + replica

 Medium budget means smaller node dimensions, not fewer database nodes.

 Do not run one large shared PostgreSQL cluster for all SOPHIX databases in production. That saves servers but creates one
 blast radius for catalog, capture, billing, subscription, fulfillment, and workflow.

 Placement rules:

   - Do not place a primary and its replica on the same physical host.

   - Do not place all primaries on the same physical host.

   - If using virtualization, anti-affinity must keep each pair split across hosts.

   - Place Cluster C on the best disks available.

   - PgBouncer may be co-located in the first phase, but dedicated PgBouncer nodes are preferred once traffic grows.

   - Backups must leave the DB node. A local backup directory is only staging, not final backup storage.

 15.3 Recommended OS
 Use one operator-standard Linux distribution:

  OS                                                                    Recommendation

  Ubuntu Server 22.04 LTS or 24.04 LTS                                  Recommended default for small/medium teams. Good package availability and
                                                                        operational familiarity.

  Rocky Linux 9 / RHEL 9                                                Use if the operator standardizes on RHEL-family systems.


 OS baseline:

   - 64-bit minimal server install.

   - No desktop packages.

   - Security patching through unattended upgrades or the operator patch window.

   - chrony or equivalent NTP enabled.

   - SSH restricted to admin VPN/network.

   - Host firewall enabled.

   - PostgreSQL version standardized across all DB nodes in the deployment.

   - Same OS and PostgreSQL minor version on primary and replica.

 Use SSD for Cluster AB and SSD/NVMe for Cluster C.

 Filesystem:

 16. AWS Deployment Recommendations
 This section applies only when deploying the database foundation on AWS. The logical requirement remains the same: three
 separated PostgreSQL clusters, each with high availability.

 16.1 Recommended AWS Shape
 Preferred managed option:

  SOPHIX cluster                              AWS service                                       Deployment

  Cluster A                                   Amazon RDS for PostgreSQL                         Multi-AZ

  Cluster B                                   Amazon RDS for PostgreSQL                         Multi-AZ

  Cluster C                                   Amazon RDS for PostgreSQL                         Multi-AZ, highest class/storage priority


 Use three separate RDS instances or Multi-AZ DB clusters, not one shared database instance with all databases. Separation
 keeps the same blast-radius boundaries as the SOPHIX architecture.

  Component                                   AWS service                                       Recommendation

                                                                                                allows

 16.3 RDS Multi-AZ Choice
 AWS has multiple Multi-AZ deployment shapes. Choose deliberately:

  Option                                                              Use when

  Multi-AZ DB instance deployment                                     Good default for budget-conscious production HA. Standby is for failover, not
                                                                      normal reads.

  Multi-AZ DB cluster deployment                                      Use when lower write latency and readable standbys are important, and the
                                                                      region/engine version supports it. Usually costs more.


 For SOPHIX medium start:

   - Cluster A: Multi-AZ DB instance is enough.

   - Cluster B: Multi-AZ DB instance is enough.

   - Cluster C: evaluate Multi-AZ DB cluster if billing/cycle-close load requires readable standbys or lower write latency.

 16.4 PgBouncer on AWS
 RDS does not replace PgBouncer for application connection pooling.

 Recommended:
           2 x small EC2 instances for PgBouncer
           Instance: t4g.small/t3.small minimum, t4g.medium preferred
           Placement: private app subnets across 2 AZs
           Front: internal Network Load Balancer or Route53 failover

 Alternative:

   - Use RDS Proxy for some application pools if it fits the stack.

   - Still document and test transaction-pooling behavior before replacing PgBouncer.

 16.6 Backups and DR on AWS
 Minimum:

   - Enable automated RDS backups.

   - Retain backups for at least 7 days; 30 days preferred for Cluster C.

   - Enable deletion protection for production RDS instances.

   - Take manual snapshots before major migrations.

   - Copy critical snapshots to another AWS Region if disaster recovery requires it.

   - Store PostgreSQL logical dumps for selected critical catalogs if the ops process requires human-readable restore artifacts.

 For self-managed EC2 PostgreSQL:

   - Archive WAL to S3.

   - Take daily base backups.

   - Test point-in-time restore.

   - Do not rely only on EBS snapshots without PostgreSQL-aware backup discipline.
