 1. Purpose
 This document updates the older process-to-module map so it matches the finalized SOPHIX DD set.

 The map answers four questions for implementers:

   1. Which module owns the process?

   2. Which modules participate?

   3. Which runtime mechanisms are used?

   4. Which DD should a developer open for implementation details?

 Owner means the module that owns the authoritative state or drives the workflow. Participant means a module that provides
 an API, event consumer, worker, user task, reference data, or external side effect.


 2. Reading Rules
   - A DD file is not automatically a separate pod or service.

   - A worker-topic name is not a deployment name. It is a Camunda external-task topic.

   - One worker app may handle many low-volume topics if metrics and retries remain visible per topic.

   - Commands use REST/internal APIs. Facts use Kafka events.

   - Source-of-truth reads come from owning APIs or approved client wrappers, not cross-module SQL.

   - Redis/read-through cache can speed reference reads, but command flows must be able to fall back to the source API.

   - Modules do not communicate all-to-all. Each process has one owner; participants are called only when the process needs
     their authoritative data or side effect.

   - Reporting dashboards and exports use REP-01, not live fan-out to operational modules.

   - Dense frontend read screens may use a BFF/read aggregator, but the aggregator must not own business state.

 13. Implementation Sequence
 Recommended dependency order:

   1. Foundations.

   2. ILM Customer Service and catalog/config capabilities.

   3. SUB-LM.

   4. SUB-WF framework and worker catalog.

   5. Billing payment/charging/invoice basics.

   6. WO framework and EM registry.

   7. OSR stock/equipment instance basics.

   8. FUL-02 order capture and FUL service execution flows.

   9. Subscription lifecycle flows.

   10. Subscription MACD flows.

   11. TCK Ticketing before final Backoffice CRM/ticketing delivery, because support cases may create WOs and must appear
     in Customer 360.

   12. Billing cycle close, dunning, wallet, tax recovery, operational refinements.

   13. NOT/ICN integrations should be started early and hardened throughout, because every workflow eventually depends on
     notification.

   14. PAY-GW, PROV-INT, MED/RAT, OSR procurement/audit, ASR flows, CVM, REP-01, and USSD according to the first
     implementation wave.


 14. What To Ignore From The Old Map
 The older process map should not be used for:

   - assigning customer ownership to billing;

   - treating onboarding, field-ops, inventory, or homepass as the final module boundaries;

   - treating one worker topic as one deployment;

   - adding business logic into gateway/adapters;

   - bypassing ILM, SUB-LM, BIL, WO, OSR, or catalog APIs with cross-database SQL.
