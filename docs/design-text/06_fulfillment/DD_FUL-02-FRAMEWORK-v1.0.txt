 2. Implementation Scope
 This DD should be implemented as part of the owning SOPHIX capability, not as an isolated service unless the deployment
 architecture explicitly separates that capability.

 Implement this DD with these rules:

   - Use the owning module APIs/repositories for authoritative writes.

   - Use approved internal APIs/client wrappers when reading another module's data.

   - Do not query another module's database tables directly from business flow code.

   - Treat worker names as logical Camunda external-task topics, not separate deployments.

   - One worker application may handle multiple topics, but metrics, retries, and logs must remain visible per topic.

   - Emit success events only after the authoritative state commit succeeds.

   - Use outbox publishing for Kafka events.

 1.8 BPMN snippet — Cancellation as interrupting boundary
 Order cancellation can come at any phase. The BPMN models this with an interrupting boundary message event on the
 top-level subprocess:
          <bpmn:subProcess id="order-main-flow">
            <bpmn:startEvent id="main-start" />
            <!-- all the order tasks and gateways -->
            <bpmn:endEvent id="main-end" />
          </bpmn:subProcess>

          <bpmn:boundaryEvent id="cancel-requested" name="Cancellation Requested"
                              attachedToRef="order-main-flow"
                              cancelActivity="true">
            <bpmn:outgoing>flow-cancel-to-cascade</bpmn:outgoing>
            <bpmn:messageEventDefinition messageRef="OrderCancellationRequestedMessage" />
          </bpmn:boundaryEvent>

          <bpmn:serviceTask id="cascade-cancellation"
                            camunda:type="external"
                            camunda:topic="order-cascade-cancellation" />

          <bpmn:message id="OrderCancellationRequestedMessage" name="OrderCancellationRequested" />

 POST /api/orders/{id}/cancel correlates OrderCancellationRequested; the boundary interrupts whatever
 subprocess was doing and routes to order-cascade-cancellation (owned by STEP-CANCELLATION). Works
 regardless of which step the order was at.

 2. Per-operator BPMN composition
 One BPMN per operator deployment. Files live in
 modules/fulfillment-order-capture/src/main/resources/workflows/. Naming convention:
 OrderCapture_{OPERATOR_CODE}.bpmn.

 v1.0 ships: OrderCapture_WIK.bpmn, OrderCapture_WUG.bpmn, OrderCapture_WTZ.bpmn,
 OrderCapture_YASSN.bpmn.

 Each operator's BPMN composes workers in any sequence, omits workers it doesn't need, defines its own user tasks and
 message catches. Workers are primitives owned by step satellites; the BPMN orchestrates. Adding a new operator: drop the
 BPMN file, add a ful_02_config row, configure Drools, configure candidate groups in FOUNDATION_AUTH. Zero new
 worker code in the common case.

 Gateway decisions needing operator-specific logic are evaluated by Drools: a worker preceding the gateway calls Drools,
 sets a process variable (e.g., payFirstRequired), the BPMN gateway routes on the variable. Keeps BPMN free of
 operator-specific JUEL.

 Camunda's deployment versioning: in-flight instances complete on the version they started on; new instances use the latest.
 BPMN bug fix never disrupts in-flight orders.

 User tasks across all step satellites use the HTTP connector pattern from §1.6, POSTing to FUL-02's
 NotificationHandlerResource. One endpoint per task type, but a shared contract.

 Endpoint pattern: POST /api/notify/{notification-type} where notification-type is set by each step

 4. Phase projection
 customer_order.current_phase is a coarse projection of Camunda's current_activity_id via
 ful_02_config.activity_phase_map (per-operator). The phase enum is the UNION across operators.

 PhaseProjector (Camunda history listener) subscribes to Camunda's history stream, on each activity transition updates
 customer_order.current_phase + customer_order.current_activity_id, appends to
 customer_order_phase_history.

 Unmapped activities → IN_PROGRESS_UNCATEGORIZED + emit warning event
 sophix.orders.unmapped-activity-warning for ops.

 Projection is for UI / analytics / customer-read. Camunda is the source of truth for runtime state — any consumer needing
 fine-grained activity-level state queries Camunda directly via GET /engine-rest/process-instance/{id}.
