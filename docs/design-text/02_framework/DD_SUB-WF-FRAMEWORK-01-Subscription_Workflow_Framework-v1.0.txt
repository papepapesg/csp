 DD_SUB-WF-FRAMEWORK-01 - Subscription Workflow
 Framework
 Developer implementation guide: DD_SUB-WF-FRAMEWORK-01-DEV_IMPL_GUIDE-v1.0.md.

 MVP simplification baseline: implement the framework once, then phase operation flows. First stabilize activation and
 revenue-critical operations; add pause/resume/terminate and dunning suspension next; implement
 upgrade/downgrade/relocation/migration after the core activation/payment/fulfillment path is stable.


 1. Purpose
 SUB-WF-FRAMEWORK-01 defines the shared orchestration layer used by all subscription lifecycle operations.

 A subscription operation is one state-changing or restriction-changing workflow execution against a subscription, for example:
          activate subscription
          pause subscription
          resume subscription
          upgrade package
          downgrade package
          relocate HomePass
          migrate package + HomePass
          apply/remove restriction
          suspend for non-payment
          terminate subscription

 This DD gives developers the common implementation contract used by those operations:

   - How an operation is recorded.

   - How only one unsafe operation runs per subscription.

   - How idempotency is enforced.

   - How Camunda process instances are correlated with database rows.

   - How framework lifecycle events are emitted through Kafka.

   - How operator-specific BPMN and configuration are selected.

 The operation-specific DDs own the actual business flow for each verb. This framework owns the shared plumbing.


 2. Ownership
 This DD owns:

   - subscription_operation, the audit and execution anchor for every subscription operation.

   - kafka_outbox, the transactional outbox used by workflow components.

   - subscription_operation_config, the per-operator configuration for operation orchestration.

   - Framework REST APIs for operation status, cancel, in-flight lookup, and operation history.

   - Framework Kafka events: started, completed, failed, and cancelled.

   - Concurrency and idempotency rules used by all operation trigger endpoints.

   - BPMN process-key resolution.

   - Common timeout and cancellation behavior.

 This DD does not own:

   - Subscription master state. See SUB-LM-01.

   - Worker catalog and worker I/O contracts. See DD_SUB-WF-FRAMEWORK-01-WORKERS.

   - BPMN files for each operation. Those belong to operation-specific satellite DDs.

   - Activation, pause, resume, upgrade, downgrade, relocation, migration, restrict, suspend-NP, or terminate business rules.
     Those belong to their satellite DDs.

   - Billing charges, proration, invoices, payments, tax, or wallets. See BIL DDs.

 3. Mental Model
 The framework is the operation ledger and coordinator. It does not know every business rule, but it makes every operation
 observable, cancellable, idempotent, and correlated with Camunda.
            flowchart LR
                Caller[BO UI / API / Scheduler / Dunning] --> Trigger[Satellite Trigger Endpoint]
                Trigger --> FW[SUB-WF Framework]
                FW --> DB[(subscription_operation)]
                FW --> CFG[(subscription_operation_config)]
                FW --> CAM[Camunda BPMN]
                CAM --> Workers[Workflow Workers]
                Workers --> SUBLM[SUB-LM-01 State APIs]
                Workers --> BIL[BIL Modules]
                Workers --> FUL[FUL Modules]
                Workers --> OUTBOX[(kafka_outbox)]
                OUTBOX --> KAFKA[Kafka]

 The expected flow is:

   1. A caller requests an operation through a satellite trigger endpoint.

   2. The trigger endpoint validates auth and request shape.

   3. The framework checks idempotency and concurrency.

   4. The framework creates one subscription_operation row.

   5. The framework starts the configured Camunda BPMN process.

   6. Workers advance the operation and update subscription_operation.current_state.

   7. The operation ends in COMPLETED, FAILED, or CANCELLED.

   8. Framework lifecycle events are emitted through kafka_outbox.

 6. Data Model
 6.1 subscription_operation
 What this table is for:

 subscription_operation is the execution record for one subscription operation. It links the API request, subscription,
 operator, Camunda process instance, current workflow state, final outcome, and audit actor.

 Use this table when:

   - Starting a subscription operation.

   - Checking if a subscription already has an in-flight operation.

   - Returning operation status to UI or API callers.

   - Correlating Camunda process instances with BSS records.

   - Auditing who started an operation and why.

   - Listing operation history for a subscription.

   - Enforcing idempotency for operation trigger endpoints.

 Do not use this table to store operation-specific payloads that only one operation understands. For example, termination
 cooling-off details belong in the termination DD table, not here.

 6.2 kafka_outbox
 What this table is for:

 kafka_outbox stores Kafka messages inside the same database transaction as the business change. A separate
 dispatcher publishes those messages to Kafka.

 Use this table when:

   - An operation changes database state and must emit an event.

   - A worker must guarantee that a database mutation and Kafka event are not separated.

   - A Kafka broker outage should not roll back the business transaction.

   - Failed event delivery needs retry and alerting.

 Do not publish directly to Kafka inside the same code path that writes domain state. Write the outbox row first, commit, and let
 the dispatcher publish asynchronously.
           CREATE TABLE kafka_outbox (
             id                 TEXT PRIMARY KEY,
             topic              TEXT NOT NULL,
             message_key        TEXT NOT NULL,
             event_type         TEXT NOT NULL,
             aggregate_id       TEXT NOT NULL,
             payload            JSONB NOT NULL,




SOPHIX BSS Design Documents                                                                                                                       Page 5
              status             TEXT NOT NULL DEFAULT 'PENDING',
              attempts           INTEGER NOT NULL DEFAULT 0,
              next_attempt_at    TIMESTAMPTZ NOT NULL DEFAULT NOW(),
              last_attempt_at    TIMESTAMPTZ NULL,
              last_error         TEXT NULL,

              created_at         TIMESTAMPTZ NOT NULL DEFAULT NOW(),
              published_at       TIMESTAMPTZ NULL,

              CHECK (status IN ('PENDING', 'PUBLISHED', 'FAILED'))

 7. Business Rules
  Rule                                                             Description

  R-SUB-WF-FW-1                                                    At most one in-flight state-affecting operation may run for one
                                                                   (operator_code, subscription_id).

  R-SUB-WF-FW-2                                                    One RESTRICT may run concurrently with one non-RESTRICT operation only if
                                                                   the satellite DD confirms it does not change status_code. Two RESTRICT
                                                                   operations must not run concurrently on the same subscription.

  R-SUB-WF-FW-3                                                    TERMINATE may interrupt an in-flight non-TERMINATE operation by sending a
                                                                   Camunda cancel message to the old operation, waiting for cancellation
                                                                   handling, then starting termination.

  R-SUB-WF-FW-4                                                    Idempotency is enforced on (operator_code, idempotency_key) for
                                                                   every trigger endpoint.

  R-SUB-WF-FW-5                                                    Reusing the same idempotency key with a different canonical request hash
                                                                   returns 409 IDEMPOTENCY_KEY_REUSED_WITH_DIFFERENT_REQUEST.

  R-SUB-WF-FW-6                                                    Trigger endpoints are asynchronous by default and return 202 Accepted with
                                                                   operation_id.

  R-SUB-WF-FW-7                                                    The BPMN process key is resolved from
                                                                   subscription_operation_config. Non-production callers may override it
                                                                   only when explicitly allowed by environment configuration.

  R-SUB-WF-FW-8                                                    The framework must set bpmn_process_instance_id as soon as Camunda
                                                                   returns it.

  R-SUB-WF-FW-9                                                    Operation timeout is enforced by BPMN boundary timer using
                                                                   operation_timeout_seconds.

  R-SUB-WF-FW-10                                                   On timeout, the operation enters REVERTING, then ends in FAILED with
                                                                   failure_reason_code = OPERATION_TIMEOUT.

  R-SUB-WF-FW-11                                                   Workers must be operator-agnostic. Operator-specific differences belong in
                                                                   BPMN, Drools, configuration, and auth groups.

  R-SUB-WF-FW-12                                                   Domain mutations and Kafka events must use the outbox pattern.

  R-SUB-WF-FW-13                                                   Notification failure must not fail a subscription operation. Notification retries
                                                                   belong to NOT-01.

  R-SUB-WF-FW-14                                                   Every satellite trigger endpoint must enforce auth before it calls the framework
                                                                   start logic. Drools may re-check authorization for defense in depth.

 12. Implementation Notes
 12.1 Trigger Endpoint Sequence
 Every satellite trigger endpoint should follow the same sequence.

   1. Authenticate the caller.

   2. Resolve operator_code, actor user ID, and actor role from auth context.

   3. Validate request fields.

   4. Validate the actor role is allowed for this operation kind.

   5. Canonicalize the request body.

   6. Hash the canonical request body.

   7. Start a database transaction.

   8. Lock the subscription row in SUB-LM using SELECT ... FOR UPDATE or the local repository equivalent.

   9. Load subscription_operation_config for (operator_code, operation_kind).

   10. Reject if config is missing or disabled.

   11. Check idempotency by (operator_code, idempotency_key).

   12. Check for existing in-flight operation.

   13. If allowed, insert subscription_operation in INITIATED.

   14. Insert SubscriptionOperationStarted into kafka_outbox.

   15. Commit the database transaction.

   16. Start the Camunda BPMN process.

   17. Save bpmn_process_instance_id.

   18. Return 202 Accepted.

 Do not call Camunda while holding a row lock on subscription. Keep the lock only long enough to reserve the operation.

 12.2 Idempotency
 Idempotency prevents network retries from starting duplicate operations.

 Use subscription_operation itself as the idempotency record:
           CREATE UNIQUE INDEX uq_subop_idempotency


SOPHIX BSS Design Documents                                                                                                      Page 11
               ON subscription_operation (operator_code, idempotency_key);

 Implementation behavior:

   1. Compute idempotency_request_hash from canonical JSON.

   2. Try to insert the operation row.

   3. If insert succeeds, this request owns the operation.

   4. If insert fails because uq_subop_idempotency already exists, load the existing row.

   5. If the existing hash differs, return 409 IDEMPOTENCY_KEY_REUSED_WITH_DIFFERENT_REQUEST.

   6. If the existing hash matches, return the existing operation_id, current_state, and final_state.

 Important: operation insert can also fail because an in-flight-operation unique index was violated. That is not an idempotency
 result. In that case, return 409 OPERATION_IN_PROGRESS with the current operation details.

 Example pseudocode:
           OperationStartResult start(StartOperationCommand cmd) {
               String hash = hash(canonicalJson(cmd.requestPayload()));

                 try {
                     Operation op = insertOperation(cmd, hash);
                     return startNewOperation(op);
                 } catch (UniqueConstraintViolation e) {
                     if (!e.constraintName().equals("uq_subop_idempotency")) {
                         throw operationInProgress(cmd.operatorCode(), cmd.subscriptionId());
                     }

                     Operation existing = operationRepo.findByIdempotencyKey(
                         cmd.operatorCode(),
                         cmd.idempotencyKey()
                     );

                     if (!existing.idempotencyRequestHash().equals(hash)) {
                         throw conflict("IDEMPOTENCY_KEY_REUSED_WITH_DIFFERENT_REQUEST");
                     }

                     return resultFromExistingOperation(existing);
                 }
           }

 Do not make idempotency optional. BO UI, dunning jobs, and schedulers will retry after timeouts.

 12.3 In-Flight Operation Check
 Use the partial unique index as the database guarantee:
           CREATE UNIQUE INDEX uq_subop_in_flight_state_changing
             ON subscription_operation (operator_code, subscription_id)
             WHERE final_state IS NULL AND operation_kind <> 'RESTRICT';

           CREATE UNIQUE INDEX uq_subop_in_flight_restrict
             ON subscription_operation (operator_code, subscription_id)
             WHERE final_state IS NULL AND operation_kind = 'RESTRICT';

 Application code should still check first so it can return a good error:
           {
               "code": "OPERATION_IN_PROGRESS",
               "currentOperationId": "subop_01HZ_NJERI_SUSPNP",
               "currentOperationKind": "SUSPEND_NP",
               "currentState": "AWAITING_FULFILLMENT_RESPONSE"
           }

 The indexes protect against race conditions where two requests pass the application check at the same time. They allow at
 most one state-changing operation and at most one RESTRICT operation per subscription. This gives the satellite DD room to
 allow a restriction change during another operation, while still preventing two restriction updates from overwriting each other.

 12.4 TERMINATE Interruption
 TERMINATE is special because the business may require termination even if another operation is running.

 Recommended sequence:

   1. Lock the subscription.

   2. Find the current in-flight operation.

SOPHIX BSS Design Documents                                                                                                Page 12
   3. If no operation exists, start termination normally.

   4. If current operation is TERMINATE, return OPERATION_IN_PROGRESS.

   5. If current operation is not TERMINATE, send Camunda message external-cancel-requested to the existing
     process.

   6. Existing BPMN moves to REVERTING.

   7. Existing BPMN marks itself CANCELLED.

   8. Start the new termination operation.

 Do not mark the old operation CANCELLED directly unless Camunda cannot be reached and the operational runbook explicitly
 allows manual repair. The BPMN owns compensation.

 12.5 Starting Camunda Safely
 The operation row is created before Camunda starts. That means a small failure window exists:
           DB commit succeeds, but Camunda start fails

 Handle this explicitly:

   - If Camunda start succeeds, update bpmn_process_instance_id.

   - If Camunda start fails, mark the operation FAILED with failure_reason_code = BPMN_START_FAILED.

   - Insert SubscriptionOperationFailed into kafka_outbox.

   - Return 502 BPMN_START_FAILED to the caller.

 Do not leave operations stuck forever in INITIATED without a process instance. Add a scheduled repair job that finds old
 INITIATED rows where bpmn_process_instance_id IS NULL.

 12.6 Updating Operation State
 Workers update subscription_operation.current_state as they pass major BPMN milestones.

 Example:
           UPDATE subscription_operation
           SET current_state = 'FULFILLMENT_CALL',
               updated_at = NOW()
           WHERE operation_id = :operationId
             AND final_state IS NULL;

 Rules:

   - Never update current_state after final_state is set.

   - Only use framework vocabulary values.

   - Keep operation-specific detail in satellite tables or Camunda variables.

 12.7 Completing an Operation
 Completion must be atomic with outbox insert.
           UPDATE subscription_operation
           SET current_state = 'COMPLETED',
               final_state = 'COMPLETED',
               completed_at = NOW(),
               duration_ms = EXTRACT(EPOCH FROM (NOW() - started_at)) * 1000,
               updated_at = NOW()
           WHERE operation_id = :operationId
             AND final_state IS NULL;

 In the same transaction, insert SubscriptionOperationCompleted into kafka_outbox.

 If the update affects zero rows, the operation is already terminal. The worker should not emit a duplicate completion event.

 12.8 Failing an Operation
 Failure must also be atomic with outbox insert.

 Required fields:

   - current_state = 'FAILED'

SOPHIX BSS Design Documents                                                                                               Page 13
   - final_state = 'FAILED'

   - failure_reason_code

   - failure_reason_detail

   - completed_at

   - duration_ms

 Keep failure_reason_detail short. It is for support and audit, not raw exception storage.

 12.9 Cancelling an Operation
 Cancel API should not directly modify subscription state. It should tell Camunda to cancel and let BPMN compensation run.

 Cancel API sequence:

   1. Authenticate cancel actor.

   2. Load operation.

   3. Reject if operation is terminal.

   4. Send Camunda message external-cancel-requested with cancel reason and actor.

   5. Return accepted/success response.

   6. BPMN compensates and marks operation CANCELLED.

 12.10 Outbox Dispatcher
 The dispatcher reads PENDING rows ordered by created_at.

 Suggested behavior:

   1. Fetch a small batch, for example 100 rows.

   2. Lock rows with FOR UPDATE SKIP LOCKED.

   3. Publish each row to Kafka.

   4. If publish succeeds, set status = 'PUBLISHED' and published_at = NOW().

   5. If publish fails, increment attempts, store last_error, and set next_attempt_at using backoff.

   6. After 10 failures, set status = 'FAILED' and raise an ICN-01 alert.

 Example query:
           SELECT *
           FROM kafka_outbox
           WHERE status = 'PENDING'
             AND next_attempt_at <= NOW()
           ORDER BY created_at
           LIMIT 100
           FOR UPDATE SKIP LOCKED;


 12.11 Transaction Boundaries
 Good transaction:
           begin
             lock subscription
             insert subscription_operation
             insert kafka_outbox started event
           commit

           start Camunda outside the lock
           update operation with process instance id

 Bad transaction:
           begin
             lock subscription
             call Camunda
             call billing
             call fulfillment
             insert operation
           commit

 13. Infrastructure Recommendations
 13.1 On-Prem Medium Deployment
 Deployment unit clarification:

   - SUB-LM-01 from the previous DD is the Subscription Lifecycle Management service/module. It owns the subscription
     master table and low-level subscription APIs.

   - SUB-WF-FRAMEWORK-01 in this DD is the Subscription Workflow Orchestration service/module. It owns operation rows,
     operation status APIs, cancel APIs, idempotency/concurrency checks, Camunda process start, and outbox dispatch.

   - In a microservice deployment, these can be two separate services: subscription-management-service for SUB-LM
      and subscription-workflow-service for SUB-WF.

   - In a budget-conscious deployment, they may run inside the same application artifact or the same Kubernetes deployment,
      but the logical ownership must remain separate in code packages, database migrations, and API routing.

 So when this section says "SUB-WF service", it means the operation orchestration module from this DD, not the SUB-LM
 management module from the previous DD.
