 2. How To Read A Module
 For each capability, read in this order:

   1. Owning DD.

   2. Its DEV_IMPL_GUIDE.

   3. Upstream dependencies listed in the DD.

   4. Downstream consumers/events listed in the DD.

   5. Related frontend DD, if a UI uses it.

   6. Relevant E2E scenarios.

 Do not start implementation from a sample payload alone. Samples explain behavior, but ownership, idempotency, events,
 and state transitions are defined across the DD and guide.

 4. Frontend Reading Order
 Frontend squads read:

   1. FE-APP-00 and its guide.

   2. DD_API-00.

   3. EM-CFG-03.

   4. The target app DD and guide.

   5. DD_CROSS-00 feature rows for the screens they build.

   6. Owning backend module DDs for every command and panel.

 Frontend rule: every command has one owning module API. Every panel lists its read owner. Dense screens lazy-load panels
 and handle partial failure.


 5. Backend Reading Order
 Backend squads read:

   1. DD_INDEX.

   2. DD_CROSS-00.

   3. DD_API-00.

   4. Owning module DD.

   5. Owning module DEV_IMPL_GUIDE.

   6. Related foundation docs: DB, Kafka, cache, Camunda, Drools, file storage.

   7. Upstream/downstream DDs named in cross-DD coordination.

   8. DD_QA-01 tests.

 Backend rule: one module owns each write. Other modules call APIs or consume events; they do not write another module's
 tables.


 6. QA Reading Order
 QA reads:

   1. HLD.

   2. Process map.

   3. DD_QA-01.

   4. DD_CROSS-00.

   5. Owning DD and guide for the feature under test.

   6. Frontend DD if the test includes UI.

 QA should build tests in this order:

   - API contract tests;

   - module integration tests;

   - event replay/idempotency tests;

   - E2E journey tests;

   - frontend smoke tests by role.

 7. DevOps Reading Order
 DevOps reads:

   1. HLD deployment topology.

   2. FOUNDATION_DB.

   3. FOUNDATION_KAFKA.

   4. FOUNDATION_CACHE.

   5. FOUNDATION_CAMUNDA.

   6. FOUNDATION_DROOLS.

   7. FOUNDATION_AUTH.

   8. MVP runtime simplification baseline.

 DevOps rule: deploy capability groups first, not one service per DD. Split later only for throughput, isolation, scaling, release
 independence, or team ownership.


 8. Canonical Warnings
   - DD_EM-02-Contractor_and_Staff_Registry is canonical. The older Team/Agent EM-02 is superseded.

   - ASR DDs are TCK ticket type/workflow satellites, not separate ticketing engines.

   - FA-01/02/03 are one field-audit capability with audit_type.

   - SUB-WF migration owns business operation; FUL-10 owns technical cross-tech fulfillment.

   - REP-01 is mandatory for reporting dashboards and exports.

   - MED/RAT are offline/batch in this design.

   - USSD is a channel adapter, not a business backend.
