 MVP simplification baseline: REP-01 is mandatory for dashboards, exports, and aggregate reporting. First release scope is a
 small mart for revenue, payments, active subscriptions, activations, tickets, work orders, stock summary, and dunning. Do not
 let reporting screens fan out to operational modules for aggregate totals.


 1. Purpose
 This DD defines the reporting backend used by FE-APP-05 Reporting Portal and embedded operational dashboards in
 Backoffice.

 REP-01 prevents reporting screens from directly querying operational module databases. It builds read models/data marts
 from module events, controlled extracts, and approved read APIs.

 4. Architecture
 Recommended medium deployment:
            Module outbox events -> Kafka -> REP ingestion workers -> reporting_staging
                                                               -> aggregate jobs -> reporting_mart
            FE-APP-05 / Backoffice -> REP dashboard APIs -> reporting_mart

 For budget-conscious deployment, REP can start on the same PostgreSQL cluster as other non-critical modules but should
 use a separate database/schema. For production growth, move reporting to a separate read-optimized
 PostgreSQL/warehouse instance.

 8. Security And Privacy
  Rule                                                                        Description

  REP-SEC-1                                                                   FOUNDATION_AUTH roles control dashboard visibility.

  REP-SEC-2                                                                   Exports require explicit permission and audit row.

  REP-SEC-3                                                                   PII fields must be masked unless the user has an approved role.

  REP-SEC-4                                                                   Export files use FOUNDATION_FILE_STORAGE and expire.

  REP-SEC-5                                                                   Report APIs must always scope by operator unless user is explicitly
                                                                              multi-operator.

  REP-SEC-6                                                                   Customer-level drill-down must link back to owning module UI/API; do not
                                                                              expose hidden copied PII.

 11. Infra Recommendation
 Budget-conscious medium deployment:

  Component                                                            Recommendation

  Ingestion worker                                                     2 pods, 1-2 vCPU, 2-4 GB RAM.

  API pods                                                             2 pods, 1-2 vCPU, 2-4 GB RAM.

  Database                                                             Separate reporting DB/schema; start PostgreSQL, partition large fact tables by
                                                                       month.

  Storage                                                              Use file storage for exports.

  Cache                                                                Redis for dashboard payload cache.


 Growth path:

   - move reporting DB to separate managed PostgreSQL/read-optimized warehouse;

   - add columnar store only if PostgreSQL aggregates become insufficient;

   - keep event ingestion idempotent so backfill/replay is possible.


 12. Implementation Notes
 Start with:

   1. Create rep_event_ingestion, rep_daily_metric, rep_dashboard_snapshot, and rep_export_job.

   2. Consume key events from SALES, FUL, BIL, SUB, WO, OSR, TCK.

   3. Implement sales/order/billing/WO/ticket daily metrics first.

   4. Implement dashboard list/detail APIs.

   5. Implement export jobs with file storage.

   6. Add reconciliation jobs for BIL, SUB, WO, TCK.
