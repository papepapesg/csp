 1. Purpose
 SIP-02 defines how SOPHIX moves a package from draft definition to approved, sellable, region/franchise-available,
 suspended, retired, or end-of-life state.

 SIP-01 owns package definition:

   - package code;

   - service composition;

   - base pricing/version records;

   - wallet/tax bindings;

   - target franchises and technical regions at definition/version level.

 SIP-02 owns lifecycle control:

   - validation before package can be launched;

   - configurable approval before launch;

   - activation date and version cutover;

   - per-franchise and per-region availability;

   - temporary suspension;

   - retirement/end-of-life.

 Use SIP-02 when:

   - product team wants to submit a new package for commercial review;

   - a package version must become the current sellable version;

   - package availability differs by franchise or region;

   - a package must be suspended due to commercial, technical, tax, or provisioning issue;

   - a package must stop being sold while existing subscribers remain on it;

   - Backoffice, sales app, order capture, or self-care needs the list of sellable packages.

 Do not use SIP-02 to change package composition. Composition remains SIP-01 and is locked after activation rules defined
 in SIP-01.

 Boundary rules:

   - SIP-02 changes package/package_version lifecycle state through SIP-01 repository/service contracts or same-module
     service boundary.

   - SIP-02 must not directly modify customer subscriptions. Subscription migration or upgrade is handled by SUB/FUL
     workflows.

   - SIP-02 may make a package unavailable for new sales while existing subscribers remain on their current package version.

   - Approval steps are not hardcoded in SIP-02. SIP-02 calls EM-CFG-04. Camunda is used only when the EM-CFG-04 policy
     mode is BPMN.

   - Drools is used for operator-variable launch, readiness, availability, and retirement decisions. Fixed validations remain
     code/database checks.



 3. Lifecycle Overview
               stateDiagram-v2
                 [*] --> DRAFT
                 DRAFT --> READY_FOR_REVIEW: validate ok
                 READY_FOR_REVIEW --> PENDING_APPROVAL: approval required
                 READY_FOR_REVIEW --> APPROVED: auto approved
                 PENDING_APPROVAL --> APPROVED: EM-CFG-04 approved
                 PENDING_APPROVAL --> REJECTED: EM-CFG-04 rejected
                 REJECTED --> DRAFT: revise
                 APPROVED --> SCHEDULED: launch date future
                 APPROVED --> ACTIVE: launch now
                 SCHEDULED --> ACTIVE: activation worker
                 ACTIVE --> SUSPENDED: suspend sales
                 SUSPENDED --> ACTIVE: resume sales
                 ACTIVE --> END_OF_SALE: stop new sales
                 END_OF_SALE --> END_OF_LIFE: no active dependency or approved migration plan
                 END_OF_LIFE --> RETIRED: archival

 Master package status in SIP-01 is the high-level state. SIP-02 also manages more granular per-version and per-availability
 state.

   - tax group is valid in PLM-CFG-02;

   - wallet configuration is valid in PLM-CFG-03;

   - billing event compatibility exists in BIL-CFG-01;

   - requested availability matches package target franchise/region restrictions;

 6.4 Approval Outcome Callback
          POST /internal/package-launch-plans/{launch_plan_id}/approval-outcome
          Content-Type: application/json

          {
              "approvalRequestId": "apr-plp-001",
              "outcome": "APPROVED",
              "decisionComment": "Approved for WIK Nairobi launch."
          }

 If approved, SIP-02 moves the plan to APPROVED or SCHEDULED. If rejected, status becomes REJECTED.

 6.5 Activate Launch Plan
          POST /api/package-launch-plans/{launch_plan_id}/activate

 Manual activation is allowed only if:

   - launch is approved;

   - requested launch time is now or past;

   - final validation has no FAIL;

   - package version has not been superseded or cancelled.

 Scheduled activation should be performed by a worker.

                                                and version exist in SIP-01.

  R-SIP-02-02                                   Package composition services must be active in        Prevent unsellable package.
                                                PLM-CFG-01.

  R-SIP-02-04                                   Availability scope must be inside package version     Commercial control.

 8. Rule Engine Guidance
 Use Drools for configurable launch and availability decisions:

  Rule file                                                            Purpose

  package-launch-readiness.drl                                         Adds operator-specific validation, warnings, and hard stops before approval.

  package-launch-approval.drl                                          Decides approval policy code or auto-approval context before EM-CFG-04 call.

  package-availability.drl                                             Controls channel/franchise/region availability where policy is not a simple DB
                                                                       filter.

  package-retirement-policy.drl                                        Decides whether end-of-sale/end-of-life requires approval or migration plan.


 Example:
              package com.sophix.catalog.package_lifecycle

              rule "First launch to sales app requires commercial approval"
              when
                $p : PackageLaunchFact(launchType == "FIRST_LAUNCH", channelCodes contains "SALES_APP")
                $d : PackageLaunchDecision()
              then
                $d.setApprovalRequired(true);
                $d.setApprovalPolicyCode("PACKAGE_LAUNCH_COMMERCIAL");
                $d.addReason("FIRST_LAUNCH_SALES_APP");
              end

 Fixed checks such as package existence, version existence, required fields, and idempotency remain normal application
 validation.

 12. Infrastructure Recommendations
 For a medium budget deployment, SIP-02 should run inside the catalog/commercial API deployment together with
 SIP-01/SIP-03/SIP-04/SIP-05 unless load proves otherwise.

  Component                                                                      Recommendation

  API                                                                            Same catalog API service exposes /api/package-launch-plans,
                                                                                 /api/packages/available, and retirement APIs.

  Database                                                                       Catalog schema in PostgreSQL.

  Cache                                                                          Redis for package availability read model, invalidated by lifecycle events.

  Workers                                                                        Shared catalog worker deployment.

  Rules                                                                          Use existing Drools/KIE foundation.

  Approval                                                                       Use EM-CFG-04 and existing Camunda only for BPMN-backed policies.

 15. Acceptance Criteria
   - SIP-02 launch plan, check, availability, cutover, lifecycle event, and retirement tables exist.

   - Package launch validates SIP-01, PLM-CFG, and BIL-CFG dependencies.

   - Launch approval is routed through EM-CFG-04; SIP-02 does not hardcode approval steps.

   - Drools rule files exist for configurable readiness, approval, availability, and retirement policy.

   - Activation updates package/version current state for new sales without changing existing subscriptions.

   - GET /api/packages/available is usable by Backoffice, sales app, order capture, and self-care.

   - Lifecycle and availability events are emitted through outbox.

   - Tests cover validation, approval callbacks, activation, suspension, end-of-sale, and version cutover.
