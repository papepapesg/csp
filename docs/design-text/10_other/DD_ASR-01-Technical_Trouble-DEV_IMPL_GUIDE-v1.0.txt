 1. How To Read This Guide
 This guide follows the flow as it executes.

 Technical trouble is a TCK ticket flow. Do not create a separate ASR ticket table or lifecycle engine. Create a
 TECHNICAL_SUPPORT ticket in TCK, then apply ASR diagnostic, outage, WO, and compensation rules.

 5. Step 4 - Customer Reports Trouble
 Backoffice or self-care creates a TCK ticket.
          POST /api/tickets

          Content-Type: application/json

          {
               "operatorCode": "WIK",
               "typeCode": "TECHNICAL_SUPPORT",
               "categoryCode": "NO_INTERNET",
               "sourceChannel": "CALL_CENTER",
               "customerId": "CUS-100045",

               "subscriptionId": "SUB-700045",
               "subject": "Customer reports no internet",
               "description": "Customer says ONT has LOS light blinking after overnight rain.",

 Expected TCK result:
          {
               "ticketId": "tck-20260603-000001",

 9. Step 8 - Remote Fix Path
 Some technical trouble can be resolved without WO.

 Examples:

   - customer power-cycles router;

   - CSR confirms wrong Wi-Fi network;

   - NOC re-applies provisioning profile through PROV-INT force-sync;

   - voice registration refreshed.

 If remote fix succeeds, call TCK resolve:
           POST /api/tickets/tck-20260603-000001/resolve
           Content-Type: application/json

           {
               "resolutionCode": "REMOTE_FIX",
               "resolutionSummary": "Customer rebooted router and service restored. ONT online confirmed.",
               "customerVisibleSummary": "Your service is now restored."
           }

 Ticket moves to RESOLVED or UNDER_REVIEW depending category policy.

 TCK already consumes WO events. ASR adds interpretation for technical trouble.

 Example event:
             {
                 "eventType": "WorkOrderFinalized",
                 "workOrderId": "wo-20260603-000045",
                 "originatingContextType": "TICKET",
                 "originatingContextId": "tck-20260603-000001",
                 "finalReasonCode": "FIXED_ON_SITE",
                 "findings": {
                   "rootCause": "DROP_CABLE_CUT",
                   "solution": "Replaced drop cable",
                   "serviceRestored": true
                 }
             }

 ASR action:

  WO final reason                                                   Ticket update

  FIXED_ON_SITE                                                     UNDER_REVIEW or RESOLVED.

  CUSTOMER_NOT_AVAILABLE                                            WAITING_CUSTOMER.

  NETWORK_ESCALATION_REQUIRED                                       WAITING_INTERNAL, queue NOC_ESCALATION.

  NO_FAULT_FOUND                                                    UNDER_REVIEW.

  CPE_REPLACED                                                      UNDER_REVIEW or RESOLVED, link equipment if provided.


 Always add a ticket timeline entry with customer-safe summary.



 12. Step 11 - Detect Repeat Fault
 When creating or reopening a technical trouble ticket, search recent resolved tickets:
             select ticket_id
             from ticket
             where operator_code = 'WIK'
               and subscription_id = 'SUB-700045'
               and type_code = 'TECHNICAL_SUPPORT'
               and category_code in ('NO_INTERNET', 'INTERMITTENT_CONNECTION')
               and status_code in ('RESOLVED', 'CLOSED')
               and resolved_at >= now() - interval '30 days';

 If found:

   - set category/subcategory or tag as REPEAT_FAULT;

   - raise priority if policy says so;

   - route to TECH_SUPPORT_L2 or NOC;

 15. Suggested Worker Commands
 These run inside the TCK/ASR worker set and can be consolidated.
           asr:detect-repeat-faults
           asr:sync-outage-status
           asr:consume-wo-events
           asr:sla-escalation-scan
           asr:compensation-policy-scan

 Recommended schedule:

  Command                                                        Frequency

  asr:detect-repeat-faults                                       On ticket create/reopen, plus daily audit.

  asr:sync-outage-status                                         Every 5 minutes if outage source exists.

  asr:consume-wo-events                                          Continuous Kafka consumer.

  asr:sla-escalation-scan                                        Every 5 minutes.

  asr:compensation-policy-scan                                   Daily or manual.




 16. Error Codes
  Error code                                                     Meaning

  ASR_CATEGORY_NOT_TECHNICAL                                     Ticket category is not valid for ASR-01.

  ASR_DIAGNOSTIC_PROFILE_NOT_FOUND                               Category has no active diagnostic profile.

  ASR_REQUIRED_DIAGNOSTIC_MISSING                                WO creation attempted before required checks.

  ASR_OUTAGE_ALREADY_LINKED                                      Ticket already linked to same outage.

  ASR_WO_POLICY_BLOCKS_CREATION                                  Category does not allow WO.

  ASR_ACTIVE_WO_ALREADY_EXISTS                                   Ticket already has active support WO.

  ASR_COMPENSATION_NOT_ELIGIBLE                                  Policy does not allow compensation recommendation.

  ASR_ADJUSTMENT_REQUEST_FAILED                                  BIL adjustment request failed.




 17. Minimum Implementation Order
 Build in this order:

   1. Seed TCK technical-support categories.

   2. Add ASR config migrations.

   3. Seed diagnostic profiles.

   4. Implement ASR guidance API.

   5. Implement diagnostic capture API.

   6. Implement known outage link API.

   7. Patch TCK create-WO validation with ASR required diagnostic rules.

   8. Implement WO event interpretation for technical trouble.

   9. Implement repeat-fault detection.

   10. Implement compensation recommendation.

   11. Integrate BIL-02-ADJ-01 adjustment request.

   12. Emit ASR business events.

   13. Patch Backoffice screens.

   14. Add E2E tests.

 18. Test Scenarios
 18.1 No Internet With WO
 Input:

   - NO_INTERNET ticket.

   - Diagnostics captured.

   - ONT offline.

 Expected:

   - Support WO can be created.

   - Ticket becomes WAITING_WORK_ORDER.

   - WO finalization resolves or reviews ticket.

 18.2 Missing Diagnostics Blocks WO
 Input:

   - NO_INTERNET ticket.

   - No diagnostic results.

   - User attempts create WO.

 Expected:

   - API returns ASR_REQUIRED_DIAGNOSTIC_MISSING.

   - No WO created.

 18.3 Known Outage
 Input:

   - Outage check finds outage id.

 Expected:

   - Ticket linked to outage.

   - Ticket routed to NOC/outage queue.

   - No individual support WO by default.

 18.4 Repeat Fault
 Input:

   - Same subscription had resolved NO_INTERNET ticket 10 days ago.

 Expected:

   - New ticket flagged or recategorized as REPEAT_FAULT.

   - Priority/queue escalated by policy.

 18.5 Compensation Recommendation
 Input:

   - WO confirms operator fault and service restored after outage threshold.

 Expected:

   - ASR compensation recommendation created.

   - BIL adjustment request can be created.

   - ASR does not directly credit wallet or invoice.

 19. Developer Checklist
 Before marking ASR-01 complete:

   - No separate ASR ticket lifecycle table exists.

   - Technical trouble uses TCK TECHNICAL_SUPPORT.

   - Required diagnostics gate WO creation.

   - TCK remains source of truth for ticket status.

   - WO remains source of truth for field execution.

   - Compensation calls BIL adjustment workflow, not wallet/invoice tables.

   - Customer-safe summaries are separated from internal diagnostics.

   - ASR events project to customer timeline.
