 1. Purpose
 This DD defines the BSS Backoffice Web App.

 The Backoffice is the main internal staff application for SOPHIX V3. It gives operational teams one place to search
 customers, manage customer-care work, monitor subscriptions, handle billing operations, supervise fulfillment, dispatch work
 orders, administer catalogs/configuration, review equipment/stock, and inspect operational incidents.

 The Backoffice is Kenya-first but must remain operator and region configurable. The same codebase must support future
 deployments with different operators, countries, languages, currencies, themes, logos, tax labels, and feature flags.

 4. Users And Roles
 Backoffice access is role-based. Navigation, screen actions, table actions, and high-risk buttons must be hidden or disabled
 according to role and feature flags. Backend authorization remains authoritative.

 Role source:

   - FOUNDATION_AUTH owns authentication, shared role names, JWT role claims, and Keycloak/LDAP group mapping.

   - The Backoffice reads role claims from the OIDC token and uses them only to render navigation, menus, and
     enabled/disabled actions.

   - Each module API remains responsible for endpoint authorization. A hidden button is not security.

   - Modules must not invent local role names. If a Backoffice flow needs a new role, add it to FOUNDATION_AUTH and the
     Keycloak realm export first, then reference it in the owning module DD/API guard.

 Role families are product-facing groupings used by the Backoffice UI. They are mapped to one or more FOUNDATION_AUTH
 roles and module-specific endpoint guards.

 17. Common Work Queue Pattern
 A work queue is a screen pattern for lists of items that require human review, assignment, retry, approval, or follow-up.

 It is not one shared backend table. Each queue is owned by the module that owns the business object. The Backoffice
 provides a consistent UI pattern across modules, but it must call the owning module API for the queue data and actions.

 Examples:

  Queue                                         Owning module/API                                          What the user does

  KYC pending L1/L2                             ILM Customer Service, FUL-02 task APIs                     Review documents, approve, reject, request
                                                                                                           correction.

  Tickets waiting assignment                    TCK-01                                                     Assign ticket to user/team, escalate, add comment.

  Failed subscription operations                SUB-WF framework, approved Camunda proxy                   Inspect operation failure, retry only through exposed
                                                                                                           recovery action.

  Activation failures                           FUL-03, SUB-WF framework                                   Review activation error, trigger backend retry if
                                                                                                           allowed.

  Dunning review                                BIL-04                                                     Review debt state, approve configured dunning
                                                                                                           override or termination review.

  Tax invoice failures                          BIL-02-TAX-01                                              Retry signing/cancellation where allowed.

  Work orders pending assignment                WO-01, EM-02, ILM-CFG-02                                   Assign/reassign contractor/team/technician.

  Equipment recovery exceptions                 OSR-INSTANCE-01, OSR-RMA-01, WO-01                         Investigate missing/damaged/mismatched
                                                                                                           equipment and open follow-up actions.

 Queue UI requirements:

   - show saved filters where the owning API supports them;

   - support role/team queues from FOUNDATION_AUTH role claims and module assignment fields;

   - use split list/detail mode for fast triage;

 19. State And Data Loading
 Rules:

   - Use server-side pagination for tables.

   - Use query parameters that match backend API contracts.

   - Use optimistic UI only for low-risk local state; not for financial/subscription/equipment state.

   - Refresh detail after a command completes.

   - Use stale/error indicators per panel in aggregate screens.

   - Avoid loading all modules at once if the screen can lazy-load panels.

 Customer 360 loading strategy:

   1. Load ILM customer/account first.

   2. Render shell and identity panel.

   3. Load subscriptions, billing, work orders, tickets, notifications in parallel.

   4. Show panel-level loading/error states.

   5. Allow retry per failed panel.


 20. Command Handling
 All create/update/action commands must:

   - validate form locally;

   - include correlation id;

   - include idempotency key where retry/duplicate submit is possible;



SOPHIX BSS Design Documents                                                                                                                   Page 21
   - disable duplicate submit while in flight;

   - show backend validation errors without losing form state;

   - show final operation id for long-running commands;

   - write no state directly to another module's local cache.

 High-risk commands require:

   - confirmation screen;

   - reason/comment;

   - impact summary;

   - role check;

   - audit visibility after completion.

   - Do not hardcode Kenya-only labels into shared components.

   - Use translation keys for menu names, buttons, table headers, status labels, and errors.

   - Show country/operator-specific legal text from runtime config where needed.


 22. Security And Privacy
 Backoffice exposes sensitive operational data.

 Required controls:

   - Auth through Keycloak/OIDC.

   - Role-based navigation and action visibility.

   - Backend authorization for every API.

   - Session timeout and re-auth for sensitive actions where required.

   - Mask sensitive PII unless role allows full view.

   - Never log tokens, ID numbers, payment secrets, or raw document contents.

   - Download files only through authorized APIs.

   - Audit all high-risk actions.

 Sensitive data examples:

   - customer ID document number;

   - KYC documents/photos;

   - payment references;

   - invoice/tax invoice documents;



SOPHIX BSS Design Documents                                                                                                                  Page 22
   - equipment serial/customer binding;

   - internal notes;

   - audit logs.


 23. Accessibility And UX Rules
 Backoffice must be efficient for repeated daily use.

 Required:

   - keyboard navigation for tables and forms;

   - accessible labels and focus states;

   - no color-only status;

   - responsive behavior down to tablet width;

   - clear empty/error/loading states;

   - compact layout for operations;

   - copy buttons for IDs/correlation ids;

   - timestamps with timezone clarity.

 Status colors must be consistent:

  Status type                                           UI treatment

  Success/completed                                     Green

  Warning/pending/manual action                         Amber

  Error/failed/overdue                                  Red

  Neutral/draft/inactive                                Gray

  Info/in-progress                                      Blue




 24. Observability
 Backoffice telemetry must include:

   - app version;

   - operator/country;

   - route/screen id;

   - user role family;

   - command type;

   - backend error code;

   - correlation id;

   - operation id when available;

   - API latency buckets;

   - panel load failures.

 Do not send PII to analytics.
