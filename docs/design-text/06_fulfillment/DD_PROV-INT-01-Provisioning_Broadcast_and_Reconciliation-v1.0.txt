 1. Purpose
 PROV-INT-01 defines the shared BSS provisioning integration layer used to send commands to network and service
 platforms, track command execution, retry safely, reconcile actual network state with BSS desired state, and perform
 controlled force-sync operations.

 This DD closes a gap in the fulfillment design. Existing fulfillment DDs define when a service should be activated, restricted,
 resumed, suspended, modified, or revoked. This DD defines how the low-level command dispatch and reconciliation are
 tracked across all those flows.

 Examples of provisioning targets:

   - OLT / fiber access controller or NMS.

   - HFC CMTS / DOCSIS platform.

   - AAA / RADIUS / subscriber policy platform.

   - VoIP switch.

   - IPTV middleware.

   - DHCP/IP address management system.

   - Partner service activation API.



 2. What This DD Owns
 PROV-INT-01 owns:

   - Provisioning target registry.

   - Adapter configuration for each external platform.

   - Common provisioning command envelope.

   - Idempotent command ledger.

   - Command attempts, retries, timeout handling, and final status.

   - Broadcast to multiple target systems where one service action needs more than one vendor command.

   - Desired network state snapshot from BSS.

   - Observed network state snapshot from external platforms.

   - Reconciliation runs and discrepancy queues.

 Rule: PROV-INT-01 does not decide which package, service, or subscription state is correct. It sends and reconciles
 technical commands based on desired state supplied by the owning modules.



 4. Design Decision
 FUL-03, FUL-04, and FUL-05 remain the business fulfillment orchestrators. PROV-INT-01 is the common provisioning
 command and reconciliation layer behind them.

 Recommended call pattern:
            Subscription Workflow
              -> FUL-03 / FUL-04 / FUL-05
              -> PROV-INT command API
              -> vendor adapter
              -> network/service platform

 The existing "Provisioner adapter" concept remains valid, but adapter implementations should write through the PROV-INT
 command ledger instead of hiding command state inside the fulfillment module. This gives NOC and support one place to
 inspect provisioning commands across activation, restriction, resume, termination, migration, and force-sync.

 6. Core Concepts
 6.1 Provisioning Target
 A provisioning target is an external system to which SOPHIX sends network or service commands.



SOPHIX BSS Design Documents                                                                                                     Page 2
 Examples:

  Target code                                                     Meaning

  HUAWEI_NCE_GPON_KE                                              Huawei access controller for GPON provisioning.

  VOIPSWITCH_NRB_01                                               VoIP switch serving Nairobi subscribers.

  IPTV_MIDDLEWARE_KE                                              IPTV middleware or entitlement platform.

  DOCSIS_CMTS_KE                                                  HFC/DOCSIS controller.



 6.2 Provisioning Command
 A provisioning command is one technical instruction sent to one target.

 Examples:

   - Create ONT service profile.

   - Set internet speed profile.

   - Create SIP profile.

   - Bar outgoing voice.

   - Suspend subscriber access.

   - Delete IPTV entitlement.

 6.3 Broadcast
 Broadcast means one fulfillment action creates multiple provisioning commands.

 Example: activating triple-play may create:

   1. GPON internet profile command.

   2. VoIP SIP profile command.

   3. IPTV entitlement command.

 6.4 Desired State
 Desired state is what BSS believes should exist on the network based on subscription/package/service state.

 Example:
           {
                "subscriptionId": "SUB-700045",
                "serviceRef": "svc_INET_100M_GPON",
                "desiredStatus": "ACTIVE",
                "speedDownMbps": 100,
                "speedUpMbps": 20,
                "targetNodeCode": "OLT-NRB-KAREN-02",
                "targetPort": "0/4/07"
           }


 6.5 Observed State
 Observed state is what the network platform reports during reconciliation.

 Example:
           {
                "targetCode": "HUAWEI_NCE_GPON_KE",
                "subscriberKey": "SUB-700045:INET",
                "observedStatus": "ACTIVE",
                "speedDownMbps": 50,
                "targetPort": "0/4/07"
           }

 If desired state says 100 Mbps but observed state says 50 Mbps, PROV-INT creates a reconciliation mismatch.

 8. Business Rules
  Rule ID                                      Rule                                                    Notes

  R-PROV-01                                    Every provisioning command must be stored before        Enables retry and audit.
                                               dispatch.

  R-PROV-02                                    Command idempotency key must be unique per              Prevents duplicate network changes.
                                               technical command.

  R-PROV-03                                    PROV-INT must not change subscription, invoice,         It only reports command results.
                                               wallet, or work-order state.

  R-PROV-04                                    A fulfillment action may create multiple provisioning   Broadcast is expected.
                                               commands.

  R-PROV-05                                    Retryable failures are retried with exponential         Adapter decides retryable vs final where possible.
                                               backoff.

  R-PROV-06                                    Non-idempotent vendor commands require                  Avoid duplicate profiles.
                                               adapter-level read-before-write or vendor
                                               idempotency token.

  Rule ID                                     Rule                                                   Notes

  R-PROV-07                                   Force-sync requires RBAC permission and usually        Example: deleting a live profile.
                                              approval for destructive actions.

  R-PROV-08                                   Reconciliation mismatches do not auto-fix by           They create review items.
                                              default.

  R-PROV-09                                   Auto-fix can be enabled only per target/command        Start disabled for medium deployment.
                                              type and must be audited.

  R-PROV-10                                   Desired state is sourced from BSS owner modules.       PROV-INT does not invent desired state.

  R-PROV-11                                   Observed state snapshots must store the source         Needed for NOC trust.
                                              target and collection timestamp.

  R-PROV-12                                   Adapter credentials are stored in secret manager,      Security baseline.
                                              not database rows.




 9. Command Status Model
  Status                                                                 Meaning

  RECEIVED                                                               Command stored but not yet dispatched.

  DISPATCHING                                                            Dispatcher is sending the command.

  ACCEPTED                                                               Vendor accepted command but final result is not known.

  SUCCEEDED                                                              Command completed successfully.

  FAILED_RETRYABLE                                                       Command failed but can be retried.

  FAILED_FINAL                                                           Command failed and should not retry without human action.

  TIMED_OUT                                                              Vendor did not respond within configured timeout.

  CANCELLED                                                              Command cancelled before dispatch.

  SUPERSEDED                                                             A newer command replaced this one before dispatch.

   - Deep links from customer 360, subscription detail, ticket detail, and NOC screens.

 13.2 FE-APP-03 Contractor Mobile App
 The contractor app normally does not call PROV-INT directly.

 It completes work orders in WO-01. The subscription workflow or fulfillment module then triggers provisioning. The mobile app
 may show provisioning result read-only if the WO completion response includes it.

 13.3 FE-APP-04 Customer Self Care
 Self-care does not call PROV-INT directly.

 If activation is delayed due to provisioning, self-care reads customer-friendly status from subscription/order/ticket APIs, not
 raw provisioning command errors.

 16. Implementation Notes
   1. Start with command ledger and synchronous dispatch before building auto-repair.

   2. Use idempotency keys from FUL correlation ids and service refs.

   3. Keep adapter classes thin and testable.

   4. Normalize vendor responses into stable SOPHIX statuses.

   5. Do not expose vendor errors directly to customers.

   6. Store redacted request/response payloads for support.

   7. Reconciliation should initially create review items, not auto-fix.

   8. Force-sync actions should create normal provisioning_command rows so audit is consistent.

 17. Definition Of Done
 PROV-INT-01 is complete when:

   - Provisioning target and adapter config are implemented.

   - FUL-03 can create commands through PROV-INT for activation.

   - FUL-04 can create commands through PROV-INT for restriction/suspension.

   - FUL-05 can create commands through PROV-INT for termination.

   - Command idempotency prevents duplicate vendor actions.

   - Retry and timeout handling are tested.

   - Command detail and attempt logs are available to Backoffice.

   - Reconciliation can compare at least one target's observed state to BSS desired state.

   - Mismatches create actionable items.

   - Force-sync is implemented with RBAC and audit.
