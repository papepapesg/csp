 1. What this module is
 When PLM-CFG-06 flags an SKU as is_serialized=TRUE (every ONT, every modem, every STB, every smart card),
 each physical unit gets its own row in equipment_instance. The row carries the device's identity (serial number, MAC
 addresses for hybrid chassis, smart card number for STBs) and a pointer to its current location.

 Location is a discriminated union: a stock_location from OSR-01 (warehouse or contractor van) OR an account_id
 from ILM-CFG-01 (the device is in the field at a customer premises) OR a special sentinel for IN_TRANSIT_TO_VENDOR /
 DECOMMISSIONED. Exactly one current location per active instance.

 The lifecycle is captured by an append-only event ledger. Every state transition (received from vendor → moved to contractor
 van → assigned to WO → installed at customer → recovered after fault → returned to contractor warehouse) is one row. The
 current location and current state of any instance are derived from the latest event row, but the events themselves are
 immutable and form the audit trail.

 One critical operational pain this module enables fixing: Wananchi KE reports ~40+ stale equipment items where
 unassigned devices on WO finalization auto-route to the main warehouse instead of the contractor team's warehouse that
 physically recovered them. The instance ledger captures *which contractor was holding the device when it was recovered*
 and downstream consumers (OSR-RMA-01, OSR-01 stock movements) use that to route the device back to the contractor
 team, not main warehouse.

 What this module does
   1. Master per serialized physical device — one row per ONT, modem, MTA, STB, smart card. Identity carries serial
     number, optional MAC addresses (CM-MAC, MTA-MAC, CPMAC for static IP packages, all derivable from chassis ID per
     workshop), smart card number for STBs (10 digits, starts with 767 for HFC TV), and the SKU FK to PLM-CFG-06.

   2. Track current location — pointer to either stock_location (warehouse or van) OR account (with customer) OR a
     sentinel state. Updated atomically with each lifecycle event.

   3. Track current state — derived enum: IN_VENDOR_WAREHOUSE / IN_MAIN_WAREHOUSE / IN_CONTRACTOR_STOCK /
     RESERVED_FOR_WO / IN_FIELD_ACTIVE / IN_FIELD_DEFECTIVE / RECOVERED_BY_CONTRACTOR /
     RETURNED_TO_MAIN_WAREHOUSE / RMA_SHIPPED_TO_VENDOR / REPAIRED_BY_VENDOR / DECOMMISSIONED.

   4. Maintain append-only lifecycle ledger — every transition is one row with timestamp, actor, from-state, to-state,
     from-location, to-location, reason code, and free-text note.

   5. Bind / unbind to customer — at WO finalization, the instance binds to an account_id (and its subscription_id if
     relevant). On disconnect / swap, the instance unbinds. The binding is the structural source of truth for *"which device does
     this customer have?"*

   6. Resolve from various lookup keys — by serial number, by MAC address (any of CM-MAC / MTA-MAC / CPMAC), by
     smart card number, by SKU, by current location, by current customer.

   7. Bulk import — XLSX/CSV upload (matching Wananchi's existing Equipment Batch Actions Utility) for new vendor
     batches. Each row creates one instance with state = IN_MAIN_WAREHOUSE (or IN_VENDOR_WAREHOUSE if marked as
     pre-delivery).

 What this module does NOT do
   - Doesn't track non-serialized consumables. Cable lengths, splices, drop cables, faceplates — those live in OSR-01 as
     SKU+quantity rows (PLM-CFG-06 is_serialized=FALSE). This module is exclusively for SKUs flagged
     is_serialized=TRUE.

   - Doesn't replace OSR-01. OSR-01 still owns SKU+quantity rollups, stock movements at the SKU level, balance views,
     reservations. This module overlays per-instance resolution onto OSR-01's stock world for serialized items. The two
     coexist; OSR-01 emits a StockMovementRecorded event for a serialized SKU and this module captures the


SOPHIX BSS Design Documents                                                                                                 Page 4
     corresponding EquipmentInstanceLifecycleTransition row(s) — both are written by the same business
     transaction.

   - Doesn't orchestrate swap workflows. The workflows (HFC field pickup, GPON remote unassign, EQP termination
     retrieval, EQU upgrade) belong to OSR-RMA-01. This module only records lifecycle transitions when consumers call its
     APIs.

   - Doesn't talk to network systems. Broadhub, NMS, CMTS, Verimatrix, VoipSwitch — those are downstream of
     provisioning workflows through capability-named provisioning adapters. This module is the BSS-side ledger of where
     devices are; network-side configuration is performed by Service Activation (FUL-03 → Network Provisioning Adapter) and
     recorded as device state by other modules.

   - Doesn't enforce slot/port binding semantics. UC-PR4 (HFC modem authorization bound to slot/port) is a workflow-level
     constraint enforced by OSR-RMA-01 swap flows. This module records the slot/port as instance metadata when supplied;
     it doesn't validate that the slot/port matches across swaps.

   - Doesn't track warranty / repair history. Vendor warranty terms, RMA SLA per vendor, repair history per serial — out of
     v1.0 scope. The lifecycle state set includes RMA_SHIPPED_TO_VENDOR and REPAIRED_BY_VENDOR as transitions, but
     no warranty / vendor-RMA metadata. Future expansion.

   - Doesn't perform reconciliation against the network's ground truth. Wananchi's
     malogs.wananchi.com/gpon_auto_find/ portal lists what ONT serials are physically connected to the OLT.
     Comparing that to instance bindings (drift detection) is a separate future reconciliation workflow.

 Regional flexibility
 Workshop sources are KE workshops (Zuku 2026-04-27+). KE is the v1.0 seed; schema designed to accommodate
 WUG/WTZ/YASSN variants:

   - MAC structure varies by tech. HFC hybrid chassis carry CM-MAC + MTA-MAC + optional CPMAC; GPON ONT carries
     only its ONT serial; smart cards carry only the 10-digit number. Schema uses three nullable MAC columns + optional
     smart card number, not a single MAC field.

   - Slot/port semantics vary. HFC modems bind to a CMTS slot/port (UC-PR4 — KE-specific Wananchi requirement);
     GPON ONTs bind to an OLT Frame/Slot/Port (F/S/P) reported by the OLT auto-discovery feed. Schema carries
     network_slot_ref as a free-text + JSONB pair to accommodate both formats without forcing a single shape.

   - Vendor RMA process varies. WIK uses different vendors than YASSN (Huawei + FiberHome for GPON, Cisco for HFC in
     KE; Free Sénégal-side vendors for YASSN). The lifecycle states are vendor-agnostic; vendor metadata (RMA reference
     number, ship date, expected return date) is in a JSONB column rather than a structured table.

 2.2 Entity relationships

 Reading the diagram:

   - equipment_instance is the root. One row per physical serialized device.

   - equipment_sku (PLM-CFG-06) is referenced by instance.sku_id — every instance carries its SKU; the SKU defines
     the device kind (ONT vs modem vs STB) and is_serialized=TRUE.

   - stock_location (OSR-01) is referenced by instance.current_location_id when the device is in a warehouse or
     contractor van (NOT when it's at a customer premises).

   - account (ILM-CFG-01) is referenced by instance.current_account_id when the device is at a customer premises.

   - equipment_instance_lifecycle_event is one-to-many off equipment_instance — every transition is one row.
     The latest event row determines the instance's current location and state (denormalized into the instance row for fast
     lookup).

   - External references from this module: stock_location (OSR-01), account (ILM-CFG-01), equipment_sku
     (PLM-CFG-06), wo (WO-01) — never owned by OSR-INSTANCE-01.

 2.3 Cross-DD anchoring
   - OSR-01 Stock Chain Engine — for serialized SKUs, every stock_movement row (movement of a serialized item
     between locations) corresponds to one lifecycle event in this module. The two writes happen in the same business
     transaction. OSR-01 carries the SKU+qty rollup; OSR-INSTANCE-01 carries the per-serial detail. v1.0 design pattern:
     when OSR-01 records a stock_movement against a serialized SKU, the caller MUST also call POST
     /api/equipment-instances/{id}/lifecycle-events with the matching serial. Application layer enforces this via
     a transactional outbox.

   - PLM-CFG-06 Equipment Type Catalog — equipment_instance.sku_id is FK to equipment_sku.sku_id. The
     SKU's is_serialized flag determines whether instances exist at all. PLM-CFG-06 also defines equipment_kind
     (ONT / CABLE_MODEM / STB / etc.) and that drives which MAC / smart-card columns are populated on the instance.

   - ILM-CFG-01 Customer Service Catalog — equipment_instance.current_account_id is FK to
      account.account_id when the instance is bound to a customer. Account ownership of the device follows
      account.account_id (not customer.customer_id): Customer is identity-only; operational concerns including equipment
      binding anchor at the Account.

   - WO-01 Work Order Module — at WO finalization, the WO carries a list of wo_equipment(wo_id, sku_id, qty,
     serial_number_ref) rows (per PLM-CFG-06 §7 migration). The serial_number_ref is resolved to an
     equipment_instance.instance_id and a lifecycle event BOUND_TO_CUSTOMER is emitted with wo_id as the origin
     reference.

   - EM-02 Contractor & Staff Registry — every lifecycle event optionally carries a contractor_id (FK to EM-02)
     recording which contractor held the device during the transition. THIS IS THE FIX for the Wananchi 40+ stale-equipment
     routing pain: when a device is recovered from the field, the recovering contractor is recorded on the event, and
     downstream RMA / return-to-warehouse logic in OSR-RMA-01 reads this contractor_id to route the device back to the
     right contractor warehouse instead of main.

   - OSR-RMA-01 Equipment Swap & RMA (pending) — the primary workflow consumer. Calls POST
     /api/equipment-instances/{id}/lifecycle-events at each swap step to advance the instance state.

 4. Rules
  Rule                                                              Description

  R-OSR-INST-1                                                      One instance per (operator_code, serial_number). The serial number is the
                                                                    primary natural key; two operators may share serial collisions across different
                                                                    vendors (handled by the operator_code partition in the unique index).

  R-OSR-INST-2                                                      Only SKUs with is_serialized=TRUE in PLM-CFG-06 may have instances.
                                                                    INSERT is rejected if the SKU is not serialized. Migration tooling for the OSR-01
                                                                    transition handles legacy SKU+qty rollups; net-new instances always go
                                                                    through the typed API.

  R-OSR-INST-3                                                      An instance has exactly one current location: either current_location_id
                                                                    (warehouse / van), current_account_id (customer premises), or
                                                                    current_sentinel ('IN_TRANSIT_TO_VENDOR' /
                                                                    'AT_VENDOR_FOR_REPAIR' / 'DECOMMISSIONED'). Enforced by CHECK
                                                                    constraint.

  R-OSR-INST-4                                                      Every state transition is one row in
                                                                    equipment_instance_lifecycle_event. The instance row's
                                                                    denormalized current_* fields MUST equal the latest event row's to_* fields after
                                                                    the transaction. Application layer enforces this.

  R-OSR-INST-5                                                      event_sequence is per-instance, monotonically increasing, no gaps. Each
                                                                    new event MUST have event_sequence = previous_event_sequence
                                                                    + 1. Concurrency conflict (two clients trying to write event sequence N+1
                                                                    simultaneously) is detected by the UNIQUE constraint and one client receives a
                                                                    409 — that client must re-read the instance and retry.

  R-OSR-INST-6                                                      Legal state transitions are enforced at the application layer per a state machine
                                                                    (§4.1). Illegal transitions (e.g., DECOMMISSIONED → IN_FIELD_ACTIVE) are
                                                                    rejected by the API with HTTP 409 + a code=ILLEGAL_STATE_TRANSITION
                                                                    body.

  R-OSR-INST-7                                                      When an instance transitions to RECOVERED_BY_CONTRACTOR, the event's
                                                                    contractor_id MUST be populated. This is the field downstream routing
                                                                    logic (OSR-RMA-01) reads to decide "route this device back to which
                                                                    warehouse?" — fixing the Wananchi 40+ stale-equipment pain. Application
                                                                    layer enforces via NOT NULL guard on this specific reason_code.

  R-OSR-INST-8                                                      Customer binding lifecycle: state IN_FIELD_ACTIVE or
                                                                    IN_FIELD_DEFECTIVE requires current_account_id set and
                                                                    current_location_id NULL. All other states require
                                                                    current_account_id NULL. Enforced by CHECK constraint + application
                                                                    layer.

  R-OSR-INST-9                                                      DECOMMISSIONED is terminal. Once an instance enters this state, no further
                                                                    lifecycle events are accepted (application layer rejects with HTTP 409 +
                                                                    code=INSTANCE_DECOMMISSIONED). The instance row's active field is set
                                                                    to false. Row is kept indefinitely for audit history.

  R-OSR-INST-10                                                     Smart card number format: must match ^767[0-9]{7}$ (10 digits starting
                                                                    767, per workshop 2026-04-30 — Verimatrix-issued smart cards for HFC TV).
                                                                    Enforced by CHECK constraint.

  R-OSR-INST-11                                                     MAC address format: AA:BB:CC:DD:EE:FF (colon-separated hex pairs,
                                                                    case-insensitive). Application layer normalizes to uppercase on write. CM-MAC
                                                                    and MTA-MAC values per workshop: MTA-MAC computed as CM-MAC + 2;
                                                                    application layer may validate this for hybrid chassis SKUs but does NOT
                                                                    auto-populate (the import file is the source of truth).

  R-OSR-INST-12                                                     network_slot_metadata JSONB shape varies by tech: for GPON
                                                                    {'frame':int,'slot':int,'port':int,'olt':text}; for HFC
                                                                    {'cmts':text,'slot':int,'port':int,'authz_bound':bool}.
                                                                    Application layer parses + validates per the SKU's equipment_kind
                                                                    (PLM-CFG-06). Unknown shapes are accepted (stored as-is) for forward
                                                                    compatibility.

  R-OSR-INST-13                                                     Cross-operator scoping: operator_code on equipment_instance MUST
                                                                    match the operator_code of the SKU referenced (PLM-CFG-06 SKUs are
                                                                    operator-scoped). Cross-operator instance creation is rejected. Cross-operator
                                                                    query requires sophix-superadmin role.

  R-OSR-INST-14                                                     vendor_metadata JSONB is populated only when the instance is in
                                                                    RMA_SHIPPED_TO_VENDOR or REPAIRED_BY_VENDOR state. Cleared (set to
                                                                    NULL) on transition out of either state. Application layer enforces.

 Notes on the state machine:

   - IN_FIELD_DEFECTIVE → IN_FIELD_ACTIVE is allowed (a customer-reported issue resolved without truck roll — e.g.,
     remote reboot fixed it; the swap workflow cancels).

   - RECOVERED_BY_CONTRACTOR → IN_CONTRACTOR_STOCK is the swap-success path: contractor brings the recovered
     unit back to van; it's now part of contractor stock awaiting return-to-main or RMA decision.

   - RECOVERED_BY_CONTRACTOR → RETURNED_TO_MAIN_WAREHOUSE skips the contractor stock step when the
     contractor batch-transfers recovered units directly to main warehouse.

   - RETURNED_TO_MAIN_WAREHOUSE → IN_MAIN_WAREHOUSE moves the unit back into available stock after main
     warehouse inspection (a recovered unit that tests OK can be re-dispatched).

   - RETURNED_TO_MAIN_WAREHOUSE → RMA_SHIPPED_TO_VENDOR is the path for units failing main-warehouse
     inspection.

   - Most states can transition to DECOMMISSIONED (write-off allowed at almost any point — lost, stolen, declared beyond
     repair).

 8. Workshop sources
 Workshop sources for v1.0 (KE Zuku 2026-04-27+; no fabricated TZ baselines — TBD pending cartography):

   - Workshop 2026-04-29 (Work Order & Field Operations deep dive) — Equipment Lookup screen behavior (search by
     last 5 hex digits returns all sub-interfaces of a chassis, e.g. 707C4 → CMD/MTP/MTA); Hybrid Chassis dialog (HYB
     chassis carries CM-MAC + MTA-MAC; CM-MAC = chars 4-15 of chassis Equipment ID, MTA-MAC = CM-MAC + 2);
     Equipment Batch Actions Utility on named persistent lists.

   - Workshop 2026-04-30 (Provisioning deep dive) — Smart card 10-digit format starting 767 (Verimatrix-issued for HFC
     TV); HFC modem authorization bound to slot/port (UC-PR4, KE-specific — moving the modem to a different slot breaks
     authorization); static-IP HFC requires double config (Broadhub + Clearcable NOMS); static-IP GPON manual via DHCP
     console; voice device (MTA/IAD) can carry multiple phone numbers each bound to an equipment port.

   - Workshop 2026-04-30 (Customer Management deep dive — Equipment-routing gap) — Today: unassigned
     equipment goes to main warehouse on WO finalization, not to the contractor team that recovered it. ~40+ stale items
     reported. Wananchi target: SOPHIX must trace the contractor team that recovered the equipment and route it back to that
     team's warehouse. THIS DD'S contractor_id on equipment_instance_lifecycle_event is the mechanism that
     enables that fix in OSR-RMA-01.

   - Workshop 2026-04-30 (Provisioning deep dive — Service Termination) — Equipment dismantle is a separate retrieval
     WO if customer doesn't bring CPE back. For both GPON and HFC, an agent contractor is sent on site. Refund processed
     via Invoice Adjustments. This drives the lifecycle states IN_FIELD_DEFECTIVE and RECOVERED_BY_CONTRACTOR and
     the contractor_id tracking.

   - wo_lifecycle.md Job Type table — EQP Equipment Pickup, EQU Equipment Upgrade, EQR Equipment Recovery
     (failed: "client paid for CPE & refuses return"). These map to OSR-RMA-01 satellite workflows; this DD's instance state
     machine accommodates them via DECOMMISSIONED reachability and RECOVERED_BY_CONTRACTOR semantics.
