 DD_SUB-WF-FRAMEWORK-01-WORKERS - Shared
 Workflow Workers, Messages, User Tasks, Drools
 Developer implementation guide: DD_SUB-WF-FRAMEWORK-01-WORKERS-DEV_IMPL_GUIDE-v1.0.md.

 MVP simplification baseline: worker names in this DD are logical task topics. They are not deployment names. First release
 should run a consolidated subscription worker application with per-topic metrics, logs, retries, and dead-letter visibility. Split
 topics into separate deployments only for throughput, dependency isolation, security, or team ownership.


 1. Purpose
 This DD defines the shared worker catalog used by subscription workflow BPMNs.

 The parent DD, SUB-WF-FRAMEWORK-01, owns operation orchestration tables and operation APIs. This companion DD
 owns the reusable workflow building blocks:

   - Camunda external task worker topics.

   - Worker input and output process variables.

   - Shared Camunda messages.

   - Shared Camunda user tasks.

   - Drools rule package naming.

   - FOUNDATION_AUTH groups used by workflow tasks and trigger endpoints.

   - Worker deployment and runtime rules.

 Use this DD when implementing:

   - A worker pod that fetches Camunda external tasks.

   - A BPMN service task that references a worker topic.

   - A BPMN message catch event.

   - A BPMN user task.

   - A Drools package called from subscription workflows.

   - Worker runtime configuration, retry behavior, and scaling.

 3. Mental Model
 Subscription BPMNs are composed from small reusable workers.
          flowchart LR
              BPMN[Camunda BPMN] -->|external task topic| W[Worker Pod]
              W -->|service token| API[Owning Module API]
              W -->|complete/failure| BPMN
              API --> DB[(Module DB)]
              API --> OUTBOX[(kafka_outbox)]

 Each worker must do one job only.

 Important operational distinction:
          Logical worker topic != dedicated pod

 This DD defines logical worker topics because BPMNs need clear, stable contracts. It does not require one pod, one Laravel
 command, or one deployment per topic.

 One worker application may subscribe to many related topics:
          subscription-worker app:
            - sub-lm-put-pending-status
            - sub-lm-commit-state
            - sub-lm-revert-to-prior
            - sub-lm-put-master-fields
            - subscription-operation-finalize

          integration-worker app:
            - bil01-charge-pre-authorize
            - bil01-confirm-charge
            - bil01-revert-pending-charge
            - ful-call-activate
            - ful-call-terminate

 The rule is that the topic contract stays single-purpose. The runtime process may consolidate several topics for easier
 operations and monitoring.

 Good worker design:
          sub-lm-commit-state
            - calls SUB-LM commit-state API
            - writes returned variables to Camunda
            - fails only for commit-state errors

 Bad worker design:
          subscription-operation-handler
            - checks operator
            - decides billing
            - calls fulfillment
            - sends notification
            - emits Kafka

 Operator-specific behavior belongs in BPMN, Drools, configuration, and auth groups. It must not be hard-coded inside
 workers.


 4. Worker Runtime Contract
 All workers use Camunda external tasks.

 Worker loop:

   1. Fetch and lock tasks by topic.

   2. Read process variables.

   3. Validate required variables.

   4. Call the owning module API or local service.

   5. Complete the task with output variables.


SOPHIX BSS Design Documents                                                                                                Page 2
   6. On retryable failure, report failure to Camunda with remaining retries.

   7. On non-retryable business failure, throw BPMN error or complete with a decision variable, depending on BPMN design.

 Camunda calls:
             POST /engine-rest/external-task/fetchAndLock
             POST /engine-rest/external-task/{taskId}/complete
             POST /engine-rest/external-task/{taskId}/failure
             POST /engine-rest/external-task/{taskId}/bpmnError

 Worker implementation can be Java/Spring, Laravel/PHP, or another approved stack. The topic contract must stay the same.


 5. Worker Implementation Rules
  Rule                                                                    Description

  R-WORKER-1                                                              A logical worker topic must represent one business step. A single worker
                                                                          application/process may handle multiple topics if each topic keeps its own
                                                                          handler, metrics, retry policy, and contract.

  R-WORKER-2                                                              A worker must not branch on operator_code for business behavior. Use
                                                                          BPMN, Drools, or config instead.

  R-WORKER-3                                                              A worker must validate required input variables before calling downstream APIs.

  R-WORKER-4                                                              A worker must be idempotent because Camunda may retry the same external
                                                                          task.

  R-WORKER-5                                                              Every downstream API call must include an idempotency key derived from
                                                                          operationId and worker topic.

  R-WORKER-6                                                              A worker must set only documented output variables.

  R-WORKER-7                                                              A worker must not store large payloads in Camunda variables. Store large
                                                                          documents in DB/object storage and pass IDs.

  R-WORKER-8                                                              A worker must not write directly to another module database. Call the owning
                                                                          module API.

  R-WORKER-9                                                              A worker must not publish directly to Kafka unless the worker is specifically
                                                                          kafka-emit and it writes to kafka_outbox.

  R-WORKER-10                                                             A worker must not complete a task after the downstream call failed unless
                                                                          failure is explicitly reliability-isolated, such as notification-send.

  R-WORKER-11                                                             Worker logs must include operationId, subscriptionId,
                                                                          processInstanceId, topicName, and externalTaskId.

  R-WORKER-12                                                             Worker failures must avoid secrets, stack traces, and full external payloads in
                                                                          user-visible fields.

 These workers call SUB-LM-01 internal APIs. Use them when a BPMN needs to mutate or compute subscription state.

 #### sub-lm-put-pending-status

 What it is for:

 Moves a subscription into a transient PENDING_* status and records the active transition type.

 When to use it:

   - At the start of activation, pause, resume, upgrade, downgrade, relocation, migration, or termination flows.

   - Before external billing/fulfillment steps when the subscription must show that a lifecycle change is in progress.

 Inputs:

  Variable                                    Meaning                                      Example

  subscriptionId                              Subscription to update.                      sub_01HZ_KAMAU_FIBER

  toStatus                                    Pending status to set.                       PENDING_TERMINATION

  currentTransitionType                       Operation type in progress.                  TERMINATE

  currentTransitionReasonCode                 Reason for the transition.                   CUSTOMER_MOVED_NO_COVERAGE


 Outputs:

  Variable                                    Meaning                                      Example

  priorStatusSnapshot                         Prior status data used for revert.           {"statusCode":"ACTIVE","activeRestrict
                                                                                           ions":[]}

  lmEventId                                   SUB-LM low-level event/outbox ID.            evt_01HZ_PENDING_TERM


 Failure behavior:

   - Retry on transient SUB-LM API/DB errors.

   - BPMN error on invalid transition.

 #### sub-lm-commit-state

 What it is for:

 Commits the final subscription status after the saga has succeeded.

 When to use it:

   - End of activation to move PENDING_ACTIVATION to ACTIVE.

   - End of pause or suspend-NP to move pending status to SUSPENDED.

   - End of termination to move PENDING_TERMINATION to TERMINATED.

 Inputs:

  Variable                                    Meaning                                      Example

  subscriptionId                              Subscription to update.                      sub_01HZ_KAMAU_FIBER

  toStatus                                    Final status.                                TERMINATED

  expectedFromStatus                          Guard status expected before commit.         PENDING_TERMINATION


 Outputs:

  Variable                                    Meaning                                      Example

  lmEventId                                   SUB-LM event/outbox ID.                      evt_01HZ_TERM_COMMIT

  committedAt                                 Commit timestamp.                            2026-07-20T14:30:18Z


 Failure behavior:

   - Retry on transient SUB-LM errors.

   - BPMN error if current status is not expectedFromStatus.

 8. Worker Registration
 Each worker deployment may declare one topic or many topics.

 For operability, prefer a small number of worker applications grouped by ownership/latency profile instead of dozens of tiny
 deployments.

 Each worker deployment must declare:

   - Topic name.

   - Lock duration.

   - Max tasks per fetch.

   - Max worker concurrency.

   - Retry count.

   - Retry timeout/backoff.

   - Owning module.

            externalTasks:
              - topic: sub-lm-put-pending-status
                owningModule: SUB-LM
                lockDurationMs: 30000
                maxTasks: 10
                concurrency: 10
                retries: 3
                retryTimeoutMs: 10000

 14. Infrastructure Recommendations
 14.1 Deployment Unit Clarification
 Workers are deployable processes/pods that talk to Camunda and module APIs. One process/pod can handle multiple logical
 worker topics.

 They may be packaged in different ways:

  Option                                       When to use                                         Notes

  Workers inside owning module deployment      Budget-conscious start.                             SUB-LM workers run with SUB-LM, billing workers
                                                                                                   with BIL, etc.

  Dedicated subscription-worker-service        Cleaner scaling than embedding in APIs.             One worker service can subscribe to multiple topics.

  One worker deployment per concern            Higher maturity.                                    Separate SUB-LM workers, billing workers,
                                                                                                   fulfillment workers, cross-cutting workers.

  One deployment per topic                     Only for exceptional high-volume or risky topics.   More operational overhead; avoid as the default.


 Recommendation for this project:

 Start medium-budget with workers grouped by owning module or concern. Split high-volume or high-risk topics later.

 14.2 On-Prem Medium Deployment

  Fulfillment worker pods              2                                   1-2 vCPU, 2-4 GB RAM                  Consolidates FUL-* topics. Network
                                                                                                                 calls may be slower; size by latency.

                                                                                                                 kafka-emit, history append.

   - Route worker-to-Camunda and worker-to-module traffic through internal load balancers.
