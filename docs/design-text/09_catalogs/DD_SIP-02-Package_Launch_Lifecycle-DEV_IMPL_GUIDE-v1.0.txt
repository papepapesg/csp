 1. Implementation Goal
 Build the package lifecycle service that turns SIP-01 package definitions into sellable packages.

 SIP-01 creates package data. SIP-02 decides when that data is ready, approved, active, available by
 channel/franchise/region, suspended, or retired.

 Main implementation flow:
          sequenceDiagram
            participant UI as Product Backoffice
            participant SIP2 as SIP-02
            participant SIP1 as SIP-01
            participant PLM as PLM/BIL config APIs
            participant RUL as Drools/KIE
            participant APR as EM-CFG-04
            participant WKR as Catalog Worker

             UI->>SIP2: POST /api/package-launch-plans
             SIP2->>SIP1: load package and version
             UI->>SIP2: POST /validate
             SIP2->>PLM: validate service/tax/wallet/billable events
             SIP2->>RUL: launch readiness rules
             UI->>SIP2: POST /submit-review
             SIP2->>APR: evaluate/start approval if required
             APR-->>SIP2: approval callback
             WKR->>SIP2: activate when due
             SIP2->>SIP1: update package current version/status
             SIP2-->>UI: package is sellable through available API

 3. Step 2 - Create Launch Plan Endpoint
 Request:
           POST /api/package-launch-plans
           Idempotency-Key: package-launch-FIBER_100M_RES-pkv-202607
           Content-Type: application/json

           {
               "operatorCode": "WIK",
               "packageId": "pkg_01HX_100M",
               "packageCode": "FIBER_100M_RES",
               "packageVersionId": "pkv-100m-202607",
               "launchType": "FIRST_LAUNCH",
               "requestedLaunchAt": "2026-07-01T00:00:00+03:00",
               "effectiveTimezone": "Africa/Nairobi",
               "availability": [
                 {
                   "franchiseId": "fr-019",
                   "techRegionCode": "NRB-WEST",
                   "channelCode": "SALES_APP"
                 }
               ]
           }

 On reception on catalog API pod:

   1. Validate required fields.

   2. Check idempotency key.

   3. Load package and package version through SIP-01 service/repository.

   4. Confirm package version belongs to package.

   5. Create package_launch_plan in DRAFT.

   6. Store requested availability as draft metadata or create package_availability rows in SCHEDULED only after
     approval. Prefer creating rows after approval to avoid exposing unapproved availability.

   7. Write package_lifecycle_event with PACKAGE_LAUNCH_PLAN_CREATED.

   8. Publish outbox event PackageLaunchPlanCreated.

 Response:
           {
               "launchPlanId": "plp-001",
               "status": "DRAFT"
           }

 Request:

   2. Load SIP-01 package.

   3. Load SIP-01 package version.

   4. Load package composition services from PLM-CFG-01.

   5. Validate service statuses are active.

   6. Validate tax group through PLM-CFG-02.

          rule "High price package requires finance approval"
          when

          then
            $decision.setApprovalRequired(true);

          end


 6.3 Block Empty Service Composition
          rule "Package must contain at least one service"
          when
            $fact : PackageLaunchFact(serviceCount == 0)
            $decision : PackageLaunchDecision()
          then
            $decision.fail("PACKAGE_HAS_NO_SERVICE", "Package cannot launch without service composition.");
          end


 6.4 Region Expansion Requires Technical Readiness
          rule "Region expansion requires technical readiness check"
          when
            $fact : PackageLaunchFact(launchType == "REGION_EXPANSION")
            $decision : PackageLaunchDecision()
          then
            $decision.warn("REGION_EXPANSION_TECH_CHECK", "Confirm technical readiness for expanded region.");
          end

 The first version can keep these rules simple. The value is that future operators can change policy by configuration/rules
 instead of code.

 8. Step 7 - Approval Callback
 Endpoint:
           POST /internal/package-launch-plans/plp-001/approval-outcome
           Content-Type: application/json

           {
               "approvalRequestId": "apr-plp-001",
               "outcome": "APPROVED",
               "decisionComment": "Approved for WIK Nairobi launch."
           }

 SIP-02 flow:

   1. Find launch plan by id.

   2. Verify approvalRequestId matches stored value.

   3. If callback already processed, return 200 with current state.

   4. If APPROVED, move to:

   - SCHEDULED if requestedLaunchAt is future;

   - APPROVED if activation needs manual trigger;

   - or directly activate if policy allows immediate activation and time is due.

   5. If REJECTED, move to REJECTED.

   6. Write package_lifecycle_event.

   7. Publish PackageLaunchApproved or rejection event.

 Callbacks must be idempotent because EM-CFG-04 may retry delivery.



 9. Step 8 - Activation Worker
 Worker job: package-launch-activation.


SOPHIX BSS Design Documents                                                                                      Page 5
 Run every minute or consume a due-queue event.

 Flow:

   1. Find launch plans where status = SCHEDULED and requested_launch_at <= now.

   2. Lock one plan.

   3. Run final validation again.

   4. If any FAIL, mark activation failed/blocked and publish alert event.

   5. Start transaction.

   6. Update SIP-01 package master status to ACTIVE if first launch.

   7. Update SIP-01 package version status to ACTIVE.

   8. If version cutover, set previous active version SUPERSEDED.

   9. Set package.current_version_id = package_version_id.

   10. Create package_availability rows with ACTIVE.

   11. Create package_version_cutover row if current version changed.

   12. Create package_lifecycle_event with PACKAGE_ACTIVATED.

   13. Commit.

   14. Publish PackageActivated and PackageAvailabilityChanged.

   15. Invalidate package availability cache.

 Pseudo-code:
           public void activateDueLaunches() {
               List<PackageLaunchPlan> plans = launchRepo.findDueForActivation(clock.now(), 50);
               for (PackageLaunchPlan plan : plans) {
                   tx.required(() -> {
                       PackageLaunchPlan locked = launchRepo.lock(plan.id());
                       ValidationResult finalCheck = validator.validate(locked);
                       if (finalCheck.hasFail()) {
                           locked.markActivationBlocked(finalCheck.summary());
                           lifecycleEventService.recordBlocked(locked, finalCheck);
                           return;
                       }

                           sip01Service.activateVersion(
                               locked.packageId(),
                               locked.packageVersionId(),
                               locked.requestedLaunchAt()
                           );

                           availabilityService.activateAvailability(locked);
                           cutoverService.recordCutover(locked);
                           locked.markActivated();
                           lifecycleEventService.recordActivated(locked);
                           outbox.publish(PackageActivated.from(locked));
                    });
               }
           }

 11. Step 10 - Suspend And Resume Availability
 Suspend request:
           POST /api/packages/pkg_01HX_100M/availability/suspend
           Content-Type: application/json

           {
               "packageVersionId": "pkv-100m-202607",
               "franchiseId": "fr-019",
               "techRegionCode": "NRB-WEST",
               "channelCode": "SALES_APP",
               "reasonCode": "TEMPORARY_PROVISIONING_ISSUE",
               "comment": "ONT stock shortage in Nairobi West."
           }

 Flow:

   1. Load matching active availability rows.

   2. Check permission through EM-CFG-03/RBAC.

   3. If suspension policy requires approval, call EM-CFG-04 using action PACKAGE_AVAILABILITY_SUSPEND.

   4. If no approval required, set availability status SUSPENDED.

   5. Write lifecycle event.

   6. Publish PackageAvailabilityChanged.

   7. Invalidate cache.

 Resume is the same pattern with action PACKAGE_AVAILABILITY_RESUME.

 12. Step 11 - Retirement Flow
 Request:
          POST /api/package-retirement-plans
          Idempotency-Key: package-retire-OLD50-20260901
          Content-Type: application/json

          {
              "operatorCode": "WIK",
              "packageId": "pkg_01HX_OLD50",
              "retirementType": "END_OF_SALE",
              "effectiveAt": "2026-09-01T00:00:00+03:00",
              "existingSubscriberPolicy": "KEEP_AS_IS",
              "reasonCode": "PRODUCT_REPLACED_BY_100M"
          }

 Flow:

   1. Validate package exists.

   2. Check current active subscriptions through subscription read API if END_OF_LIFE or RETIRE_VERSION.

   3. If active subscriptions exist and policy is MIGRATE_REQUIRED, require migrationWorkflowRef.

   4. Run package-retirement-policy.drl.

   5. Evaluate approval through EM-CFG-04 when required.

   6. Schedule retirement.

   7. Worker executes at effectiveAt.

 Execution behavior:

   - END_OF_SALE: mark availability rows ENDED; leave package/version valid for existing subscriptions.

   - END_OF_LIFE: allowed only if no blocking active dependencies or approved migration plan exists.

   - RETIRE_VERSION: supersede/archive one version; do not break subscriptions that reference it historically.



 13. Step 12 - Cache Invalidation
 Use Redis keys like:
          catalog:package-availability:{operatorCode}:{channelCode}:{franchiseId}:{techRegionCode}:{date}

 Invalidate when these events happen:

   - PackageActivated

   - PackageAvailabilityChanged

   - PackageEndOfSale

   - PackageRetired

   - SIP-01 package/version updated

   - PLM-CFG-01 service status changed

 Do not rely only on TTL. Use event invalidation plus a short TTL.

 16. Step 15 - Frontend Flow
 Backoffice implementation should call modules in this order:

   1. Create/edit package definition through SIP-01.

   2. Create launch plan through SIP-02.

   3. Validate launch plan through SIP-02.

   4. Display launch checks with PASS/WARN/FAIL.

   5. Submit for review through SIP-02.

   6. If approval required, show EM-CFG-04 approval request/task link.

   7. After approval, show scheduled activation state.

   8. Once active, sales app/order capture uses GET /api/packages/available.

 The frontend should not call SIP-01 and directly set package status to active. Activation must go through SIP-02.

 18. Tests To Write First
   1. Create launch plan for existing package/version.

   2. Create launch plan for missing version returns 404.

   3. Validation fails when service is inactive.

   4. Validation passes with warning when Drools requires approval.

   5. Submit review calls EM-CFG-04 and stores approval request.

   6. Approval callback approved moves plan to scheduled/approved.

   7. Approval callback rejected moves plan to rejected.

   8. Activation worker updates SIP-01 current version and availability.

   9. Available packages API filters by channel/franchise/region/date.

   10. Suspension removes package from available API for that scope.

   11. End-of-sale blocks new sales but does not alter existing subscriptions.

   12. Retirement with active subscriptions and no migration plan is blocked.
