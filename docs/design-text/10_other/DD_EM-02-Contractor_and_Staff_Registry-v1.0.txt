 The system of record for who can do field work, where, and when: contractor companies + their staff, the geographic
 regions and service scopes each contractor covers, the technical skills each contractor is qualified for, the time-window
 availability slots each contractor accepts work in with concurrency caps, the per-WO slot commitments that consume that

 Owned at operator scope. Referenced by WO module Drools routing rules (the assign-contractor rule queries EM-02 to

 (ILM-CFG-02 provides region IDs that EM-02 references; no reverse FK), by OSR-01 (contractor_id referenced on

 foundation_auth_user_id linkage for notification dispatch).

 v1.0 scope: full contractor + scope + skills + availability + slot commitment + staff (main handler mandatory, optional roster)
 model. The slot ledger is owned by EM-02 (per user decision earlier in design discussion — one place owns both capacity
 and commitments). Per-staff skill certification is explicitly out of scope — BSS is not an HR or training system; staff
 qualification tracking belongs in the operator's HR / training systems.



 1. What this module is
 When WO module asks *"who can install fiber in KE-NRB-KAREN on Monday 2026-02-23 at 14:00 with skills
 fiber-install + ftth-cpe + vip-handling, and has capacity?"*, the answer is structural: there is a list of
 contractors covering KE-NRB-KAREN for service scope INSTALL, each with a skill profile and an availability slot schedule.
 EM-02 owns that structural data.

 The model is intentionally contractor-anchored — not staff-anchored. A contractor commits to a coverage window with a
 concurrency cap (e.g., "Franchise A van accepts up to 5 concurrent install WOs on Mondays 09:00–18:00"); how Franchise A
 internally staffs that capacity (which crew, which technician, which truck) is Franchise A's problem. The operator schedules
 against the slot, decrements the capacity at commitment, and trusts the contractor to deliver.

 The main-handler model
 For staff tracking, EM-02 takes a pragmatic two-tier approach reflecting the operational reality that external contractor staff
 churn is high and trying to mirror each contractor's internal HR moves is fragile:



SOPHIX BSS Design Documents                                                                                                                   Page 4
   - MAIN_HANDLER (mandatory) — every active contractor MUST have exactly one active MAIN_HANDLER staff record.
     The main handler is the operator's spoke into that contractor: the person of contact for assignations, slot scheduling,
     dispatching, escalation, and acknowledgments. ICN-01 dispatches contractor-facing notifications to the main handler's
     FOUNDATION_AUTH user. If the main handler leaves the contractor, the contractor's BO admin updates the main
     handler before the change takes effect (handover event tracked).

   - OPTIONAL_ROSTER (opt-in per contractor) — additional staff records for contractors who want full roster visibility in the
     operator system. Typically populated for INTERNAL contractors (where Wananchi is the employer) and for some large
     franchises with sophisticated ops. For most franchises, this stays empty — and that's fine. The operator system does not
     need to know every technician's name to schedule work.

 WO routing does not depend on individual staff data. The Drools assign-contractor rule filters by
 contractor_region_skill (contractor-level certification) — the question is "does this contractor have the skill in this
 region", not "does this specific technician have the skill". Per-person qualification tracking is not in EM-02 scope.

 What this module does
   1. Catalog contractors — operator-scoped, with identity (legal entity name, registration number, type — FRANCHISE /
     INTERNAL / SUB_CONTRACTOR), contract reference, contact details, performance reference (link to EM-04 Reporting
     metrics, pending).

   2. Define contractor coverage — per (contractor, tech_region_id, service_scope) row with effective dates. A contractor
     can be INSTALL+SUPPORT in one region but only SUPPORT in another.

   3. Maintain skill catalog — operator-extensible technical skill codes (fiber-install, ftth-cpe, dwdm-config,
     vip-handling, iptv-stb-setup, etc.). Operator can add new codes via config.

   4. Track contractor skill profiles per region — which skills a contractor is certified to perform in each region they cover.
     This is what WO routing filters on. Different regions may require different skill mixes.

   5. Define availability slots — day-of-week + hour-range windows with concurrency caps, per (contractor, region,
     service_scope). Multiple slots per contractor allowed (Monday morning + Monday afternoon as separate rows with
     different caps).

   6. Maintain slot commitment ledger — immutable record of every WO committed against a slot, with consumption +
     release. The slot's "remaining capacity at time T" is derived from the ledger.

   7. Resolve availability — POST /api/contractor-availability is the WO module's hot path: given (region, scope,
     required skills, datetime window, demand qty), return ranked list of contractors with capacity, with slot identifiers to
     consume.

   8. Track contractor main handlers — exactly one main handler per active contractor, mandatory; the spoke for all
     operator-contractor communication. Tracked via contractor_staff.staff_role_tier = MAIN_HANDLER.

   9. Optionally track contractor roster — for contractors who want it; same contractor_staff table with
     staff_role_tier = OPTIONAL_ROSTER. Most contractors leave this empty; the operator system doesn't require it.

 What this module does NOT do
   - Doesn't own tech region definitions. Region IDs, boundaries, candidate group codes — all ILM-CFG-02. EM-02 carries
     tech_region_id references only.

   - Doesn't define service scopes. The set of valid service scope values (INSTALL, SUPPORT, MAINTENANCE, RECOVERY,
     AUDIT) is operator-extensible and lives in a separate catalog or operator config. EM-02 enforces no canonical list at the
     schema level.

   - Doesn't pick the technician for a specific WO. EM-02 picks the contractor + commits to a slot. Which individual staff
     member from that contractor goes to that WO is the contractor's internal scheduling — not exposed to the operator
     system. (Some operators may surface this later via a staff-assignment-on-WO field; out of v1.0 for EM-02.)

   - Doesn't require a full contractor staff roster. OPTIONAL_ROSTER staff records are opt-in per contractor. The
     operator-contractor relationship runs through the main handler; the rest is internal to the contractor.

   - Doesn't track staff real-time location. Where a tech currently is, what they're doing — not EM-02. WO module tracks
     WO state; nothing tracks tech location in v1.0.

   - Doesn't filter WO routing by individual staff skills. Contractor-level certification (contractor_region_skill) is the
     routing filter. Per-staff skill data isn't tracked at all.




SOPHIX BSS Design Documents                                                                                                  Page 5
   - Doesn't track per-staff skill certifications. BSS is not an HR or training system. Operator HR / training departments
     already run systems that track who is qualified for what; replicating that in BSS adds maintenance burden with no
     operational payoff (WO routing uses contractor-level cert, not per-person).

   - Doesn't own staff personal data beyond identity + role. Payroll, leave, performance metrics, personal contact details —
     out of EM-02 v1.0 scope. Future HRM module owns those.

   - Doesn't manage contractor contracts as legal documents. Contract reference field is just a string identifier; the actual
     contract document, terms, vendor SLAs — live in an external contract management system or future procurement DD.

   - Doesn't decide work order priority within a slot. If a slot has 3 capacity remaining and 5 WOs come in, EM-02's
     commitment API returns "INSUFFICIENT_CAPACITY" for the overflow; the operator's WO module decides queueing /
     rescheduling policy.

 Regional flexibility
 Contractor structures vary significantly between operators:

   - WIK (Kenya) — hybrid: large internal team (wik-internal-tech-team) plus 6-8 franchise contractors across Nairobi
     neighborhoods + Mombasa + Diani. Franchises are small (10-20 staff each); internal team is larger. Mix of full-time staff +
     commission agents.

   - WUG (Uganda) — primarily franchise model; 3-4 contractors across Kampala divisions. Smaller scale, lighter
     administrative overhead.

   - WTZ (Tanzania) — TBD pending workshop; assumed smaller franchise network.

   - YASSN (Senegal) — Dakar-centric; mix of franchise and direct-employee model; bilingual French + Wolof staff records.

 The schema accommodates:

   - Multiple contractor types (FRANCHISE / INTERNAL / SUB_CONTRACTOR) — operator-extensible

   - Multi-region contractors (same contractor with rows in multiple contractor_region_scope)

   - Multi-skill contractors with operator-extensible skill catalogs

   - Multiple availability slots per (contractor, region, scope) for fine-grained scheduling

   - Bilingual staff and contractor display names

  R-EM-CS-1                   A contractor with active=false is
                              excluded from POST
                              /api/contractor-availability
                              results. In-flight slot commitments to
                              deactivated contractors continue to
                              honor existing WO completions; new
                              commitments are rejected.

  R-EM-CS-2                   coverage_role: a region+scope
                              may have ONE EXCLUSIVE row
                              (excludes all others), or one PRIMARY
                              + zero-or-more BACKUP rows. A
                              second PRIMARY row for the same
                              (region, scope) is permitted but
                              indicates load-share — Drools rule
                              decides allocation.

  R-EM-CS-3                   Skill certification at the contractor level
                              (contractor_region_skill) is
                              REQUIRED for the contractor to
                              appear in POST
                              /api/contractor-availability
                              results filtered by required skills. Skills
                              are a hard filter: a contractor lacking
                              even one required skill is excluded.
                              Per-staff skill data is not tracked by
                              EM-02; the contractor-level
                              certification is the only signal WO
                              routing consults.

  R-EM-CS-4                   Slot eligibility evaluation: for a WO
                              with committed_for_datetime =
                              X, a slot is eligible if (a)
                              active=true, (b)
                              committed_for_datetime falls
                              within the slot's [hour_start,
                              hour_end) window in the slot's
                              timezone, (c) the WO's day-of-week
                              matches day_of_week or

 7. Stub retirement
 EM-02 retires osr_contractor_stub from OSR-01.

 7.1 Retirement plan
 The stub osr_contractor_stub(contractor_id PK, contractor_name) exists today in OSR-01 v1.0 to satisfy the
 FK reference from stock_location.contractor_id. EM-02's contractor table is the canonical replacement.

 Migration steps:

   1. Pre-deployment: EM-02 schema deployed alongside osr_contractor_stub. Both tables coexist.

   2. Backfill: a one-time job iterates osr_contractor_stub rows. For each, insert a corresponding contractor row with
     contractor_type='FRANCHISE' (default; ops review for any INTERNAL ones), effective_from=<reasonable
     historical date>, and seed-script-derived display names. The contractor_id value is preserved verbatim (since
     stock_location rows already reference it).

   3. FK switch: stock_location.contractor_id FK target updated from osr_contractor_stub.contractor_id
     to contractor.contractor_id. Since the contractor_id values are identical, this is a metadata change only — no
     row updates needed.

   4. Verification window: 1 week with both tables coexisting. Spot-check that every active stock_location row resolves to a
     contractor row.

   5. Removal: drop osr_contractor_stub. OSR-01 §3.1 / §10 documentation updated to reference EM-02 directly.

 7.2 Caller-side changes
 OSR-01 BO admin UI ("Contractors" tab) now reads from EM-02's /api/contractors endpoint. Previously it read from the
 stub; now full contractor metadata (legal entity, contract reference, contact details, skills, slots) is available.

 WO module Drools rules previously had to fetch contractor info from EM-02 directly (since stub had only name); after
 retirement, the rules continue to call EM-02 — no code change required since stub-vs-EM-02 was already abstracted at the
 rule layer.
