 architecture explicitly separates that capability.

   - Use the owning module APIs/repositories for authoritative writes.

 A — Target
 1. What this process is about
 READ-01 owns the read-side surface for invoices: list, detail, status, and PDF stream endpoints consumed by the customer
 portal, mobile app, admin console, and B2B integrations.

 Reads are served from BIL-02 Core's tables. Invoice-type documents (cycle, one-off, credit/debit notes, tax invoices) live in
 invoice. Pro forma documents live in pro_forma (separate table by design — pro forma are informational projections,
 not legal documents). READ-01 reads both and exposes them through unified endpoints, with the response payload reflecting
 which table the row came from.

 #### The boundary with DD_NOT-01 Notification Service

  Concern                                                         Owned by

  Invoice list / detail / status retrieval (JSON)                 READ-01

  PDF stream retrieval (binary stream from object storage)        READ-01

  PDF rendering using per-operator templates                      DD_NOT-01 Notification Service

  Storage of rendered PDF artifacts                               DD_NOT-01 Notification Service (writes); READ-01 reads

  Per-channel templates (email, SMS, WhatsApp, Telegram, push)    DD_NOT-01 Notification Service

  Push delivery dispatch and retry on failure                     DD_NOT-01 Notification Service

  Caching of read responses                                       READ-01

  Access control on reads                                         READ-01

  Download audit log                                              READ-01


 #### What "downloading a PDF" actually means in this DD

 The PDF a consumer retrieves via READ-01 is not generated by READ-01. It was rendered by DD_NOT-01 Notification
 Service at issuance (consuming events like InvoiceIssued / CreditNoteIssued / TaxInvoiceSigned), stored in
 object storage, with its URL written to invoice.metadata.pdf_url. NOT-01 also sent that same PDF (or a link to it) to
 the customer through configured channels (email/SMS/etc.) at issuance.

 READ-01's "download" endpoint simply re-fetches that stored artifact. The customer or admin who already received the PDF
 at issuance can re-retrieve it any time.

 ##### The typical flow — basics before the deep dive

 Reading this DD in order, this is what actually happens 99% of the time:

   1. At issuance: GEN-01 (or TAX-01) writes the invoice row and emits InvoiceIssued. NOT-01 picks up the event,
     renders the PDF using the operator's template, stores it in object storage, writes the URL to
     invoice.metadata.pdf_url, and dispatches the customer notification (email/SMS/WhatsApp/etc. with the PDF or a
     link to it). All of this happens automatically, within seconds of the invoice being generated. The customer doesn't do


SOPHIX BSS Design Documents                                                                                                                Page 4
     anything — they just receive the notification.

   2. Later, when the customer or admin wants to re-retrieve the PDF: they hit GET /api/invoices/{id}/pdf.
     READ-01 reads metadata.pdf_url, fetches the file from object storage, streams it back. 200 OK, done. No
     request-to-render, no wait.

 The customer never explicitly requests rendering. Rendering is automatic. The download endpoint just serves what's already
 there.

 Read flow — list endpoint
          Client → GET /api/invoices?account_id=X&status=PENDING&sort=issue_date_desc&limit=20

          Step 1 — Auth & validation
            - Validate JWT
            - Extract scope: customer_id (CUSTOMER), operator_codes (ADMIN), or integration_id + customer_ids (INTEGRATION)
            - Validate filters: ensure customer_id matches JWT for CUSTOMER scope, operator_code is allowed for ADMIN, etc.

          Step 2 — Cache lookup
            - Build cache key: invoice:list:{customer_id}:{sha256(filter+sort+cursor)}:{limit}
            - GET from Redis
            - If hit → return cached payload (typical hot-path latency < 5ms)
            - If miss → acquire per-key lock (cache stampede protection); continue to Step 3

          Step 3 — Database query
            - InvoiceReadRepository.findByFilter(filter, cursor, limit)
            - Read-optimized query against `invoice` table with proper indexes
            - Returns slim projection per R-READ-01-L-4
            - For CUSTOMER scope, query already filters by customer_id; for ADMIN, by operator_code(s)

          Step 4 — Cache write
            - Serialize result; write to Redis with TTL = 1 min (per R-READ-01-C-2)
            - Release lock

          Step 5 — Return response
            - JSON body: { items: [...], next_cursor: "...", total_count: N }
            - Total typical p99 latency: 50ms on miss, 5ms on hit


 Read flow — detail endpoint
          Client → GET /api/invoices/{id}

          Step 1 — Auth & validation
            - Same as list

          Step 2 — Cache lookup

              - GET from Redis

 Read flow — PDF download
           Client → GET /api/invoices/{id}/pdf

           Step 1 — Auth & validation
             - Same as detail

           Step 2 — Detail read (cached)
             - Reuses the detail cache path to get invoice header
             - Check invoice.metadata.pdf_url
               - NULL → 202 Accepted with retry hint (R-READ-01-P-2)
               - "RENDER_FAILED" → 503 Service Unavailable (R-READ-01-P-3)
               - URL present → continue

           Step 3 — Object store fetch
             - InvoicePdfService.stream(pdf_url):
                 - Reads from S3-compatible store (or local FS in dev)
                 - Streams directly to client (no buffering in READ-01 memory)
                 - Supports range requests for partial downloads

           Step 4 — Audit log
             - Asynchronously write invoice_download_log row
             - Does NOT block the response

           Step 5 — Return PDF stream
             - Content-Type: application/pdf
             - Content-Disposition: attachment; filename="{legal_invoice_number}.pdf"
             - ETag: derived from invoice_id + pdf_url version
             - Cache-Control: private, max-age=31536000, immutable


 Cache invalidation flow
           Event arrives on Kafka (e.g., sophix.billing.invoice.cancelled, or sophix.notification.pdf.ready from NOT-01)

           Step 1 — InvoiceLifecycleEventConsumer reads the event
             - Extracts invoice_id, customer_id, operator_code

           Step 2 — InvoiceCacheInvalidator.invalidate(invoice_id, customer_id):
             - DELETE invoice:detail:{invoice_id}
             - DELETE invoice:status:{invoice_id}
             - SCAN + DELETE invoice:list:{customer_id}:* (all list pages for this customer)

           Step 3 — Ack the Kafka event

 B — Current TZ
 A unified invoice read API does not exist as a first-class concept in TZ Sophix. Various per-channel endpoints exist scattered
 across the codebase, but there is no consolidated read service with caching, ACL, or audit to describe or compare against.



 C — Gap & bridge
 READ-01 is entirely new functionality. The capability described in section A — unified API across consumers, event-driven
 Redis caching, NOT-01-rendered PDF serving, centralized access control, download audit logging — is introduced fresh by
 V3.
