 1. Purpose
 This DD defines the business RBAC catalog for SOPHIX BSS.

 FOUNDATION_AUTH owns authentication, Keycloak, JWT validation, and service-token validation. EM-CFG-03 owns the
 business authorization model layered on top of authentication:

   - business role catalog;

   - permission catalog;

   - role-to-permission matrix;

   - user role assignment;

   - user scope assignment;

   - frontend navigation/action visibility matrix;

   - API authorization lookup contract.

 Without this DD, every module and frontend would invent local role names. That creates inconsistent security and makes
 implementation hard to test.



 2. What This Module Is For
 Use EM-CFG-03 when the system needs to answer:

  Question                                                      EM-CFG-03 answer

  Which roles exist in this operator deployment?                Read role catalog.

  What can a role do?                                           Read role-permission matrix.

  Which user has which business roles?                          Read user role assignments, or mirror Keycloak groups into assignments.

  Which franchise/region/team can this user operate on?         Read user scope assignments.

  Should Backoffice show this menu/action?                      Read frontend role/action matrix.

  Should an API allow this command?                             Module checks JWT plus RBAC permission/scope.

  Which roles can approve future workflows?                     Approval catalog will reference role/permission codes from this DD.

 4. Ownership Boundary With FOUNDATION_AUTH
  Concern                                      Owner                                               Rule

  User login and sessions                      FOUNDATION_AUTH                                     Keycloak authenticates users and issues tokens.

  JWT roles claim                              FOUNDATION_AUTH                                     Token contains coarse roles/groups.

  Business role catalog                        EM-CFG-03                                           Defines canonical role codes and descriptions.

  Permission catalog                           EM-CFG-03                                           Defines permission codes modules enforce.

  User scopes                                  EM-CFG-03                                           Defines which operator/franchise/region/team a user
                                                                                                   can act on.

  API enforcement                              Owning module, using EM-CFG-03                      Module remains the final authority for its endpoint.

  Frontend visibility                          FE apps, using EM-CFG-03 matrix                     Hidden buttons are UX only, not security.


 Implementation rule: a module must never trust the frontend. Every protected endpoint validates the JWT, then checks
 required permission and scope server-side.

 11. Business Rules
  Rule                                                               Description

  RBAC-1                                                             Modules must validate JWT first, then permission, then scope.

  RBAC-2                                                             Frontend role/action matrix is UX only; backend authorization remains
                                                                     authoritative.

  RBAC-3                                                             Role codes and permission codes are stable API contracts and must not be
                                                                     renamed casually.

  RBAC-4                                                             A user without active role assignment has no business permissions, even if
                                                                     authenticated.

  RBAC-5                                                             A permission with scope_required = true must match target scope.

  RBAC-6                                                             GLOBAL scope is only allowed for approved admin roles.

  RBAC-7                                                             Critical permissions like rbac.manage, wallet.adjust, and
                                                                     billing.adjustment.approve must be audited.

  RBAC-8                                                             Removing a role assignment takes effect on next access check; tokens may still
                                                                     contain old coarse roles until expiry, so modules should use RBAC effective
                                                                     access for high-risk actions.

  RBAC-9                                                             Keycloak groups may seed role assignments, but EM-CFG-03 remains the
                                                                     business catalog used by BSS modules.

  RBAC-10                                                            Scope assignment values must resolve to their owning module before
                                                                     activation.

 13.4 FE-APP-04 Customer Self-Care
 Customer self-care normally uses customer-account scope from customer authentication mapping, not staff RBAC. If the
 same RBAC service is used, the role must be CUSTOMER_SELFCARE and the scope must be customer/account-bound. Staff
 roles must never grant access to customer self-care accounts.

 15. Infrastructure And Deployment
 For a budget-conscious medium deployment:

  Component                                                  Recommendation

  Runtime                                                    Run inside EM/business-services pod with EM-01 and EM-02.

  Database                                                   PostgreSQL em or rbac schema in shared business DB.

  Cache                                                      Redis for effective-access cache with short TTL, for example 2-5 minutes.

  Kafka                                                      Outbox events for cache invalidation and audit.

  Keycloak                                                   Keep as authentication source; mirror groups/roles through sync job if needed.

  Camunda                                                    Not required. Approval workflows use EM-CFG-04 later.

  Drools                                                     Not required. Permission checks should be deterministic service logic.

  Observability                                              Track deny rates, RBAC lookup latency, cache hit rate, sync failures, and
                                                             high-risk permission changes.

  Events                                                           Existing MSK/Kafka.

  Secrets                                                          Secrets Manager/SSM for Keycloak admin sync credentials.

  Audit                                                            Push RBAC audit events into central log/SIEM if available.




 16. Security Notes
   - Never allow a frontend-only decision to authorize an API write.

   - Never accept actorUserId or role from request body for user actions. Use JWT principal.

   - Cache effective access briefly, but invalidate on RBAC change events.

   - For high-risk actions, modules should call POST /api/rbac/check or use a freshly loaded effective access snapshot.

   - Keep role and scope changes auditable forever.

   - Do not expose all role assignments to ordinary users. Only administrators can browse role assignment data.



 17. Tests

  Test                                                             Expected result

  User with role and matching scope checks permission              ALLOW.

  User with role but missing target scope                          DENY.

  User with scope but missing permission                           DENY.

  Inactive role assignment                                         DENY.

  Retired permission                                               Not granted.

  Same idempotency key and same assignment payload                 Same response, no duplicate row.

  Same idempotency key with different payload                      409.

  Scope assignment to unknown franchise                            422.

  Effective access for Backoffice                                  Returns roles, permissions, scopes, and frontend actions.

  Role removal invalidates cache                                   Next effective access no longer includes role.

  Critical permission change                                       Audit row and outbox event created.
