 A — Target
 1. What this process is about
 BIL-03 is the cycle close engine — the module that detects when a Subscription's billing cycle has reached its end (or, for
 pre-payment, its start), and triggers the appropriate downstream actions. It runs continuously: scheduled scanners
 periodically evaluate every active Subscription against its cycle anchor, and at each cycle boundary fire the events and
 module coordination required by the Subscription's billing model.

 For postpaid Subscriptions (Wananchi KE/UG/TZ): at cycle end, BIL-03 emits CycleClosed so BIL-02 can generate the
 cycle's invoice. The customer's billing for what they consumed during the cycle is finalized at this point.

 For pre-payment Subscriptions (Yas SN): at cycle boundary, BIL-03 checks whether the upcoming cycle has been paid. If
 yes, it emits CycleActivated and the new cycle begins. If no, it emits CyclePaymentMissed and BIL-04 enters the
 Subscription into dunning. The customer's billing model demands prepayment-before-activation.

 BIL-03 is fundamentally a per-Subscription cycle anchor tracker, with the anchor and cycle window owned by SUB-LM-01
 (cycle_model, cycle_anchor_day, cycle_frequency_months, etc. — already documented in SUB-LM-01 and
 referenced in the canonical billing envelope per SUB-WF-FRAMEWORK-01). BIL-03's job is to detect the boundary, fire the
 right events, and update the Subscription's cycle anchor for the next cycle.

 Out of scope:

   - Generating invoices — owned by BIL-02 (invoicing). BIL-03 emits CycleClosed; BIL-02 consumes and generates the
     invoice.

   - Computing what's owed — owned by BIL-01 (charging engine). Charges accumulated during the cycle are queried by
     BIL-02 at invoice generation; BIL-03 itself does not compute amounts.

   - Detecting unpaid invoices post-due-date — owned by BIL-02 (invoicing). BIL-02 evaluates due dates after invoice
     generation and emits InvoiceOverdue when grace period expires.

   - Driving the dunning state machine — owned by BIL-04 (dunning). BIL-03 emits CyclePaymentMissed for
     pre-payment; BIL-04 consumes and creates the dunning state.

   - Cycle anchor configuration — owned by SUB-LM-01. Cycle attributes are set at Subscription activation by
     SUB-WF-ACTIVATE-01 and can be adjusted by SUB-WF-UPGRADE-01 / DOWNGRADE-01 / RELOCATION-01 /
     MIGRATION-01 as documented in those DDs.

   - Money math, prorate, settlement — owned by BIL-01.

   - Wallet balance, topup processing, wallet debit operations — owned by BIL-05 (Wallet & Topup, pending DD). BIL-03
     queries BIL-05 for balance and calls BIL-05 for debit at cycle boundary for PREPAID Subscriptions, but does not own
     wallet state.

   - Notification dispatch (cycle-end reminders, payment-required notices, etc.) — owned by notification module. BIL-03
     emits Kafka events at each cycle boundary; notification consumes.

   - Mid-cycle one-off charges — owned by BIL-01. These don't affect cycle close; they're settled at cycle close along with
     the regular cycle charge.

 Cycle close service — core logic
            @Service
            public class CycleCloseService {

                @Transactional
                public CycleCloseOutcome closeOne(String subscriptionId, CycleCloseRun run) {
                    CycleEvaluation eval = evaluationRepo.lockBySubscriptionId(subscriptionId);
                    SubscriptionSnapshot snapshot = subscriptionStateApi.fetchSnapshot(subscriptionId);

                    // Gate per R-BIL-03-C-4 and S-6
                    if (!isCloseEligible(snapshot)) {
                        return handleSkip(eval, snapshot);
                    }

                    // Idempotency per R-BIL-03-C-5
                    if (eval.getLastCycleClosedWindowEnd() != null
                        && !snapshot.getCycleWindow().getEnd().isAfter(eval.getLastCycleClosedWindowEnd())) {
                        return CycleCloseOutcome.SKIPPED_IDEMPOTENT;



SOPHIX BSS Design Documents                                                                                                      Page 12
                   }

                   try {
                       switch (snapshot.getBillingMode()) {
                           case POSTPAID:
                               return closePostpaid(subscriptionId, snapshot, eval);
                           case PREPAID:
                               return evaluatePrepaidWallet(subscriptionId, snapshot, eval);
                           case PREPAYMENT:
                               return evaluatePrePayment(subscriptionId, snapshot, eval);
                           default:
                               throw new IllegalStateException("Unknown billing mode");
                       }
                   } catch (Exception e) {
                       return handleFailure(eval, e);
                   }
               }

               private CycleCloseOutcome closePostpaid(String subscriptionId, SubscriptionSnapshot snapshot,
                                                        CycleEvaluation eval) {
                   cycleClosedEventPublisher.publish(buildCycleClosedEvent(snapshot));
                   cycleAnchorAdvancer.advance(subscriptionId, snapshot);
                   eval.recordClosed(snapshot.getCycleWindow().getEnd());
                   evaluationRepo.save(eval);
                   return CycleCloseOutcome.CLOSED;
               }

               private CycleCloseOutcome evaluatePrepaidWallet(String subscriptionId, SubscriptionSnapshot snapshot,
                                                                CycleEvaluation eval) {
                   BigDecimal cycleCharge = computeCycleCharge(snapshot);
                   WalletBalance balance = walletApi.fetchBalance(subscriptionId);

                   if (balance.getAmount().compareTo(cycleCharge) >= 0) {
                       // Wallet sufficient — debit and activate
                       String idempotencyKey = "cycle-debit-" + subscriptionId + "-" + snapshot.getCycleWindow().getEnd().toString();
                       WalletDebitResult debitResult = walletApi.debit(subscriptionId, cycleCharge, idempotencyKey);
                       cycleActivatedEventPublisher.publish(buildCycleActivatedPrepaidEvent(snapshot, debitResult));
                       cycleAnchorAdvancer.advance(subscriptionId, snapshot);
                       eval.recordClosed(snapshot.getCycleWindow().getEnd());
                       evaluationRepo.save(eval);
                       return CycleCloseOutcome.ACTIVATED;
                   }

                   // Wallet insufficient → CyclePaymentMissed (PREPAID variant)
                   cyclePaymentMissedEventPublisher.publish(buildCyclePaymentMissedPrepaidEvent(snapshot, balance, cycleCharge));
                   eval.recordPaymentMissed(snapshot.getCycleWindow().getEnd());
                   evaluationRepo.save(eval);
                   // Note: cycle anchor NOT advanced (R-BIL-03-W-3) — BIL-04 advances on wallet topup recovery (R-BIL-04-R-8)
                   return CycleCloseOutcome.PAYMENT_MISSED;
               }

               private CycleCloseOutcome evaluatePrePayment(String subscriptionId, SubscriptionSnapshot snapshot,
                                                             CycleEvaluation eval) {
                   String invoiceId = snapshot.getNextCycleChargeInvoiceId();
                   PaymentStatus paymentStatus = billingPaymentApi.fetchInvoicePaymentStatus(invoiceId);

                   if (paymentStatus == PaymentStatus.PAID) {
                       cycleActivatedEventPublisher.publish(buildCycleActivatedPrepaymentEvent(snapshot));
                       cycleAnchorAdvancer.advance(subscriptionId, snapshot);
                       eval.recordClosed(snapshot.getCycleWindow().getEnd());
                       evaluationRepo.save(eval);
                       return CycleCloseOutcome.ACTIVATED;
                   }

                   // UNPAID or PARTIALLY_PAID → CyclePaymentMissed (PREPAYMENT variant)
                   cyclePaymentMissedEventPublisher.publish(buildCyclePaymentMissedPrepaymentEvent(snapshot, paymentStatus));
                   eval.recordPaymentMissed(snapshot.getCycleWindow().getEnd());
                   evaluationRepo.save(eval);
                   // Note: cycle anchor NOT advanced (R-BIL-03-P-3) — BIL-01 advances on PaymentApplied (PREPAYMENT recovery)
                   return CycleCloseOutcome.PAYMENT_MISSED;
               }
          }

 C — V3 design rationale
 This DD's V3 design choices follow from the workshop requirements (section A) and the cross-operator billing-model variation
 (POSTPAID Wananchi, PREPAID wallet Wananchi, PREPAYMENT Yas SN). The design intent:

 What V3 introduces
   1. Dedicated billing-cycle-close module separate from invoice generation. Cycle-close emits events; invoice
     generation consumes them. Decoupling allows other consumers (BIL-04 dunning, BIL-05 wallet, notifications) to react to
     the same cycle events without reaching into invoice-generation internals.

   2. Three billing models on day 1: POSTPAID (Wananchi some customers), PREPAID wallet (majority of Wananchi
     customers), PREPAYMENT (Yas SN). Same module, three behaviors driven by the Subscription's billing_mode field.

   3. Eight distinct cycle events for downstream consumption — including WalletLowBeforeCycle for PREPAID
     pre-notice and CycleActivated (multi-mode) for both PREPAID wallet-debit success and PREPAYMENT cycle-paid.

   4. PREPAID wallet integration: BIL-03 queries BIL-05 for balance at cycle boundary, calls BIL-05 to debit wallet on
     successful activation, fires CyclePaymentMissed on insufficient balance.

   5. PREPAID auto-recovery coordination: BIL-04 calls BIL-03's advance-cycle-on-recovery endpoint after a wallet
     topup brings the customer back to good standing.

   6. Workflow event consumption for cycle evaluation sync — 8 workflow event consumers keep cycle evaluations aligned
     with subscription lifecycle changes.

   7. Mid-cycle prorate via CyclePartiallyClosed driving immediate prorated invoicing at pause.

   8. Pre-notice scanners for both PREPAYMENT (cycle invoice due soon) and PREPAID (wallet low before cycle).

   9. Late-payment realignment for PREPAYMENT (realign-on-late-payment) and recovery-cycle-advance for
     PREPAID (advance-cycle-on-recovery) — two distinct internal endpoints for the two billing models.

 Migration approach (TZ-baseline-agnostic)
   1. Deploy billing-cycle-close module with two tables on cluster C. Requires BIL-05 (Wallet & Topup) deployed first
     since BIL-03 calls BIL-05 for PREPAID cycle activation — BIL-05 is a hard dependency.

   2. Backfill phase (one-time at V3 cutover): for each currently-active Subscription, create a
     subscription_cycle_evaluation row with next_evaluation_at = current_cycle_end and
     next_evaluation_type = STANDARD_CLOSE. For Wananchi PREPAID Subscriptions: also create the daily
     wallet-low pre-notice entry. For Yas SN PREPAYMENT Subscriptions: also schedule the PRE_INVOICING and
     PRE_NOTICE entries. Cycle attributes come from SUB-LM-01 backfill (done as part of SUB-LM-01 migration). Billing
     mode comes from the V3 Subscription master record.

   3. Deploy Kafka consumers for SUB-WF-* events. These start populating the cycle evaluation table for new Subscriptions.

   4. Shadow mode: BIL-03 runs alongside whatever existing cycle-close mechanism the redeployed codebase has. BIL-03
     scans, emits events, but BIL-02 (still in pre-cutover mode) ignores them. Operators verify cycle detection accuracy on the
     new path — including the PREPAID wallet-debit dry-run mode (BIL-05 supports a dry-run debit that does not actually
     deduct balance, for shadow-mode verification). Concrete details of the existing mechanism will be confirmed in the
     cartography phase.

   5. Cutover: BIL-02 (new V3 mode) switches to consuming BIL-03's events. BIL-04 starts consuming
     CyclePaymentMissed and WalletLowBeforeCycle. Pre-cutover mechanism is disabled. BIL-05 wallet debits go live.

   6. Per-operator activation order (recommended): start with Wananchi POSTPAID (smallest segment, simplest), then
     Wananchi PREPAID (largest segment, most complex), then Yas SN PREPAYMENT (separate operator, isolatable).
