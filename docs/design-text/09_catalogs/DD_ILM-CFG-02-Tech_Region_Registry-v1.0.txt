 1. What this module is

SOPHIX BSS Design Documents                                                                                                                   Page 3
 When a customer orders new fiber at "Karen Hardy, Karen, Nairobi", the system must first answer: *what geographic region is
 this address in, is it inside the operator's footprint, and which Camunda candidate group should be notified for the dispatcher
 task?* This module answers those geographic questions. It provides a structured registry of:

   - Tech regions — the operator's named geographic zones (e.g., KE-NRB-KAREN, KE-NRB-EASTLANDS,
     KE-MOMBASA-NYALI).

   - Region boundaries — polygons, postcodes, or named-area lists defining what's inside each region.

   - Candidate group codes — Camunda BPMN-readable group codes (e.g., tech-region-NRB-KAREN) that map
     (region, task_type) to FOUNDATION_AUTH groups for ICN-01 dispatch.

 The matching follow-up question — *which contractor is qualified and available to actually do the work in this region for the
 requested service scope, on the requested day, with the required skills?* — is answered by EM-02 (pending). ILM-CFG-02
 provides the region identifier; EM-02 provides the scheduling answer.

 What this module does
   1. Catalog tech regions — operator-scoped named zones with stable IDs, display names, and parent regions (for
     hierarchy: country → province → city → neighborhood).

   2. Define region boundaries — three representations supported: polygon (GeoJSON), postcode/zip code list, or
     named-area list. Operators pick the representation that matches their data quality.

   3. Address lookup — given a service address (free text or structured), return the matching region(s). This is the entry point
     for WO routing and FUL-02 footprint validation.

   4. Footprint check — is this address in our operator's footprint? — yes / no answer used by FUL-02
     STEP-CAPTURE to gate order creation.

   5. Provide candidate group resolution — given a tech region + a task type (install / shift / support / NOC / dispatcher),
     return the appropriate FOUNDATION_AUTH group code that ICN-01 + Camunda use for notification + task assignment.

   6. Track footprint lifecycle — the operator may roll out new regions over time. Regions carry effective_from /
     effective_to for audit + retrospective routing analysis.

 What this module does NOT do
   - Doesn't model contractors or technicians. All entities around contractor identity, contractor service-scope per region,
     contractor technical skill sets, contractor availability slots (day/hour windows with concurrency caps), technician roster,
     skill certifications, and contractor performance live in EM-02 (pending). ILM-CFG-02 carries zero contractor or technician
     columns.

   - Doesn't route work orders. Contractor selection — "which contractor covers KE-NRB-KAREN, has skill ftth-cpe, and has
     a free slot Monday at 14:00 with VIP-handling certification" — is answered by EM-02. The Drools assign-contractor
     rule in WO module queries EM-02, not ILM-CFG-02.

   - Doesn't track technician location or dispatch state. That's WO module's domain (the WO row carries the assigned
     contractor + status). ILM-CFG-02 does not track who's in which region or where any person is.

   - Doesn't define the operator's coverage policy. The polygon, postcode list, or named-area list is operator-supplied. We
     store it and look up against it; we don't decide what's a covered area.

   - Doesn't replace FOUNDATION_AUTH. Candidate groups are FOUNDATION_AUTH groups; this module records the
     mapping (tech_region, task_type) → candidate_group_code but doesn't own group membership. A user
     being IN the FOUNDATION_AUTH group tech-region-NRB-KAREN is a FOUNDATION_AUTH concern; this module
     just says "for the NRB-KAREN region, install tasks notify this group code."

   - Doesn't do geocoding. When given a free-text address, the lookup may use an external geocoding service (Google Maps
     Geocoding API or HERE, configured per operator) to resolve to lat/lng + structured components. The cached geocode
     result is stored on the customer's account, not in this module. ILM-CFG-02 just consumes the geocoded result.

 Regional flexibility
 Different operators have different zone-naming conventions and different coverage models:

   - WIK (Kenya) — uses neighborhood-named regions (KE-NRB-KAREN, KE-NRB-EASTLANDS, KE-MOMBASA-NYALI, etc.).
     Hybrid coverage: some neighborhoods are direct internal teams, others are franchise contractors. Postal codes are
     sparse in Kenya; region boundaries primarily as named-area lists (with polygon fallback for high-detail regions).




SOPHIX BSS Design Documents                                                                                                  Page 4
   - WUG (Uganda) — uses district-named regions (UG-KAMPALA-CENTRAL, UG-KAMPALA-NAKAWA, UG-ENTEBBE, etc.).
     Mostly franchise contractors.

   - WTZ (Tanzania) — uses postcode + region hybrid (TZ-DSM-1101, TZ-DSM-1102, etc.). Postcode-based boundary
     representation is primary.

   - YASSN (Senegal) — uses arrondissement + commune (SN-DKR-PLATEAU, SN-DKR-MEDINA, etc.). Polygon-based
     boundaries (better address data in Dakar). Multi-language: zones display in both French and Wolof labels where used.

 The schema accommodates all four via:

   - region_boundary_type enum (POLYGON_GEOJSON | POSTCODE_LIST | NAMED_AREA_LIST) — operator picks per
     region

   - Multi-slot display labels (display_name_primary, display_name_secondary) for bilingual operators

   - Per-operator region_code_prefix convention (KE, UG, TZ, SN) baked into stored IDs but not validated by
     ILM-CFG-02

   - Per-operator candidate-group-code naming convention (e.g., WIK uses tech-region-<code>; YASSN uses
     tech-zone-<code>) configured per operator

 Regional flexibility is intentional throughout: the boundary representation has 3 options and the candidate-group naming is
 per-operator config. New operators' conventions land via config, not DDL.

 2. Tables overview + relationships
 2.1 Tables overview
 ILM-CFG-02 owns three tables — purely structural-geographic. Contractor identity, contractor service-scope per region,
 contractor skills, contractor availability slots, technician rosters, and skill certifications all live in EM-02
 (Employment Management, pending). The link from EM-02 entities back to ILM-CFG-02 is via tech_region_id
 references on EM-02-owned rows; ILM-CFG-02 itself carries no contractor or technician data.

  Table                                                            Purpose

  tech_region                                                      Operator-scoped catalog of named geographic zones, with hierarchy + display
                                                                   labels.

  tech_region_boundary                                             Per-region boundary definition; one row per region, one of three representations
                                                                   (polygon, postcode list, named area).

  tech_region_candidate_group_map                                  The (tech_region, task_type) → FOUNDATION_AUTH group_code
                                                                   mapping for Camunda + ICN-01 dispatch.

 #### What EM-02 owns (not in this DD)

 For context, the EM-02 module (pending) will own:

   - Contractor entity — the company/franchise/internal-team record. Identity, contract terms, billing, performance metrics,
     address.

   - Contractor region+scope coverage — which contractor handles which tech_region_id for which service_scope
     (INSTALL / SUPPORT / MAINTENANCE / RECOVERY / AUDIT). A contractor may handle INSTALL+SUPPORT in one
     region but only SUPPORT in another.



SOPHIX BSS Design Documents                                                                                                                Page 6
   - Contractor skills per region — which technical skills (fiber-install, ftth-cpe, dwdm, vip-handling, ...) this
     contractor is qualified to perform in this region. Drools routing in WO module filters candidate contractors by required skill
     set.

   - Contractor availability slots — day-of-week + hour-range windows during which the contractor accepts new
     assignments, with a concurrency cap per slot (e.g., "MONDAY 09:00–18:00, max 5 concurrent assignments";
     "SATURDAY closed"; "SUNDAY emergency-only, max 1"). The operator schedules WOs against these slots, not against
     individual technicians.

   - Technician staff under contractor — individual people employed by the contractor, with their FOUNDATION_AUTH user
     IDs. How a contractor internally staffs their slot capacity is the contractor's responsibility; the operator sees only "this
     contractor has accepted N WOs out of slot capacity M."

   - Skill catalog + certifications — the master list of skill codes + which staff members carry which certifications, with
     effective dates and expiry.

 ILM-CFG-02 references EM-02 indirectly: WO module's Drools rules query EM-02 for "contractors available in
 KE-NRB-KAREN for service_scope=INSTALL on Monday 14:00 with skill ftth-cpe", and EM-02 in turn references
 tech_region_id to filter. ILM-CFG-02 does not query EM-02 itself.

 2.3 Cross-DD anchoring
   - FUL-02 STEP-CAPTURE calls POST /api/tech-regions/check-footprint to validate a customer's service
     address is in footprint before allowing order capture (the workshop's "is this a covered area?" gate).

   - WO module FLOW-INSTALLATION / FLOW-SHIFTING / FLOW-SUPPORT queries ILM-CFG-02 for region resolution +
     candidate group code, then queries EM-02 for the actual contractor selection (which contractor has scope INSTALL in this
     region, has the required skills, has an available slot at the requested datetime). ILM-CFG-02 provides the region identifier;
     EM-02 provides the scheduling answer.

   - ICN-01 does NOT query this module directly — it queries FOUNDATION_AUTH for group members. But ICN-01's
      candidate-group codes (e.g., tech-region-NRB-KAREN) ORIGINATE here in
      tech_region_candidate_group_map. Camunda BPMN authors look up the right group code from this module's
      tables when designing per-operator BPMNs.

   - ILM-CFG-01 (Customer Service) customer_account rows can carry an optional home_tech_region_id denormalized
      field (resolved at order time, stored for fast access during support calls). This module is the source of truth; the account
      row is a cached pointer.

 7. Runtime walkthrough — narrative
 Two scenarios: (a) FUL-02 STEP-CAPTURE checks footprint before order creation; (b) WO module FLOW-INSTALLATION
 resolves tech assignment.

 7.1 Scenario A — FUL-02 footprint check at order capture
 A door-to-door agent in Lavington opens the FUL-02 BO UI to capture a new order at "Othaya Road 14, Lavington,
 Nairobi", customer Hon. Sarah Wanjiku. The agent enters the address. The BO UI calls FUL-02 STEP-CAPTURE, which
 before persisting the order calls:
          POST /api/tech-regions/check-footprint HTTP/1.1
          Authorization: Bearer <ful-02-service-jwt>
          Content-Type: application/json

          {
              "operatorCode":     "WIK",
              "structuredAddress": {
                 "city":         "Nairobi",
                 "neighborhood": "Lavington",
                 "country":      "KE"
              },
              "latLng":          { "lat": -1.2745, "lng": 36.7691 }
          }

 ILM-CFG-02's resolver:

   1. Pulls all active tech_region rows for WIK.

   2. For each region with boundary_type='POLYGON_GEOJSON': runs point-in-polygon for the lat/lng. (Spatial index would
     accelerate this in production.)

   3. For each region with boundary_type='NAMED_AREA_LIST': substring-matches the address neighborhood against
     boundary_named_areas. "Lavington" matches KE-NRB-LAVINGTON (the region's display_name_primary also
     matches; both signals agree).

   4. Returns KE-NRB-LAVINGTON as the primary match.

 Response:
          {
              "operatorCode":      "WIK",
              "inFootprint":       true,
              "primaryRegionId":   "KE-NRB-LAVINGTON",
              "checkedAt":         "2026-02-16T17:25:00Z"
          }

 FUL-02 stores KE-NRB-LAVINGTON on the order record's home_tech_region_id field, proceeds to KYC + payment steps.
 Per R-ILM-TR-12, the geocode result (lat/lng) is also stored on the order so future operations don't re-geocode.

   1. ILM-CFG-01 (Customer Service) — already shipped; provides the customer_account.home_tech_region_id field.

   2. FOUNDATION_AUTH — groups must exist before being referenced in tech_region_candidate_group_map.
     Operator deployment includes a auth-groups-seed.sql script creating the standard groups
     (tech-region-*-install, *-support, *-DISPATCHER, kenya-l1-kyc, kenya-kyc-leaders, etc.).

   3. Geocoding service — operator deployment configures geocoder_provider (one of google-maps, here, none). If
     none, footprint check operates polygon/postcode-only without geocoder fallback for unstructured addresses.

   4. Region + boundary + candidate-group-map seed — per-operator seed scripts populate the three tables from the
     operator's existing CRM/GIS data. WIK v1.0 seed includes all Nairobi neighborhoods + Mombasa + Diani; YASSN v1.0
     seed includes Dakar arrondissements; WUG and WTZ have partial seeds (pending full operator data).

   5. EM-02 (pending — does NOT block ILM-CFG-02 v1.0) — ILM-CFG-02 v1.0 ships and operates without EM-02. WO
     module routing rules can fall back to a flat config-file contractor list until EM-02 lands. ILM-CFG-02 itself has no FK
     dependency on EM-02.
