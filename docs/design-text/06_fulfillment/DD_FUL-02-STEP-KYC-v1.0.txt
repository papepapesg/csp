 Verdict: ■ New | Wave: 1 | Group III: Fulfillment | Version: v1.0 | Satellite of: DD_FUL-02-Order_Capture-v1.0.md

 Two human-in-the-loop approval steps that gate install dispatch in the KE WIK flow. The customer has paid, but before a
 contractor is sent out, two Wananchi staff must verify the customer's identity documents. L1 (regional supervisor) reviews
 first; if approved, Team Leader (operator-level) reviews second. Either rejection terminates the order. Phase: IN_KYC.



 1. What this step does
 The WIK business policy inherited from the workshop is no install dispatch without two-level KYC sign-off. The reason is
 regulatory + fraud control: ISP licences in Kenya require customer-identity verification before service activation, and
 contractors are expensive to dispatch — verifying the customer is real and the documents check out reduces wasted
 dispatches and protects the operator from fraud-driven chargebacks.

 The step has two user tasks stacked sequentially in the BPMN:

   1. kyc-l1-supervisor-approval — assigned to candidate group kenya-l1-kyc. A regional/franchise supervisor
     opens the customer's documents (ID front, ID back, address proof, captured by the field agent at order capture time and
     stored in document storage), checks them against IPRS (national ID registry) where available, and decides APPROVE or
     REJECT.

   2. kyc-team-leader-approval — assigned to candidate group kenya-kyc-leaders. Only created if L1 approved.
     The Team Leader sees L1's review as context and decides APPROVE or REJECT independently. This second review is a
     four-eye control — even if L1 was wrong or compromised, the order doesn't proceed to dispatch without Team Leader
     sign-off.

 A user task is a BPMN step that doesn't run code — it sits in Camunda's task list waiting for a human to claim and complete it
 through a UI. When Camunda creates the task, it triggers an HTTP connector that POSTs to FUL-02's
 NotificationHandlerResource (FRAMEWORK §3), which dispatches notifications (email, in-app push) to everyone in
 the task's candidate group. The first person to claim the task in the BO UI sees the documents, makes a decision, completes
 the task. The BPMN then advances.

 What this step deliberately doesn't do
   - Doesn't auto-reject on inactivity. There's no boundary timer on the user tasks in v1.0. If a supervisor doesn't pick up the
     task, ops sees the SLA breach on a NOC dashboard (driven by the OrderKycAwaitingL1 Kafka event timestamp) and
     pages someone. The customer has already paid; auto-cancelling for staff-side delay would be unfair. Future v1.x may add
     a soft escalation timer that pages without cancelling.

   - KYC two-level is a KE WIK business rule. Other operators in the architecture may adopt different qualification models
     via their own BPMN; v1.0 ships only the WIK BPMN with the two-level KYC pattern.

   - Doesn't persist decisions onto customer_order. Decisions live in Camunda process variables (kycL1Decision,
     kycL1Actor, kycTeamLeaderDecision, kycTeamLeaderActor, etc.) and are summarized in
     customer_order_phase_history.metadata when the phase transitions. The only customer_order change is
     failure_reason + failure_detail on rejection.

   - Doesn't fetch documents from storage itself. The notification payload carries document references (e.g.,
     idoc_01HX...front); the BO UI fetches actual document images from the document-storage service when the
     supervisor opens the task.

 7. Step-pinned rules
  ID                                                         Rule

  R-FUL-02-KYC-1                                             Two-level approval mandatory in WIK before install dispatch: L1 supervisor
                                                             (kenya-l1-kyc) → Team Leader (kenya-kyc-leaders). Both must
                                                             APPROVE. Team Leader is created only if L1 approved; if L1 rejected, Team
                                                             Leader never sees the task.

  R-FUL-02-KYC-2                                             Either level rejecting → terminal REJECTED state via order-mark-rejected
                                                             (STEP-VALIDATE's terminal worker, reused). No appeal path in v1.0 —
                                                             customer submits a new order if circumstances change. Rejection with
                                                             payment_received_amount > 0 triggers OrderRefundRequested via
                                                             order-mark-rejected (refund cascade).

  R-FUL-02-KYC-3                                             L1's decision (kycL1Decision, kycL1DecisionNotes, kycL1Actor) is
                                                             passed forward as context fields in the Team Leader's notification payload.
                                                             Team Leader is not blind — they see what L1 thought.

  R-FUL-02-KYC-4                                             Completion endpoint verifies the actor is in the task's candidate group via
                                                             FOUNDATION_AUTH before forwarding to Camunda. Out-of-group attempts →
                                                             403. The actor's user ID must also match the JWT subject — preventing one
                                                             person from "approving on behalf of" another.

  R-FUL-02-KYC-5                                             Candidate groups are operator-scoped in FOUNDATION_AUTH. v1.0 carries
                                                             only kenya-l1-kyc and kenya-kyc-leaders. Future WUG/WTZ
                                                             deployments adopting KYC two-level would have their own candidate groups
                                                             (e.g., uganda-l1-kyc, uganda-kyc-leaders). Group naming convention:
                                                             {country}-{level}-kyc and {country}-kyc-leaders.

  R-FUL-02-KYC-6                                             NO boundary timer on KYC user tasks in v1.0. KYC approvals are not
                                                             auto-rejected for inactivity (would be unfair to the customer who already paid).
                                                             Ops monitors via NOC SLA dashboards driven by OrderKycAwaiting* Kafka
                                                             event timestamps; tasks unclaimed >15 min trigger a pager alert.

  R-FUL-02-KYC-7                                             The KE WIK BPMN owns these two user tasks. Other operator BPMNs in the
                                                             architecture may use different qualification models; v1.0 ships only the WIK
                                                             BPMN.

  R-FUL-02-KYC-8                                             Decisions are NOT persisted as dedicated customer_order columns. They
                                                             live in Camunda's history (GET /engine-rest/history/variable-insta
                                                             nce?processInstanceId=...&variableName=kycL1Decision) and
                                                             customer_order_phase_history.metadata. Downstream needing
                                                             filterable orders by KYC outcome should use the OrderRejected Kafka event
                                                             (failureReason discriminates).

  R-FUL-02-KYC-9                                             Document references in the notification payload are opaque IDs (idoc_*); the
                                                             BO UI fetches actual document images from the document-storage service
                                                             when the supervisor opens the task. This step's payload deliberately doesn't
                                                             embed image bytes — would bloat the notification flow and create stale-image
                                                             risk.
