 3. Runtime Guardrails
 3.1 Workers
 Worker names in DDs are logical task contracts, not mandatory pods. A single worker application may handle many
 low-volume topics if metrics, retries, logs, and dead-letter handling remain visible per topic.

 Start with a small set of worker apps: subscription operations, billing operations, field operations, equipment operations,
 integration, and reporting/CVM. Split only for throughput, dependency isolation, security, or team ownership.

 3.2 Camunda
 Use Camunda for long-running workflows with timers, user tasks, approvals, compensation, retries, and visible operation
 state.

 Do not use Camunda for simple CRUD, request validation, read-only aggregation, or deterministic scans that can be
 scheduled commands/jobs.

 3.3 Drools
 Use Drools for operator-configurable policy: eligibility, routing, approval requirement, discounts, dunning thresholds,
 field-audit discrepancy treatment, and similar business decisions.

 Keep fixed validation in service code: required fields, enum checks, FK/existence checks, idempotency, unique constraints,
 and simple permission guards.

 Do not split a group until throughput, security, scaling, release independence, or team ownership requires it.

 6. Dev Guide Endpoint Note
 Some generated implementation guides include an Endpoint scan reference row in the runtime metadata table. Treat
 that row only as an extracted endpoint hint, not as the primary business command. The actual implementation order is
 defined by the DD's API section, request/response examples, and execution-flow guide.


 7. Remaining Implementation Deliverables
 The DD set is now broad enough for squad planning, but implementation still needs these concrete deliverables:

   - per-module OpenAPI files generated from the DD contracts;

   - automated contract tests for each published API;

   - cross-module E2E tests from DD_QA-01;

   - HLD and process-map PDFs refreshed to match the final DD set;

   - regenerated PDF/zip review pack after this coherence pass.


 8. Dev Reading Order
 For a new squad, read in this order:

   1. DD_INDEX.md and DD_CROSS-00-System_Traceability_and_Implementation_Map-v1.0.md.

   2. Foundation DDs for auth, DB, Kafka, cache, Camunda, Drools, file storage, and API standards.

   3. The owning module DD and its dev implementation guide.

   4. Any upstream/downstream DD listed in the module's cross-DD coordination section.

   5. The frontend DD that will consume the module API.

   6. DD_QA-01 scenarios that cover the feature.
