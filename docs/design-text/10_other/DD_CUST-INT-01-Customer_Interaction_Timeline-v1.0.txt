 1. Purpose
 This DD defines the unified Customer Interaction Timeline for SOPHIX BSS.

 The timeline gives customer care, supervisors, sales, service assurance, CVM, and reporting one chronological view of
 customer-facing activity:

   - manual customer notes and structured interactions from ILM;

   - ticket/case events from TCK;

   - sales lead activity from SALES;

   - customer notifications from NOT;

   - work order/customer visit milestones from WO;

   - billing/dunning customer-facing events from BIL;

   - future ASR and CVM activities.

 CUST-INT-01 is not a replacement for ILM, TCK, SALES, NOT, WO, or BIL. It is a normalized customer-history projection.
 Each owning module remains the source of truth for its own domain record.



 2. What This Module Is For
 Use CUST-INT-01 when the system needs to answer:

 10. Business Rules
  Rule                                                                   Description

  CINT-1                                                                 Source modules remain source of truth. Timeline rows are read-model
                                                                         summaries.

  CINT-2                                                                 Timeline ingestion must be idempotent by (operator_code,
                                                                         source_module, source_event_id).

  CINT-3                                                                 Customer-visible timeline events must be explicitly marked customer-safe by
                                                                         source module.




SOPHIX BSS Design Documents                                                                                                                    Page 7
  Rule                                                             Description

  CINT-4                                                           Internal-only notes, diagnostics, and staff comments must never appear in
                                                                   customer self-care.

  CINT-5                                                           If customer/account cannot be resolved, store an ingest error instead of
                                                                   dropping silently.

  CINT-6                                                           Timeline summary must be redacted before storage.

  CINT-7                                                           Entity links are references only; no cross-module foreign keys.

  CINT-8                                                           Reads must enforce RBAC and customer/account scope.

  CINT-9                                                           Corrections are additive. Do not mutate historical timeline content except for
                                                                   legal redaction/anonymization.

  CINT-10                                                          Customer 360 may tolerate missing timeline data; source modules still hold
                                                                   authoritative detail.




 11. Frontend Usage
 11.1 FE-APP-01 Backoffice
 Backoffice uses CUST-INT for the Customer 360 history panel.

  Area                                                             API

  Customer timeline panel                                          GET /api/customers/{customer_id}/timeline?limit=50

  Account timeline panel                                           GET /api/accounts/{account_id}/timeline?limit=50

  Filter by type                                                   query category=TICKET, category=BILLING, etc.

  Open source detail                                               Use timeline links[] and call owning module detail API.

  Ingest error repair                                              Platform ops screen over ingest-error APIs.


 UI rule: timeline is for scanning history. Source module detail pages remain the place to act.

 11.2 FE-APP-04 Customer Self-Care
 Self-care can use CUST-INT only for customer-visible events:
             GET /api/customers/me/timeline?visibility=CUSTOMER_VISIBLE&limit=20

 If this endpoint is not enabled, self-care continues to show ticket history from TCK and notification history from NOT
 separately.

 14. Tests
 Minimum tests:

  Ingest valid TCK event                                       Timeline row and link created.

  Ingest same source event twice                               One row only, same response.

  Ingest event missing customer id                             Ingest error created.

  RBAC missing customer scope                                  Timeline read returns 403.

  Redaction test                                               Sensitive fields not stored in summary.

  Consumer retry after transient failure                       Event eventually ingested once.




 15. Open Decisions For Review
  Decision                                                     Recommendation

  Should CUST-INT own manual customer notes?                   No. ILM already owns notes/interactions. CUST-INT projects them.

  Should CUST-INT be a separate deployment?                    Not initially. Start inside ILM/shared business services; split later if volume
                                                               grows.

  Should self-care show unified timeline?                      Optional. Start with tickets/notifications separately unless product wants one
                                                               customer-facing history.

  Should timeline store full event payload?                    No. Store safe summary and links; source module keeps full detail.

  Should source modules publish events or call internal API?   Prefer Kafka events. Allow internal API for early modules until event coverage is
                                                               complete.
