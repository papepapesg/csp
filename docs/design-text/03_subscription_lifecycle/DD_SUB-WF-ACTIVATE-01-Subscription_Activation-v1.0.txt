 DD_SUB-WF-ACTIVATE-01 - Subscription Activation
 Developer implementation guide: DD_SUB-WF-ACTIVATE-01-DEV_IMPL_GUIDE-v1.0.md.


 1. Purpose
 SUB-WF-ACTIVATE-01 defines the activation operation for a subscription.

 Activation moves a subscription from:
           CREATED -> ACTIVE

 It is the first state-changing workflow in the customer service lifecycle. After activation succeeds, the customer can receive
 service, billing can start, fulfillment has provisioned the network, equipment is bound, and downstream systems receive a
 SubscriptionActivated event.

 Use this DD when implementing:

   - POST /api/subscriptions/{subscription_id}/activate.

   - Activation preview.

   - Activation validation rules.

   - subscription_activation_config.

   - Activation-specific BPMN variables.

   - Activation-specific Kafka events.

   - Activation-specific Drools package behavior.

   - The activation composition of shared workers from DD_SUB-WF-FRAMEWORK-01-WORKERS.

 3. Mental Model
 Activation is not a simple status update.

 It is a saga:
            flowchart LR
                API[Activate endpoint] --> FW[SUB-WF Framework]
                FW --> BPMN[Activation BPMN]
                BPMN --> VALIDATE[Drools validation]
                BPMN --> LM1[SUB-LM pending status]
                BPMN --> BIL[Billing intent / payment]
                BPMN --> FUL[Fulfillment activation]
                BPMN --> HP[HomePass claim]
                BPMN --> OSR[Equipment bind]
                BPMN --> LM2[SUB-LM commit ACTIVE]
                BPMN --> EVT[Kafka event]
                BPMN --> NOTIF[Notification]

 The subscription must not become ACTIVE until the required activation work has succeeded.

 For WIK, the reference flow is pay-first:
            validate -> PENDING_ACTIVATION -> billing/payment -> network activation -> HomePass claim -> equipment bind -> ACTIVE

 Other operators may have different BPMNs, but they must use the same framework and worker contracts.


 4. Deployment Unit Clarification
 This DD does not introduce a standalone activation-service.

 Activation is deployed as part of the subscription workflow capability:

   - Route/controller in the SUB-WF application: POST /api/subscriptions/{subscription_id}/activate.

   - Config migration/table: subscription_activation_config.

   - BPMN process definition, for example sub-activate-wik.

   - Drools package, for example rules.subscription.activate.wik.

   - Worker usage through the shared worker catalog.

 Budget deployment:
            subscription app deployment:
              - SUB-LM module
              - SUB-WF framework module
              - activation endpoint/controller
              - activation BPMN deployment package
              - worker pods/commands as defined in the WORKERS DD

 Logical ownership still remains separate by DD, package/module, migration, route group, and metrics label.

 6. Data Model
 6.1 subscription_activation_config
 What this table is for:

 subscription_activation_config stores operator-level activation policy. The activation endpoint, Drools rules, and
 BPMN use this row to decide which activation paths are allowed.

 Use this table when:

   - Checking whether customer self-service activation is enabled.

   - Checking whether sales-field activation is enabled.

   - Checking whether scheduled activation is enabled.

   - Resolving the default cycle-anchor overflow policy.

   - Deciding whether equipment validation is strict.

   - Deciding whether backdated activation is allowed.

 Do not use this table for:

   - Package-specific equipment requirements. Use SIP/PLM catalog data.

   - Billing prices or proration formulas. Use BIL configuration and BIL-01.

   - Per-customer exceptions. Use operation request data or an approved override flow.

   - BPMN process key selection. Use subscription_operation_config from the framework DD.
           CREATE TABLE subscription_activation_config (
             operator_code                       TEXT PRIMARY KEY,
             cycle_anchor_overflow_default       TEXT NOT NULL DEFAULT 'PRORATE_PARTIAL_CYCLE',
             customer_self_service_enabled       BOOLEAN NOT NULL DEFAULT FALSE,
             sales_field_activation_enabled      BOOLEAN NOT NULL DEFAULT TRUE,
             scheduled_activation_enabled        BOOLEAN NOT NULL DEFAULT TRUE,
             equipment_binding_validation_strict BOOLEAN NOT NULL DEFAULT TRUE,
             backdating_allowed                  BOOLEAN NOT NULL DEFAULT FALSE,
             backdating_max_days                 INTEGER NOT NULL DEFAULT 0,
             backdating_required_role            TEXT NULL,
             updated_at                          TIMESTAMPTZ NOT NULL DEFAULT NOW(),
             updated_by                          TEXT NOT NULL,

             CHECK (cycle_anchor_overflow_default IN (
               'ROUND_TO_28',
               'ROUND_TO_1_NEXT_MONTH',
               'PRORATE_PARTIAL_CYCLE'
             )),
             CHECK (
               (
                  backdating_allowed = FALSE
                  AND backdating_max_days = 0
                  AND backdating_required_role IS NULL
               )
               OR
               (
                  backdating_allowed = TRUE
                  AND backdating_max_days > 0
                  AND backdating_required_role IS NOT NULL
               )
             )
           );

 7. Business Rules
 7.1 Preconditions
  Rule                                                                         Description

  R-ACT-P-1                                                                    Subscription must be in CREATED. Otherwise return 409
                                                                               INVALID_STATE_FOR_ACTIVATION.

  R-ACT-P-2                                                                    Package must exist and be ACTIVE in SIP-01 at activation time. Otherwise
                                                                               return PACKAGE_RETIRED or PACKAGE_NOT_ACTIVE.

  R-ACT-P-3                                                                    HomePass must be sellable in RLM-CFG-01. Otherwise return
                                                                               HOMEPASS_NOT_SELLABLE.

  R-ACT-P-4                                                                    Trigger role must match the trigger and config flags.

  R-ACT-P-5                                                                    Operation framework must reject duplicate in-flight state-changing operations
                                                                               for the same subscription.

  R-ACT-P-6                                                                    Idempotent retry with same key and same payload returns the existing
                                                                               operation. Same key with different payload returns 409.



 7.2 Cycle Anchor Overflow
 Overflow applies only when:
           cycle_model = CALENDAR_ANCHOR
           activation day is 29, 30, or 31

  Policy                                            Behavior                                                When to use

  ROUND_TO_28                                       Set cycle_anchor_day = 28.                              Simple rule, no special first-cycle logic.




SOPHIX BSS Design Documents                                                                                                                               Page 4
  Policy                                     Behavior                                            When to use

  ROUND_TO_1_NEXT_MONTH                      Set cycle_anchor_day = 1 for the next month.        Operator wants clean monthly billing from day 1.
                                             Billing cycle starts next month.

  PRORATE_PARTIAL_CYCLE                      Set cycle_anchor_day = 1; bill partial period       Operator wants immediate service and fair
                                             from activation date to next day 1.                 partial-cycle charge.


 Rules:

  Rule                                                                Description

  R-ACT-OV-1                                                          Caller may provide cycleAnchorOverflowPolicy; if absent, use subscrip
                                                                      tion_activation_config.cycle_anchor_overflow_default.

  R-ACT-OV-2                                                          Resolved cycle_anchor_day must be valid for SUB-LM, which means 1 to
                                                                      28.

  R-ACT-OV-3                                                          For ROLLING_DAYS, no overflow policy applies. Cycle starts from
                                                                      activated_at.

  R-ACT-OV-4                                                          BIL-01 computes money for partial cycle. Activation workflow only passes cycle
                                                                      and context facts.



 7.3 Equipment Bindings
 Equipment binding request item:
           {
               "equipmentRequirement": "GPON_ONT",
               "equipmentRef": "ont_01HZ_NEW01"
           }

 Rules:

  Rule                                                                Description

  R-ACT-EB-1                                                          Supplied equipmentRequirement values must match package/service
                                                                      equipment requirements from SIP/PLM.

  R-ACT-EB-2                                                          Missing required equipment returns 400 EQUIPMENT_MISSING.

  R-ACT-EB-3                                                          Extra equipment not required by the package returns 400
                                                                      EQUIPMENT_NOT_REQUIRED, unless operator rules explicitly allow it.

  R-ACT-EB-4                                                          When strict validation is enabled, equipmentRef must exist in OSR and be
                                                                      available for binding.

  R-ACT-EB-5                                                          After fulfillment succeeds, osr-equipment-bind binds equipment to the
                                                                      subscription.

  R-ACT-EB-6                                                          Equipment authoritative state is OSR. Activation events may include equipment
                                                                      binding summary for downstream visibility.



 7.4 Backdating
 Rules:

  Rule                                                                Description

  R-ACT-BD-1                                                          Backdating is allowed only when backdating_allowed = true.

  R-ACT-BD-2                                                          Backdated date must be within backdating_max_days.

  R-ACT-BD-3                                                          Backdating requires backdating_required_role.

  R-ACT-BD-4                                                          Future activation dates must not be accepted by this endpoint. Use
                                                                      scheduler-driven activation instead.

  R-ACT-BD-5                                                          When backdating is accepted, activated_at uses the intended date, but the
                                                                      workflow still runs now.



 7.5 Final State Rules
  Rule                                                                Description

  R-ACT-F-1                                                           Activation success must commit SUB-LM status to ACTIVE.

  R-ACT-F-2                                                           Activation failure after pending state must revert subscription to CREATED.

  R-ACT-F-3                                                           Activation must emit SubscriptionActivated only after final state commit
                                                                      succeeds.

  R-ACT-F-4                                                        Activation failure must emit SubscriptionActivationFailed after

 12. Auth
 Activation endpoint must use FOUNDATION_AUTH.

 Rules:

   - Resolve actor user and role from JWT/service token.

   - Do not trust actor role from request body.

   - Service-to-service calls must use service accounts.

   - CUSTOMER_SELF_SERVICE trigger requires both role and config flag.

   - SALES_FIELD trigger requires both role and config flag.

 13. Error Handling
  Error code                                    HTTP/status                                   Meaning

  INVALID_STATE_FOR_ACTIVATION                  409                                           Subscription is not CREATED.

  ALREADY_ACTIVE                                409                                           Subscription is already ACTIVE.

 14. Implementation Notes
 14.1 Trigger Endpoint Sequence
 Use this sequence:

   1. Authenticate caller.

   2. Resolve actor user ID, role, and operator scope from auth context.

   3. Validate Idempotency-Key.

   4. Validate request shape.

   5. Load subscription from SUB-LM/read model.

   6. Load subscription_activation_config.

   7. Load framework subscription_operation_config for (operator_code, ACTIVATE).

   8. Validate trigger role and config flags.

   9. Validate subscription is CREATED.

   10. Validate package and HomePass references.

   11. Validate equipment request shape.

   12. Call framework start operation contract with operationKind=ACTIVATE.

   13. Framework creates subscription_operation and starts BPMN.

   14. Return 202 Accepted.

 Keep trigger endpoint logic thin. Detailed orchestration belongs in BPMN.

 14.2 Idempotency
 Activation trigger must use framework idempotency:
             (operator_code, idempotency_key)

 Same key and same request:
             return existing operation

 Same key and different request:
             409 IDEMPOTENCY_KEY_REUSED_WITH_DIFFERENT_REQUEST

 Recommended idempotency key from FUL-02:
             activation:<subscriptionId>:<onboardingRef>


 14.3 Activation Date Resolution
 Compute these values before billing and final commit:

  Value                                                                Meaning

  resolvedActivatedAt                                                  Date/time that business treats as activation time.

  resolvedCycleAnchorDay                                               SUB-LM-safe anchor day, 1 to 28.

  cycleAnchorOverflowApplied                                           Null or selected overflow policy.

  partialCycleDays                                                     Days to pass to billing for partial-cycle calculation.


 Do not let SUB-LM accept invalid anchor days. Activation must resolve days 29-31 before calling
 sub-lm-put-master-fields.

 14.4 Equipment Validation
 Validation has two layers:

   1. Shape validation in API/BPMN: array exists, fields are present, no duplicate equipmentRequirement.

   2. Business validation through catalog/OSR: required equipment matches package, equipment instances exist and can be
     bound.

 Do not bind equipment before network activation succeeds unless the operator BPMN explicitly requires early reservation.

 14.5 Compensation
 Minimum compensation behavior:

  Failure point                                                        Compensation

  Validation fails before pending state                                Finalize failed; no subscription revert needed.

  Pending state set, billing fails                                     sub-lm-revert-to-prior, finalize failed.

  Payment timeout                                                      bil01-revert-pending-charge, sub-lm-revert-to-prior, finalize
                                                                       failed.

  Fulfillment fails                                                    bil01-revert-pending-charge, sub-lm-revert-to-prior, finalize
                                                                       failed.

  Equipment bind fails after fulfillment                               Reverse fulfillment if available, revert charge, revert subscription, finalize failed.

  SUB-LM commit fails after fulfillment                                Route to manual recovery; do not silently mark completed.



 14.6 Event Timing
 Emit SubscriptionActivated only after:

   1. SUB-LM commit to ACTIVE succeeded.

   2. Required billing confirmation succeeded, if pay-first is used.

   3. Required fulfillment succeeded.

   4. Required equipment binding succeeded or was explicitly skipped by policy.

 15. Infrastructure Recommendations
 Activation does not require separate infrastructure from SUB-WF.

 Deploy these artifacts with the subscription workflow service:

  Artifact                                                          Where it runs

  Activation endpoint/controller                                    SUB-WF API pods.

  Activation config migration                                       Application DB migration pipeline.

  Activation BPMN files                                             Camunda deployment pipeline.

  Activation Drools packages                                        Drools/KIE deployment pipeline.

  Activation worker usage                                           Worker pods from the WORKERS DD.


 Medium deployment guidance:

   - Use the SUB-WF API and worker sizing already defined in the framework and worker DDs.

   - Ensure at least two worker replicas can process activation topics.

   - Ensure activation worker topics have dashboards for backlog, failure rate, and p95 duration.

   - Ensure FUL-03 and BIL-01 latency stays below worker lock-duration safety margins.

 AWS guidance:

   - No separate ECS/EKS service is required just for activation.

   - Deploy activation BPMN and rules as versioned artifacts.

   - Use CloudWatch alarms for activation failure rate, payment timeout count, fulfillment failure count, and stuck
     PENDING_ACTIVATION subscriptions.
