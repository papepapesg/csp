 1. What this flow is
 A Support WO captures one customer-reported issue from creation through resolution. Caller — the future Ticketing module
 (creating Support WOs from customer tickets with originating_context_type=TICKET), CSR via BO UI (manual
 creation), or the field contractor (raising a QCS escalation) — supplies the customer, the HomePass, the issue category, the
 contact info, and any operator metadata. The flow handles assignment, optional dispatch (some Support WOs resolve at the
 desk without a site visit), on-site work, the resolution gate, equipment binding when hardware is replaced, the QCS escalation
 pattern when the contractor cannot resolve, and warranty-aware RPT linkage when the issue is a repeat.

 Three non-negotiable rules from the workshop:

   1. Some Support WOs don't need a site visit. The Job Type catalog marks each code with requires_site_visit.
     Codes like remote-modem-reboot (HS4 Modem Disconnection rare case), Proactive Support (PSO, PSI) when handled
     remotely, and QCS escalation routed to NOC (NOC resolves remotely or dispatches maintenance themselves) may
     complete without dispatching a tech. The BPMN's first gateway routes between desk-resolution path and full-on-site-flow
     path based on the WO's job_type.requires_site_visit flag.

   2. Escalation is two-WO (Pattern A), not single-WO. Unlike Installation (Pattern B reassignment within same wo_id),
     Support uses a finalize-original-then-spawn-new pattern. The contractor finalizes their support WO with a final reason
     indicating "could not resolve; escalating" and the framework's flow worker emits WorkOrderEscalationCandidate. A
     new QCS WO is then created — either by the contractor directly (BO UI manual creation) in v1.0, or by the future
     Ticketing module subscribing to the event and auto-creating. Both paths land at POST /api/work-orders with
     master_wo_id set to the original.

   3. Area-outage is a clean closure with the customer not resolved. When the field tech determines the issue is an
     area-wide outage handled separately by NOC's outage-management process, the Support WO closes with
     final_reason=AREA_OUTAGE_OPEN. No QCS is raised — the outage already has its own tracking. The customer
     remains affected until the outage is fixed (out of this flow's concern).

 The Support flow is single-phase — current_phase stays NULL throughout. Unlike Shifting, Support does not have
 sub-phases. Unlike Installation, it does NOT use Pattern B reroute (same wo_id, new team) — when work hits a wall, the WO
 closes and a separate QCS WO opens.

 Cross-country variation
 This BSS deploys in any Wananchi-Group country. Support flow's cross-country differences are smaller than Installation's (no
 topology-capture concern — the customer's HomePass already has the topology from their prior install). The variation surface
 is mostly:

   - Job Type catalog rows (each country has its own service codes).

   - Final-reason catalog (operator-specific resolution categories).

   - Required-before-finalize checklist (operator preferences for evidence).

   - Drools rules for assignment + resolution-gate thresholds.

 The same per-operator BPMN/Drools/config pattern applies; no flow code changes between operators.

 What this flow does NOT do
   - Doesn't create tickets. The future Ticketing module owns ticket lifecycle (customer reaches out → ticket opened →
     categorized → routed); Ticketing creates a Support WO when field action is needed. v1.0 ships without Ticketing —
     Support WOs in v1.0 come from BO UI manual creation by CSRs.



SOPHIX BSS Design Documents                                                                                                Page 4
   - Doesn't manage area outages. Outages have their own NOC process (out-of-scope for v1.0 SOPHIX). The Support flow
     just provides the AREA_OUTAGE_OPEN exit so contractors can close their visit cleanly while the outage is handled
     elsewhere.

   - Doesn't compute warranty status. The wo-check-warranty-linkage worker (§7) queries existing WOs by customer
     to find a recent install/support within the warranty window; the result drives RPT creation but the warranty calculation itself
     is pure read against work_order.completed_at + warranty_days. No separate warranty subsystem.

   - Doesn't bill the customer. Customer billing is unaffected by support visits in v1.0; contractor invoicing (which DOES
     depend on TRC/TRD/standard codes) is downstream of WorkOrderSupportCompleted event consumed by Finance.

   - Doesn't define the WO module's state machine, REST API, schemas, contractor model, or Kafka primitives —
     those live in DD_WO-01-FRAMEWORK.

                                                                     the RPT mostly exists for tracking + contractor billing implications (TRC/TRD

 The Drools resolution-gate reads the WO's final-reason code + the optical/signal readings + the notes. Three outcomes
 per workshop:

   - RESOLVED — issue addressed; equipment bindings captured if hardware was changed; final close.

   - NOT_RESOLVED_ESCALATE — issue beyond contractor's scope; escalation candidate flag set; final close with that
     final_reason; Pattern A QCS spawning happens after.

   - AREA_OUTAGE — issue is part of a known area outage; closes cleanly without escalation (no QCS); customer-affecting
     status handled by NOC's separate outage process.

 2.4 Cancellation
 Same framework pattern as DD_WO-01-FLOW-INSTALLATION §2.3 and DD_WO-01-FLOW-SHIFTING §2.3 — interrupting
 boundary message event on WorkOrderCancellationRequested. Valid in any non-terminal status.

 2.5 Per-operator BPMN composition
 The Support flow varies per operator without code change. v1.0 ships WIK. Future operators can:

   - Adjust the no-site-visit eligibility (some operators may always require a tech visit regardless of job type).

   - Tune the Drools resolution-gate thresholds (signal-level cutoffs differ by network deployment).

   - Add a pre-dispatch ticket-triage user task between WO creation and contractor assignment.

   - Change escalation behavior (some operators may use Pattern B reroute for Support, like Installation, instead of Pattern A
     QCS spawn).

 5. Pattern A escalation — narrative
 The Support flow's escalation pattern is fundamentally different from Installation's. Installation uses Pattern B (same wo_id,
 reassigned to maintenance/construction, returns to install contractor for finalize). Support uses Pattern A: two-WO
 sequence — finalize the original Support WO, raise a new QCS WO.

 5.1 Pattern A rationale (workshop quote)
 From the workshop transcript:

 Previously the same WO was passed between contractor and maintenance — making it impossible to separately track the
 maintenance team's output. QCS gives maintenance their own trackable count.

 So Pattern A exists for operational accountability: the contractor's WO count reflects their workload; the NOC's QCS count
 reflects theirs. Pattern B (Installation) doesn't have this problem because the install contractor retains ownership end-to-end;
 with Support, the work genuinely transfers to a different team.

 5.2 Pattern A mechanics
 When the contractor first-confirms the original Support WO with final_reason = COULD_NOT_RESOLVE_ESCALATED:

   1. Drools resolution-gate returns NOT_RESOLVED_ESCALATE.

   2. Flow worker wo-mark-escalation-candidate runs. Appends an escalation_candidate_reason note with the
     contractor's handoff summary ("ONT RX -32 dBm, optical fault upstream — need OLT-side check"). Sets
     metadata.escalationCandidatePending = true on the WO.

   3. Second-confirm proceeds. Framework's checklist passes; WO transitions to COMPLETED.

   4. wo-emit-state-event fires WorkOrderFinalized (framework event, status=COMPLETED).

   5. wo-emit-escalation-candidate-if-needed runs AFTER WorkOrderFinalized. Reads
     wo_final_reason_catalog.triggers_escalation_event for the WO's (operator, kind, job_type,
     final_reason). For COULD_NOT_RESOLVE_ESCALATED this is true. Worker emits
     WorkOrderEscalationCandidate (framework event from DD_WO-01-FRAMEWORK §7).

 The original Support WO is now closed. A separate QCS WO needs to be created — that's step 6, which has two
 implementations depending on whether Ticketing module exists.

 5.3 QCS WO creation — v1.0 (no Ticketing module yet)
 In v1.0 the future Ticketing module hasn't shipped. The QCS WO must be created manually by the contractor via BO UI:

   1. Contractor's BO UI subscribes to WorkOrderEscalationCandidate events for their own WOs. When one arrives, UI
     surfaces a prompt: "Original WO finalized as escalation. Create QCS handoff to NOC?"

   2. Contractor confirms via UI button. UI calls:
            POST /api/work-orders HTTP/1.1

          {
              "operatorCode":           "WIK",
              "kind":                   "SUPPORT",

 The new QCS WO starts a fresh Camunda process instance (same Support BPMN). The auto-assignment Drools picks
 ctr_NOC_MAINT (rule r3-qcs-noc-maintenance). NOC owns the new WO.

 5.4 QCS WO creation — future (with Ticketing module)
 When Ticketing module ships, the option to use automatic spawning opens. Ticketing subscribes to
 WorkOrderEscalationCandidate events and:

   1. Reads the event payload (carries the original wo_id, customer, homepass, final reason, last findings note).

   2. Decides whether to spawn QCS based on operator-configurable Drools rules in the Ticketing module.

   3. If yes: Ticketing calls the same POST /api/work-orders endpoint above with
     originating_context_type=TICKET (the new ticket Ticketing opened) and master_wo_id set to the original.

   4. Returns success or "decided not to escalate" with a reason captured on the ticket.

 Both paths coexist — contractor can still raise manual QCS via BO UI; Ticketing can auto-create. If both fire for the same
 source event (race), the framework's idempotency on (operator_code, originating_context_type,
 idempotency_key) deduplicates — Ticketing's auto-create uses one idempotency key, contractor's manual uses a
 different one, so they could in theory both succeed. Best-practice: Ticketing's auto-create includes the original wo_id in the
 idempotency key (qcs-auto-from-<original-wo-id>); contractor's manual uses the same key
 (qcs-from-<original-wo-id>). Same key → second call returns 409 IDEMPOTENCY_HIT. The flow doesn't enforce
 which side wins; it only ensures one QCS exists per source escalation.

 5.5 What the QCS WO does
 The QCS WO is just another Support WO with job_type=QCS. It runs through the same Support BPMN as any other
 Support WO. Differences from a regular Support WO:

   - Assigned team is ctr_NOC_MAINT (internal NOC), set by Drools contractor-assignment-decision.

   - master_wo_id is set to the original Support WO + link_type=ESCALATION.

   - NOC verifies optics / signal levels remotely first. If they can resolve remotely →
     final_reason=MAINTENANCE_RESOLVED, close.

   - If they cannot resolve remotely → dispatch maintenance team physically. Same QCS WO, reassigned (TEAM-mode
      reassignment) within NOC.

   - Workshop is explicit: "Once maintenance resolves: updates and closes the QCS WO. No further WO raised back to
     the contractor."

 QCS does NOT trigger a Pattern A escalation back. If maintenance escalates further, it's a separate operational matter
 outside the WO flow (engineering ticket, area-outage declaration, customer compensation review — handled by other
 modules, not by spawning more QCS WOs).

 5.6 Cancellation during escalation
 If the contractor cancels the original Support WO before second-confirm, no escalation candidate event fires. If the original
 WO is cancelled AFTER second-confirm (which means it's already COMPLETED — cancellation from COMPLETED is not
 allowed per framework state machine), the situation doesn't arise. If a QCS WO is cancelled, the original Support WO is
 unaffected — they're independent.



 6. Warranty linkage + RPT WO


SOPHIX BSS Design Documents                                                                                                 Page 14
 Workshop: when a second WO is raised within the warranty window of a prior installation (6 months) or support visit (3
 months), an RPT WO is raised alongside to track the repeat pattern. The original new Support WO progresses normally; the
 RPT WO exists for tracking + contractor billing implications.

 6.1 Warranty detection at creation
 The wo-check-warranty-linkage flow worker runs immediately after wo-validate-create for every new Support
 WO. It queries:
          SELECT wo_id, kind, job_type_code, completed_at, metadata
          FROM work_order
          WHERE customer_id = $customerId
            AND operator_code = $operatorCode
            AND status = 'COMPLETED'
            AND completed_at >= NOW() - INTERVAL '180 days'
          ORDER BY completed_at DESC
          LIMIT 1

 Then checks whether the prior WO's completion date plus its warranty_days is still in the future:

   - Prior Installation WO with warranty_days=180 completed 90 days ago → warranty window is 90 days remaining → still
     under warranty → spawn RPT.

   - Prior Support WO with warranty_days=90 completed 100 days ago → expired → no RPT.

   - No prior WO within 180 days → no RPT.

 If under warranty:

   1. Append warranty_linkage note to the NEW Support WO with prior WO details.

   2. Create an RPT WO via POST /api/work-orders:
          POST /api/work-orders HTTP/1.1
          {
            "operatorCode":           "WIK",
            "kind":                   "SUPPORT",
            "jobTypeCode":            "RPT",
            "customerId":             "<same as new WO>",
            "homepassId":             "<same as new WO>",
            "originatingContextType": "MASTER_WO",
            "originatingContextRef": "<prior wo_id under warranty>",
            "masterWoId":             "<prior wo_id under warranty>",
            "linkType":               "REPEAT_WITHIN_WARRANTY",
            "idempotencyKey":         "rpt-<new-support-wo-id>",
            "metadata":               {
              "linkedSupportWoId":   "<new support wo_id>",
              "priorJobTypeCode":    "<prior>",
              "priorWarrantyDays":   180
            }
          }

 The RPT WO is created with master_wo_id pointing to the prior under-warranty WO (not to the new Support WO). The
 new Support WO is referenced in the RPT's metadata.linkedSupportWoId for back-reference.

 6.2 RPT WO lifecycle
 The RPT WO is mostly an audit-and-billing marker. It runs through the Support BPMN but requires_site_visit=false
 (RPT itself doesn't generate field work — the linked Support WO is what generates the actual work). Lifecycle:

   1. Created with status=PENDING, kind=SUPPORT, job_type=RPT.

   2. Skips the on-site flow (no_site_visit branch).

   3. Desk-resolution path captures warranty_linkage note (auto-populated by wo-check-warranty-linkage).

   4. Auto-finalizes with final_reason=RPT_LINKAGE_RECORDED once the linked Support WO is finalized.

   5. Emits WorkOrderRPTLinkageRecorded event (§8) for Finance.

 Finance uses the RPT WO + the linked Support WO's contractor info to apply warranty billing rules: typically the contractor
 isn't paid for warranty visits (or is paid at reduced rate). TRC/TRD codes apply when the warranty visit involves a
 disconnect/reconnect for equipment swap — Finance reads those codes from the linked Support WO's equipment bindings.

 6.3 What if multiple prior WOs are eligible?



SOPHIX BSS Design Documents                                                                                             Page 15
 The worker picks the most recent prior WO whose warranty window is still open. Even if the customer has 3 prior
 under-warranty WOs, only one RPT is raised (linked to the most recent prior). This matches workshop intent: RPT is a "this is
 a repeat" marker, not a comprehensive incident history (history lives in the audit log + reporting layer).

 6.4 Operator override
 The 90/180-day warranty windows are operator-configurable via wo_job_type_catalog.warranty_days. Future
 operators can deploy different windows by editing the catalog rows — no flow code change.



 7. Flow-specific workers
 Four workers specific to this flow, plus two reused from the Installation flow.

 7.1 wo-check-warranty-linkage
 External task topic: wo-check-warranty-linkage.

 Runs right after wo-validate-create for every new Support WO. Action:

   1. Query for the customer's most recent COMPLETED WO within the last 180 days (§6.1 SQL).

   2. If found AND prior WO's completed_at + warranty_days > NOW(): append warranty_linkage note to the new
     WO; create RPT WO via internal POST /api/work-orders call.

   3. If not found or out of warranty: no-op.

   4. Complete the Camunda task.

 Lock duration: 8s (the SQL query + potential RPT WO creation).

 7.2 wo-mark-escalation-candidate
 External task topic: wo-mark-escalation-candidate.

 Runs after resolution-gate Drools returns NOT_RESOLVED_ESCALATE. Action:

   1. Verify an escalation_candidate_reason note is present (contractor must have captured why they can't resolve). If
     missing, fail the task with an error code that the BPMN routes to a user task for the contractor to add the note.

   2. Set metadata.escalationCandidatePending = true on the WO.

   3. Complete the Camunda task.

 Lock duration: 3s.

 7.3 wo-emit-escalation-candidate-if-needed
 External task topic: wo-emit-escalation-candidate-if-needed.

 Runs after wo-emit-state-event confirms WorkOrderFinalized for any Support WO. Action:

   1. Read wo_final_reason_catalog.triggers_escalation_event for the WO's (operator, kind,
     job_type, final_reason).

   2. If true: emit WorkOrderEscalationCandidate (framework event from DD_WO-01-FRAMEWORK §7) with payload
     including:

   - woId, operatorCode, kind, jobTypeCode, customerId, homepassId

   - finalReasonCode, escalationCandidateReason (the note content)

   - originalAssignedContractorId, originalAssignedTeamId

   - suggestedHandoffTeam = "ctr_NOC_MAINT" (per Pattern A rules)

   3. If false: no-op.
