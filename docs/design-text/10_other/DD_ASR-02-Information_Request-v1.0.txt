 MVP simplification baseline: ASR-02 is implemented as TCK-01 information-request ticket categories, templates, queues,
 and closure rules. It is not a separate ticketing service, database, or deployment in the first release.



 1. Purpose
 ASR-02 defines the information request flow for customer questions that require a trackable answer but do not start as a
 technical fault, complaint, or operational service request.

 Examples:

   - customer asks which package they are subscribed to;

   - customer asks whether an address is covered;

   - customer asks why a package is not available at their HomePass;

   - customer asks for an explanation of invoice lines;

   - customer asks about payment channels;

   - customer asks about KYC status;

   - customer asks about installation/order status;

   - customer asks for a document or reference already available in SOPHIX.

 This DD does not create a new ticketing engine. Information requests are implemented as configured TCK ticket
 types/categories, with ASR-specific answer templates, research tasks, and closure rules.

 3. When To Use This Flow
 Use ASR-02 when the expected outcome is an answer, explanation, document/reference, or routing guidance.

 Do not use ASR-02 when:

  Scenario                                                                       Use

  Customer reports service not working                                           ASR-01 Technical Trouble

  Customer is unhappy and requests correction/escalation                         ASR-03 Complaint

  Customer requests an action such as address change, SIP reset, equipment       ASR-04 Service Request or owning workflow
  swap, or package change

  Customer disputes an invoice and wants a correction                            TCK billing complaint plus BIL adjustment flow

 6.2 asr_info_answer_template
 Stores safe agent answer templates for common information requests.

 This table is not a customer-notification template catalog. It contains canned-answer content shown to support agents inside
 TCK/ASR screens so they can answer consistently. If an answer must be pushed to a customer through SMS, email,
 WhatsApp, portal notification, or another delivery channel, ASR passes the selected answer text or event-kind hint to
 NOT-01. NOT-01 still owns delivery template, channel, language, quiet hours, fallback, and retry policy.

 Use this table to make answers consistent and customer-safe.

   2. Adds customer-visible TCK comment.

   3. Resolves the TCK ticket.

   4. Emits InformationRequestAnswered.

 10. Common Source APIs
 ASR-02 does not own the data it explains. It calls owning module APIs.

  Question                                                               Source module/API

  Current package                                                        SUB-LM subscription detail, SIP-01 package detail.

  Available packages                                                     SIP-01 package APIs, RLM coverage/sellability APIs.

  Coverage/HomePass                                                      RLM-CFG-01 HomePass search/detail.

  Invoice line explanation                                               BIL-02-READ-01 invoice detail/read APIs.

  Payment channel explanation                                            PAY-GW-01 channel config, BIL-05 wallet topup channels.

  KYC status                                                             ILM/FUL KYC status APIs.

  Order/install status                                                   FUL-02 order APIs, WO status APIs where linked.

 12. Infra Recommendation
 ASR-02 should run inside the TCK service/module. No separate pod is required for a medium budget deployment.

  Component                                                         Recommendation

  API                                                               Existing TCK API pods.

  DB                                                                Existing TCK schema with ASR info tables.

  Workers                                                           Existing TCK worker pool.

  Cache                                                             Optional cache for category/template config.


 AWS deployment follows TCK deployment: same ECS/EKS service, RDS schema, Kafka/MSK, and CloudWatch monitoring.

 Alarms:

   - research task backlog above threshold;

   - answer SLA breach count;

   - repeated conversion from information request to complaint, indicating poor first-contact answer quality.



 13. Testing Requirements
 13.1 Unit Tests
   - Category guidance resolves source module and template.

   - Self-care blocked for category where selfcare_allowed = false.

   - Answer-and-resolve requires answer body.

   - Convert action preserves original ticket history.

   - Customer-visible answer redaction validation blocks internal details.

 13.2 Integration Tests

 13.3 End To End Tests

   - CSR cannot close information request without customer-visible answer.

 14. Definition Of Done
 ASR-02 is complete when:

   - Information request categories are seeded in TCK.

   - ASR info category config exists.

   - Answer templates exist for common questions.

   - Guidance API works.

   - Research task flow works.

   - Answer-and-resolve stores structured answer and resolves ticket through TCK.

   - Conversion/linking to other ASR flows works.

   - Customer timeline receives information request events.

   - Backoffice and self-care can execute the intended flows.
