 This rewritten DD is the developer-facing version of the module contract
 DD_ICN-01-Internal_Communications-v1.0.md.

 for staff-facing notification dispatch: emails, Slack messages, Microsoft Teams cards, and in-app push notifications sent to
 BO users (dispatchers, CSRs, technicians, NOC, Finance, KYC reviewers). Called by Camunda BPMN HTTP connectors via

 2. Implementation Scope
 This DD should be implemented as part of the owning SOPHIX capability, not as an isolated service unless the deployment
 architecture explicitly separates that capability.

 Implement this DD with these rules:

   - Use the owning module APIs/repositories for authoritative writes.

   - Use approved internal APIs/client wrappers when reading another module's data.

   - Do not query another module's database tables directly from business flow code.

   - Treat worker names as logical Camunda external-task topics, not separate deployments.

   - One worker application may handle multiple topics, but metrics, retries, and logs must remain visible per topic.

   - Emit success events only after the authoritative state commit succeeds.

   - Use outbox publishing for Kafka events.

 Verdict: ■ New | Wave: 2 | Group I: Foundations | Version: v1.0 | Module: Internal Communications

 The system of record for staff-facing notification dispatch: emails, Slack messages, Microsoft Teams cards, and in-app push
 notifications sent to BO users (dispatchers, CSRs, technicians, NOC, Finance, KYC reviewers). Called by Camunda BPMN
 HTTP connectors via per-module NotificationHandlerResource wrappers when a workflow parks at a user task and
 needs human action. Retires staff_notification_stub in FUL-02 FRAMEWORK §6.3 and WO module FRAMEWORK
 §9.1.

 ICN-01 is strictly staff-scoped. Customer-facing notifications are owned by DD_NOT-01 and travel a separate path. This
 separation is enforced by API surface and by event-topic naming — the two modules never overlap.



 1. What this module is
 When a Camunda BPMN process parks at a user task — "L1 supervisor must approve KYC", "contractor dispatcher must
 assign a tech", "NOC must verify provisioning succeeded", "Finance must approve a refund" — the relevant human(s) need to
 be told the task exists, ideally on the channel they actually check (email today, Slack/Teams in many teams, in-app push
 when they're in the BO UI).

 Today (v1.0 with staff_notification_stub) every such alert goes via internal SMTP only. That misses people who don't
 watch email closely and delays response. ICN-01 fans the alert out across the channels each recipient prefers, falling back
 across them in priority order until one acknowledges.

 What this module does
   1. Receives dispatch requests from per-module NotificationHandlerResource (FUL-02, WO, future SUB-WF) over
     HTTP.

   2. Resolves candidate groups to individual staff users via FOUNDATION_AUTH's group-membership API.

   3. Looks up each recipient's channel preferences (which channels are enabled, priority order, working-hours,
     suppression).

   4. Dispatches the message on each enabled channel (Email via internal SMTP, Slack via Slack Bot API, MS Teams via
     Incoming Webhook, in-app push via WebSocket fanout to BO UI sessions).

   5. Tracks delivery state per (notification, recipient, channel): DISPATCHED / FAILED / ACKNOWLEDGED.

   6. Emits Kafka events for delivery state changes — observability + analytics consumers.

   7. Provides template rendering — operator-localised text + variable substitution. v1.0 ships ~30 templates (KE seed) for
     KYC, install dispatch, support ticket, dunning escalation, finance approvals.

   8. Handles bouncing — failed-email bounce-back via SMTP, Slack/Teams 4xx responses, push-WebSocket disconnects.
     Retries with backoff up to 3 times per channel; falls through to next channel on exhaustion.

   9. Surfaces an in-app inbox — every BO user sees their pending user-task notifications in a tray in the BO UI, deep-linked
     to the Camunda task in their queue.

 What this module does NOT do
   - Doesn't notify customers. Strict scope: every endpoint is staff-only. Customer notifications (SMS to subscriber, email to
     billing-email) live in DD_NOT-01 and are entirely separate. There is no shared code path. Architectural rule: ICN-01 never
     writes to a customer_* table, never reads customer_contact_method, never knows a customer's MSISDN.

   - Doesn't define candidate groups. Group codes (kenya-l1-kyc, kenya-kyc-leaders, tech-region-NRB-KAREN,
     noc-team, finance-refunds-approvers, etc.) are owned by FOUNDATION_AUTH. ICN-01 looks up members; it
     does not create groups.



SOPHIX BSS Design Documents                                                                                                                 Page 5
   - Doesn't define templates' business semantics. Templates ship with field placeholders. The calling module decides
     what to put in them via the templateVariables payload. ICN-01 doesn't validate that the template's variables match
     the calling workflow.

   - Doesn't drive workflow state. When a recipient ACKs a notification, that's an observability signal only. The actual
     task-completion path is the BO UI calling the owning module's /user-tasks/{taskId}/complete endpoint (per
     FUL-02 FRAMEWORK §3, WO module FRAMEWORK §6). ICN-01 is a transport layer.

   - Doesn't decide who acts. Workflow modules choose the candidate group; FOUNDATION_AUTH defines who's in it;
     ICN-01 just notifies all members of that group. Priority / round-robin / load-balancing across staff members is the
     workflow's concern, not ICN-01's.

   - Doesn't store the canonical user task. Camunda owns that. ICN-01 stores a reference (camunda_task_id) and the
     rendered notification — never duplicates task data.

   - Doesn't implement audit-grade non-repudiation. Delivery confirmations are best-effort and recorded in
     staff_notification_delivery; that table is for operational observability, not legal-grade proof of receipt.
     Audit-grade trails go in FOUNDATION_AUDIT (separate module).

   - Doesn't expose customer-PII-bearing message bodies. Rendered messages reference customer/account by identifier
     and minimal context (name on customer.name, account number) — not by full identification numbers, full address, or
     financial detail. PII minimization is enforced at template definition time.

 Regional flexibility
 Different operators (WIK, WUG, WTZ, YASSN) may use different mixes of channels:

   - WIK (Kenya) — Email + Slack heavy; in-app push for dispatchers. Teams not used.

   - WUG (Uganda) — Email + WhatsApp Business (extension future-roadmap; v1.0 ships Email + Slack + in-app push,
     WhatsApp deferred).

   - WTZ (Tanzania) — Email primary; some teams use Slack.

   - YASSN (Senegal) — Email + Microsoft Teams; Slack not in standard usage.

 The schema and APIs support all four channel kinds (EMAIL, SLACK, MSTEAMS, IN_APP_PUSH) regardless of operator.
 Per-operator config decides which channels are enabled, the priority order, the fallback rules, and the integration endpoint
 configuration (Slack workspace, Teams webhook URL, SMTP relay, push WebSocket URL). KE is the v1.0 seed; UG/TZ/SN
 seeds are added as catalog rows + per-operator config without schema change.

 Per memory rule #18 (regional flexibility): the channel kinds enumeration is intentionally a TEXT column (not a PostgreSQL
 enum) so future channel additions (WhatsApp, SMS-to-staff-on-call) land without DDL.

 2. The dispatch model
 2.1 Request flow
           Camunda BPMN user task fires
              ↓ HTTP connector (X-Camunda-Connector-Secret)
           Per-module NotificationHandlerResource (FUL-02 / WO / future)
              ↓ Build dispatch request
           POST /api/staff-notifications (ICN-01)
              ↓
           ICN-01:
              1. Resolve candidateGroup → list of BO users
                 via FOUNDATION_AUTH GET /api/groups/{group}/members
              2. For each user:
                 a. Read user's channel preferences (priority + enabled set)
                 b. Render template with templateVariables for each channel
                 c. For each enabled channel in priority order:
                    - Insert staff_notification_delivery row (PENDING)
                    - Async dispatch via channel adapter
                    - On success → DISPATCHED + emit Kafka event
                    - On fail → FAILED + try next channel
              3. Return 202 Accepted with notification_id
              ↓
           Recipient sees the message:
              - Email: a link to BO UI deep-link
              - Slack/Teams: a card with "Open in BO UI" button
              - In-app push: a tray entry that opens the task
              ↓
           Recipient clicks deep-link OR opens task in BO UI:
              ↓
           Either:
              - Click on deep-link: GET /api/staff-notifications/{id}/ack?recipient={userId}
              - Or: BO UI calls owning-module's task-completion endpoint;
                    that module's handler then calls ICN-01 ACK as a side effect
              ↓
           ICN-01 marks staff_notification_delivery row ACKNOWLEDGED + emits event

 The async dispatch is the only workflow path. ICN-01 returns 202 immediately. Workflow waits (or doesn't wait — depends
 on whether the BPMN's user task has a boundary timer for escalation) for the staff member to actually complete the task in
 the BO UI.

 2.4 Templates
 A template is identified by (operator_code, template_code, channel) — same template code may have variant
 rendering per channel (an email is verbose; a Slack card is terse). v1.0 KE seed templates:

   - KYC: kyc-l1-approval-needed, kyc-final-approval-needed, kyc-rejected-resubmit

   - Install: install-wo-awaiting-dispatcher, install-wo-awaiting-tech-claim,
      install-wo-finalize-confirm-needed

   - Support: support-wo-tech-needed-internal, support-wo-tech-needed-contractor

   - Shifting: shifting-disconnect-confirm, shifting-reconnect-tech-needed

   - Dunning escalation: dunning-l2-escalation-internal, dunning-l3-escalation-internal

   - Finance: refund-approval-needed, adjustment-approval-needed, outage-credit-batch-ready

   - NOC: provisioning-failure-noc-investigate, network-incident-confirmation-needed

   - Customer service: vip-customer-escalation, customer-complaint-routed-for-attention

 Templates carry a variable list — {customerName}, {accountNumber}, {taskId}, {deeplinkUrl},
 {urgencyLabel}, etc. The calling module supplies these in templateVariables. Variable substitution uses
 Mustache-style {{varname}} rendering. Unknown variables render as «MISSING:varname» and emit a warning Kafka
 event — never a 500.

 3.6 staff_notification_adapter_binding
 Channel-provider endpoint configuration. This is where SMTP host, Slack workspace ID, MS Teams webhook URL,
 Microsoft Graph tenant ID, AWS SES region, Mailgun API base, push WebSocket URL, etc. live. ICN-01 reads this table
 to know which adapter implementation handles each (operator, channel) combination and how to configure it.

 Each binding row identifies one adapter implementation (e.g., smtp-classic, microsoft-graph-mail,
 slack-bot-api, msteams-incoming-webhook, msteams-graph-channel, inapp-websocket-fanout, aws-ses,
 etc.) and carries an opaque config_jsonb whose shape is interpreted only by that adapter. Secret material (passwords,
 API tokens, OAuth refresh tokens) is NEVER stored inline in config_jsonb — only Vault path references.

 The decoupling means:

   - KE may use smtp-classic for EMAIL today and migrate to microsoft-graph-mail tomorrow by inserting a new
     binding row + removing the old; no schema change, no code change, no domain-config change.

   - A future operator can plug in a wholly new adapter implementation (twilio-programmable-chat,
     whatsapp-business-api, pagerduty-events-v2) by deploying the adapter code and inserting the binding row.

   - Multiple operators can share an adapter implementation with completely different config (e.g., both KE and WUG use
     slack-bot-api but each has its own workspace + token).

               config_jsonb          JSONB NOT NULL,                 -- adapter-specific config; opaque to ICN-01; secret refs only
               enabled               BOOLEAN NOT NULL DEFAULT TRUE,

               created_at            TIMESTAMP NOT NULL DEFAULT NOW(),
               updated_at            TIMESTAMP NOT NULL DEFAULT NOW(),

 use the user identity (delivery is channel-scoped, not user-scoped, per §7.3); but if YASSN migrates to
 msteams-graph-channel later, that adapter will need the user identifier to post to user DMs, and the object_id is the
 format Microsoft Graph prefers. Capturing both now means the future migration is data-only.

SOPHIX BSS Design Documents                                                                                                 Page 15
 #### 3.7.1 Resolution semantics — when there's no row

 A user may not have a row for every channel they could potentially receive notifications on. ICN-01's resolution policy at
 dispatch time:

   1. If a row exists for (user_id, channel) → pass identity_jsonb to the adapter.

   2. If no row exists → pass null to the adapter. The adapter then decides its fallback:

   - smtp-classic and microsoft-graph-mail: fall back to FOUNDATION_AUTH GET /api/users/{user_id} to
     read the email attribute from the user's Keycloak profile; if found, proceed with that address and OPTIONALLY backfill
     the identity row (the adapter MAY insert a new identity row with source='auto-resolved-from-auth',
     verified=false — convenience, not required).

   - slack-bot-api: fall back to FOUNDATION_AUTH email lookup, then Slack users.lookupByEmail against the
     workspace; on success, MAY backfill the identity row.

   - msteams-incoming-webhook: NO fallback — delivery is channel-scoped, not user-scoped (the webhook posts to a
     Teams channel based on candidate_group_to_channel mapping in the binding's config, not to a user). The adapter
     ignores the per-user identity entirely. The identity row, if present, is just for forward-compatibility.

   - msteams-graph-channel (future): fall back to FOUNDATION_AUTH email lookup → MS Graph users lookup by mail.

   - inapp-websocket-fanout: NO fallback needed — adapter uses user_id to look up active WebSocket sessions. The
     identity row's existence is informational but not required.

 This policy means: a user can receive notifications on most channels without any identity row pre-populated, provided
 FOUNDATION_AUTH carries their email. The identity table is for performance (skip the AUTH call) + for cases where the
 channel identifier is NOT derivable from email (e.g., a Slack workspace where users joined with a different email than their
 Keycloak account uses).

 #### 3.7.2 Directory sync

 A scheduled job (identity-sync-<operator>-v<n>, daily) reconciles
 staff_notification_user_channel_identity with each operator's external directories:

   - Pulls every staff user from FOUNDATION_AUTH for the operator

   - For each user × each enabled channel, calls the adapter's resolveIdentity(userProfile) method (a separate
     ChannelAdapter interface method beyond dispatch)

   - Upserts the resulting identity_jsonb with source='directory-sync', verified=true (since it came from the
     authoritative directory)

   - Removes rows for users who've been deactivated in FOUNDATION_AUTH

 Users can override sync-managed identities via the BO UI (source='self'); self-managed rows are not overwritten by
 sync. Admin overrides (source='admin') are honored similarly.

  R-ICN-01-D-8                If ALL recipients have ALL channels TERMINALLY_FAILED or SUPPRESSED,
                              the parent staff_notification.status moves to EXPIRED with reason
                              ALL_CHANNELS_EXHAUSTED. A high-severity Kafka event
                              StaffNotificationFailedToReachAnyone fires for ops alerting.

  R-ICN-01-D-9                The dispatch is asynchronous; POST /api/staff-notifications returns
                              202 the moment the parent row + recipient delivery rows are persisted. Actual
                              channel adapter calls run in a background worker pool. This means a Camunda
                              HTTP connector firing into ICN-01 gets a 202 back quickly even if Slack is slow.

  R-ICN-01-D-10               ICN-01 NEVER dispatches to a customer. The schema does not contain any FK
                              to customer or customer_account. Calling modules may include customer

                              {{customerName}}), but the recipients of the message are STRICTLY staff
                              users resolved from candidate_group via FOUNDATION_AUTH.

  R-ICN-01-D-11               Idempotency: POST /api/staff-notifications accepts an optional
                              Idempotency-Key header. Repeated calls with the same key within 24h
                              return the existing notification_id with HTTP 200 (not 202), and do NOT
                              re-dispatch. This protects against Camunda HTTP connector retries during
                              transient ICN-01 unavailability.

  R-ICN-01-D-12               All adapter-specific secret material (SMTP credentials, Slack bot tokens, MS
                              Teams webhook URLs, Microsoft Graph app secrets, etc.) is stored ONLY as
                              Vault path references inside
                              staff_notification_adapter_binding.config_jsonb. Never inline
                              values. Adapters resolve the Vault reference at dispatch time (or at adapter init,
                              with TTL cache).

  R-ICN-01-D-13               Template rendering treats missing required variables as a soft-error: render as

  R-ICN-01-D-14               PII minimization: templates MUST NOT reference customer identification

 7. Channel adapters
 A channel is a logical kind (EMAIL, SLACK, MSTEAMS, IN_APP_PUSH). An adapter is a concrete implementation that talks
 to one specific provider for that channel kind. For each (operator_code, channel) exactly one adapter implementation
 is active at any time — selected by staff_notification_adapter_binding.adapter_impl (§3.6).

 Every adapter implements the same Java interface:
           interface ChannelAdapter {
             String adapterImplCode();      // matches staff_notification_adapter_binding.adapter_impl

               void init(JsonNode configJsonb, SecretResolver secretResolver);


SOPHIX BSS Design Documents                                                                                                          Page 21
              //    configJsonb is the adapter binding's config_jsonb passed verbatim;
              //    secretResolver resolves Vault path refs found inside it.

              ChannelDispatchResult dispatch(
                 StaffNotificationDelivery row,
                 RenderedMessage message,
                 RecipientInfo recipient
              );

              // Optional — called by directory-sync job to populate staff_notification_user_channel_identity
              default Optional<JsonNode> resolveIdentity(UserProfile userProfile) {
                return Optional.empty();
              }
          }

          record RecipientInfo(
             String   userId,                  // FOUNDATION_AUTH user id
             JsonNode identityJsonb,            // from staff_notification_user_channel_identity, or null
             Supplier<UserProfile> fallbackProfileLookup // lazily calls FOUNDATION_AUTH if needed
          );

          record ChannelDispatchResult(
             String providerMessageId,    // e.g., Slack 'ts', email Message-ID
             boolean success,
             String failureReason,         // when !success
             Map<String,Object> providerResponse
          );

 Adapter implementations are discovered at boot via Java's ServiceLoader
 (META-INF/services/com.sophix.icn.ChannelAdapter). Adding a new adapter is: write the class, register it via
 ServiceLoader, deploy the jar, insert a binding row.

 7.0 Dispatch resolution — how an adapter gets picked and called
 For every PENDING staff_notification_delivery row, the ICN-01 dispatch worker performs these steps before
 calling an adapter:

   1. Read the delivery row. From the row: notification_id, recipient_user_id, channel. From the parent
     staff_notification: operator_code, template_code, template_variables.

   2. Resolve the adapter binding. Query staff_notification_adapter_binding for (operator_code,
     channel):
               SELECT adapter_impl, config_jsonb, enabled
               FROM staff_notification_adapter_binding
               WHERE operator_code = $1 AND channel = $2;

 If no row → delivery TERMINALLY_FAILED with failure_reason = NO_BINDING_FOR_CHANNEL. If enabled = false
 → delivery SUPPRESSED with failure_reason = ADAPTER_BINDING_DISABLED (per R-ICN-01-D-18).

   3. Look up the registered ChannelAdapter instance. ICN-01 maintains a process-local registry Map<String,
     ChannelAdapter> keyed by adapter_impl. The instance was already init()'d at boot time (or at last config-reload)
     with config_jsonb and secretResolver. If adapter_impl is not registered → delivery TERMINALLY_FAILED with
     failure_reason = ADAPTER_NOT_REGISTERED (per R-ICN-01-D-17).

   4. Render the message. Pull the staff_notification_template row for (operator_code, template_code,
     channel), substitute template_variables into the body (Mustache style). Missing required variables → emit
     StaffNotificationTemplateRenderWarning, render as «MISSING:varname» (per R-ICN-01-D-13).

   5. Read the per-user channel identity. Query staff_notification_user_channel_identity for
     (recipient_user_id, channel):
               SELECT identity_jsonb
               FROM staff_notification_user_channel_identity
               WHERE user_id = $1 AND channel = $2;

 The result (or null if no row) is wrapped into a RecipientInfo along with the user_id and a lazy fallback UserProfile
 supplier that, when invoked, calls FOUNDATION_AUTH GET /api/users/{user_id}.

   6. Call adapter.dispatch(deliveryRow, renderedMessage, recipientInfo). The adapter reads
     recipientInfo.identityJsonb. If it has what it needs, it dispatches. If identityJsonb is null AND the adapter
     supports fallback, it invokes recipientInfo.fallbackProfileLookup.get() to fetch the user's Keycloak profile,
     derives the channel identifier from there, and proceeds (optionally backfilling the identity row for next time). If the adapter
     cannot derive an identifier → returns ChannelDispatchResult(success=false,
     failureReason=IDENTITY_UNRESOLVABLE).



SOPHIX BSS Design Documents                                                                                                     Page 22
   7. Update the delivery row. Adapter result → staff_notification_delivery.status (DISPATCHED / FAILED),
     provider_message_id, provider_response, attempts++, last_attempt_at. On FAILED, schedule retry per
     staff_notification_channel_config.retry_backoff_seconds (per R-ICN-01-D-7).

   8. Emit Kafka event. StaffNotificationDelivered on success, StaffNotificationDeliveryFailed on
     TERMINALLY_FAILED.

 This 8-step path runs once per delivery row (one notification with 4 recipients × 3 channels = 12 invocations of this path,
 executed in parallel by the worker pool). Each step is idempotent — a worker crash mid-path resumes safely on the next
 worker pickup because the delivery row's status remains PENDING until step 7 commits.

 7.4 IN_APP_PUSH — v1.0 adapter implementation
 inapp-websocket-fanout — the BO UI maintains a WebSocket connection to ICN-01's push endpoint after login.

 config_jsonb shape:
          {
              "ws_endpoint":               "wss://push.wik.sophix.com/staff",
              "polling_fallback_endpoint": "https://push.wik.sophix.com/staff/inbox",
              "session_jwt_audience":      "icn-01",
              "session_ttl_seconds":       3600,
              "buffer_unack_hours":        72
          }

 ICN-01 fans out the notification to all active sessions for the recipient. The adapter uses user_id directly to look up active
 sessions in its in-memory session registry — identity_jsonb is not consulted for routing. If a
 staff_notification_user_channel_identity row exists for (user_id, IN_APP_PUSH), it's an informational
 marker that this user is set up to receive in-app pushes; if absent, dispatch still proceeds.

 If no active session, the delivery row stays PENDING (subject to retry policy in R-ICN-01-D-7); on session establishment, the
 BO UI subscribes "give me my unACKed notifications for the last N hours" via the polling fallback endpoint and catches up.
 After ack_window_hours of no session, the row goes SUPPRESSED — not TERMINALLY_FAILED, because the user
 wasn't reachable on this channel, but it's not the channel's fault.

 WebSocket auth: JWT in the connection upgrade handshake; verified against FOUNDATION_AUTH on connect.

 Future: inapp-server-sent-events (alternative transport for environments where WebSocket is hard);
 inapp-firebase-cloud-messaging (if a native Wananchi staff mobile app exists).

 7.5 Indirection consequences
 The adapter binding pattern means:

   - Operator choice is decoupled from code. YASSN choosing Microsoft Graph for email instead of SMTP doesn't require a
     code branch — it just inserts a different binding row.

   - Provider migration is data-only. Swapping SMTP for Graph mid-flight is an UPDATE on the binding row plus possibly a
     parallel-run period (two bindings briefly coexisting, one enabled=false). Zero domain-config change.



SOPHIX BSS Design Documents                                                                                                 Page 24
   - Future channels land cleanly. Adding WhatsApp Business: write a new adapter implementing ChannelAdapter, add
     channel value WHATSAPP_BUSINESS to the templates + bindings, insert config. No schema migration on the core ICN-01
     tables.

   - Multi-operator deployments share code. WIK and WUG both use smtp-classic for EMAIL — same Java class,
     different config_jsonb rows.

   - Testing in production is safe. New adapter implementations can be deployed and inserted as enabled=false
     bindings, allowing dry-runs or canary tests without affecting live dispatch.

     push integration is a future enhancement.

 11.3 ICN-01 resolves recipients
 ICN-01's request handler synchronously:

   1. Validates the JWT (FUL-02 service account is recognised; operator scope matches).

   2. Validates the template exists: (WIK, kyc-l1-approval-needed) resolved to 3 channel variants (EMAIL, SLACK,
     IN_APP_PUSH).

   3. Calls FOUNDATION_AUTH: GET /api/groups/kenya-l1-kyc/members?operatorCode=WIK → returns 4
     supervisor user IDs.

   4. Inserts staff_notification row: notif_01HZ_KYC_L1_JANE, status=PROCESSING, expected_recipients=4,
     expires_at=2026-02-17T17:30:00Z.

   5. For each of the 4 supervisors:

   - Reads staff_notification_user_pref if exists; else uses operator default channel config.

   - Computes effective channel list per R-ICN-01-D-4 (priority order × enabled × not-suppressed × quiet-hours-honoured).

   - For each channel in the list: inserts a staff_notification_delivery row with status=PENDING.

   6. Returns 202 to FUL-02.

 By the end of step 6: 4 supervisors × ~3 channels = ~12 delivery rows inserted (some channels may be SUPPRESSED if a
 supervisor opted out — those rows skip insertion or insert as SUPPRESSED).

 11.4 Async dispatch
 A background worker pool picks up each PENDING delivery row and runs the 8-step dispatch resolution from §7.0. Briefly, for
 each row:

   1. Reads the staff_notification_adapter_binding for (operator_code, channel) — for WIK, this resolves to:
     EMAIL → smtp-classic, SLACK → slack-bot-api, IN_APP_PUSH → inapp-websocket-fanout.

   2. Looks up the registered ChannelAdapter instance (already init'd at boot from the binding's config_jsonb).

   3. Reads staff_notification_user_channel_identity for the recipient × channel — for
     supervisor_franchise_KE-NRB-04's EMAIL delivery, this returns
     {"address":"sup_NRB04@wik.wananchi.com"}; for SLACK, {"slack_user_id":"U04K1S0PH1XKE"}; for
     IN_APP_PUSH, the empty {} row (adapter uses user_id directly anyway).

   4. Invokes adapter.dispatch(deliveryRow, renderedMessage, recipientInfo) with recipientInfo
     containing the identity_jsonb + a lazy fallback profile lookup.

   5. Records the result on the delivery row.

 For Jane's notification, this fans out to:

   - 4 × IN_APP_PUSH via inapp-websocket-fanout: WebSocket fanout to each supervisor's session. For 3 supervisors
     logged into BO UI at this moment, message arrives instantly; their tray badge increments. For 1 supervisor not logged in,
     delivery stays PENDING (no retry on the WebSocket side; waits for next BO UI session per §7.4).

   - 4 × SLACK via slack-bot-api: posts the formatted block-kit card to each supervisor's Slack DM. All 4 succeed; delivery
      rows → DISPATCHED with provider_message_id = Slack ts.

   - 4 × EMAIL via smtp-classic: SMTP relay accepts all 4; delivery rows → DISPATCHED with Message-ID.

 If YASSN had received the same notification, EMAIL would have routed through microsoft-graph-mail instead, calling
 Graph's sendMail endpoint — same delivery row shape, different adapter implementation. The choice was made at the
 binding layer, transparent to the workflow + transparent to the rest of ICN-01.

 ICN-01 emits StaffNotificationCreated once and StaffNotificationDelivered per successful delivery (10
 deliveries × 1 event each = 10 events on sophix.icn.notification-delivered).

 Within ICN-01, this notification leaves the following audit trail:

   - 1 staff_notification row, status=ACKNOWLEDGED, time-to-ACK = ~15 hours (overnight wait is normal).

   - 1 StaffNotificationAcknowledged event.

 Total: one staff member needed action, three channels reached them, fan-out to peer supervisors was suppressed once one
 acted. Net effect: the team isn't drowned in duplicate notifications, but redundancy was present in case the first supervisor
 was unavailable.
