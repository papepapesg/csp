 1. How To Read This Guide
 Information request is a TCK ticket flow. It is not a separate ASR case engine.

 The flow creates a TCK ticket, resolves guidance from ASR config, optionally performs research, then stores a
 customer-visible answer and resolves the ticket.

 5. Step 4 - Customer Creates Information Request
 Self-care or Backoffice calls TCK:
          POST /api/tickets
          Idempotency-Key: selfcare-info-20260603-001
          Content-Type: application/json

          {
              "operatorCode": "WIK",
              "typeCode": "PACKAGE_OR_CATALOG_QUERY",
              "categoryCode": "PACKAGE_EXPLANATION",
              "sourceChannel": "SELF_CARE",
              "customerId": "CUS-100045",
              "accountId": "ACC-900045",
              "subscriptionId": "SUB-700045",
              "subject": "Package information request",
              "description": "Customer wants to know current package and price.",
              "customerVisible": true
          }

 Before allowing self-care create, validate:
          select selfcare_allowed
          from asr_info_category_config
          where operator_code = 'WIK'
            and category_code = 'PACKAGE_EXPLANATION'
            and status = 'ACTIVE';

 If selfcare_allowed = false, return:
          403 ASR_INFO_SELFCare_CATEGORY_NOT_ALLOWED




 6. Step 5 - Load Guidance
 Backoffice opens the ticket:
          GET /api/asr/information-requests/tck-20260603-000020/guidance

 Response:
          {
              "ticketId": "tck-20260603-000020",
              "categoryCode": "PACKAGE_EXPLANATION",
              "answerSourceModule": "SIP-01",
              "researchRequired": false,
              "answerTemplateCode": "PACKAGE_EXPLANATION_BASIC",

 Frontend uses this to show the right actions. Do not hardcode topic behavior in the UI.

 7. Step 6 - Fetch Source Data
 For package explanation, the service gathers:

   1. Subscription from SUB-LM.

   2. Package version from SIP-01.

   3. Service summary from PLM-CFG-01 if needed.

 Example internal source refs:
           [
               {"module": "SUB-LM", "ref": "SUB-700045"},

           ]

 If source API is unavailable, create a research task or move ticket to WAITING_INTERNAL.

 11. Step 10 - Convert To Another Flow
 If a customer asks for invoice explanation and then says the charge is wrong, convert or link to complaint/adjustment path.

          Content-Type: application/json

          {

               "targetCategoryCode": "BILLING_DISPUTE",
               "reason": "Customer rejects invoice explanation and requests correction."
           }

 Recommended implementation:

   1. Create linked TCK ticket for ASR-03, or change current ticket category if policy allows.

   2. Add ticket_link between old and new ticket.

   3. Close original with resolutionCode = CONVERTED.

   4. Emit InformationRequestConverted.

 Never delete the original information-request history.



 12. Suggested Worker Commands
 These run inside TCK/ASR workers and can be consolidated.
           asr-info:research-sla-scan
           asr-info:template-validation-scan
           asr-info:source-api-retry

 Recommended schedule:

  Command                                                           Frequency

  asr-info:research-sla-scan                                        Every 10 minutes.

  asr-info:template-validation-scan                                 On template change and nightly.

  asr-info:source-api-retry                                         Every 5 minutes for failed API research tasks.




 13. Error Codes
  Error code                                                        Meaning

  ASR_INFO_CATEGORY_NOT_FOUND                                       No active config for category.

  ASR_INFO_SELFCARE_CATEGORY_NOT_ALLOWED                            Self-care attempted blocked category.

  ASR_INFO_TEMPLATE_NOT_FOUND                                       Answer template missing.

  ASR_INFO_TEMPLATE_VARIABLE_MISSING                                Required template variable not available.

  ASR_INFO_ANSWER_REQUIRED                                          Cannot resolve without customer-visible answer.

  ASR_INFO_RESEARCH_TASK_OPEN                                       Cannot resolve while required research is open.

  ASR_INFO_CONVERSION_TARGET_INVALID                                Target flow/category not allowed.




 14. Minimum Implementation Order
 Build in this order:

   1. Seed TCK information request categories.

   2. Add ASR info config migrations.

   3. Seed answer templates.

   4. Implement guidance API.

   5. Implement self-care category validation.

   6. Implement research task create/complete APIs.

   7. Implement answer-and-resolve API.

   8. Implement conversion/link API.

   9. Emit ASR-02 business events.

   10. Project to CUST-INT-01.

 15. Test Scenarios
 15.1 Package Question Answered Immediately
 Input:

   - Self-care creates PACKAGE_EXPLANATION.

 Expected:

   - TCK ticket created.

   - Guidance returns SIP source and template.

   - CSR answers and resolves.

   - Customer-visible answer appears in ticket/timeline.

 15.2 Invoice Explanation Needs Research
 Input:

   - Customer asks about invoice line.

 Expected:

   - Research task created for billing-care.

   - Ticket moves WAITING_INTERNAL.

   - Completed research allows answer.

 15.3 Missing Answer Blocks Closure
 Input:

   - User tries to resolve without answer body.

 Expected:

   - API returns ASR_INFO_ANSWER_REQUIRED.

 15.4 Convert To Complaint
 Input:

   - Customer rejects explanation and requests correction.

 Expected:

   - Original info ticket is linked to ASR-03 complaint ticket or converted by policy.

   - History preserved.



 16. Developer Checklist
 Before marking ASR-02 complete:

   - Information request uses TCK ticket lifecycle.

   - ASR-02 does not mutate business records.

   - Guidance is config-driven.

   - Self-care categories are explicitly allowed.

   - Research tasks preserve source module and result.

   - Final answer is customer-visible and stored.
