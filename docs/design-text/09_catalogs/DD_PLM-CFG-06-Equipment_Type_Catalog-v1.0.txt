 1. What this module is
 When a Wananchi installer arrives at Hon. Sarah Wanjiku's address with a router, an ONT, and a wall socket, every piece of
 equipment they leave behind needs an identity. That identity has several axes: what kind of thing is it (router, ONT, splitter,
 …), what brand + model is it (Huawei HG8245H5, MikroTik hAP ac², …), what SKU does the operator inventory it under
 (WIK-RTR-HG8245-H5), how much does it cost the customer (deposit + monthly rental), and is it a returnable / consumable /

SOPHIX BSS Design Documents                                                                                                                   Page 3
 one-shot. This DD owns all of that.

 The catalog is structural and operator-scoped — each operator catalogs their own equipment, sometimes overlapping
 (Huawei HG8245H5 is sold in KE and UG, with different SKUs and prices). The catalog is read by every module that touches
 equipment in any way: stock chain, work orders, fulfillment, billing, audit.

 What this module does
   1. Catalog equipment SKUs — operator-scoped, the master identifier (e.g., WIK-RTR-HG8245-H5) that all other modules
     reference.

   2. Classify equipment by kind — operator-extensible kind hierarchy: ROUTER, ONT, STB, SPLITTER, WALL_SOCKET,
     CABLE_PATCH, MOUNTING_KIT, EXTERNAL_ANTENNA, etc. Used by WO module to validate "an install WO must include
     exactly one ROUTER + exactly one ONT".

   3. Record brand + model — manufacturer + model number, for ordering, returns, RMA workflows, and customer support
     context.

   4. Define equipment fees — one-time install fees, monthly rental fees, deposit (refundable on return). Currency follows
     operator. References to PLM-CFG-04 discount eligibility codes for promo bundling.

   5. Define equipment ownership semantics — RETURNABLE (customer must return on disconnect; refundable deposit),
     CONSUMABLE (no return expected; e.g., a wall socket is left in place), ONE_SHOT (e.g., a cable is consumed at install time;
     no return), or RENTED (Wananchi-owned, customer keeps custody but ownership stays with operator).

   6. Surface stock signals (read-only from OSR-01) — does this SKU have stock available right now? (This is a
     read-through to OSR-01; PLM-CFG-06 does not store stock balances. For v1.0 with OSR-01 pending, PLM-CFG-06
     surfaces a placeholder "stock-status-unknown" via OSR-01 stub.)

   7. Record compatibility constraints — operator-extensible compatibility rules between SKUs (e.g., "this ONT requires this
     specific splitter type"; "this router is incompatible with this ONT firmware"). v1.0 ships a minimal compatibility table; full
     constraint resolution lives in WO module.

   8. Track equipment-fee history — fee changes are versioned (effective_from / effective_to); historical WO +
     invoice queries resolve to the fee active at the time of the install / billing event.

 What this module does NOT do
   - Doesn't track stock balances or movements. Where the SKU is physically located, how many are in central warehouse
     vs. contractor van vs. customer premises — all OSR-01 (pending). PLM-CFG-06 is the *definition*; OSR-01 is the
     *quantity + location*.

   - Doesn't track individual equipment instances. Each physical router has a serial number; that data lives in OSR-01
     (equipment_instance table per OSR-01 plan). PLM-CFG-06 carries only the SKU/type level.

   - Doesn't own provisioning configuration. Which firmware, which provisioning profile, which RADIUS realm — those
     belong to provisioning modules (FUL-03 + downstream). PLM-CFG-06 records "this is a Huawei HG8245H5"; what gets
     pushed to it lives elsewhere.

   - Doesn't manage RMA / return workflows. RMA, repair, refurbishment, write-off — all OSR-01 + WO module (return work
     orders). PLM-CFG-06 supplies the SKU metadata they need.

   - Doesn't manage contracts with equipment vendors. Vendor procurement (POs, vendor SLAs, lead times) is EM-02
     (pending — Procurement / Contractor Registry) or a dedicated procurement DD. PLM-CFG-06 just records
     "brand=Huawei", not "we source it from Huawei East Africa via vendor PO #12345".

   - Doesn't model packaged bundles. A "starter kit" combining router + ONT + cables is a package modeled in SIP-01
     (Package Management) or PLM-CFG-01 (Service Catalog), not here. PLM-CFG-06 records the individual SKUs that
     bundles reference.

 Regional flexibility
 Different operators stock different equipment based on network technology, regional vendor relationships, and regulatory
 constraints:

   - WIK (Kenya) — primarily Huawei + ZTE for ONTs (Wananchi's GPON network), MikroTik + TP-Link for routers,
     locally-procured patch cables and wall sockets. Kenya allows direct import; SKU codes follow WIK-<KIND>-<MODEL>
     convention.




SOPHIX BSS Design Documents                                                                                                   Page 4
   - WUG (Uganda) — similar to WIK on technology (also GPON), but local vendor relationships and import constraints differ;
     some SKUs are UG-specific even for the same physical device. SKU prefix WUG-.

   - WTZ (Tanzania) — TBD; pending workshop. Likely smaller equipment range. SKU prefix WTZ-.

   - YASSN (Senegal) — different vendor mix: Senegal market favors Sagemcom + Huawei. SKU prefix YASSN-.
     French-language display names; deposit amounts in XOF currency.

 The schema accommodates all four via:

   - Operator-scoped SKU IDs (each operator's catalog is independent)

   - TEXT-typed kind_code enum-style values (operator-extensible — new kinds land via config, not DDL)

   - Currency-aware fee columns (fee_currency per row)

   - Multi-language display names (display_name_primary + display_name_secondary) for bilingual operators

 Glossary
  Term                                                           Meaning

  Equipment                                                      Any physical item Wananchi installs, ships, holds in stock, or returns. Includes
                                                                 both customer-side (router, ONT, STB, wall socket, cables at premises) and
                                                                 operator-side (network equipment is OUT of scope — that's RLM/NMS).

  SKU                                                            Stock Keeping Unit — the operator's master identifier for one variant of one
                                                                 product. Two routers with the same brand+model but different firmware versions
                                                                 sold for different prices are two SKUs.

  Kind                                                           The functional category — what does this device DO. ROUTER, ONT, STB,
                                                                 SPLITTER, WALL_SOCKET, etc. Operator-extensible.

  Brand + model                                                  Manufacturer identification (Huawei, ZTE, MikroTik, Sagemcom) + their model
                                                                 designation (HG8245H5, ZXHN H267A, hAP ac², F@st 3686).

  Ownership semantics                                            Whether the customer can keep the equipment, must return it, must pay a
                                                                 deposit, etc. Drives disconnect-flow + dunning-flow behaviors. RETURNABLE /
                                                                 CONSUMABLE / ONE_SHOT / RENTED.

  Install fee                                                    One-time charge applied at install for this equipment, in addition to subscription
                                                                 fees. Workshop term often "activation fee" but the catalog separates
                                                                 equipment-specific from service-activation.

  Monthly rental                                                 Recurring monthly charge for equipment use; applied via BIL-01 as a recurring
                                                                 line item. For RETURNABLE ownership, monthly rental continues until equipment
                                                                 is returned.

  Deposit                                                        Refundable amount charged at install, refunded (via PLM-CFG-05 adjustment)
                                                                 when equipment is returned in working condition. Only applies to RETURNABLE
                                                                 SKUs.

  Compatibility                                                  A rule restricting which SKUs can be installed together (e.g., "ONT-X requires
                                                                 SPLITTER-Y"). Read by WO module at WO finalization to flag invalid
                                                                 equipment combinations.

 3.3 equipment_fee
 Time-versioned per-SKU fee schedule.
           CREATE TABLE equipment_fee (
              fee_id                TEXT PRIMARY KEY,               -- 'fee_01HZ...' ULID
              sku_id                TEXT NOT NULL REFERENCES equipment_sku(sku_id),
              install_fee_amount    NUMERIC(12,2) NOT NULL DEFAULT 0, -- one-time charge at install
              monthly_rental_amount NUMERIC(12,2) NOT NULL DEFAULT 0, -- recurring monthly
              deposit_amount        NUMERIC(12,2) NOT NULL DEFAULT 0, -- refundable; only meaningful for RETURNABLE
              fee_currency          TEXT NOT NULL,                  -- 'KES' | 'UGX' | 'TZS' | 'XOF'
              tax_inclusive         BOOLEAN NOT NULL DEFAULT TRUE,
              effective_from        DATE NOT NULL,
              effective_to          DATE NULL,                      -- NULL = current
              notes                 TEXT NULL,
              created_at            TIMESTAMP NOT NULL DEFAULT NOW(),
              created_by            TEXT NOT NULL
           );

           CREATE INDEX idx_fee_sku           ON equipment_fee (sku_id, effective_from);
           CREATE INDEX idx_fee_sku_active    ON equipment_fee (sku_id) WHERE effective_to IS NULL;
           CREATE UNIQUE INDEX uq_fee_sku_active
             ON equipment_fee (sku_id) WHERE effective_to IS NULL; -- only one active fee row per SKU

 The unique partial index enforces that at any given time, each SKU has at most one current fee row. To change a fee: insert a
 new row with effective_from = today, update the previous row's effective_to = today - 1.

 3.4 equipment_compatibility
 Rule rows defining required-with / incompatible-with relationships between SKUs.
            CREATE TABLE equipment_compatibility (
               compatibility_id      TEXT PRIMARY KEY,               -- 'compat_01HZ...'
               operator_code         TEXT NOT NULL,
               rule_type             TEXT NOT NULL,                  -- 'REQUIRES' | 'INCOMPATIBLE_WITH' | 'RECOMMENDED_WITH'
               source_sku_id         TEXT NOT NULL REFERENCES equipment_sku(sku_id),
               target_sku_id         TEXT NULL,                      -- the partner SKU; NULL if rule is kind-level
               target_kind_code      TEXT NULL,                      -- alternative: rule targets a kind (e.g., 'any ROUTER')
               severity              TEXT NOT NULL,                  -- 'BLOCK' | 'WARN'
               notes                 TEXT NULL,
               effective_from        DATE NOT NULL,
               effective_to          DATE NULL,
               created_at            TIMESTAMP NOT NULL DEFAULT NOW(),
               created_by            TEXT NOT NULL,
               CHECK ((target_sku_id IS NOT NULL) OR (target_kind_code IS NOT NULL))
            );

            CREATE INDEX idx_compat_operator ON equipment_compatibility (operator_code);
            CREATE INDEX idx_compat_source   ON equipment_compatibility (source_sku_id) WHERE effective_to IS NULL;

 rule_type:

   - REQUIRES — source SKU MUST be paired with target SKU (or target kind) in the same WO. Used for: "this ONT requires
     the matching splitter".

   - INCOMPATIBLE_WITH — source SKU cannot be paired with target. Used for firmware mismatches, regulatory restrictions.

   - RECOMMENDED_WITH — soft hint to dispatcher / installer; not enforced.

 severity:

   - BLOCK — WO module rejects the WO finalization if rule is violated.

   - WARN — WO module flags the WO for review but allows it.

                                                                     The ID is stable across fee changes, brand corrections, hardware revisions (use

 7. Stub retirement
 PLM-CFG-06 retires wo_equipment_ref_stub, the placeholder schema in DD_WO-01-FRAMEWORK §9.3.

 7.1 Stub recap
 DD_WO-01-FRAMEWORK §9.3 defines a stub wo_equipment_ref_stub(wo_id, equipment_ref) where
 equipment_ref was an opaque string carrying brand/model/qty information without structure. The stub was always known
 to be temporary; per DD_WO-01-FRAMEWORK's stub-retirement note, when "the future Inventory/Equipment Catalog DD is
 written" the stub would be replaced with:

   - SKUs as first-class entities in PLM-CFG-06 (this DD)

   - A WO equipment table referencing equipment_sku.sku_id as FK

   - Equipment kind collapse into the SKU's kind reference (per row 12 column WO retains only (wo_id,
     equipment_ref) → after retirement, WO has wo_id + sku_id + qty)

 7.2 Migration steps
   1. Pre-deployment: PLM-CFG-06 schema deployed; SKU catalog seeded per operator (KE / UG / TZ / SN initial SKUs from
     operator inventory lists).

   2. WO module schema migration: new table wo_equipment(wo_id, sku_id, qty, serial_number_ref)
     deployed alongside the old wo_equipment_ref_stub. Both coexist during transition.

   3. Backfill: a one-time job iterates wo_equipment_ref_stub rows. For each, parses the opaque equipment_ref string
     (operator-specific parsing logic) and maps (brand, model) → sku_id by joining with equipment_sku.brand +
     .model. Where the mapping is ambiguous or fails, the row is flagged for manual review; the migration ops team resolves
     them by hand.

   4. WO module cutover: WO finalization code switches from INSERT INTO wo_equipment_ref_stub to INSERT INTO
     wo_equipment. Pre-finalization SKU validation now calls POST /api/equipment-skus/validate (per §5.5) before
     allowing the WO to commit.

   5. Verification window: 2 weeks of dual-write — WO module writes to BOTH wo_equipment_ref_stub (legacy path)
     AND wo_equipment (new path). A daily reconciliation job compares the two and reports deltas. Production traffic on the
     new path is monitored.

   6. Removal: Drop wo_equipment_ref_stub table; remove the dual-write code path in WO module;
     DD_WO-01-FRAMEWORK §9.3 documentation replaced with "retired — see DD_PLM-CFG-06."

 7.3 Caller-side changes
 In DD_WO-01-FRAMEWORK FINALIZATION step:

 7. (Legacy) Write the equipment reference string to wo_equipment_ref_stub for downstream provisioning.

 becomes:

 7. Call POST /api/equipment-skus/validate with the equipment lines. If valid, insert one row into wo_equipment per
 line referencing equipment_sku.sku_id. Emit WorkOrderEquipmentBound event with the structured equipment data
 (SKU IDs, qtys).


SOPHIX BSS Design Documents                                                                                             Page 14
 Downstream consumers of WO equipment data (provisioning, billing, OSR-01 stock decrement) now read structured sku_id
 references rather than parsing the opaque string. OSR-01 in particular needs the structured data to track stock movements
 accurately.

 7.4 Historical preservation
 wo_equipment_ref_stub rows from before migration are preserved during the dual-write window in an archive table
 wo_equipment_ref_stub_archive (created at migration step 6 just before drop). Historical WO queries for pre-migration
 orders pull from the archive; new queries hit wo_equipment.

   - Inventory workshop (separate deep-dive) — stock chain operations; informs how PLM-CFG-06 catalog must surface to
      OSR-01.

   - Work Order workshop (deep-dive 07) — equipment-on-WO finalization, install / shifting / support flows; informs validation
     rules.

 V3 design intent: provide a structured, operator-extensible equipment catalog that decouples SKU definitions from stock
 tracking, fee charging, WO binding, and compatibility validation — each of those concerns lives in its own module. The TZ
 codebase's current handling of equipment is unverified pending cartography; placeholder: "TBD pending codebase review."

 Out of v1.0 scope:

   - Stock balances + movements — owned by OSR-01 (pending).

   - Individual equipment instance tracking (serial numbers) — owned by OSR-01.

   - Vendor / procurement records — owned by EM-02 (pending) or future procurement DD.

   - Firmware / provisioning profile per SKU — owned by FUL-03 / RLM provisioning modules.

   - RMA workflows — owned by WO module (return WO types).

   - Bundled equipment kits — packages live in SIP-01; this DD records only the constituent SKUs.

   - Multi-currency same-SKU pricing — out; one currency per fee row per operator default.

   - Per-region SKU restrictions — out; SKU catalog is operator-scoped, not region-scoped. Future enhancement if needed.
