                                                                  END_OF_CURRENT_CYCLE (commit at the current cycle's cycle_end; the

                                                                  timestamp). For non-IMMEDIATE, BPMN parks on a Camunda intermediate

 1. What this is
 The downgrade operation. SUB-WF-DOWNGRADE-01 is one of the 10 operation kinds in the framework. Triggered by: a
 customer requesting a downgrade (CC, portal, retail) or an admin downgrading on the customer's behalf (e.g., as part of a
 retention save).

 Outcomes (at actual commit time, which may be NOW or a future moment per effectiveTiming): subscription
 package_ref + package_version_id updated to target Package, previous_package_ref snapshot retained, credit
 applied per cycleAnchorPolicy (or zero delta for END_OF_CURRENT_CYCLE + PRESERVE), network reconfigured for
 new Service profile (FUL-03 MODIFY_SERVICE), equipment-unbind step run if equipment-drop delta exists AND
 unbindObsoleteEquipment = true, cycle anchor preserved or reset per the operation's chosen policy, customer
 notified.

 For non-IMMEDIATE effectiveTiming, the subscription remains ACTIVE on the source Package during the wait. A
 second pending-future downgrade against the same subscription is rejected; any state-affecting operation that fires during the
 wait cancels the pending downgrade per R-EF-5.

 4. Rules

 4.1 State precondition + transition
  Rule                                 Description

  R-SUB-WF-DOWNGRADE-01-S-1            Downgrade requires the subscription's status_code = ACTIVE at request
                                       time AND at commit time. Other statuses return 409
                                       INVALID_STATE_FOR_DOWNGRADE. For scheduled-future downgrades, the
                                       check at commit time may fail if the subscription was paused or terminated
                                       during the wait — handled by R-EF-5.

  R-SUB-WF-DOWNGRADE-01-S-2            The transition at commit is ACTIVE → PENDING_DOWNGRADE → ACTIVE.
                                       PENDING_DOWNGRADE is the framework-internal transient state during the
                                       commit sequence. For scheduled-future downgrades, the subscription stays
                                       ACTIVE during the wait — PENDING_DOWNGRADE is entered only when the
                                       timer fires.

  R-SUB-WF-DOWNGRADE-01-S-3            Per framework R-FW-1, downgrade COMMIT is mutually exclusive with other
                                       state-affecting operations on the same subscription. A second downgrade
                                       COMMIT cannot fire while another commit is in progress. A scheduled-future
                                       downgrade in its wait state DOES allow other operations to fire (e.g.,
                                       customer-requested PAUSE) — see R-EF-5 for cancellation semantics.

  R-SUB-WF-DOWNGRADE-01-S-4            The subscription's current_transition_type is set to DOWNGRADE during
                                       PENDING_DOWNGRADE. current_transition_reason_code is set to
                                       the supplied downgradeTrigger. NOT set during scheduled-future wait.

  R-SUB-WF-DOWNGRADE-01-S-5            Restrictions on the subscription (active_restrictions[]) are NEITHER
                                       cleared NOR validated by this workflow. A customer with a restriction MAY
                                       downgrade — the restriction persists post-downgrade.

  R-SUB-WF-DOWNGRADE-01-S-6            At most one pending-future downgrade per subscription. A second
                                       non-IMMEDIATE downgrade request returns 409
                                       PENDING_DOWNGRADE_ALREADY_SCHEDULED with the existing operation id.
                                       An IMMEDIATE downgrade request while a pending-future downgrade exists
                                       returns 409 (caller must cancel the pending one first or wait).

 4.4 Equipment-drop delta
  Rule                         Description

  R-SUB-WF-DOWNGRADE-01-EQ-1   The workflow computes the set of service classes in the source Package that
                               are NOT in the target Package. For each obsolete service class, the workflow
                               inspects existing equipment bindings (OSR-INSTANCE-01) to identify
                               equipment that fulfills only that obsolete service class. The list is
                               obsoleteEquipmentList.

  R-SUB-WF-DOWNGRADE-01-EQ-2   When unbindObsoleteEquipment = true (the request value, defaulting
                               from operator config), the BPMN runs the equipment-unbind step for each entry
                               in obsoleteEquipmentList. OSR-INSTANCE-01 marks the equipment as
                               returned-to-inventory; physical recovery (RMA, pickup WO) is OSR-RMA-01's
                               responsibility.

  R-SUB-WF-DOWNGRADE-01-EQ-3   When unbindObsoleteEquipment = false, equipment stays bound to the
                               subscription post-downgrade. The Service Profile sent to FUL-03 drops the
                               obsolete service class, so the equipment is provisioning-orphaned — it's
                               vestigial. Operator policy decides; some operators leave the STB with the
                               customer in case they upgrade back later.

  R-SUB-WF-DOWNGRADE-01-EQ-4   Equipment that fulfills BOTH an obsolete service class AND a retained service
                               class is NOT unbound. Example: a multi-service ONT fulfilling both data and
                               voice — when downgrading to data-only, the ONT stays bound (still fulfills
                               data).



 4.5 Billing + fulfillment
  Rule                         Description

  R-SUB-WF-DOWNGRADE-01-B-1    Workflow calls bil01-emit-intent with intentKind =
                               DOWNGRADE_INTENT. Context: {sourcePackageRef,
                               sourcePackageVersionId, sourcePackagePrice,
                               targetPackageRef, targetPackageVersionId,
                               targetPackagePrice, billingFrequencyChanged,
                               downgradeTrigger, cycleAnchorPolicy, effectiveTiming}. BIL-01
                               computes the appropriate credit per cycleAnchorPolicy (see R-CA-3), may
                               apply BillableEvents per BIL-CFG-01.

  R-SUB-WF-DOWNGRADE-01-B-2    Pay-first gate does NOT apply (downgrade is value-decreasing — never
                               produces a positive customer charge). Credit distribution per BIL-01's
                               billing-mode policy: prepaid → wallet top-up; postpaid → invoice credit line.
                               BIL-01 owns the mechanism.

  R-SUB-WF-DOWNGRADE-01-B-3    FUL-03 called with intent=MODIFY_SERVICE, passing source + target
                               Package snapshots. FUL-03 owns the per-service-class fan-out: (a) Service
                               classes in both source and target → provisioner modifyService (or no-op if
                               Service profile unchanged); (b) service classes in source but NOT target →
                               provisioner deactivate, dispatched via the HomePass's

 4.6 Cycle anchor policy
  Rule                         Description

  R-SUB-WF-DOWNGRADE-01-CA-1   The request supplies cycleAnchorPolicy ∈ {PRESERVE,
                               RESET_TO_DOWNGRADE_DATE}. If absent, the workflow defaults to
                               subscription_downgrade_config.default_cycle_anchor_policy
                               for the operator. Unknown value returns 400
                               UNKNOWN_CYCLE_ANCHOR_POLICY.

  R-SUB-WF-DOWNGRADE-01-CA-2   cycleAnchorPolicy is captured per downgrade — NOT a subscription-level
                               invariant. The resolved policy is persisted to the Kafka event payload + the
                               framework's subscription_operation audit row.

  R-SUB-WF-DOWNGRADE-01-CA-3   BIL-01 interprets cycleAnchorPolicy in the DOWNGRADE_INTENT context.
                               PRESERVE → BIL-01 returns a prorated credit line item
                               (DOWNGRADE_PRORATE_CREDIT BillableEvent — negative amount) for
                               cycle-days-remaining × price-difference. RESET_TO_DOWNGRADE_DATE →
                               BIL-01 returns an old-cycle credit line (DOWNGRADE_OLD_CYCLE_CREDIT) for
                               the unused portion of the source-priced cycle + a fresh first-cycle line
                               (DOWNGRADE_FIRST_CYCLE — positive at target price) for the new cycle
                               starting at commit time. Net is still ≤ 0 (downgrade never charges the customer
                               more).

  R-SUB-WF-DOWNGRADE-01-CA-4   When RESET_TO_DOWNGRADE_DATE, the new cycle starts at commit time and
                               runs for targetPackage.billing_frequency_days. Subsequent cycles
                               roll forward from the new anchor. Cycle-anchor mutation is committed via the
                               master-fields step alongside package_ref.



 4.7 Effective timing
  Rule                         Description

  R-SUB-WF-DOWNGRADE-01-EF-1   The request supplies effectiveTiming ∈ {IMMEDIATE,
                               END_OF_CURRENT_CYCLE, SCHEDULED_AT}. If absent, the workflow defaults
                               to subscription_downgrade_config.default_effective_timing
                               (KE v1.0: END_OF_CURRENT_CYCLE). Unknown value returns 400
                               UNKNOWN_EFFECTIVE_TIMING.

  R-SUB-WF-DOWNGRADE-01-EF-2   When effectiveTiming = SCHEDULED_AT, the request MUST also supply
                               scheduledAt (ISO 8601 timestamp). Missing → 400
                               SCHEDULED_AT_MISSING. scheduledAt MUST be strictly in the future AND
                               within max_future_scheduled_days from now. Past or beyond-window →
                               400 SCHEDULED_AT_OUT_OF_BOUNDS.

  R-SUB-WF-DOWNGRADE-01-EF-3   Combination effectiveTiming = END_OF_CURRENT_CYCLE AND
                               cycleAnchorPolicy = RESET_TO_DOWNGRADE_DATE is redundant.
                               Returns 400 REDUNDANT_POLICY_COMBINATION with guidance to use
                               cycleAnchorPolicy = PRESERVE for end-of-cycle downgrades.

  R-SUB-WF-DOWNGRADE-01-EF-4   For non-IMMEDIATE timings: the BPMN parks on a Camunda intermediate
                               timer. The subscription_operation.current_state is set to
                               SCHEDULED. The trigger endpoint returns 202 with scheduledCommitAt
                               populated. SubscriptionDowngradeScheduled is emitted on Kafka. At the
                               timer fire, the BPMN re-validates and proceeds with the commit sequence.

  R-SUB-WF-DOWNGRADE-01-EF-5   Cancellation paths during the wait: (a) explicit DELETE
                               /pending-downgrade/{operationId} from BO admin or customer —
                               stops the timer, emits SubscriptionDowngradeCancelled, closes the
                               operation as CANCELLED; (b) any state-affecting operation on the same
                               subscription (PAUSE, SUSPEND-NP, TERMINATE, UPGRADE, another
                               DOWNGRADE) — the framework's external-cancel-requested
                               mechanism stops the timer and emits SubscriptionDowngradeCancelled
                               with cancellationReasonCode =
                               SUPERSEDED_BY_<otherOperationKind>.


SOPHIX BSS Design Documents                                                                            Page 9
  Rule                                                           Description

  R-SUB-WF-DOWNGRADE-01-EF-6                                     At commit time (after the wait), the workflow re-validates all preconditions (S-1,
                                                                 TP-1 through TP-7, equipment-drop delta still consistent). If any check fails at
                                                                 commit, the workflow rejects with SubscriptionDowngradeRejected
                                                                 carrying rejectionStage = COMMIT_REVALIDATION. Example: target
                                                                 Package transitioned to END_OF_LIFE between schedule and commit → reject.

  R-SUB-WF-DOWNGRADE-01-EF-7                                     The cycleAnchorPolicy recorded at request time is honored at commit time.
                                                                 For END_OF_CURRENT_CYCLE + PRESERVE, the commit naturally lands on the
                                                                 cycle boundary; BIL-01 returns zero delta (the current cycle finishes on source
                                                                 price, next cycle starts on target price); no anchor mutation needed. For
                                                                 SCHEDULED_AT mid-cycle commits, BIL-01 behaves identically to IMMEDIATE
                                                                 at the commit moment (credit delta if PRESERVE; old-cycle credit + fresh cycle
                                                                 if RESET_TO_DOWNGRADE_DATE — anchor moves to the scheduled date).

  R-SUB-WF-DOWNGRADE-01-EF-8                                     Credit settlement is performed at commit time (not request time) — for
                                                                 non-IMMEDIATE downgrades, the customer's wallet / invoice is only touched at
                                                                 commit. This matches the principle that scheduled downgrades shouldn't
                                                                 pre-issue credits (the customer keeps using the higher-tier service through the
                                                                 wait).
