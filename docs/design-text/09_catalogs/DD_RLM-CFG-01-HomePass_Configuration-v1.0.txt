 1. What this process is about
 This DD covers the three entities that describe where Wananchi can sell and serve customers. They are all owned by a
 new homepass module.

   - A Franchise is a top-level commercial / operational region. Wananchi KE has roughly six franchises (e.g., Nairobi 002).
     The Franchise drives which sales team covers an address, which contractor pool installs, and which per-franchise price
     applies. A Franchise has a real geographic footprint (a polygon on the map), captured here as optional GeoJSON.

   - A TechContractorSkill is a configurable skill type used to describe what kind of work a contractor is qualified to do:
     INSTALLATION, MAINTENANCE, SUPPORT, B2B, etc. Admins manage this as a catalog so new skills can be added
     without code change. Skills feed two downstream concerns: installation routing (FUL-03 picks a contractor with
     INSTALLATION skill) and ticketing (ASR-01 routes a ticket to a contractor with SUPPORT skill). Skills are properties of
     contractors, NOT of regions.

   - A TechContractor is a contractor company or team that performs network or customer-facing work. It carries a non-empty
     skills[] array (e.g., [INSTALLATION, MAINTENANCE] for a fiber install crew; [SUPPORT] for a helpdesk team). A
     TechContractor is assigned to one or more TechRegions — the geography it serves.

   - A TechRegion is a pure technical / operational geographic zone. Nairobi has roughly 8–9 TechRegions. TechRegions
     are NOT structurally inside Franchises — they are independent registries. A TechRegion is served by one or more
     TechContractors (via a join), and the *skills available in that TechRegion* are the union of the assigned contractors'
     skills. This was a deliberate v1 design choice: the commercial team manages Franchises, the technical team manages
     TechContractors and the regions they serve, and we don't want one to block the other. A TechRegion also has an optional
     GeoJSON footprint and an optional coverage polygon (the area within it that has GPON / HFC reach).

   - A HomePass is a single addressable termination point — one apartment, one home, one shop. It is the addressable unit of
     coverage: a customer can only be onboarded at an address that exists as a HomePass with an eligible status. A
     HomePass is linked to one or more Franchises (a building in a commercial overlap zone, or B2B + B2C franchises both
     covering the address, may yield several refs) and one or more TechRegions (e.g., a residential TechRegion for the
     building's main service, plus a separate TechRegion if part of the building is in another administrative area). The
     HomePass exposes a primitive — "given a required skill, which contractors are eligible to work this address" — by walking
     HomePass → TechRegions → assigned Contractors filtered by skill; the actual WO routing logic that consumes this

     access technology that physically reaches the address (GPON / HFC / COPPER / FTTH / WIRELESS — what cable is
     in the ground / on the pole), (2) the services supported derived from the network path (DATA, VOICE, IPTV_MULTICAST
     — what the HomePass can carry at its physical termination; cloud / OTT services consumed over the customer's DATA
     connection are NOT listed here — they're Service-level concerns on the PLM-CFG-01 / PLM-CFG-08 side. A phone-only
     POTS customer would have a HomePass with accessTechnology = COPPER and servicesSupported =

     ONT serial, ...) the address sits behind, each node a reference into the network_node catalog, and (4) its current status
     in the network construction lifecycle.

 #### HomePass status codes

 HomePass status is NOT a hardcoded enum. It is a per-deployment configurable catalog (homepass_status_code —
 see data model) where admins seed whatever codes their operation needs. Each catalog entry carries semantic flags read
 by downstream modules:

   - is_initial — valid as the default status when a HomePass is created

   - is_sellable — sales-eligibility lookups return this HomePass to onboarding/coverage-check

   - is_active — a customer is installed and consuming service (drives search dual-status, billing trigger)

   - is_terminal — no further transitions allowed

   - requires_approval_to_enter — the reference strict BPMN gates transitions INTO this status on a user-task
     approval

   - triggers_lead_notification — first time a HomePass enters a status with this flag set, the
     HomePassReachedSellable event fires (drives lead-notify; default catalog has this on the RFS row)

   - blocks_soft_delete — HomePass cannot be soft-deleted while in this status

 The transitions between codes are owned by the deployment's Camunda workflow (see Status Workflow section). The
 catalog defines which codes EXIST and what each one MEANS; the workflow defines how a HomePass moves between
 them.

 ##### Wananchi KE seed (richer set, mirrors BH vocabulary)

 Wananchi's KE deployment seeds the catalog with BH's actual codes (observed in production: NSR Not Ready, NSV No RoE,
 PH1/PH2/PH3 HFC construction phases, RFC ready for sale construction, RFN ready for sale none-sellable, plus the
 default-seed codes). The legacy BH code is preserved on each migrated row in a legacy_status_code field for audit. New
 transitions are defined in the deployment's Camunda workflow.

 ##### Status semantics are read, never hardcoded

 The eligible-lookup endpoint, the soft-delete check, the first-time-sellable event, and the reference BPMN all consult the
 catalog flags rather than hardcoded code names. A deployment can call its sellable status RFS, LIVE, READY, or anything
 else — the system behaves the same because downstream code reads is_sellable, never the literal code.

 #### Catalog lifecycle states (Franchise, TechRegion, TechContractor)

 Same model as PLM-CFG-04, simpler:

   - DRAFT — admin still building it; not visible to other modules

   - ACTIVE — published; referenced by HomePasses (or by TechRegion ↔ TechContractor join), downstream modules see it

   - RETIRED — terminal; cannot be re-activated

 Transitions: DRAFT → ACTIVE (admin activates after rules pass), ACTIVE → RETIRED (admin retires, terminal). No
 "INACTIVE" middle state for Franchise / TechContractor / TechRegion — these are not time-bound entities; they exist or they
 don't.

 TechContractorSkill uses the same lifecycle (DRAFT / ACTIVE / RETIRED) for consistency, though in practice skill entries
 rarely retire.

 Maker-checker UI for HomePass status transitions:

   - A user with HOMEPASS_ADMIN proposes a transition (e.g., NSN → RFS). The proposal is created with status PROPOSED,
     the proposer recorded.


SOPHIX BSS Design Documents                                                                                                              Page 19
   - A user with HOMEPASS_APPROVER (must be a different user than the proposer) sees a queue of pending proposals, opens
     each, and approves or rejects.

   - On approve: the HomePass status flips, an event is emitted, the proposal record is marked APPROVED.

   - On reject: the proposal record is marked REJECTED with a reason; the HomePass status does not change.

 ##### Structure of network_path

 The network_path JSONB column captures the chain of network nodes the HomePass sits behind, including the port on
 each node when known. Modeling as JSONB (not a normalized homepass_network_node table) is a deliberate v1
 choice: the path is small (typically 3–5 nodes), heterogeneous (different node sequences per technology), and most reads
 want the whole path or a single endpoint — patterns JSONB serves cleanly. If reporting needs like "all HomePasses behind
 OLT X port 1/2/3" become hot and frequent, a future DD can derive a normalized table from this column or materialize a view;
 the JSONB stays as the source of truth.
           {
               "captureMode": "PRE_INSTALLATION",
               "nodes": [
                 { "type": "OLT",      "code": "OLT-NRB-WTL-01",     "role": "service_management", "port": "1/2/3" },
                 { "type": "SPLITTER", "code": "SPL-NRB-WTL-FAT-12", "role": "passive",            "port": "P05"   },
                 { "type": "FAT",      "code": "FAT-NRB-WTL-12-A4", "role": "termination",         "port": "A4-7" },
                 { "type": "ONT",      "code": "ONT-SN-1234567890", "role": "termination",         "port": null    }
               ]
           }

 Fields:

   - captureMode — PRE_INSTALLATION (full path with ports known at HomePass time, typical for KE) or
     AT_INSTALLATION (only the upstream chunk is known at HomePass time; port and last-mile binding completed by
     fulfillment when the customer is installed, typical for TZ-style fiber-on-customer-install regions where field ops captures
     port details on the install ticket)

   - nodes[] — ordered chain. Order matters: index 0 is upstream-most (closest to the network core), the last entry is closest
     to the customer.

   - nodes[i].type — enum: OLT, SPLITTER, FAT, FDT, ONT, HEADEND, DISTRIBUTION_NODE, AMPLIFIER,
     LINE_EXTENDER, VOIPSWITCH, NMS, OTHER. Extensible — adding a new node type means an enum addition and (if
     needed) a service-management mapping rule update.

   - nodes[i].code — vendor-or-internal identifier for this specific node (e.g., the OLT shelf identifier, the FAT plate code).
     The string format is per-deployment.

   - nodes[i].role — service_management (a node that the gateways need to call for service operations — typically
     OLT and VOIPSWITCH and NMS), passive (just a hop — splitters, FATs, amplifiers in a pass-through role), or
     termination (the last node before the customer endpoint).

   - nodes[i].port — nullable string identifier of the specific port / slot / line on this node that serves this HomePass (e.g.,
     "1/2/3" for an OLT port, "P05" for a splitter port, "A4-7" for a FAT plate position). null when the node has no
     meaningful port concept (e.g., an ONT where the serial number IS the identifier) or when the port is not yet known
     (AT_INSTALLATION mode, before install). Format is opaque, per-deployment, validated only for non-empty when present
     (R-RLM-CFG-01-H-13).

 For AT_INSTALLATION captureMode, the path captured at HomePass time covers only the upstream nodes (and their ports
 may be filled with placeholder or null values for the downstream entries). When the customer is installed (FUL-08),
 fulfillment appends and/or updates the last-mile nodes — adding the specific ONT serial, filling in the OLT port
 assignment, etc. — via a dedicated PATCH endpoint. The HomePass's network_path is then UPDATED; the original
 captureMode = AT_INSTALLATION is preserved for audit / reporting (so we can tell at-install regions from pre-install
 ones) even when the actual path is now complete.

 ##### Structure of service_management_endpoints

 Derived from network_path at save time. Pre-computed so provisioning-gw, voice-gw, iptv-gw, fulfillment,
 and any other gateway can read one short JSONB blob instead of walking the path. Each entry carries both the node code
 AND the port — both are required for the gateway to address a specific subscriber line.



SOPHIX BSS Design Documents                                                                                                   Page 31
 The keys name a service family (the kind of service being managed), NOT the gateway that handles it. Symmetric naming
 across families: every key answers "what service family is this endpoint for?"
          {
              "data":             { "nodeCode": "OLT-NRB-WTL-01",      "port": "1/2/3"    },
              "voice":            { "nodeCode": "VOIPSWITCH-NRB-01",   "port": "EXT-5421" },
              "iptv_multicast":   { "nodeCode": "OLT-NRB-WTL-01",      "port": "1/2/3"    },
              "monitoring":       { "nodeCode": "NMS-MAIN",            "port": null       }
          }

 The keys are service-family identifiers — data, voice, iptv_multicast, monitoring for now; extensible (e.g., a future
 deployment that offers a managed-CCTV service over the HomePass network would add cctv). The values are objects
 {nodeCode, port} pulled from network_path.nodes[] where role = "service_management" and the node's
 type matches the service family by a deployment-configurable mapping (default: OLT → data + iptv_multicast,
 VOIPSWITCH → voice, NMS → monitoring). The port is copied verbatim from the matched node — it may be null if
 the matched node's port hasn't been captured yet (AT_INSTALLATION path before install). If no node in network_path
 matches a given service family, that family is absent from the map (rather than null) — keeps the JSON small.

 Note that data and iptv_multicast may legitimately point at the same node + port (e.g., an OLT delivering both
 subscriber-line data service and multicast IPTV through the same GPON port). Different services, same physical endpoint.

 This map is recomputed on every HomePass save (cheap — walk a 3–5-element array) and stored. Consumers always read
 from here, never re-derive.

 ##### How fulfillment uses service_management_endpoints to dispatch commands

 At activation (FUL-03) and on every subsequent service operation (suspend, upgrade, terminate — FUL-04, FUL-05),
 fulfillment resolves the target node via the following flow.

 Inputs at the moment fulfillment runs:

   - A subscription_id, which carries the customer_id, the package_ref (SIP-01), and the homepass_id (HomePass
     at the installed address).

   - The operation type (ACTIVATE, SUSPEND, UPGRADE, TERMINATE).

 Fulfillment then:

   1. Loads the Package (SIP-01). The Package lists its constituent service_refs[].

   2. For each Service in the Package, loads the Service def (PLM-CFG-01). The Service def carries:

   - networkProfileShape.provisionerKey — which Provisioner adapter to use (e.g., GPON_RES_PROFILE,
     VOIP_SIP_PROFILE)

   - networkProfileShape.params — the recipe inputs (downstream/upstream Mbps, profile template, etc.)

   - equipmentRequirement — what equipment the service expects (e.g., GPON_ONT)

   - serviceManagementKey — which endpoint family on the HomePass this Service consumes (e.g., "data" for an
     internet Service, "voice" for a VoIP Service, "iptv_multicast" for a multicast STB-IPTV Service). Defined by
     R-PLM-CFG-01-6. Nullable — see below.

   3. Loads the HomePass (this DD). The HomePass carries service_management_endpoints, the pre-computed map
     of {serviceFamily → {nodeCode, port}}.

   4. Resolves the node and port: for each Service, looks up
     homepass.service_management_endpoints[service.serviceManagementKey]. That returns both the
     nodeCode and the port to address. If port is null (AT_INSTALLATION mode, install not yet run), fulfillment rejects the
     operation with a clear error — the install workflow must complete first.

   5. Calls the Provisioner adapter (registered by provisionerKey per PLM-CFG-01's activation flow):
     Provisioner.activate(params, customer, equipment, targetNodeCode, targetPort). The Provisioner
     translates the recipe into concrete NMSGateway / AAAGateway / VoiceGateway calls, addressing the resolved node
     code AND port.

 When serviceManagementKey is null (partner-telco fulfilled services — e.g., a bundled mobile SIM data pack from a
 partner MVNO, an OTT cloud-IPTV app, a streaming subscription resold over the customer's data connection): the Service is
 NOT addressed at the HomePass. The Provisioner adapter sources its target from elsewhere — typically the Service def's
 partnerEndpoint metadata (the partner's API URL, account ref, etc.). Fulfillment skips the HomePass endpoint lookup for
 these. PLM-CFG-01 documents the null-key case; this DD's responsibility is just to NOT require an endpoint when the
 Service didn't ask for one.

SOPHIX BSS Design Documents                                                                                                              Page 33
   - Service def is portable. "Internet 100MB" is the same Service whether the customer is in Nairobi or Mombasa. It carries

 Service def touched, no Package version bumped.

 ##### Cross-DD coherence with PLM-CFG-01

 This flow depends on Service.serviceManagementKey (PLM-CFG-01 R-6). The two DDs are coherent: PLM-CFG-01
 defines the column, Fact, DRL rule, and event payload; RLM-CFG-01 defines the endpoint family keys. The default value for
 an addressable Service that omits the key is "data". For services not addressed at the HomePass (partner-telco mobile SIM
 data, OTT IPTV apps, third-party streaming bundles), serviceManagementKey is null — fulfillment skips the HomePass
 endpoint lookup and the Provisioner adapter sources its target from elsewhere on the Service def.

 GIS integration (optional, additive — internal to this module)
 This section describes how RLM-CFG-01 integrates with a GIS service for address enrichment, geographic lookups, and map
 rendering. The integration is strictly opt-in — a deployment without GIS configured continues to work exactly as before.
 Every HomePass field can still be entered manually. The GIS integration is value-add, never a hard dependency.

 The integration lives inside the homepass module as an internal geo-client sub-area, not as a separate foundation
 gateway. The decision is deliberate: RLM-CFG-01 is the only consumer today, and the abstraction cost of a separate
 foundation is not justified by one consumer. If a second module (Equipment for ONT GPS validation, WO for crew dispatch
 optimization, Construction for design-zone polygons) later needs the same capabilities, geo-client will be promoted to a
 geo-gw foundation at that point. The interface contract documented below is forward-compatible with that promotion.

 The default GIS provider is Google Maps Platform (Wananchi's current GIS — formerly known as Google Maps PRO). The
 adapter pattern in geo-client keeps the door open for other backends: ArcGIS, GeoServer, Carto, a local PostGIS server,
 or a custom in-house map service. Switching providers is an adapter swap behind the interface; the rest of homepass code
 does not change.

 #### Two GIS layers

 V3 distinguishes two GIS layers:

   1. Public geographic data — streets, addresses, admin boundaries, coordinates. Sourced from Google Maps Platform via
     the geo-client adapter.

   2. Wananchi's private network topology — FAT positions, OLT-to-FAT chains, building-level coverage. Sourced from
     PDF design maps for human reference and from the network_node catalog for structured queries. See "Design map
     PDFs and structured topology" below.

 The two layers are addressed with different mechanisms in this DD: the public layer through geo-client API calls, the
 private layer through map_link URL references and the network_node catalog.

 #### geo-client sub-module

 An internal sub-area of the homepass module providing the GIS capability. Responsibilities:

   - abstracts the GIS provider behind a stable adapter interface (Java interface or PHP contract — same shape in both stacks)

   - holds the API key / credentials per deployment (config-driven, never logged)

   - caches responses in the geo_lookup_cache table (Google Maps bills per call; same address geocoded twice in 30 days
      hits cache, not Google)

   - normalizes responses to a stable internal shape across adapter implementations

 The Java adapter contract:
          public interface GeoAdapter {
              GeocodeResult geocode(String address, BiasContext bias);
              ReverseGeocodeResult reverseGeocode(double lat, double lng);
              List<AutocompleteSuggestion> autocomplete(String query, String sessionToken, BiasContext bias);
              PlaceDetails placeDetails(String providerPlaceId);
              ContainmentResult contains(double lat, double lng, List<String> layers);
          }

 v1 ships with one adapter, GoogleMapsAdapter, calling:

   - Geocoding API for geocode and reverseGeocode

   - Places API (Place Autocomplete + Place Details) for autocomplete and placeDetails

   - In-process polygon-in-point test against franchise.boundary_geojson / tech_region.boundary_geojson for
      contains (no provider call needed; the polygons live in this module's DB)

 The providerPlaceId returned by geocode / reverseGeocode / placeDetails is opaque to the rest of homepass;
 with the Google adapter it's a Google Place ID, with an ArcGIS adapter it would be an ArcGIS feature ID, with PostGIS it
 might be a row PK. The module stores it verbatim in homepass.google_place_id and round-trips it.

 When a deployment has the homepass.gis.enabled flag false, all geo-client methods are no-ops (returning empty
 results) and the integration points described below silently degrade — no errors, just no enrichment.

 Adding a non-Google adapter later is a matter of writing a new class implementing GeoAdapter and flipping
 homepass.gis.adapter in config. No other module code changes.

 #### Design map PDFs and structured topology

 Network design today lives in PDF artifacts: pink FAT polygons, labeled FAT codes (104-25, 104-26), blue building boxes
 with apartment-count annotations (e.g., 48/13). No programmatic GIS contains this data, and automated extraction is

 non-trivial (vector vs raster classification, named-layer parsing for vector PDFs, manual digitization for rasters).

 V3 handles network design with two coexisting artifacts:

 PDFs as link-attached reference. The map_link column on homepass stores the URL of the building's / area's design

 Structured topology in the network_node catalog. Admins transcribe FATs / OLTs / Splitters from PDFs into the

 Automated PDF-to-GeoJSON conversion is out of V3 scope. If prioritized later, it lands as a separate DD (working name
 GIS-MIGRATION-01 / NETWORK-TOPOLOGY-01) feeding into the existing network_node.metadata and
 tech_region.boundary_geojson columns with no schema change here.

 #### Forward-looking: PostGIS as a future optimization

 In v1, polygons on franchise.boundary_geojson and tech_region.boundary_geojson are stored as plain JSONB.
 Polygon containment queries (via the geo-client adapter) work by fetching all polygons of the relevant layer and testing
 them in application code (or in the adapter against Google Maps' containment API).

 This scales fine for Wananchi's volumes (~6 Franchises + ~50 TechRegions across KE). When polygon counts grow or
 spatial queries become hotter (e.g., a future construction-planning DD does "find all HomePasses within 100m of this
 proposed new FAT"), v1 can upgrade to:

   - Enable the PostGIS extension on the homepass DB: CREATE EXTENSION postgis;

   - Migrate boundary_geojson to boundary_geom GEOMETRY(MULTIPOLYGON, 4326) columns

   - Add GiST spatial indexes

   - Move polygon-in-point tests from in-process to direct in-database queries

 The migration is non-breaking (the API surface stays the same; only the storage and execution change). PostGIS becomes
 attractive when call-volume to Google's containment API gets expensive OR when the query needs are richer than Google's
 API offers (e.g., "find HomePasses within polygon X but outside polygon Y").

 Not v1 work. Documented here so a future reader understands the upgrade path.

 Status workflow
 Every HomePass status transition flows through a Camunda BPMN process instance. The DD defines the contract the
 workflow must honor, ships two reference BPMN definitions (strict maker-checker and passthrough admin-driven), and
 leaves the choice between them — or any deployment-specific variant — to per-deployment configuration. There are NO
 transition-validity rules in DRL or in DB constraints; the workflow IS the rules.

 #### Camunda is the engine; maker-checker is a pattern

 The two terms are not alternatives:

   - Camunda is the workflow engine. It runs BPMN processes, persists state, routes work to user tasks, records history, and
     signals end events. It does not define what happens in a transition — it runs whatever BPMN is deployed under the
     homepass-status-transition process key.

   - Maker-checker is an approval pattern in which the proposer (maker) and the approver (checker) are different users. It is
     implemented here as a Camunda user task with an assignment listener that rejects assignment to the proposer.

 Every HomePass status transition runs as a Camunda process instance. The strict reference BPMN includes the
 maker-checker user task; the passthrough reference BPMN does not. Both run on Camunda.

 Whether a given transition is gated on approval is data, not code: the requires_approval_to_enter flag on the
 destination status code's catalog row. The strict BPMN reads this flag at its decision gateway; the passthrough BPMN ignores


SOPHIX BSS Design Documents                                                                                               Page 38
 it (always auto-applies). A deployment changes its approval policy by flipping the catalog flag — no BPMN or application
 redeployment.

 #### Why every transition routes through Camunda

   - Single code path in the service layer — startProcessInstance regardless of deployment policy.

   - Uniform audit lineage — every transition is a process instance in Camunda history with the same shape (proposedBy,
     proposedAt, decidedBy, decidedAt, reasons, variables).

   - HOMEPASS-OP-01 integration — the future construction workflow is also Camunda and calls the status-transition
     workflow as a child process via call-activity. A bypass path would break this integration.

   - Policy evolves without a code release — catalog flag flip, BPMN swap if needed.

 #### Process key and variables

   - Process key: homepass-status-transition (each deployment ships one or more BPMN under this key, selected at
     runtime via Camunda's process-versioning).

   - Start variables (passed by the service layer when proposing a transition):

   - homepassId (string) — target HomePass

   - fromStatusCode / toStatusCode (string) — proposed transition

   - toStatusCatalogEntry (object) — the destination status's catalog row including all semantic flags, snapshotted at start
     so the workflow gateway has a stable view

   - proposedBy (string) — actor

   - proposedReason (string, nullable) — comment

   - End event types:

   - transition-approved → service-layer listener updates homepass.status_code to toStatusCode, sets
     has_been_sellable = true if this is the first time entering an is_sellable AND
     triggers_lead_notification status, emits HomePassStatusChanged, and (if the sellable latch flipped) emits
     HomePassReachedSellable. All persisted atomically with an outbox event in one DB transaction.

   - transition-rejected → listener emits HomePassTransitionRejected. HomePass row unchanged. No DB row in
     this module — the rejection lineage is in Camunda's history.

 #### Contract that any workflow must honor

 A deployment may ship any BPMN under the homepass-status-transition key, but the BPMN MUST:

   1. End with exactly one of the two end events (transition-approved or transition-rejected). Listeners on
     these end events do the actual HomePass row update + event emission.

   2. Honor maker-checker if the BPMN has an approval user task: the task's assignee-validation listener must reject
     assignment to proposedBy (same user can't approve their own proposal). Both reference BPMNs include this listener
     pattern.

   3. Carry the standard process variables named above, so the history queries
     (/api/homepasses/{id}/transitions) can project them uniformly across deployments.

 The BPMN owns: which transitions are valid (any not-defined-in-BPMN transition fails to start the workflow), which require
 user tasks, which require additional gates (e.g., checks against external systems), what notifications to send during the
 workflow itself.

 #### BPMN file layout

 homepass-status-transition BPMNs live in the homepass module's workflow folder (per FOUNDATION_CAMUNDA
 convention):
          modules/homepass/
          ■■■ src/main/resources/
              ■■■ workflows/
                  ■■■ homepass-status-transition--strict.bpmn             ← reference strict maker-checker (KE default)
                  ■■■ homepass-status-transition--passthrough.bpmn        ← reference passthrough admin-driven

 Both files declare the same process key homepass-status-transition and the same end-event names
 (transition-approved, transition-rejected). A deployment ships exactly ONE of them — Camunda's process
 definition deployer picks up whichever .bpmn is in the workflow folder. KE ships the strict one; deployments that prefer
 admin-driven flips ship the passthrough one. A custom deployment can replace either with its own BPMN as long as the

 contract holds (same process key, same end-event names, same start-variable shape, same listener wiring).

 Both reference BPMNs are checked into the homepass module's resources folder and deployed at module startup via

     null. Whether this is a significant or marginal gap depends on the actual state of BH data — the technical team should
     sample-audit before committing to a remediation plan. The Risks section documents this open question.

   4. Order of seeding:

     unknown node code, so the catalog must be complete first.

   - Seed the HomePassStatusCode catalog with the deployment's status set. For Wananchi KE, seed all BH codes (NPL,

 Risks
   - Address normalization at bulk import. BH has free-text Address and Apartment fields with inconsistent formatting
     (case, abbreviations, trailing whitespace). Without normalization, R-RLM-CFG-01-H-1 uniqueness will under-detect
     duplicates. Mitigation: a normalization step in BulkImportService (uppercase, trim, collapse whitespace) applied
     before uniqueness check; the normalized form is stored alongside the original for display.

   - Workflow definition correctness. Transition validity now lives entirely in the Camunda BPMN. A misconfigured BPMN —
     e.g., one that allows NPL → RETIRED, or one that forgets the maker-checker user-task — would silently allow incorrect
     behavior. Mitigation: ship the strict reference BPMN as the KE default with a CI test suite that exercises every transition
     path against expected outcomes; require BPMN reviews on PR for deployments that fork it. The DD does NOT enforce a
     specific transition graph because different deployments legitimately need different graphs (e.g., a fully
     decommissioned-only flow for a winding-down deployment).

   - Maker-checker workflow flexibility. The strict BPMN's gating policy (which transitions require approval, who can
     approve) is encoded in BPMN, not in code. If a deployment finds the rule too strict — for instance, wanting to auto-apply
     transitions that carry verified upstream evidence — that becomes a BPMN edit on a per-deployment basis, not a code
     release. The Status Workflow section documents the workflow contract every BPMN must honor; the policy choices on top
     are deployment-owned.

   - Workflow process instance hygiene. Long-running pending approvals could pile up in Camunda's runtime. Mitigation:
     set a deployment-configurable timeout (e.g., 30 days) via a timer boundary event in the BPMN that triggers
     transition-rejected with reason "timed out"; an admin can re-propose if needed. The reference BPMN includes this
     timer.

   - Port-data quality at migration — to confirm with the team. It is unclear at design time how complete BH's port capture
     is. The technical team should sample-audit a representative slice of BH HomePasses (across GPON and HFC, across
     WAI/ACT and earlier statuses) to determine the actual gap before any sub-project is committed. *If* it turns out a
     significant fraction of WAI/ACT HomePasses lack accurate ports, a reconciliation pass (comparing the imported
     network_path against the OLT NMS / design map) becomes necessary because fulfillment cannot operate the service
     without correct port-on-OLT data. For HomePasses still in NPL / NSN at import time, ports can be filled lazily as
     construction completes. The DD does not commit to a specific mitigation until the audit results are known.

   - HomePassReachedSellable event semantics for re-sellable. R-RLM-CFG-01-H-6 fires the event only on the FIRST
     transition into a sellable status (latches via has_been_sellable). If a HomePass goes sellable → non-sellable →
     sellable (e.g., RFS → NSN → RFS for a re-design), the second flip does NOT re-fire. Confirm this is the desired
     semantics for the lead-notify use case — if Wananchi wants to re-notify on every entry into a sellable status, the rule
     changes to fire every time (and the latch goes away).

   - Bulk import atomicity at scale. Importing hundreds of thousands of rows in one transaction is impractical. The
     "all-or-nothing per call" semantic in the API should be per-batch (e.g., 1000 rows per call). For the initial Franchise-level
     migration, the user uploads multiple batches; each batch atomic; failures in batch N do not roll back batch N-1.
