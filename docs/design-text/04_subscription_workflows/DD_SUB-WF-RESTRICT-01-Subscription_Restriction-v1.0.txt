 1. What this is
 The restriction operation. SUB-WF-RESTRICT-01 is one of the 10 operation kinds in the framework, and the only one that
 does not mutate status_code. Two intents (ADD and REMOVE) share the same workflow shape; intent is carried as a
 process variable.

 ADD path: validate subscription is ACTIVE → look up restriction catalog row → check restriction not already active → check
 role gating + customer-self-service eligibility → call billing intent (RESTRICTION_ADD_INTENT — usually no fee but
 operator may declare BillableEvents) → call FUL-04 with intent=APPLY_RESTRICTION → on success, append to
 active_restrictions[] via SUB-LM-01 put-active-restrictions → emit SubscriptionRestrictionAdded.

 REMOVE path: validate subscription is ACTIVE → check restriction is currently active → check role gating + dunning-marker
 → call billing intent (RESTRICTION_REMOVE_INTENT — may carry reactivation fee for some restrictions) → call FUL-04
 with intent=LIFT_RESTRICTION (with remainingActiveRestrictions[] for adapter logic) → on success, remove
 from active_restrictions[] → emit SubscriptionRestrictionRemoved.

 What this DD owns
   1. subscription_restrict_config table — per-operator config: customer-self-service enablement, dunning-marker
     enforcement on removal, default reason taxonomy.

   2. Intent taxonomy — 2 intents with role-gating rules.

   3. Trigger taxonomy — 4 channel triggers.

   4. Dunning marker rules — when set, by whom, when human-actor REMOVE is rejected.

   5. Trigger REST endpoints — POST /api/subscriptions/{subscription_id}/restrictions (ADD) + DELETE
     /api/subscriptions/{subscription_id}/restrictions/{code} (REMOVE).

 API convention note: most subscription operations use verb endpoints such as /activate or /pause because they mutate
 the subscription status through a single operation verb. RESTRICT intentionally uses a sub-resource collection because
 restrictions can be listed, added, and removed independently while the subscription remains ACTIVE. This is the approved
 exception to the MACD verb-suffix convention.

   6. Domain Kafka events — SubscriptionRestrictionAdded + SubscriptionRestrictionRemoved +
     SubscriptionRestrictionAddRejected + SubscriptionRestrictionRemoveRejected.

   7. Restriction workflow rules — 15 rules in §4.

 What this DD does NOT own
   - BPMN files — owned by per-operator satellites.

   - Worker implementations — catalogued in DD_SUB-WF-FRAMEWORK-01-WORKERS.

   - The subscription_restriction catalog itself — owned by SUB-LM-01.

   - The active_restrictions[] JSONB column — owned by SUB-LM-01.

   - The put-active-restrictions API — owned by SUB-LM-01.

   - Network-side restriction enforcement — owned by FUL-04 (translates fulfillment_action codes to vendor
     commands).

   - Restriction-related billing fees — owned by BIL-CFG-01 + BIL-01 (BillableEvents filter on restriction code).

   - Dunning ladder orchestration — owned by BIL-04.

 4. Rules
SOPHIX BSS Design Documents                                                                                                                   Page 5
 4.1 State precondition + array mutation
  Rule                                     Description

  R-SUB-WF-RESTRICT-01-S-1                 Both ADD and REMOVE require the subscription's status_code = ACTIVE.
                                           Restrictions cannot be added/removed on SUSPENDED, PENDING_*,
                                           TERMINATED, RETIRED, or CREATED. Returns 409
                                           INVALID_STATE_FOR_RESTRICTION with the current status.

  R-SUB-WF-RESTRICT-01-S-2                 The subscription's status_code does NOT change during restriction
                                           operations. Only the active_restrictions[] JSONB array is mutated. No
                                           PENDING_* transient state is used.

  R-SUB-WF-RESTRICT-01-S-3                 Per framework R-FW-1, RESTRICT is non-exclusive: it MAY run concurrently
                                           with any other in-flight operation on the same subscription (since neither side
                                           mutates status_code). Two RESTRICT operations on the same subscription
                                           are serialized via row-level lock on the subscription record during the
                                           put-active-restrictions call.



 4.2 Intent rules
  Rule                                     Description

  R-SUB-WF-RESTRICT-01-I-1                 ADD: if the restriction code is already in active_restrictions[], returns
                                           409 ALREADY_RESTRICTED with the existing entry's metadata.

  R-SUB-WF-RESTRICT-01-I-2                 REMOVE: if the restriction code is NOT in active_restrictions[], returns
                                           409 RESTRICTION_NOT_APPLIED.

  R-SUB-WF-RESTRICT-01-I-3                 Multiple distinct restrictions may be active simultaneously on the same
                                           subscription. Each is added or removed independently via separate workflow
                                           runs.

  R-SUB-WF-RESTRICT-01-I-4                 The optional notes field on both ADD and REMOVE requests captures the
                                           operator's justification. Audit-logged in
                                           subscription_operation.failure_reason_detail (success path) and
                                           active_restrictions[].add_notes / release_notes.



 4.3 Catalog validation
  Rule                                     Description

  R-SUB-WF-RESTRICT-01-C-1                 The restriction code must reference an active row in SUB-LM-01's
                                           subscription_restriction catalog (where is_active = true).
                                           Unknown codes return 400 UNKNOWN_RESTRICTION_CODE. Inactive codes
                                           return 400 RESTRICTION_CODE_INACTIVE.

  R-SUB-WF-RESTRICT-01-C-2                 The catalog row supplies fulfillment_action (FUL-04 input),
                                           customer_self_service_eligible, admin_only, is_active. The
                                           workflow snapshots these into the workflow's process variables at validation
                                           time.

  R-SUB-WF-RESTRICT-01-C-3                 A CUSTOMER_SELF_SERVICE-role request requires (a)
                                           subscription_restrict_config.customer_self_service_enabled
                                           = true for the operator AND (b) the catalog row's
                                           customer_self_service_eligible = true. Mismatch → 403
                                           CUSTOMER_SELF_SERVICE_NOT_ALLOWED.

  R-SUB-WF-RESTRICT-01-C-4                 A request against a catalog row with admin_only = true requires
                                           SUBSCRIPTION_ADMIN role. Insufficient role → 403
                                           ADMIN_ONLY_RESTRICTION.



 4.4 Role gating per trigger
  Rule                                     Description

  R-SUB-WF-RESTRICT-01-RG-1                Role-trigger gating: BACKOFFICE_OPERATOR requires
                                           SUBSCRIPTION_OPERATOR or SUBSCRIPTION_ADMIN. CALL_CENTER
                                           requires CALL_CENTER. CUSTOMER_SELF_SERVICE requires
                                           CUSTOMER_SELF_SERVICE plus the catalog + config checks per R-C-3.
                                           DUNNING_DRIVEN requires BILLING_INTERNAL.

  R-SUB-WF-RESTRICT-01-RG-2                The framework's drools-decide worker is invoked with
                                           rules.subscription.restrict.<operator> and the request facts; the
                                           operator-scoped package enforces role-gating + may add operator-specific
                                           rules.



 4.5 Dunning marker

SOPHIX BSS Design Documents                                                                                        Page 6
  Rule                                                           Description

  R-SUB-WF-RESTRICT-01-DM-1                                      When activationTrigger = DUNNING_DRIVEN, the added restriction's
                                                                 metadata includes dunning_marker = true and dunning_reference
                                                                 (BIL-04 dunning wave or step ID). Set automatically by the workflow; cannot be
                                                                 overridden by caller.

  R-SUB-WF-RESTRICT-01-DM-2                                      When dunning_marker_strict = true (operator config), a human-actor
                                                                 REMOVE (any non-BILLING_INTERNAL role) on a dunning-marked restriction
                                                                 returns 403 SYSTEM_MANAGED_RESTRICTION with guidance: "this restriction
                                                                 was applied by automated dunning; settle the outstanding balance to remove it".

  R-SUB-WF-RESTRICT-01-DM-3                                      When dunning_marker_strict = false, a SUBSCRIPTION_ADMIN role
                                                                 MAY override dunning-marker protection. The override requires explicit
                                                                 dunning_override = true in the REMOVE request. Audit-logged in the
                                                                 SubscriptionRestrictionRemoved event with override_actor and
                                                                 override_reason.

  R-SUB-WF-RESTRICT-01-DM-4                                      A BILLING_INTERNAL actor (BIL-04 resume-after-payment) may always
                                                                 remove a dunning-marked restriction.
