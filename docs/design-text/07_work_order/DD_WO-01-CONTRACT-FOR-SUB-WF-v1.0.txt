 2. Implementation Scope
 This DD should be implemented as part of the owning SOPHIX capability, not as an isolated service unless the deployment
 architecture explicitly separates that capability.

 Implement this DD with these rules:

   - Use the owning module APIs/repositories for authoritative writes.

   - Use approved internal APIs/client wrappers when reading another module's data.

   - Do not query another module's database tables directly from business flow code.

   - Treat worker names as logical Camunda external-task topics, not separate deployments.

   - One worker application may handle multiple topics, but metrics, retries, and logs must remain visible per topic.

   - Emit success events only after the authoritative state commit succeeds.

   - Use outbox publishing for Kafka events.

 1. The integration model
 1.1 One WO per physical operation
 A physical operation that touches the customer premises generates one Work Order, not multiple. For multi-step operations
 (e.g., a relocation involving both source-side disconnect and target-side install work), the WO module uses its multi-phase
 mechanism: one wo_id cycles through phases (e.g., DISCONNECT → RECONNECT) within a single Camunda process
 instance.
             WO created (status=PENDING, current_phase=NULL)
               ↓
             WO assigned, started (status=IN_PROGRESS, current_phase=<first phase>, job_type_code=<first phase code>)
               ↓
             First-phase work completed → first-confirm finalize → second-confirm finalize
               ↓
             [multi-phase only] PHASE TRANSITION (current_phase advances; job_type_code may swap)
               ↓

 Single-phase WOs (e.g., a fresh installation) finalize once. Multi-phase WOs finalize per phase + final WO completion.

 homepassRefs.primary and homepassRefs.secondary cover one- or two-location physical operations. For an
 INSTALLATION, only primary is set (install address). For a SHIFTING, both are set (primary = new, secondary = old).
 For TECHNOLOGY_MIGRATION, use the same shape when both old and new HomePass references are relevant.

 1.4 Job type code selection
 Job type codes are operator-scoped. Each operator's wo_job_type_catalog defines its own codes for each kind.
 Subscription workflows resolve the code via Drools at WO-creation time, using the source HomePass's network root type and
 the target Package's service classes as input.

 The selection rule (operator-neutral form):
           sourceNetworkRootType = sourceHomePass.networkPath.rootNodeType   // e.g., a fiber root type, a coax root type
           flowContext.equipmentPath in {KEEP_EXISTING, NEW_INSTALL}
           flowContext.crossTech = (sourceNetworkRootType != targetNetworkRootType)

 For each operator, Drools maps (kind, sourceNetworkRootType, equipmentPath, crossTech) →
 jobTypeCode. The mapping is operator-specific — operators register their codes in wo_job_type_catalog and their
 Drools KJAR. Each operator's catalog populates its own codes; no canonical cross-operator codeset is assumed by this
 contract.

 For multi-phase WOs that swap codes mid-flow (e.g., disconnect → reconnect), the WO module handles the transition
 internally; the subscription workflow only specifies the FIRST phase's code at creation.

 1.5 Equipment handling
 The WO module handles equipment binding internally. Subscription workflows do not call separate osr-equipment-bind /
 osr-equipment-unbind workers for operations that have a WO.

 At WO creation, the workflow passes currentEquipmentBindings and flowContext.equipmentPath. The WO's
 internal logic (FLOW-specific) decides whether to:

   - Record new equipment serials captured by the tech at finalize-time (NEW_INSTALL)

   - Carry forward existing equipment between locations (KEEP_EXISTING with transport)

   - Recover and return existing equipment to inventory (NEW_INSTALL with old-equipment recovery)

 The WorkOrderFinalized event payload includes finalEquipmentBindings[] — the post-WO equipment state.
 Subscription workflows read this for downstream FUL-03 ACTIVATE_SERVICE calls + FUL-07 CLAIM context.

 For operations where the customer self-handles equipment (no tech dispatch — e.g., disconnectMode =
 CUSTOMER_SELF_MOVE in subscription terms), the subscription workflow may skip WO creation entirely. The integration
 choice is the workflow's: WO = tech dispatched; no WO = customer self-service.

 1.7 Timeouts and cancellation


SOPHIX BSS Design Documents                                                                                                                       Page 5
 WO timeouts come from the WO module's wo_kind_config.default_timeout_days table (per
 DD_WO-01-FRAMEWORK §7). Subscription workflows reference this single source — they don't carry their own duplicate
 timeout columns.

 WorkOrderTimedOut event fires when the timeout is exceeded. The subscription workflow's compensation path runs on
 receipt: revert state to pre-workflow snapshot, emit Rejected event with rejectionReasonCode = WO_TIMEOUT, finalize
 FAILED.

 Cancellation flows in two directions:

   - Subscription workflow → WO: if customer cancels the workflow request (before commit window), the workflow calls
     POST /api/work-orders/{id}/cancel to abort the WO. WO-01 terminates the process instance and emits
     WorkOrderCancelled.

   - WO → subscription workflow: if dispatcher cancels the WO (operations intervention), WorkOrderCancelled arrives at
     the workflow's catch. Workflow runs compensation.

 If the workflow is in the commit window (atomic-switch in progress, past the point of no return), the cancel REST endpoint
 on the subscription side returns 409 OPERATION_IN_COMMIT_WINDOW. Whether the WO can still be cancelled at that point
 is the WO module's decision — operations may force-cancel a WO regardless of subscription-side state, in which case the
 subscription workflow handles the unexpected cancel via its existing failure-mode compensation.

 1.8 Cross-tech and complex variations
 Subscription operations that involve cross-technology HomePass moves (for example source on legacy network root type,
 target on current network root type) are coordinated by FUL-10 Technology Migration Fulfillment. When a field
 visit is needed, FUL-10 creates one or more WOs through this same endpoint using either:

   - existing SHIFTING with operator-specific job-type codes when the operator's field process is close to shifting; or

   - TECHNOLOGY_MIGRATION when the operator needs a dedicated cross-tech field workflow.

 Both are supported by the framework — kind is a config-driven enum, not a hardcoded one. Operators register their own
 kinds as their needs evolve, and subscription workflows pick the kind via the same Drools-resolved mapping in §1.4.

 1.9 Operator-specific FLOW behavior is the FLOW satellite's concern
 Anything that varies per operator — account sub-status codes, equipment recovery policy at disconnect, topology-capture vs
 topology-confirm at reconnect, multi-phase vs single-phase structure for a given operation type, contractor-payment
 side-effects, finalize-checklist note kinds, capture mechanism (back-office vs field-app) — lives in the per-operator FLOW
 satellite (DD_WO-01-FLOW-<KIND>-<OPERATOR>) or in operator-scoped catalogs and KJAR packages. Subscription
 workflows are insulated from those choices by the integration surface defined here: REST, Kafka, caller context, framework
 events.

 2.5 Flow context fields
 flowContext is opaque to the integration surface and interpreted by the FLOW satellite. Subscription workflows or FUL-10
 populate it per the FLOW's requirements. Common shape for HomePass-change flows (SHIFTING and
 TECHNOLOGY_MIGRATION):
           {
               "equipmentPath":   "KEEP_EXISTING | NEW_INSTALL",
               "disconnectMode": "TECH_DISPATCH | CUSTOMER_SELF_MOVE",
               "sourceHomepassId": "hp_...",     // also in homepassRefs.secondary
               "targetHomepassId": "hp_..."      // also in homepassRefs.primary
           }

 Single-location flows (INSTALLATION) populate fewer fields. Each FLOW satellite specifies its own.
