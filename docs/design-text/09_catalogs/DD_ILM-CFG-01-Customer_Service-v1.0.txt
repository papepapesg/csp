 2. Implementation Scope
 This DD should be implemented as part of the owning SOPHIX capability, not as an isolated service unless the deployment
 architecture explicitly separates that capability.

 Implement this DD with these rules:

   - Use the owning module APIs/repositories for authoritative writes.

   - Use approved internal APIs/client wrappers when reading another module's data.

   - Do not query another module's database tables directly from business flow code.

   - Treat worker names as logical Camunda external-task topics, not separate deployments.

   - One worker application may handle multiple topics, but metrics, retries, and logs must remain visible per topic.

   - Emit success events only after the authoritative state commit succeeds.

   - Use outbox publishing for Kafka events.

 Verdict: ■ New | Wave: 2 | Group I: Foundations | Version: v1.0 | Module: Customer Service

 The system of record for the Wananchi customer master. Owns the Customer and Account entities of the workshop's 3-tier
 CAS hierarchy. The third tier — the Subscription / service-instance — is owned by SUB-LM-01 and looked up cross-module
 via (customer_id, homepass_id). KYC lifecycle, account status + sub-status registry, contact methods, customer notes,
 preferences, search, and interaction history. The module is the read-after-anything-customer-related authority for every other
 module in SOPHIX. Retires customer_stub in FUL-02 framework and WO module framework.

 The module is operator-agnostic at the code level: WIK, WUG, WTZ, YASSN all use the same schema, the same REST API,
 the same Kafka event surface. Per-operator differences (KYC document types, status enums, language) live in
 operator-config rows.



 1. What this module is


SOPHIX BSS Design Documents                                                                                                                   Page 4
 Every internal team in Wananchi — CSR, dispatcher, technician, finance, sales agent — opens a customer record before any
 action. Workshop quote: *"The single pane of glass any internal agent opens before any action on the customer's account."*
 This module owns that record.

 Customer is identity; Account is operations
 The module enforces a strict separation between two layers:

   - Customer — the legal-identity entity Wananchi recognizes: a person (Residential) or a registered business (Commercial).
     Holds name, type, identification documents, date of birth, primary contact channels (msisdn / email — the *legal-known*
     channels), preferred language, KYC state. Contact methods, notes, and interactions also hang from the Customer
     because they describe communication with the legal entity. Nothing operational lives here.

   - Account — the operational anchor for everything Wananchi does for the customer. Each Account corresponds to one
     physical service deployment (one HomePass) and is linked 1:1 to one Subscription. Status + sub-status, service-class
     tier, attention banner, flags (NPD, churn risk, fraud, ...), notification preferences, payment account number, billing cycle
     dates, account manager, franchise code — all live on customer_account. Every other module anchors at the
     Account, not the Customer:
  Concern                                                            Where anchored

  Work Orders (WO module)                                            Account (accountId filter on WO queries)

  Billing & Charging (BIL-01)                                        Account (via the Account's subscription_id, 1:1)

  Invoicing (BIL-02-GEN-01)                                          Account (one Invoice per Account per cycle)

  Payments + reconciliation (BIL-05)                                 Account (resolved via payment_account_number)

  Dunning (BIL-04)                                                   Account (each Account dunned independently)

  Provisioning (FUL-03)                                              Account (via the Account's Subscription)

  Notification dispatch (DD_NOT-01)                                  Account (account-scoped notification preferences)

  Status & lifecycle                                                 Account

  Flag system (NPD, etc.)                                            Account

  Service class                                                      Account

  Attention banner                                                   Account


 A customer with multiple accounts (e.g., one at home, one at a holiday cottage) has each Account managed completely
 independently — separate status, separate flags, separate invoices, separate dunning, separate notifications. The Customer
 entity ties them together for legal identity only.

 Capability areas
 The module is structured around six capability areas, each backed by data and APIs:

   1. Master record — the Customer entity (legal identity only — name, type, IDs, KYC, contact channels, language). The
     Account entity (per-deployment, one Account per physical service location per workshop rule). Subscription instances per
     package live in SUB-LM-01 — this DD references them via cross-module queries, does not own them.

   2. Status lifecycle — Account-level. Main statuses ACTIVE / INACTIVE + a rich catalog of sub-statuses (active,
     complementary discount, DND active, seasonal disconnect, VIP, staff account, inactive-pending-customer, churned, etc.).
     Sub-statuses are operator-configurable per workshop's cloned-from-main pattern. Service-class tier (VIP / Platinum / Gold
     / STAFF) is informational, no billing impact.

   3. Account flag system (§3.5) — operator-extensible per-Account flags (NPD, churn risk, fraud suspected, high-value,
     loyalty tier, ...). Evaluated daily by a Drools worker per operator. Workshop's NPD boolean flag becomes one entry in this
     system.

   4. KYC — capture, two-level approval flow (L1 supervisor → Team Leader), IDs accepted (National ID, Passport, Business
     Registration), document references. Captured on the Customer (legal identity), but the activation gate is per-Account: an
     Account cannot be activated until its Customer's KYC reaches APPROVED. Future IPRS integration is out of scope for
     v1.0.

   5. Contacts + notes + interactions + preferences — primary phone (MSISDN, required, enforced at every contact-update
     operation per workshop rule), email, alternate contacts, all on the Customer. Notes + interactions on the Customer with
     optional account_id scope (a CSR call about "Jane's Diani account billing" is account-scoped; a customer-relationship
     note like "deceased" is customer-scoped). Notification preferences (§4.4) are account-scoped, not customer-scoped —
     per-Account channel + topic preferences.

   6. Search — by Account #, MSISDN, name, ID, address (with the workshop's required result columns: Address, Last Name,
     First Name, M St, E Stat, City, Pending WO, Type, Account Name). Also by flag (§7.8) for BIL-04 dunning and Finance
     reporting.

 The module is exclusively a customer service authority — it does not own billing data (transaction history is read from billing
 modules), it does not own work orders (read from WO module), it does not own subscription state (read from SUB-LM-01). It
 owns identity (on Customer) + operational anchors (on Account). Other modules consume via REST + subscribe to Kafka
 events for status changes.

 What this module does NOT do
   - Doesn't own billing or invoicing. Transaction History tab on the workshop's "single pane of glass" reads from BIL-01
     (Charging Engine) + BIL-02-GEN-01 (Invoice Generation) + BIL-05 (Wallet); ILM-CFG-01 just hands over customer_id
     (or account_id) and surfaces the join. Adjustments, refunds, billing-cycle changes — all live in BIL. The
     Account-to-Invoice relationship is documented in §11.4 BIL-* sibling entry.

   - Doesn't own work orders. Pending WOs, Completed WOs grid, WO Notes — all read from WO module (DD_WO-01) via
     customer_id filter. ILM-CFG-01 provides the customer context; WO module owns the WO data.

   - Doesn't own subscription state. Active/Suspended/Terminated subscriptions live in SUB-LM-01. ILM-CFG-01's status
     field is the *customer-level* lifecycle (ACTIVE vs INACTIVE + sub-statuses); per-subscription state is separate.

   - Doesn't compute dunning. BIL-04 owns the dunning state machine. When a customer is dunned to SUSPENDED,
     BIL-04 emits an event and ILM-CFG-01 updates the customer's sub_status to reflect "inactive pending customer" or
     similar; this is event-driven consumption of dunning side-effects, not authority over dunning logic.

   - Doesn't initiate KYC document scanning or OCR. v1.0 captures references to documents stored elsewhere
     (id_document_ref); future IPRS integration is out of scope. ILM-CFG-01 holds the audit trail of who approved what
     when.

   - Doesn't own customer bulk import (workshop: not used in Kenya).

   - Doesn't own credit limit (workshop: postpaid feature; Wananchi runs prepaid).

   - Doesn't own multi-location account support (workshop: in Kenya, each location = separate Account; the
     multi-Account-per-Customer model handles this naturally).

   - Doesn't own document management (KYC + contract live in Agent App; install photos with contractor's local FTP; future
     unified DM module is "good-to-have" per workshop).

   - Doesn't compute SLA (workshop: SLA evaluation lives outside the platform today; future FUL-OPS-SLA may bring
     inside).

   - Doesn't own the customer risk profile or scoring (workshop: not used in Kenya). v1.0 supports operator-extensible
     per-Account flags via §3.5 (NPD, churn-risk, fraud-suspected, etc.), evaluated by a daily Drools worker. The workshop's
     NPD boolean flag becomes one entry in this flag system, scoped to the Account.

 Regional flexibility
 The Customer Management workshop (deep-dive 01, 2026-04-27 / 2026-04-28) is a Kenya source. The schema and APIs
 here support Kenya's actual workflow — but the module is designed to deploy across all four Wananchi-Group countries
 (WIK, WUG, WTZ, YASSN) without code change. Regional variation is supported via:

   - Operator-scoped catalogs. customer_sub_status_catalog, KYC document-type lists, contact-channel types,
     notification preferences — all keyed on operator_code. KE's sub-status list is the v1.0 seed; UG/TZ/SN seeds will be
     added at their respective deployment time without affecting the schema.

   - Multi-slot identifications. identification_type_1 + identification_number_1 + identification_type_2
     + identification_number_2 support regions where customers carry two IDs concurrently (e.g., ECOWAS card holds
     both a card-ID and a national-ID, common in Senegal/YASSN); KE typically uses _1 only with _2 NULL.

   - Optional fields. Most workflow-specific fields (franchise_code, account_manager_id, kyc_documents_jsonb,
     identification slots) are NULL-able. Operators that don't use a concept simply leave it NULL; operators that do, populate it.

   - Multi-axis classification. service_class_1/2/3 and three classification slots support deployments that need
     multi-dimensional segmentation. KE v1.0 uses _1 only.

   - Operator-extensible flag system. customer_account_flag_catalog is operator-scoped — each operator defines
     its own flag types (NPD, churn risk, fraud suspected, payment delay, loyalty tier, etc.) with its own Drools rules. The KE
     seed (NPD + CHURN_RISK + FRAUD_SUSPECTED + PAYMENT_DELAY_FREQUENT + LOYALTY_TIER +


SOPHIX BSS Design Documents                                                                                                  Page 6
     HIGH_VALUE) is v1.0; future operators add their own catalog rows without schema change.

   - Independent payment reference. customer_account.payment_account_number is a separately-stored, mutable
      field — distinct from the immutable internal account_number. Operators with a custom gateway-reference scheme (KE
      M-Pesa Paybill, TZ Vodacom M-Pesa, SN/YASSN Orange Money or Wave) supply the reference per their gateway's
      format. Operator-config decides whether it's auto-populated from account_number at creation or supplied
      independently.

   - Per-operator BPMNs and Drools (for the workflows that consume ILM events — FUL-02, WO module). The
     customer-service module just emits events; downstream operators decide what to do with them.

 The Kenya workshop is the v1.0 seed, not the limit. Future workshop findings from WUG/WTZ/YASSN may reveal new
 identification types, status sub-statuses, KYC requirements, or contact channels — those land as catalog additions and
 per-operator config, never as schema migrations.

 2.3 Subscription linkage — owned by SUB-LM-01, referenced from Account
 ILM-CFG-01 does not own a subscriber/subscription entity. The workshop's "Subscriber" tier of the CAS model maps to
 SUB-LM-01's subscription entity, which is the V3 first-class record of a service instance (one row per package delivered
 to a customer at a HomePass).

 The link is materialized via customer_account.subscription_id (added in §2.2). The relationship is 1:1: each
 Account is linked to at most one Subscription; each Subscription belongs to exactly one Account. Multi-service customers
 (Internet + TV + Voice) hold a single Subscription whose Package contains multiple Services — the multi-service
 decomposition lives in PLM-CFG-01 + SIP-01, not in additional ILM/SUB-LM rows.

 SUB-LM-01's subscription table carries:

   - subscription_id — PK; the value referenced from customer_account.subscription_id

   - customer_id — links to ILM-CFG-01's customer (must match customer_account.customer_id)

   - homepass_id — links to RLM-CFG-01's HomePass (must match customer_account.homepass_id)

   - package_ref + package_version — links to SIP-01's package catalog

   - status_code — the subscription lifecycle state (ACTIVE / PAUSED / SUSPENDED_NP / TERMINATED / etc.)

   - All the workflow-driven state-transition data

 Multi-location customers: each Account holds its own subscription_id pointing to a separate Subscription record.

 The 1:1 Account ↔ Subscription rule. Every Account is linked to exactly one Subscription; every Subscription belongs to
 exactly one Account. The Account's lifecycle (ACTIVE / INACTIVE + sub-statuses) mirrors its single Subscription's lifecycle
 — there is no ambiguity from one Subscription being ACTIVE while another on the same Account is SUSPENDED, because
 no Account ever holds more than one Subscription.

 Multi-service customers are modelled at the Package layer, not by adding Subscriptions. A customer with Internet +
 TV + VOIP at one HomePass holds ONE Subscription whose Package contains three Services. The multi-Service
 decomposition lives in PLM-CFG-01 + SIP-01 — the Package catalog defines which Services compose a given Package.
 Service-level state (e.g., TV temporarily disabled while Internet stays on) is owned by PLM-CFG-01 / SUB-LM-01 and does
 not change the Account's sub-status. The Account stays ACTIVE as long as the Subscription has at least one non-terminated
 Service.

 Multi-Subscription customers — a customer with two service locations holds two Accounts, each at a different HomePass
 (per uq_account_customer_homepass), each with its own subscription_id pointing to a separate Subscription. The
 customer-level view (single pane of glass) shows both Accounts and walks to both Subscriptions via the FK.

 Workshop "1 account = 1 deployment" rule preserved. Each Account corresponds to exactly one physical deployment
 (one HomePass) and delivers exactly one Subscription (one Package) there. A customer adding TV to their existing Internet
 does NOT get a second Account — they get a Package upgrade on their existing Subscription (MACD Change-of-Service
 workflow in SUB-LM-01).

 MACD operations. When a customer Changes their package (upgrade / downgrade): SUB-LM-01's MACD workflow either
 updates the existing Subscription row in-place (same subscription_id, new Package) or creates a new Subscription and
 terminates the old one. In the terminate-and-recreate case, the Account's subscription_id is updated to point to the new
 Subscription via the PUT subscription endpoint; the previous Subscription row stays in SUB-LM-01 with
 status=TERMINATED for audit but is no longer referenced from any Account. In the in-place case, subscription_id is
 unchanged.

 Account ↔ Invoice relationship. Because each Account is linked 1:1 to one Subscription, each Account also corresponds
 to exactly one billing stream. BIL-01 (Charging Engine) generates charges keyed by subscriptionId; BIL-02-GEN-01
 (Invoice Generation) attaches those charges as line items to the Invoice for the corresponding Account's billing cycle. So per
 billing cycle, per Account, there is exactly one Invoice — containing the line items for the Services delivered by that
 Account's single Subscription's Package.

 Concretely:

SOPHIX BSS Design Documents                                                                                               Page 11
   - A customer with multi-service at one location (Internet + TV + VOIP in one Package on one Account) gets one Invoice per
     cycle with multiple line items (one per Service in the Package).

   - A customer with two service locations (two Accounts, two Subscriptions) gets two Invoices per cycle — one per Account,
     each containing the line items for that Account's Subscription.

   - Dunning operates per-Account (BIL-04): an Account whose Invoice goes unpaid is dunned independently of the
     customer's other Accounts.

   - Payment reconciliation uses customer_account.payment_account_number to resolve the inbound gateway callback
     to the Account, then applies the payment against that Account's open Invoice(s).

 3.3 Status-change rules
 The framework enforces a small set of universal rules across all operator status changes:

   - R-ILM-S-1. Every customer_account.status or sub_status change writes a row to
     customer_account_status_history. Enforced via DB trigger on update. The history table is append-only.

   - R-ILM-S-2. When customer_sub_status_catalog.requires_approval = TRUE, the change must include a
     non-null approval_reference. Enforced at the API layer.

   - R-ILM-S-3. When customer_sub_status_catalog.affects_provisioning = TRUE, the change emits
     CustomerAccountStatusChanged event (§7) carrying the transition; FUL-03 / provisioning consumes this to apply
     network-level changes.

   - R-ILM-S-4. Service-class tier changes are recorded on customer_account.service_class and also generate a
     customer_account_status_history entry where prev_sub_status = new_sub_status (the sub-status didn't
     change; only the tier flag did). Per workshop rule: service class is informational only; no billing impact, no provisioning
     impact.

   - R-ILM-S-5. A status change initiated by another module (BIL-04 dunning, WO module Shifting flow, FUL-02
     STEP-ACTIVATION) carries source_event_ref pointing to the originating event ID for traceability.

   - R-ILM-S-6. When sub_status changes on an Account, that Account's attention_banner may also be auto-set per
     operator-config (e.g., entering inactive pending customer could auto-set "Account in dunning" on THAT account
     only — not on the customer's other accounts); v1.0 ships with this rule disabled — manual banner updates only.
     Operator-config can enable per sub-status.

 3.5 Account flag system
 Separate from status / sub-status, every Account carries a set of operational flags — boolean or scored signals used for risk
 management, segmentation, dunning policy, fraud detection. Workshop's NPD is one such flag; the system is extensible to
 many more (churn risk, fraud suspected, high-value, loyalty tier, payment-delay frequency, etc.).

 Three components:

   1. Operator-scoped catalog of flag types — defines what flags exist for an operator, how each is evaluated, what values it
     can hold.

   2. Per-account flag state — one row per (account_id, flag_code), holding current value + evaluator + timestamp.

   3. Daily Drools worker — re-evaluates every Account against the catalog's Drools rules; writes/updates
     customer_account_flag rows; emits Kafka events for any flag transitions.

 #### 3.5.3 Daily Drools evaluator worker

 A Camunda external task worker — flag-evaluator-<operator>-v<n> — runs on the operator's configured schedule
 (typically nightly per customer_account_flag_catalog.refresh_schedule_cron). For each Account in the
 operator's tenant:

   1. Load the account's recent context: last N payments (from BIL-05), open invoices (from BIL-02-GEN-01), current
     sub_status, subscription state, age of account.

   2. For each flag_code in the catalog with evaluator='DROOLS': invoke the corresponding KJAR rule with the context.

   3. Compare the rule output to the existing customer_account_flag.value_*; if different, write a new value + emit
     CustomerAccountFlagChanged Kafka event.

   4. Update evaluated_at even when value is unchanged (so consumers can see "last checked at" without inferring from
     history).

 The worker is operator-scoped — flag-evaluator-wik-v1 is one Camunda job, flag-evaluator-yassn-v1 is
 another. Each operator's Drools KJAR can be deployed and versioned independently.
           POST /engine-rest/external-task/fetchAndLock HTTP/1.1
           {
             "workerId":"flag-evaluator-wik-v1-instance-3",
             "maxTasks": 100,
             "topics":[{"topicName":"sophix.ilm-cfg-01.flag-evaluation","lockDuration": 300000}]
           }

 Each fetched task carries an account batch (typically 1,000 accounts) — the worker processes the batch, completes the task,
 fetches the next. Long jobs split across multiple Camunda task instances.

 5.2 KYC approval chain — append-only history
 Approvals are recorded as a list (one row per approval action), not as fixed-position columns. This supports any number of
 levels without schema changes when a future operator deploys more or fewer levels.
          CREATE TABLE customer_kyc_approval (
             approval_id          TEXT PRIMARY KEY,                -- 'kycappr_01HX...' ULID
             customer_id          TEXT NOT NULL REFERENCES customer(customer_id),
             approval_level       INTEGER NOT NULL,                -- 1, 2, 3, ... (1 = L1)
             approval_level_name  TEXT NOT NULL,                   -- 'L1_SUPERVISOR' | 'TEAM_LEADER' | operator-defined
             decision             TEXT NOT NULL,                   -- 'APPROVED' | 'REJECTED'
             is_final             BOOLEAN NOT NULL,                -- TRUE on the level that closes the chain
             approver_id          TEXT NOT NULL,                   -- BO user id
             approver_role        TEXT NOT NULL,                   -- FOUNDATION_AUTH role at approval time
             comments             TEXT NULL,
             approved_at          TIMESTAMP NOT NULL DEFAULT NOW()

          CREATE INDEX idx_kyc_approval_customer ON customer_kyc_approval (customer_id, approved_at);
          CREATE UNIQUE INDEX uq_kyc_one_per_level
            ON customer_kyc_approval (customer_id, approval_level)
            WHERE decision = 'APPROVED'; -- each level can have only one APPROVED row; rejections aren't constrained

 The customer.kyc_status field is derived from the approval chain:

   - No customer_kyc_approval rows → PENDING

   - At least one APPROVED row but no is_final=true APPROVED row → LN_APPROVED where N is the highest
     approval_level present

   - An APPROVED row with is_final=true → APPROVED

   - Any decision=REJECTED row → REJECTED (rejections at any level terminate the chain)

 The kyc_l1_approver_id, kyc_l1_approved_at, kyc_final_approver_id, kyc_final_approved_at columns
 are removed from customer (was in §2.1; updated below) — they're now derived from customer_kyc_approval. The
 kyc_status field on customer is maintained as a denormalized fast-read field, updated by trigger on insert into
 customer_kyc_approval.

 5.5 KYC rules
  Rule                                                           Description

  R-ILM-K-1                                                      customer.kyc_status is derived from customer_kyc_approval rows.
                                                                 Maintained by trigger on insert. Possible values: PENDING (no rows),
                                                                 LN_APPROVED (highest non-final approved level), APPROVED (final approval
                                                                 row present), REJECTED (any rejection row), WITHDRAWN (admin-set).

  R-ILM-K-2                                                      An approval at level N requires at least one APPROVED row at level N-1 (when
                                                                 N > 1). Enforced server-side; 409 KYC_PREREQUISITE_LEVELS_MISSING
                                                                 on violation. v1.0 KE WIK uses only levels 1 (L1_SUPERVISOR) and 2
                                                                 (TEAM_LEADER, isFinal=true).

  R-ILM-K-3                                                      The approving user must have a FOUNDATION_AUTH role that matches the
                                                                 approval level. Mapping per operator config: KE L1 → role kenya-l1-kyc; KE
                                                                 Final → role kenya-kyc-leaders. Future operators register their own role
                                                                 mapping.

  R-ILM-K-4                                                      Each approval emits a Kafka event. LN_APPROVED for non-final approvals
                                                                 (where N=approval_level); KYC_APPROVED when isFinal=true; KYC_REJECTED
                                                                 for rejections. FUL-02 STEP-VALIDATE consumes only the final
                                                                 KYC_APPROVED for its CUSTOMER_ELIGIBLE check.

  R-ILM-K-5                                                      KYC documents are stored as first-class rows in customer_kyc_document
                                                                 with full path/mime/hash; ILM-CFG-01 holds references, not bytes. The bytes
                                                                 live in the SOPHIX foundation file-storage system.

  R-ILM-K-6                                                      customer_kyc_document.content_hash (SHA-256) supports integrity
                                                                 verification on retrieval AND duplicate-document detection within the same
                                                                 customer (e.g., re-captured ID) AND across customers (fraud detection — same
                                                                 passport image used for multiple customers).

  R-ILM-K-7                                                      KYC approval emits CustomerAccountAvailableForActivation event
                                                                 for each non-superseded account belonging to the customer when
                                                                 kyc_status reaches APPROVED. This is the trigger for FUL-02
                                                                 STEP-VALIDATE's CUSTOMER_ELIGIBLE clearance.

  R-ILM-K-8                                                      Document supersession (superseded_by_id) preserves the original
                                                                 document row + audit trail; never hard-deletes. GDPR purge is via the
                                                                 retention-class job, not via document update.

 7.3 Subscription data — owned by SUB-LM-01
 ILM-CFG-01 does NOT expose subscription detail endpoints. Callers needing subscription data follow the FK directly. A
 typical "view all services for this customer" UI call sequence:

   1. GET /api/customers/{id} → ILM-CFG-01 returns the customer + accounts list (with subscription_id on each
     account).

   2. For each account with a non-NULL subscription_id: GET /api/subscriptions/{subscription_id} →
     SUB-LM-01 returns the subscription detail (package, status, workflow data).

 The 1:1 FK pattern means each lookup is O(1) — no WHERE customer_id = ... AND homepass_id = ... searches
 needed.

 Specific feature areas covered:

   - Customer Account Creation — door-to-door capture on Field Agent PWA; 3-tier CAS model; "1 account = 1 deployment"
     rule; account number as the only operational key; V3 first-class customer entity replacing dummy-account-from-pool.

     through dedicated UCs; service-class badge informational only.

     accepted IDs (National ID, Passport, Business Registration); planned IPRS integration as future enhancement.

   - Account Status Management — main statuses (INACTIVE / ACTIVE / SUSPENDED / CHURN / TERMINATED +
     sub-statuses + service class). Workshop ambiguity: SUSPENDED / CHURN / TERMINATED are presented as additional
     main statuses in one section and as sub-statuses cloned from INACTIVE in another section. V3 design follows the
     "Customer Preferences" workshop view: only INACTIVE and ACTIVE as main statuses, everything else as
     sub-statuses (workshop quote: "Base statuses are only INACTIVE and ACTIVE; everything operational below is a
     sub-status"). This collapses SUSPENDED/CHURN/TERMINATED into the sub-status registry. Specifically: churned (in
     catalog), and the dunning-driven inactives (inactive pending customer, hold). TERMINATED is a
     subscription-level state in SUB-LM-01 (subscription.status_code = TERMINATED), not an ILM account state.

   - Customer Interaction History — structured Last Note per workshop (Agent name · Call reason · Findings · Resolution ·
     VOC).

   - Customer Notes — Attention banner + Last Note.

   - Customer Contact Management — primary phone (MSISDN) required; multiple channels.

   - Customer Segmentation — service class flags (VIP / Platinum / Gold / STAFF) informational only.

   - Customer Search — by Account #, Address, Contact Methods, Name, Identification, Equipment ID, Drop Tag, PPV
     Lookup, Last Accessed Homes; result columns per workshop.

   - Customer Document Management — KYC/contract held in Agent App; install photos with contractor's FTP; future unified
     DM is "good-to-have" — out of v1.0 scope.

   - Customer Notifications — preference held per-customer; channel rule "Email if available, otherwise SMS".
