 1. What this step does
 When STEP-CAPTURE finished, Camunda advanced the BPMN to a step called validate-order. This step is what
 Camunda calls an external task — a step in the recipe where Camunda doesn't do the work itself but instead puts a job on a
 queue called a "topic" (here, the topic is order-validate) and waits for our code to pick it up. The piece of our code that
 picks up and processes such jobs is called a worker — it's a Java bean inside our module that long-polls Camunda asking
 "anything on the order-validate topic for me?" When Camunda hands it a task, the worker runs, reports the result back,
 Camunda then advances the BPMN to whatever comes next.

 The work order-validate does is a sequence of five checks against catalog DDs that already exist:

   1. HOMEPASS_SELLABLE — ask RLM-CFG-01 if the HomePass is in a sellable status. RLM-CFG-01's catalog of
     HomePass statuses carries a is_sellable semantic flag per code; the actual code (RFS, LIVE, etc.) varies by
     deployment. We trust whatever RLM-CFG-01 says.

   2. PACKAGE_ACTIVE — ask SIP-01 if the Package's status = ACTIVE. Packages in DRAFT, INACTIVE, or
     END_OF_LIFE can't be ordered.

   3. TECH_REGIONS_INTERSECT — the Package's target_tech_regions (list of region codes where this Package is
     sold) must overlap with the HomePass's tech_regions (list of region codes the HomePass falls under). If they're
     disjoint, the Package isn't sold in the HomePass's area.

   4. NO_DUPLICATE_SUBSCRIPTION — ask SUB-LM-01 whether this customer already has an active subscription at this
     HomePass for this Package. If yes, we can't create a duplicate.

   5. CUSTOMER_ELIGIBLE — ask the customer service (v1.0: customer_stub; future: ILM-CFG-01) whether the
     customer is in a state that allows new subscriptions (KYC not blocked, no fraud flag, no eligibility hold).

 If all five pass, the worker reports success and Camunda advances to STEP-SUBSCRIPTION. If any fail, the worker reports
 the failure detail; the BPMN's gateway after validate-order routes the flow to order-mark-rejected — a second

 worker that's the terminal-failure handler for this step.

 What happens on failure
 Failure means *the order genuinely cannot proceed* — not a transient network blip. A duplicate subscription means the
 customer already has this Package at this HomePass; resubmitting won't change that. A non-sellable HomePass means we
 don't sell at this address yet; resubmitting won't change that either. The terminal action is:

   1. The worker reports validationOutcome = FAIL with validationDetails (which check failed, why).

   2. The BPMN gateway routes to order-mark-rejected.

   3. order-mark-rejected sets current_phase = REJECTED, writes failure_reason + failure_detail onto the
     row, emits OrderRejected on Kafka.

   4. DD_NOT-01 sees OrderRejected and sends the customer a notification with the failure reason in customer-friendly
     language ("Sorry, we don't yet service your area").

   5. The Camunda process instance ends. No retry path. If the customer's circumstances change (e.g., HomePass becomes
     sellable later), they need to submit a new order.

 What happens on upstream system unreachable
 This is different from a check failing. If RLM-CFG-01, SIP-01, SUB-LM-01, or the customer service can't be reached (network
 error, 5xx response, timeout), the worker reports a different kind of failure to Camunda: /failure with errorMessage =
 UPSTREAM_UNREACHABLE. This raises a Camunda incident — a flag on the process instance saying "something's wrong,
 ops should look." The order is parked until ops resolves; the BPMN doesn't advance to order-mark-rejected because
 the order isn't actually invalid, we just couldn't check. No customer notification fires.

 The worker short-circuits on first failure (doesn't run the remaining checks); the validationDetails array carries only the
 checks that ran. The order of evaluation is HomePass → Package → TechRegions intersect → Duplicate →
 CustomerEligible.

 Failure modes:

   - A check fails → worker completes with validationOutcome = FAIL and the detail. Camunda gateway routes to
     order-mark-rejected. Customer is eventually notified (via DD_NOT-01 on OrderRejected). Order is terminal.

   - Upstream system unreachable (RLM-CFG-01 down, SIP-01 down, etc.) → worker reports /failure with
     errorMessage = UPSTREAM_UNREACHABLE. Camunda raises an incident; ops is alerted via NOC; the order is parked
     until ops resolves. No customer notification fires.

 7. Step-pinned rules
  ID                                                               Rule

  R-FUL-02-VAL-1                                                   order-validate runs the 5-check matrix on every captured order. Checks
                                                                   evaluate in order HomePass → Package → TechRegions intersect → Duplicate
                                                                   → CustomerEligible; the worker short-circuits on first failure.

  R-FUL-02-VAL-2                                                   The check sequence is deterministic and operator-agnostic — workers don't
                                                                   depend on operator shape. The KE WIK BPMN runs the standard 5-check
                                                                   sequence. Other operator BPMNs may parameterize the check set (e.g., skip
                                                                   duplicate check when subscription is deferred) via future configuration; v1.0
                                                                   ships only the WIK BPMN.

  R-FUL-02-VAL-3                                                   order-validate has 0 retries on /failure. Validation should be
                                                                   deterministic on retry; a non-deterministic upstream call is reported as
                                                                   UPSTREAM_UNREACHABLE and raises a Camunda incident, parking the order
                                                                   until ops resolves (no auto-rejection, no customer notification — the order is
                                                                   genuinely fine, we just couldn't check).

  R-FUL-02-VAL-4                                                   Worker short-circuits on first FAIL — doesn't run remaining checks. The
                                                                   validationDetails array carries only the checks that ran. Order of
                                                                   evaluation: HomePass → Package → TechRegions intersect → Duplicate →
                                                                   CustomerEligible.

  R-FUL-02-VAL-5                                                   Any check FAIL → validationOutcome = FAIL with failureReason
                                                                   (enum) + failureDetail (free-text). BPMN gateway routes to
                                                                   order-mark-rejected.

  R-FUL-02-VAL-6                                                   order-mark-rejected is terminal: phase REJECTED, no recovery path. If
                                                                   circumstances change (HomePass becomes sellable, customer ineligibility
                                                                   lifted), the customer must submit a new order — the existing rejected order is
                                                                   not re-validated.

  R-FUL-02-VAL-7                                                   The OrderRejected Kafka event is emitted by order-mark-rejected,
                                                                   NOT by order-validate. The split is deliberate: the validate worker returns a
                                                                   verdict; the mark-rejected worker turns that verdict into the visible terminal state
                                                                   + event. DD_NOT-01 only consumes OrderRejected.

  R-FUL-02-VAL-8                                                   RLM-CFG-01 / SIP-01 lookups are cacheable (Package + HomePass change
                                                                   rates are low). Cache TTL 5 minutes inside the worker JVM. SUB-LM-01 +
                                                                   customer-service lookups are NOT cached (customer state can change at any
                                                                   moment).

  R-FUL-02-VAL-9                                                   failureReason enum is closed: HOMEPASS_NOT_SELLABLE,
                                                                   PACKAGE_NOT_ACTIVE,
                                                                   PACKAGE_NOT_AVAILABLE_IN_HOMEPASS_REGION (tech regions disjoint),
                                                                   DUPLICATE_SUBSCRIPTION, CUSTOMER_NOT_ELIGIBLE. Adding a new
                                                                   failure category requires extending DD_NOT-01's customer-message templates
                                                                   first.
