 1. What this process is about
 A Package is what customers buy. It groups one or more Services (from PLM-CFG-01) at a price, for a billing frequency,
 available in specific franchises and tech regions. Examples: "GPON Internet 100MB Residential" packages together one
 Service (the Internet 100MB Service from the catalog) at 5,000 KES/month, available in Nairobi and Mombasa via GPON.

 This DD covers the configuration of Packages by an admin user: create, read, update, soft-delete, plus audit. There is no
 workflow here — this is administrative CRUD on catalog data.

 Important boundary: SIP-01 owns the Package's definition (code, composition, price, geo-scope, wallet/tax bindings). The
 Package lifecycle (Draft → Active → Inactive → EndOfLife, per franchise) is owned by SIP-02 (Package launch). SIP-01
 creates Packages in DRAFT state; transitioning them requires SIP-02 endpoints. This DD focuses on definition only.

 PLM scope. PLM owns the catalog of products: Services (PLM-CFG-01), Packages (this DD), Bundles (PLM-CFG-08).
 PLM-CFG-08 (Bundle) composes Packages from this DD. PLM never calls back into customer/billing modules.

 Downstream modules (subscription-engine, fulfillment, billing, search index, etc.) consume Package data via Kafka events
 and keep their own caches in sync.

 Versioning model: Package definition (code, name, composition, wallet/tax bindings) lives on the package row. Pricing
 and geo-scope changes create a new package_version row. The package.current_version_id points at the active
 version. When the admin publishes a new version, the previous one transitions to SUPERSEDED and the new one becomes
 ACTIVE at its effective_from. Active customer subscriptions reference a specific package_version_id and remain on
 that version until they upgrade (FUL-04) — preserving historical pricing.

            package com.sophix.plm.rules

            import com.sophix.plm.facts.PackageFact
            import com.sophix.plm.facts.PackageCompositionFact
            import com.sophix.plm.facts.ExistingCodesFact
            import com.sophix.plm.facts.ReferencingActiveSubscriptionsFact
            import com.sophix.plm.facts.ReferencingActiveBundlesFact
            import com.sophix.plm.facts.ValidationError

            // R-SIP-01-1 — Package code must be unique across plm catalog

            rule "R-SIP-01-1-code-uniqueness"
            when
                 $p: PackageFact($code: code, $id: id, action != "DELETE")
                 $existing: ExistingCodesFact(codes contains $code, ownerId != $id)
            then
                 insert(new ValidationError("R-SIP-01-1",
                                            "code",
                                            "Code already exists in catalog: " + $code));
            end

            // R-SIP-01-3 — Package must compose at least 1 Service

            rule "R-SIP-01-3-minimum-composition"
            when
                 $p: PackageFact($id: id, action != "DELETE")
                 $c: PackageCompositionFact(packageId == $id, services.size() < 1)
            then
                 insert(new ValidationError("R-SIP-01-3",
                                            "services",
                                            "Package must compose at least 1 Service"));
            end

            // R-SIP-01-4 — All composed Services must be Active
