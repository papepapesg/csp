 This DD should be implemented as part of the owning SOPHIX capability, not as an isolated service unless the deployment
 architecture explicitly separates that capability.

 1. What this flow is
 A Shifting WO covers one business operation: a customer is staying with Wananchi but relocating. The old address must be
 vacated (drop returned to inventory or recovered in place, account inactivated) and the new address must be served (new
 drop spliced or activated, account reactivated at the new location). The two halves are tightly coupled by business rule: the
 disconnect must finalize before the reconnect can start, and the reconnect's finalization is what updates the HomePass and
 reactivates the account at the new place. Shifting is free for the customer.

 The framework's multi-phase BPMN mechanism is built precisely for this case. The flow uses a single wo_id with
 current_phase cycling NULL → DISCONNECT → RECONNECT over the life of one process instance. Same WO, same
 audit trail, finalization-order rule enforced naturally by BPMN sequence.

 Three non-negotiable rules from the workshop:

   1. Finalization order is sequential, not parallel. Disconnect finalizes first; reconnect cannot start until then. The BPMN
     enforces this with a single-thread sequence (no parallel gateway).

   2. The disconnect phase has no site visit. GSD/HSD are system-driven — the network simply turns off provisioning at the
     old address. No technician dispatched. The framework's wo_job_type_catalog.requires_site_visit = false
     for these codes; the BPMN takes the no-site-visit fast path.

   3. The reconnect phase is a full installation-like flow. Tech dispatched, on-site work, optical check, equipment binding
     (where the relocation involves new equipment), HomePass topology resolution at finalize. Same primitives as the
     Installation flow uses.

 This BSS is deployable in any country Wananchi Group operates. The cross-country variation that affects Installation (§1 of
 DD_WO-01-FLOW-INSTALLATION) applies equally here:

   - In Kenya (WIK), the new address's HomePass record carries OLT port + PBO + splitter details from the network-planning
      team. The reconnect tech *confirms* this topology when finalizing — or *corrects* it if reality differs from planning.

   - In Senegal (YASSN), the new address's HomePass record at relocation time may have only the address + upstream
      anchor; if the last mile to the new premise isn't already deployed, the reconnect tech *captures* the topology via "app
      terrain" mobile app — same mechanism as a fresh install.

 What this flow does NOT do
   - Doesn't handle non-Wananchi-staying disconnects. Termination, suspension, churn — those are separate flows
     (future OSR-DISCONNECT). Shifting is specifically *the customer stays with us, just moves*.

   - Doesn't handle network migration. HFC → GPON migration (job codes GPO, HHD) is a different kind of operation — the
     customer doesn't physically move, only the technology serving them changes. Future flow.

   - Doesn't own contractor invoicing for shifting visits. Same as Installation — Finance consumes
     WorkOrderShiftingCompleted (§8) for invoicing per the contractor's shifting-fee arrangement (separate from install
     fee schedules).

   - Doesn't bill the customer. Shifting is free of charge. No coupling to BIL-*.

   - Doesn't define the WO module's state machine, REST API, schemas, contractor model, or Kafka primitives —
     those live in DD_WO-01-FRAMEWORK. This satellite extends the framework with shifting-specific Camunda BPMN,
     Drools rules, operator config rows, and the phase-transition semantics.

 The flow has two subprocesses (DISCONNECT and RECONNECT) chained sequentially within one process instance. The
 reconnect phase's middle section mirrors the Installation flow (assignment → claim → start → work loop → 2-step finalize →
 Drools client-up gate → Pattern B option). The differences from Installation are the explicit phase-entry workers, the
 disconnect-phase wrapper around all of it, and the final HomePass update going to the new address rather than confirming
 the existing one.

 2.2 BPMN XML — phase-transition snippet
 The phase transitions use a flow service task (not the REST /transition-phase API) because the transition is internal —
 the BPMN itself drives it, no external caller needs to push.
           <bpmn:serviceTask
               id="wo-shifting-enter-reconnect"
               name="Enter RECONNECT phase"
               camunda:type="external"
               camunda:topic="wo-shifting-enter-reconnect">
             <bpmn:extensionElements>
               <camunda:inputOutput>
                 <camunda:inputParameter name="woId">${woId}</camunda:inputParameter>
                 <camunda:inputParameter name="targetPhase">RECONNECT</camunda:inputParameter>
                 <camunda:inputParameter name="updateJobTypeCode">true</camunda:inputParameter>
               </camunda:inputOutput>
             </bpmn:extensionElements>
           </bpmn:serviceTask>

 The worker (§7.2) calls the framework's internal phase-update service (same code path the public /transition-phase
 REST API would use), and additionally updates job_type_code from GSD → GSR (or HSD → HSR) based on the WO's
 network type.

 2.3 BPMN XML — cancellation boundary
 Same framework pattern as DD_WO-01-FLOW-INSTALLATION §2.2 — interrupting boundary message event on
 WorkOrderCancellationRequested attached to the top-level subprocess. Cancellation is valid at any phase. If cancelled
 during DISCONNECT, the account stays as it was before the WO; if cancelled during RECONNECT, account stays in INA
 (the disconnect already finalized), and ops must follow up to either re-issue a reconnect WO or terminate the customer.

 2.4 Per-operator BPMN composition
 The Shifting flow can be composed differently per operator without code change. v1.0 ships WIK. Future operators can:

   - Make the DISCONNECT phase require dispatcher confirmation (WIK auto-confirms after the prepare worker; YASSN
     might require a CSR step).

   - Insert a pre-disconnect equipment-recovery check (some operators require the modem returned before
      disconnect-finalize; others recover the equipment at reconnect at the new address; others ignore equipment recovery
      during shifting).

   - Tune the RECONNECT phase's Drools client-up thresholds and Pattern B routing rules.

   - Add intermediate user tasks for compliance approvals or VIP-customer handling.

 All of these are BPMN edits and config-row additions, not framework or code changes.

 5. Phase transition mechanics
 5.1 Single-WO two-phase model
 Workshop documents two distinct WO codes (GSD/GSR for GPON, HSD/HSR for HFC) and a strict finalization order. We
 model these as one WO row with current_phase cycling, not two paired WOs. The decision (settled during framework
 design):

   - One audit trail. Searching the WO history shows the complete shifting story in one place.

   - Finalization order enforced by BPMN sequence, not by cross-WO coordination logic. If the disconnect subprocess
     hasn't completed, the reconnect subprocess can't run.

   - No master/sub linkage needed. The master_wo_id primitive (framework §5.1) is reserved for Ticketing-driven
     escalations and RPT linkages.

   - wo_id stable across the whole operation. Reporting, customer-facing references, contractor invoicing all use one
     identifier.

 5.3 The job_type_code change
 The job type code on the WO row changes between phases. This is unusual — most WOs have one job type for life. Shifting
 is the v1.0 exception. The wo-shifting-enter-reconnect worker updates job_type_code in the same transaction as
 the phase transition:

   - GSD → GSR for GPON shifting.

   - HSD → HSR for HFC shifting.

 The network type stays the same (GPON or HFC) across the transition; only the disconnect/reconnect suffix changes.

 This matters because wo_finalization_requirements lookups are keyed on (operator_code, kind,
 job_type_code). When the disconnect phase finalizes, the framework reads the GSD/HSD row (no notes/attachments
 required beyond dispatcher_note + summary). When the reconnect phase finalizes, the framework reads the GSR/HSR row
 (full install-like checklist). Same wo_id, same row — different requirements at each phase boundary, because the WO has
 *become* a reconnect WO by then.

 Future enhancement: if other flows need similar mid-flight job-type changes, the framework could promote this to a first-class
 primitive. v1.0 keeps it as a flow-internal detail.

 5.4 What if reconnect can't happen?
 If the disconnect phase finalizes (account → INA, customer detached from old HomePass) but the reconnect phase can't
 complete (new address not serviceable, customer disappears, contractor never schedules), the WO sits in
 current_phase=RECONNECT, status=IN_PROGRESS indefinitely. This is operationally bad — the customer is paying for
 service they're not getting.

 The flow does not auto-resolve this. Two operational responses are available:

   - Cancel the WO via POST /api/work-orders/{woId}/cancel. The WO transitions to CANCELLED. Operations
     follow up: either reactivate the customer at the old address (manual intervention through ILM-CFG-01) or terminate the
     customer (future OSR-DISCONNECT flow).

   - Finalize with NEW_ADDRESS_NOT_SERVICEABLE as the final reason. Customer's account stays in INA. Retention (via
     Kafka subscription to WorkOrderShiftingCompleted filtering on this final reason) opens a separate conversation with
     the customer.

 Neither response involves un-doing the disconnect-phase finalization. Once an account goes to INA, restoring it to ACT
 requires a separate, deliberate action — never an implicit "undo" inside the WO module.



 6. Account-status side-effects
 Two side-effects fire as part of a Shifting WO's lifecycle. Both are emitted as event-payload fields for ILM-CFG-01 (Customer
 Service module) to consume. The WO module does NOT directly UPDATE the customer-account record — separation of
 concerns.

 6.1 At disconnect-phase finalize
 The wo-shifting-finalize-disconnect-phase worker emits a WorkOrderPhaseFinalized event (flow-specific,
 §8) with payload field accountSubStatusChange = {to: "INA", reason: "SHIFTING_DISCONNECT"}.


SOPHIX BSS Design Documents                                                                                               Page 11
 ILM-CFG-01 consumes and updates customer_account.sub_status.

 The worker also emits a WorkOrderHomePassDetachment event (flow-specific) with payload {homepassId: <OLD>,
 customerId, detachedAt}. RLM-CFG-01 consumes and clears the old HomePass's customer_id field (the HomePass
 row stays — it's a physical address record — but the customer association is removed). The old HomePass becomes
 available for a new customer in the future.

 6.2 At reconnect-phase finalize
 The wo-shifting-finalize-reconnect-phase worker emits a WorkOrderPhaseFinalized event with payload
 accountSubStatusChange = {to: "STF", reason: "SHIFTING_RECONNECT"}. ILM-CFG-01 consumes and
 updates the customer account.

 Then wo-emit-homepass-update-at-finalize emits a WorkOrderHomePassTopologyResolved event for the
 NEW HomePass (carrying captured or confirmed topology fields). RLM-CFG-01 writes the topology to the new HomePass
 record and attaches the customer to it.

 This separation — account-status events go to ILM-CFG-01, HomePass-update events go to RLM-CFG-01 — keeps each
 downstream module owning its own data without the WO module needing to know any of them directly. The WO module just
 emits events.

 6.3 Failure modes
 If ILM-CFG-01 misses the event (downstream outage, DLQ), the customer's account stays in its previous status. Operations
 recovery: the framework's events are Kafka with at-least-once semantics; ILM-CFG-01's consumer should be idempotent on
 (woId, phase). For manual recovery, the flow exposes a replay endpoint POST
 /api/work-orders/{woId}/phase-events-replay (§9.2) that re-emits the phase-finalize events for the specified
 phase.

 Same goes for RLM-CFG-01 missing the HomePass detachment / topology-resolution events — re-emit via the replay
 endpoint.



 7. Flow-specific workers
 Five workers live in this flow on top of the framework's generic ones and the Installation flow's shared ones (which it reuses):

 7.1 wo-shifting-enter-disconnect
 External task topic: wo-shifting-enter-disconnect.

 Runs right after wo-validate-create. Action:

   1. Set current_phase = DISCONNECT on the WO row.

   2. Emit WorkOrderPhaseTransitioned with previousPhase=null, newPhase=DISCONNECT.

   3. Complete the Camunda task.

 Lock duration: 3s.

 7.2 wo-shifting-enter-reconnect
 External task topic: wo-shifting-enter-reconnect.

 Runs after the disconnect phase's wo-shifting-finalize-disconnect-phase worker completes. Action:

   1. Update job_type_code on the WO row from GSD → GSR (or HSD → HSR) per network_type.

   2. Set current_phase = RECONNECT.

   3. Emit WorkOrderPhaseTransitioned with previousPhase=DISCONNECT, newPhase=RECONNECT.

   4. Audit-log the job_type change.

   5. Complete the Camunda task.

 Lock duration: 3s.

 7.3 wo-shifting-disconnect-prepare


SOPHIX BSS Design Documents                                                                                                 Page 12
 External task topic: wo-shifting-disconnect-prepare.

 Runs inside the DISCONNECT subprocess. Action:

   1. Validate that the WO has a dispatcher_note capturing the shifting circumstances (customer relocating from X to Y,
     scheduled date).

   2. Validate that the WO has a new_address note with a valid newHomepassId. (This is captured at creation time; if
     missing, fail with 400 — the agent should have selected the new address before raising the shifting.)

   3. Mark the OLD HomePass record as "vacating" via a lightweight event (WorkOrderHomePassVacating, internal to
     RLM-CFG-01's subscription).

   4. Complete the Camunda task.

 If validation fails, the worker fails the task with an error code that routes the BPMN to a user task for the dispatcher to correct
 the inputs before retrying.

 Lock duration: 5s.

 7.4 wo-shifting-finalize-disconnect-phase
 External task topic: wo-shifting-finalize-disconnect-phase.

 Runs at the end of the DISCONNECT subprocess. Action:

   1. Verify the framework's wo-enforce-finalize-checklist has passed for the GSD/HSD job_type_code (required
     notes: dispatcher_note + shifting_disconnect_summary + final_reason_set).

   2. Emit WorkOrderPhaseFinalized (flow event, §8) with:

   - phase = DISCONNECT

   - accountSubStatusChange = {to: "INA", reason: "SHIFTING_DISCONNECT"}

   - oldHomepassId (read from WO)

   3. Emit WorkOrderHomePassDetachment (flow event, §8) with {homepassId: <OLD>, customerId,
     detachedAt}.

   4. Complete the Camunda task.

 The worker does NOT transition WO status — status=IN_PROGRESS continues into the RECONNECT phase. Only
 current_phase changes (via the next worker, wo-shifting-enter-reconnect).

 Lock duration: 5s.

 7.5 wo-shifting-finalize-reconnect-phase
 External task topic: wo-shifting-finalize-reconnect-phase.

 Runs at the end of the RECONNECT subprocess, after the framework's checklist has passed. Action:

   1. Transition status FINALIZATION_PENDING → COMPLETED (this is the WO's terminal transition).

   2. Set completed_at = NOW().

   3. Emit WorkOrderPhaseFinalized with:

   - phase = RECONNECT

   - accountSubStatusChange = {to: "STF", reason: "SHIFTING_RECONNECT"}

   - newHomepassId (read from WO)

   4. Emit framework's WorkOrderFinalized (in addition to the phase event — the WO has completed).

   5. Complete the Camunda task.

 Lock duration: 5s.

 10. Workshop sources
 The Wananchi KE Shifting workflow (workshop 2026-04-29 + Bildad Gitonga transcript 2026-04-30) requires:

   - A two-leg operation per shifting: Disconnect (GSD for GPON, HSD for HFC) at the old address, then Reconnect
     (GSR/HSR) at the new address.

   - The Disconnect leg is system-driven, no site visit, work units = 0. Triggers sub_status → INA on the customer account
     and removes the customer from the old HomePass.

   - The Reconnect leg requires a full site visit (work units = 1), schedules a team, captures the new address in Notes, requires
     optical/signal check before finalization, triggers sub_status → STF, and updates the HomePass to the new location.

   - Finalization order is strict: Disconnect must finalize before Reconnect can begin.

   - Shifting is free of charge for the customer (no billing coupling).

   - Shifting can be raised by CSR or by contractor teams.

   - Standard Wananchi finalization discipline applies to the Reconnect leg: required-before-finalize checklist (findings,
     solution, optical/signal, final reason, photos), 2-step finalize, Pattern B reroute available if the new address can't be
     brought up due to signal/infrastructure issues.

 Cross-country variation. In Senegal, the Reconnect leg may involve last-mile deployment (running fiber from a PBO to the
 new premise). The tech captures topology via "app terrain" — same REST API as other clients. The variation is supported by
 per-operator note-kind registration + per-operator finalization requirements (§3.6); no code change between KE and SN
 models.
