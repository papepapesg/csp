 DD_SUB-LM-01 - Subscription Lifecycle Management
 Developer implementation guide: DD_SUB-LM-01-DEV_IMPL_GUIDE-v1.0.md.


 1. Purpose
 SUB-LM-01 defines the canonical Subscription entity for SOPHIX.

 A Subscription is the long-lived operational record that says:
           customer X consumes package Y at homepass Z under billing mode M

 Billing, fulfillment, dunning, work orders, equipment, notifications, analytics, and customer care all anchor back to this record.

 Use this DD when implementing:

   - The subscription table.

   - Subscription status catalog.

   - Subscription creation in CREATED status.

   - Internal state update APIs used by workflows.

   - Active restriction catalog and active restriction storage.

   - Cycle-window computation.

   - Low-level subscription Kafka events.


 2. Ownership
 SUB-LM-01 owns:

   - Subscription master entity.

   - Subscription status catalog.

   - Subscription transition reason catalog.

   - Subscription restriction catalog.

   - active_restrictions storage on the subscription.

   - Cycle model fields stored on the subscription.

   - Internal state mutation APIs used by workflow BPMNs.

   - Generic low-level subscription events.

 SUB-LM-01 does not own:

   - Operation orchestration. See SUB-WF-FRAMEWORK-01 and operation DDs.

   - Activation, pause, resume, terminate, upgrade, downgrade, relocation, migration, restrict, suspend-NP trigger APIs. Those
     are owned by operation DDs.

   - Billing fees, proration money math, tax, invoices, wallets, or credit/debit notes. See BIL DDs.

   - Network provisioning, restriction enforcement, suspension, termination, or HomePass claim/release. See FUL DDs.

   - Package definition. See SIP-01.

   - Service definition. See PLM-CFG-01.

   - HomePass definition. See RLM-CFG-01.

   - Customer/KYC data. See ILM-CFG-01.

   - Equipment instance lifecycle. See OSR-INSTANCE-01.

 SUB-LM-01 is the state-of-record layer. Workflows ask it to mutate state; it does not decide the full business process.

 4. Core State Machine
 Canonical state family:
            CREATED
            PENDING_ACTIVATION
            ACTIVE
            PENDING_PAUSE
            SUSPENDED
            PENDING_RESUME
            PENDING_UPGRADE
            PENDING_DOWNGRADE
            PENDING_RELOCATION
            PENDING_MIGRATION
            PENDING_TERMINATION
            TERMINATED
            RETIRED

 Restriction operations are special: adding/removing restrictions does not change status_code. It mutates
 active_restrictions.

                                  not active.

  PENDING_ACTIVATION              Activation saga in progress.             Transient               No

  SUSPENDED                       Service suspended by voluntary           Yes                     No

  PENDING_TERMINATION             Termination saga in progress.            Transient               Usually no after fulfillment step

  TERMINATED                      Contract/service ended.                  Yes                     No

                                  operational use.




 5. Data Model
 5.1 subscription
 What this table is for:

 subscription is the master operational record for an account's service. Every billing cycle, fulfillment action, dunning step,
 work order, equipment binding, and lifecycle workflow references this row.


SOPHIX BSS Design Documents                                                                                                            Page 2
 SUB-LM follows the ILM-CFG-01 invariant: Customer is identity; Account is operations. account_id is therefore the
 operational anchor for the subscription. customer_id stays on the row as a denormalized identity/search reference so
 screens, integrations, and audit payloads do not need an extra customer lookup for every list view.

 Use this table when:

   - Creating a subscription after order capture.

   - Reading the customer's current service/package/HomePass/status.

   - Locking the subscription during a lifecycle workflow.

   - Computing cycle windows for billing or workflow decisions.

   - Recording current active restrictions.

   - Auditing the current lifecycle state.

 Do not use this table to store:

   - Customer personal details. Use ILM-CFG-01.

   - Package/service definitions. Use SIP-01 and PLM-CFG-01.

   - Money amounts, invoices, balances, payments, or tax. Use BIL modules.

   - Network endpoint topology. Use RLM-CFG-01/HomePass and FUL modules.

 5.3 subscription_transition_reason
 What this table is for:

 subscription_transition_reason is the reason-code catalog for status and lifecycle changes. It gives every transition
 a structured business reason instead of free text.

 Use this table when:

   - A workflow needs to store why a transition happened.

   - UI needs to show selectable reasons for admin actions.

   - Reports need to group transitions by business cause.

   - Downstream modules need a stable reason code in event payloads.

 Do not use this table to model full workflow rules. It identifies the reason; it does not decide whether the action is allowed.

 6. Business Rules
 6.1 Subscription Master Rules
  Rule                                                             Description

  R-SUB-LM-S-1                                                     A subscription is identified by subscription_id, a ULID-style text ID.

  R-SUB-LM-S-2                                                     Only one non-terminal subscription may exist for (account_id,
                                                                   homepass_id, package_ref). customer_id alone is not sufficient
                                                                   because one customer may operate multiple accounts.

  R-SUB-LM-S-3                                                     package_ref must resolve to an ACTIVE package at activation time.

  R-SUB-LM-S-4                                                     homepass_id must resolve to a sellable HomePass at activation time.

  R-SUB-LM-S-5                                                     billing_mode is set at activation and is immutable for the same subscription.

  R-SUB-LM-S-6                                                     Package version is pinned at activation. Later package publishes do not mutate
                                                                   existing subscriptions.

  R-SUB-LM-S-7                                                     Fulfillment reads current HomePass service endpoints from RLM-CFG-01;
                                                                   endpoints are not snapshotted on the subscription.

  R-SUB-LM-S-8                                                     Active/suspended subscriptions cannot be soft-deleted. They must terminate
                                                                   first.

  R-SUB-LM-S-9                                                     start_date must be on or before service start, and end_date, when set,
                                                                   must be after start_date.



 6.2 Cycle Rules
  Rule                                                             Description

  R-SUB-LM-CYC-1                                                   CALENDAR_ANCHOR requires cycle_anchor_day from 1 to 28.

  R-SUB-LM-CYC-2                                                   ROLLING_DAYS requires cycle_period_days > 0.

  R-SUB-LM-CYC-3                                                   Days 29-31 are not valid anchors. Operator overflow policy is handled by
                                                                   activation workflow before commit.

  R-SUB-LM-CYC-4                                                   Cycle fields are immutable after activation unless a future
                                                                   billing-mode/cycle-change workflow explicitly owns the change.

  R-SUB-LM-CYC-5                                                   SUB-LM computes date windows only. BIL-01 computes money.



 6.3 Status Catalog Rules
  Rule                                                             Description

  R-SUB-LM-SC-1                                                    Status code is uppercase snake-case and unique.

  R-SUB-LM-SC-2                                                    Status code is immutable once referenced.

  R-SUB-LM-SC-3                                                    Status cannot be retired while non-terminal subscriptions reference it.

  R-SUB-LM-SC-4                                                    Pending statuses are transient and not final downstream business facts.



 6.4 Restriction Rules

  R-SUB-LM-RES-1                                                Restriction code is uppercase snake-case and unique.

 7. REST APIs

 8. Cycle Window Algorithm
 Calendar anchor:
          CycleWindow computeCalendarAnchor(LocalDateTime operationAt, int anchorDay, int frequencyMonths) {
              LocalDate anchorThisMonth = LocalDate.of(operationAt.getYear(), operationAt.getMonth(), anchorDay);
              LocalDate cycleStart = anchorThisMonth.isAfter(operationAt.toLocalDate())
                  ? anchorThisMonth.minusMonths(frequencyMonths)
                  : anchorThisMonth;
              LocalDate cycleEnd = cycleStart.plusMonths(frequencyMonths);
              return CycleWindow.of(cycleStart, cycleEnd, operationAt);
          }

 Rolling days:
          CycleWindow computeRollingDays(Instant activatedAt, Instant operationAt, int periodDays) {
              long daysSinceActivation = Duration.between(activatedAt, operationAt).toDays();
              long cycleIndex = Math.floorDiv(daysSinceActivation, periodDays);
              Instant cycleStart = activatedAt.plus(cycleIndex * periodDays, ChronoUnit.DAYS);
              Instant cycleEnd = cycleStart.plus(periodDays, ChronoUnit.DAYS);
              return CycleWindow.of(cycleStart, cycleEnd, operationAt);
          }

 Implementation notes:

   - Use operator timezone where the workflow/DD requires local cycle behavior.

   - Store timestamps as TIMESTAMPTZ.

   - Avoid month-end anchors by enforcing 1-28.

 12. Implementation Notes
 This section is written for the developer implementing the subscription module. The main idea is simple: every state
 mutation must be deterministic, locked, validated, written with its outbox event in the same transaction, and safe to retry.

 12.1 Row Locking
 All internal mutation APIs must lock the subscription row before reading or changing status/master fields/restrictions.

 Why this matters:

 Two workflow workers may run close together. Example: a dunning suspension and a customer-requested pause could hit
 the same subscription at nearly the same time. Without a row lock, both workers can read ACTIVE, both can think they are
 allowed to proceed, and the later commit can overwrite the earlier one. FOR UPDATE prevents that.
              SELECT *
              FROM subscription
              WHERE subscription_id = :subscriptionId
              FOR UPDATE;

 Basic sequence for every mutation API:

   1. Start DB transaction.

   2. Read subscription using SELECT ... FOR UPDATE.


SOPHIX BSS Design Documents                                                                                                             Page 14
   3. Validate the current state and requested change.

   4. Apply the update.

   5. Insert the outbox event.

   6. Commit.

 Pseudocode:
            @Transactional
            public PutStateResponse putState(String subscriptionId, PutStateRequest req) {
                Subscription sub = repository.findByIdForUpdate(subscriptionId)
                    .orElseThrow(() -> notFound("SUBSCRIPTION_NOT_FOUND"));

                transitionValidator.validate(sub.statusCode(), req.targetStatusCode(), req.transitionType());

                String previousStatus = sub.statusCode();
                sub.setStatusCode(req.targetStatusCode());
                sub.setCurrentTransitionType(req.transitionType());
                sub.setCurrentTransitionReasonCode(req.reasonCode());
                sub.setLastStatusChangedAt(clock.now());
                sub.clearLastFailureIfSuccessfulPendingMove();

                repository.save(sub);

                outbox.insert(subscriptionStateChangedEvent(sub, previousStatus, req));

                return responseFrom(sub, previousStatus);
            }

 Important rule: do not call external services while holding the row lock. The workflow should call billing/fulfillment outside
 SUB-LM. SUB-LM should only update its own DB and outbox inside the transaction.

 12.2 Outbox
 Every mutation that emits an event must write to the outbox in the same transaction.
            BEGIN;

            UPDATE subscription
            SET status_code = :targetStatus,
                current_transition_type = :transitionType,
                updated_at = NOW()
            WHERE subscription_id = :subscriptionId;

            INSERT INTO messaging.outbox_event (...);

            COMMIT;

 Why this matters:

 If the subscription update commits but the event is not recorded, downstream modules never learn about the change. If the
 event is recorded but the update rolls back, downstream modules see a false event. Writing both in one transaction prevents
 both problems.

 Do this:
            @Transactional
            public void commitState(...) {
                // 1. lock + update subscription
                // 2. insert messaging.outbox_event
                // 3. transaction commits both together
            }

 Do not do this:
            public void commitState(...) {
                repository.save(subscription);         // commits
                kafkaProducer.send(event);             // can fail after DB commit
            }

 12.3 Idempotency
 Create subscription must use idempotency.

 Suggested table:
          CREATE TABLE subscription_idempotency_key (
             operator_code     TEXT NOT NULL,
             idempotency_key   TEXT NOT NULL,
             request_hash      TEXT NOT NULL,
             status            TEXT NOT NULL CHECK (status IN ('PROCESSING', 'SUCCEEDED', 'FAILED')),
             response_json     JSONB,
             error_code        TEXT,
             created_at        TIMESTAMPTZ NOT NULL DEFAULT NOW(),
             updated_at        TIMESTAMPTZ NOT NULL DEFAULT NOW(),
             PRIMARY KEY (operator_code, idempotency_key)
          );

 If the same key is reused with a different request hash, return 409
 IDEMPOTENCY_KEY_REUSED_WITH_DIFFERENT_REQUEST.

 The primary key is what prevents a second row from being inserted for the same (operator_code, idempotency_key).
 Do not rely only on an application-level check, because two HTTP requests can arrive at the same time.

 How to implement create idempotency:

   1. Require Idempotency-Key on POST /api/subscriptions.

   2. Canonicalize the request body.

   3. Hash the canonical request body.

   4. Start a database transaction.

   5. Try to insert a reservation row with status = 'PROCESSING'.

   6. If the reservation insert succeeds, this request owns the creation.

   7. If the insert fails because the primary key already exists, load the existing row:

   - Different request hash: return 409.

   - Same request hash and SUCCEEDED: return the stored response.

   - Same request hash and PROCESSING: return 409 or 425 with Retry-After, because another identical request is still
     running.

   - Same request hash and FAILED: either return the stored failure or allow retry only if the failure policy explicitly says it is
     retryable.

   8. For the owner request, create the subscription, insert the outbox event, store the response JSON, set status to
     SUCCEEDED, and commit.

 The reservation insert can use INSERT ... ON CONFLICT DO NOTHING. If zero rows are inserted, the code must
 immediately read the existing row and compare the hash.

 Pseudocode:
          @Transactional
          public CreateSubscriptionResponse create(CreateSubscriptionRequest req, String idemKey) {
              String requestHash = hash(canonicalJson(req));

               boolean reserved = idemRepo.tryInsertProcessing(
                   req.operatorCode(),
                   idemKey,
                   requestHash
               );

               if (!reserved) {
                   IdempotencyRecord existing = idemRepo.findForUpdate(req.operatorCode(), idemKey);

                    if (!existing.requestHash().equals(requestHash)) {
                        throw conflict("IDEMPOTENCY_KEY_REUSED_WITH_DIFFERENT_REQUEST");



SOPHIX BSS Design Documents                                                                                                     Page 16
                    }

                    if (existing.status() == SUCCEEDED) {
                        return json.fromJson(existing.responseJson(), CreateSubscriptionResponse.class);
                    }

                    if (existing.status() == PROCESSING) {
                        throw retryLater("IDEMPOTENCY_REQUEST_IN_PROGRESS");
                    }

                    throw conflict("IDEMPOTENCY_PREVIOUS_REQUEST_FAILED");
                }

                Subscription sub = createSubscriptionRow(req);
                outbox.insert(subscriptionCreatedEvent(sub));

                CreateSubscriptionResponse response = responseFrom(sub);
                idemRepo.markSucceeded(req.operatorCode(), idemKey, response);
                return response;
           }

 Example SQL for the reservation:
           INSERT INTO subscription_idempotency_key (
             operator_code,
             idempotency_key,
             request_hash,
             status
           )
           VALUES (:operatorCode, :idempotencyKey, :requestHash, 'PROCESSING')
           ON CONFLICT (operator_code, idempotency_key) DO NOTHING;

 If this statement inserts one row, continue with create. If it inserts zero rows, the key already exists; read that row and apply
 the hash/status rules above.

 Do not make idempotency optional for create. Channels and mobile networks retry HTTP requests; without idempotency, the
 same customer/order may create duplicate subscriptions.

 12.4 Validation Order
 Use the same validation order in code so errors are predictable.

 For POST /api/subscriptions:

   1. Authenticate caller.

   2. Validate required fields and enum values.

   3. Validate idempotency key.

   4. Validate package exists and is active through SIP-01 or cached package snapshot.

   5. Validate HomePass exists and is sellable through RLM-CFG-01 or cached HomePass snapshot.

   6. Validate cycle fields.

   7. Check duplicate active subscription.

   8. Insert subscription row in CREATED.

   9. Insert SubscriptionCreated outbox event.

   10. Store idempotency response.

 For put-state:

   1. Authenticate service token.

   2. Validate request fields.

   3. Start transaction.

   4. Lock subscription row.

   5. Validate current status allows requested target.

   6. Update state fields.

   7. Insert SubscriptionStateChanged outbox event.

   8. Commit.

 12.5 Transition Validation
 Do not hardcode only one giant if block. Use a small transition validator that is easy to test.

 Example transition map:
          private static final Set<Transition> ALLOWED = Set.of(
              t("CREATED", "PENDING_ACTIVATION", "ACTIVATE"),
              t("PENDING_ACTIVATION", "ACTIVE", "ACTIVATE"),
              t("ACTIVE", "PENDING_PAUSE", "PAUSE"),
              t("PENDING_PAUSE", "SUSPENDED", "PAUSE"),
              t("SUSPENDED", "PENDING_RESUME", "RESUME"),
              t("PENDING_RESUME", "ACTIVE", "RESUME"),
              t("ACTIVE", "PENDING_TERMINATION", "TERMINATE"),
              t("PENDING_TERMINATION", "TERMINATED", "TERMINATE")
          );

 Validation:
          void validate(String from, String to, String operation) {
              if (!ALLOWED.contains(t(from, to, operation))) {
                  throw conflict("INVALID_SUBSCRIPTION_TRANSITION",
                      Map.of("from", from, "to", to, "operation", operation));
              }
          }

 Operation DDs may add operation-specific rules before they call SUB-LM. SUB-LM still enforces the core lifecycle safety net.

 12.6 Master Field Updates
 put-master-fields must update only the fields provided in the request.

 12.7 Active Restriction Updates
 Treat active_restrictions as a full replacement array, not a partial patch. The workflow worker computes the desired
 final list, then SUB-LM stores it atomically.

 Why:

   - ADD and REMOVE flows can be retried safely.

   - SUB-LM does not need to understand every restriction operation.

   - The row lock prevents lost updates.


SOPHIX BSS Design Documents                                                                                             Page 18
 Implementation steps:

   1. Lock subscription row.

   2. Validate every restriction code exists and is active in subscription_restriction.

   3. Validate no duplicate code in the incoming array.

   4. Replace active_restrictions.

   5. Insert SubscriptionRestrictionsChanged event with previous and current arrays.

   6. Commit.

 When status commits to SUSPENDED or TERMINATED, clear active_restrictions in the same transaction as the status
 change unless the calling workflow has already done so.

 12.8 Handling last_failure
 last_failure is for UI and operations support. It tells a support/admin user why the latest workflow failed and whether they
 can act on it.

 Example:
          {
              "operation": "TERMINATE",
              "category": "FULFILLMENT",
              "reasonCode": "TERMINATION_FULFILLMENT_FAILED",
              "reasonDetail": "AAA timeout while removing service profile",
              "actionable": true,
              "processInstanceId": "pi_01HX",
              "failedAt": "2026-05-27T10:20:00Z"
          }

 Rules:

   - revert writes last_failure.

   - A later successful state-affecting operation clears last_failure.

   - Do not put stack traces or secrets in last_failure.

   - Keep it customer-safe enough for support tooling, but not necessarily customer-visible.

 12.9 External Reads During Validation
 Some create/activation validation needs package and HomePass data. SUB-LM may call SIP/RLM directly or use a
 Kafka-maintained cache, depending on the implementation.

 Rules:

   - Source of truth remains SIP/RLM.

   - Cache misses must fall back to source APIs.

   - If source API is unavailable and no valid cached data exists, fail safely with dependency error.

   - Do not create a subscription against a package or HomePass that cannot be validated.

 12.10 Transaction Boundaries
 Keep transactions short.

 Good transaction:
          lock subscription -> validate -> update row -> insert outbox -> commit

 Bad transaction:
          lock subscription -> call billing -> call fulfillment -> update row -> commit

 Billing and fulfillment calls belong in workflow workers, not inside SUB-LM transactions.

 15. Build Order
 Implement in this order:

   1. Base subscription schema and status/restriction catalogs.

   2. Create/read/list APIs.

   3. Internal mutation APIs.

   4. Cycle-window computation.

   5. Outbox event emission.

   6. Admin catalog APIs.

   7. Integration with SUB-WF-FRAMEWORK-01 workers.

   8. Integration tests with first operation workflow, usually activation.
