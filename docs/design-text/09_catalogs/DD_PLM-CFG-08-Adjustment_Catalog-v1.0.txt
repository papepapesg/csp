 1. What this process is about
 A Bundle is a set of Packages sold as one marketed product — effectively a "mega-package" with its own properties that
 override the components' properties when sold as part of the Bundle. Example: a "Triple Play" bundle combines an Internet
 Package (normally billed monthly), a TV Package (normally monthly), and a Voice Package (normally weekly) into one
 offering at one price on the Bundle's own billing cycle.

 The customer subscribes to the bundle as a single entity, not to its individual packages. Billing charges the Bundle's price
 on the Bundle's billing cycle using the Bundle's wallet and tax bindings — the components' standalone properties are not
 used at charge time. The components retain their standalone properties for when they are sold individually (outside this
 Bundle).

 Modifications are all-or-nothing: a customer wanting to change one component must change the whole Bundle.

 This DD covers the configuration of Bundles by an admin user: create, read, update, soft-delete, plus audit. There is no
 workflow — administrative CRUD on catalog data.

 PLM scope. PLM owns the catalog of products: Services, Packages, Bundles. PLM-CFG-08 owns Bundle and
 BundleComposition. References to Packages are FK links within the plm database (Bundle's components are Packages in
 the same module).

 Downstream modules (subscription-engine, fulfillment, billing, search index, etc.) consume Bundle data via Kafka events and
 keep their own caches in sync. PLM never calls back into them.

 #### Fact classes (POJOs in com.sophix.plm.facts)

 A Fact class is a plain Java object that Drools evaluates DRL rules against. The KJAR project (modules/plm-rules/)
 contains these classes; the rules engine deserializes JSON payloads (sent by the calling module over HTTPS) into these
 objects, fires rules, returns results as JSON. Facts use the standard @Data + @NoArgsConstructor +
 @AllArgsConstructor Lombok annotations (used throughout the codebase to remove getter/setter/constructor
 boilerplate).

 BundleFact.java
          package com.sophix.plm.facts;

          import lombok.Data;
          import lombok.NoArgsConstructor;

          import java.math.BigDecimal;
          import java.util.List;

          @NoArgsConstructor

 The caller's responsibility:

   - For create/update: insert BundleFact + BundleCompositionFact (with the bundle's package list) +
     ExistingCodesFact (from catalog) + PackageAvailabilityFact (lookup of each component's status, price, and
     franchises); fire rules; collect ValidationError and ValidationWarning.

   - For activate: same as create/update plus action="ACTIVATE" on the BundleFact to enable R-3.

   - For delete: insert BundleFact (action="DELETE") + ReferencingSubscriptionsFact (from subscription-engine API
     or local view); fire rules; if ValidationError, reject with BUSINESS_RULE_ERROR carrying the rule ID.

   - For Package-delete (coordinated with PLM-CFG-01 / SIP-01): the Package-delete path inserts
     BundleCompositionFact with action="DELETE_PACKAGE", packageId=..., and
     referencingActiveBundles=... to enable R-7.

 ValidationWarning results are returned to the caller as advisory messages — the caller (UI) presents them as
 confirmation prompts rather than blocks.

 B — Current TZ
 Bundle entity exists in TZ codebase (Bundle Java class in one of the billing modules) but:

   - No formal lifecycle states (no Draft / Active / Retired transitions)

   - No per-franchise availability (TZ is single-deployment)

   - No composition rules in code (the bundle's package list is set in DB but not validated)

   - No price-independence enforcement (the bundle price field exists but isn't separated semantically from sum of packages)

   - No KRA tax-invoice integration

   - No Kafka events on bundle changes

   - Catalog admin via JHipster CRUD pages (basic, not workflow-aware)

 The TZ Bundle entity is essentially a database row with no behavior — all business logic happens in adjacent code
 (subscription creation, billing).
