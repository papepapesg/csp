 1. How To Read This Guide
 This guide is written in execution order. Follow it as the system runs, from provider setup, to callback receipt, to routing, to
 reconciliation and repair.

 PAY-GW-01 does not apply invoice balances or wallet balances directly. It receives provider money notifications, stores them,
 then calls the correct internal module.

 Target modules:

  Payment target                               Internal module                             Internal API

  POSTPAID invoice/account payment             BIL-01-PAY-01                               POST /api/payments/receive

  PREPAID wallet topup                         BIL-05                                      POST /api/wallets/{wallet_id}/credit

 3.1 Controller Logic
 The controller must do these actions in this order:

   1. Find provider by callback route and operator context.

   2. Verify signature or provider authentication.

   3. Parse provider payload into normalized structure.

   4. Build idempotency key.

   5. Store callback event.

   6. Upsert gateway transaction.

   7. Return provider acknowledgement after durable store.

 Pseudo-code:
          public function mpesaCallback(Request $request): JsonResponse
          {
              $provider = $this->providers->findActiveByCode('WIK', 'MPESA_KE');
              $adapter = $this->adapterRegistry->forProvider($provider);

                $signatureStatus = $adapter->verifySignature($request, $provider);

                if ($signatureStatus->isInvalid()) {
                    $this->callbackEvents->recordRejected($provider, $request, 'INVALID_SIGNATURE');
                    return response()->json(['result' => 'rejected'], 403);
                }

                $parsed = $adapter->parseCallback($request);
                $idempotencyKey = $adapter->buildIdempotencyKey($parsed);



SOPHIX BSS Design Documents                                                                               Page 2
                $result = DB::transaction(function () use ($provider, $request, $parsed, $idempotencyKey) {
                    $event = $this->callbackEvents->recordParsed($provider, $request, $parsed, $idempotencyKey);
                    return $this->gatewayTransactions->upsertFromCallback($provider, $event, $parsed);
                });

                return response()->json([
                    'result' => 'accepted',
                    'gatewayTransactionId' => $result->gateway_txn_id
                ], 200);
          }

 5.2 Duplicate Callback
 If another callback arrives with:
          provider_code = MPESA_KE
          provider_transaction_id = QL91ABCD
          amount = 2500.00
          currency = KES
          paid_at = 2026-05-29T09:42:00Z

 Then do not insert a second gateway transaction and do not call PAY-01 or BIL-05 again. Return 200 to the provider.

 5.3 Duplicate Conflict
 If another callback arrives with same provider transaction id but different amount:
          existing amount = 2500.00
          new amount = 3000.00

 Set the existing transaction or a conflict record to:
          status = DUPLICATE_CONFLICT
          hold_reason = DUPLICATE_CONFLICT

 Create a gateway_pending_resolution row so operations can investigate.



 6. Step 5 - Resolve Target
 The routing worker loads transactions with:
          select *
          from gateway_transaction
          where status in ('ROUTING_PENDING', 'ROUTING_RETRY')
          order by paid_at asc
          limit 100;

 For each transaction, it resolves the payment target.

 6.1 Reference Is An Account Or Invoice
 If payment_reference = ACC-900045, call the customer/account lookup API or internal repository and resolve:
          {

              "customerId": "CUS-100045",
              "accountId": "ACC-900045",
              "invoiceId": null,
              "applicationModule": "BIL-01-PAY-01"
          }

 10. Step 9 - Handle Provider Callback Responses
 The provider response depends on what happened before durable storage.

  Scenario                                 Store callback?        Route payment?                   HTTP response

  Valid callback, stored                   Yes                    Async                            200

  Duplicate callback, same values          Yes                    No                               200

  Duplicate callback, conflicting values   Yes                    No, hold                         200 or provider-specific accepted
                                                                                                   response

  Invalid signature                        Minimal audit only     No                               403

  Malformed payload                        Audit if parseable     No                               400

  Database unavailable before store        No                     No                               500 so provider retries


 Important: once money appears real and the callback is stored, prefer holding and repairing over rejecting. Rejecting a real
 payment can make provider and customer support more difficult.

 12. Step 11 - Run Settlement Reconciliation
 The reconciliation worker runs daily per provider after the provider settlement window closes.

 It loads provider settlement rows from API, SFTP file, or manual upload.

 Example normalized settlement row:
          {
              "providerCode": "MPESA_KE",
              "settlementDate": "2026-05-29",
              "providerTransactionId": "QL91ABCD",
              "amount": 2500.00,
              "currency": "KES",
              "paidAt": "2026-05-29T09:42:00Z",
              "settlementStatus": "SUCCESS"
          }


 12.1 Reconciliation Logic
 For each provider settlement row:

   1. Find gateway_transaction by (provider_id, provider_transaction_id).

   2. If not found, create MISSING_IN_BSS.

   3. If found but amount differs, create AMOUNT_MISMATCH.

   4. If found but status is not APPLIED, create STATUS_MISMATCH.

   5. If found and values match, mark transaction RECONCILED.

 Then compare SOPHIX gateway transactions for the same provider/date that were not present in provider settlement. Create
 MISSING_IN_PROVIDER when needed.

 13. Step 12 - Reversal Or Chargeback Event
 Some providers may send reversal, chargeback, or failed settlement events.

 PAY-GW receives the event and finds the original gateway transaction.

 Do not directly reverse invoices or wallet ledgers in PAY-GW.

 Recommended handling:

  Original application module                                      Action

  BIL-01-PAY-01                                                    Call PAY-01 reversal API if policy allows automatic reversal. Otherwise create
                                                                   approval/repair task.

  BIL-05                                                           Call BIL-05 debit adjustment or reversal endpoint if configured. Otherwise
                                                                   create approval/repair task.

  Unknown/not applied                                              Mark gateway transaction REVERSED or REJECTED as appropriate.


 Initial implementation may hold all provider reversals for finance review. That is safer than automatic ledger reversal without
 business approval.

 15. Validation Rules
 Implement these checks before marking a transaction routeable:

  Check                                                               Failure status

  Provider is active                                                  REJECTED

  Channel is active                                                   HELD with CHANNEL_INACTIVE

  Signature is valid                                                  REJECTED

  Provider transaction id is present                                  REJECTED

  Amount is positive                                                  REJECTED

  Currency matches channel/provider                                   HELD with CURRENCY_MISMATCH

  Paid timestamp is valid                                             HELD with INVALID_PAID_AT

  Idempotency conflict absent                                         DUPLICATE_CONFLICT

  Target reference resolves                                           ROUTING_PENDING, otherwise HELD




 16. Error Codes
 Use stable error codes so QA and Backoffice can handle failures consistently.

  Error code                                                          Meaning

  PAYGW_PROVIDER_INACTIVE                                             Provider is not active.

  PAYGW_SIGNATURE_INVALID                                             Signature or HMAC verification failed.

  PAYGW_PAYLOAD_MALFORMED                                             Provider payload cannot be parsed.

  PAYGW_DUPLICATE_CONFLICT                                            Same provider transaction id has conflicting values.

  PAYGW_UNKNOWN_REFERENCE                                             Payment reference cannot be resolved.

  PAYGW_MULTIPLE_TARGETS                                              Payment reference maps to multiple targets.

  PAYGW_TARGET_UNAVAILABLE                                            Internal target module is down or timed out.

  PAYGW_TARGET_REJECTED                                               PAY-01 or BIL-05 rejected the request.

  PAYGW_RECON_MISSING_IN_BSS                                          Provider settlement has a row missing in SOPHIX.

  PAYGW_RECON_AMOUNT_MISMATCH                                         Provider and SOPHIX amounts differ.

 18. Minimum Implementation Order
 Build in this order:

   1. Database migrations for provider, channel, callback event, transaction, routing attempt, reconciliation, pending resolution.

   2. Provider adapter interface.

   3. M-Pesa-style adapter with parser, signature stub, redaction, idempotency key builder.

   4. Public callback controller.

   5. Gateway transaction repository with duplicate and conflict handling.

   6. Routing resolver.

   7. PAY-01 routing client.

   8. BIL-05 routing client.

   9. Routing worker and retry logic.

   10. Held payment operations APIs.

   11. Reconciliation run and item tables.

   12. Daily reconciliation worker.

   13. Channel configuration API for frontend.

   14. RBAC permissions and audit log.

   15. Metrics and alerts.

 This order lets QA test real callback-to-payment behavior before adding all reconciliation features.

 20. Developer Checklist
 Before marking implementation complete:

   - Provider secrets are loaded from secret manager.

   - Callback endpoint stores before acknowledging provider.

   - Callback event redaction is tested.

   - Duplicate callback does not double-credit.

   - Duplicate conflict creates held resolution.

   - PAY-01 route uses idempotency key.

   - BIL-05 route uses idempotency key.

   - Routing attempts are recorded for every target call.

   - Held transaction repair is audited.

   - Reconciliation can create discrepancy items.

   - FE apps can read active channel instructions.

   - Metrics exist for callback success/failure, routing backlog, held queue, and reconciliation discrepancies.
