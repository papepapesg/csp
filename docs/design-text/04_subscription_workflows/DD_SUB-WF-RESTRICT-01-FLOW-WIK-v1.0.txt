 This DD should be implemented as part of the owning SOPHIX capability, not as an isolated service unless the deployment
 architecture explicitly separates that capability.

 Implement this DD with these rules:

   - Use the owning module APIs/repositories for authoritative writes.

   - Use approved internal APIs/client wrappers when reading another module's data.

   - Do not query another module's database tables directly from business flow code.

   - Treat worker names as logical Camunda external-task topics, not separate deployments.

   - One worker application may handle multiple topics, but metrics, retries, and logs must remain visible per topic.

   - Emit success events only after the authoritative state commit succeeds.

   - Use outbox publishing for Kafka events.

 1. What this flow is
 KE WIK's BPMN composes the framework workers for restriction operations. Trigger endpoint accepts the request (from
 BIL-04 dunning, BO admin, call center, customer portal), persists subscription_operation row, starts process instance
 of sub-restrict-wik with intent variable set to ADD or REMOVE. The BPMN orchestrates: Drools validation → billing
 intent → FUL-04 call (APPLY or LIFT depending on intent) → put-active-restrictions (append for ADD, remove for REMOVE)
 → emit domain event → notification → finalize operation.

 2.3 Compensation paths


SOPHIX BSS Design Documents                                                                                         Page 5
 Restrictions are a simpler compensation case than ACTIVATE/TERMINATE because the subscription's status_code never
 changes. The only mutation that needs reverting on partial failure is the active_restrictions[] array — but since the
 BPMN orders fulfillment BEFORE the array mutation (FUL-04 must succeed before SUB-LM-01 commits), there's no
 partial-commit window to compensate.

  If this step fails                                                     What happens

  drools-decide validation                                               No mutations yet; emit *Rejected event; finalize FAILED

  bil01-emit-intent                                                      No state mutations; emit *Rejected; finalize FAILED

  ful-call-restrict returns FAILED                                       No state mutations; emit *Rejected; finalize FAILED. Note: FUL-04 internally
                                                                         handles network-side compensation per its own §CO rules.

  sub-lm-put-active-restrictions                                         This SHOULD NOT fail (it's idempotent + atomic at the DB level). If it does (DB
                                                                         unavailable), the network-side restriction has been applied but the array isn't
                                                                         updated → manual recovery via manual-recovery-decision user task.

  kafka-emit                                                             Retried by outbox dispatcher; BPMN proceeds

  notification-send                                                      Logged but NOT compensated (reliability-isolated); BPMN proceeds

 3.1 validate-preconditions
              package rules.subscription.restrict.wik

              import com.sophix.subwf.facts.RestrictRequestFact
              import com.sophix.subwf.facts.SubscriptionStateFact
              import com.sophix.subwf.facts.RestrictionCatalogFact

              rule "Eligibility: subscription must be ACTIVE"
              when
                $req: RestrictRequestFact()
                $sub: SubscriptionStateFact(subscriptionId == $req.subscriptionId, statusCode != "ACTIVE")
              then
                modify($req) { setEligible(false); setEligibilityReasonCode("INVALID_STATE_FOR_RESTRICTION") }
              end

              rule "Eligibility: restriction code must exist + be active"
              when
                $req: RestrictRequestFact(eligible == null)
                not (RestrictionCatalogFact(code == $req.restrictionCode, isActive == true))
              then
                modify($req) { setEligible(false); setEligibilityReasonCode("UNKNOWN_OR_INACTIVE_RESTRICTION_CODE") }
              end

              rule "Eligibility ADD: not already restricted"
              when
                $req: RestrictRequestFact(intent == "ADD", eligible == null)
                $sub: SubscriptionStateFact(subscriptionId == $req.subscriptionId)
                eval($sub.getActiveRestrictionCodes().contains($req.getRestrictionCode()))
              then
                modify($req) { setEligible(false); setEligibilityReasonCode("ALREADY_RESTRICTED") }
              end

              rule "Eligibility REMOVE: must be applied"
              when



SOPHIX BSS Design Documents                                                                                                                      Page 6
            $req: RestrictRequestFact(intent == "REMOVE", eligible == null)
            $sub: SubscriptionStateFact(subscriptionId == $req.subscriptionId)
            eval(!$sub.getActiveRestrictionCodes().contains($req.getRestrictionCode()))
          then
            modify($req) { setEligible(false); setEligibilityReasonCode("RESTRICTION_NOT_APPLIED") }
          end

          rule "Eligibility: default-pass"
          salience -100

            $req: RestrictRequestFact(eligible == null)
          then
            modify($req) { setEligible(true) }
          end


 3.2 validate-role-gating
          rule "Role: BACKOFFICE_OPERATOR requires SUBSCRIPTION_OPERATOR or SUBSCRIPTION_ADMIN"
          when
            $req: RestrictRequestFact(activationTrigger == "BACKOFFICE_OPERATOR",
                                       initiatingActorRole not in ("SUBSCRIPTION_OPERATOR", "SUBSCRIPTION_ADMIN"),
                                       roleAllowed == null)
          then
            modify($req) { setRoleAllowed(false); setRoleReasonCode("ROLE_NOT_AUTHORIZED_FOR_TRIGGER") }
          end

          rule "Role: CUSTOMER_SELF_SERVICE requires operator config + catalog eligibility"
          when
            $req: RestrictRequestFact(activationTrigger == "CUSTOMER_SELF_SERVICE", roleAllowed == null)
            $cat: RestrictionCatalogFact(code == $req.restrictionCode)
            $cfg: OperatorConfigFact()
            eval(!$cfg.isCustomerSelfServiceEnabled() || !$cat.isCustomerSelfServiceEligible())
          then
            modify($req) { setRoleAllowed(false); setRoleReasonCode("CUSTOMER_SELF_SERVICE_NOT_ALLOWED") }
          end

          rule "Role: admin_only catalog row requires SUBSCRIPTION_ADMIN"
          when
            $req: RestrictRequestFact(roleAllowed == null)
            $cat: RestrictionCatalogFact(code == $req.restrictionCode, adminOnly == true)
            $req: RestrictRequestFact(initiatingActorRole != "SUBSCRIPTION_ADMIN")
          then
            modify($req) { setRoleAllowed(false); setRoleReasonCode("ADMIN_ONLY_RESTRICTION") }
          end

          then
            modify($req) { setRemoveAllowed(true) }
