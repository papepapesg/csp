 1. What this process is about
 A customer expresses intent to subscribe to a Wananchi Kenya, Wananchi Uganda, Wananchi Tanzania, or Yas Senegal
 Package at a known HomePass. The capturing channel (Field Agent PWA, Backoffice UI, Call Center, self-service portal)
 calls FUL-02's POST /api/orders. FUL-02 writes a row into customer_order and then asks Camunda — a workflow
 engine that lives in its own server outside our module, like a separate database for orchestration — to start running the
 operator's order-capture flow for this customer.

 The "operator's flow" is defined in a BPMN file — a flowchart-like XML document that lists the steps an order goes through, in
 what order, with which branches. BPMN files live inside our module's resources folder
 (modules/fulfillment-order-capture/src/main/resources/workflows/) and get deployed into Camunda at
 module startup. Once Camunda has the BPMN, it can execute it. Each running execution is called a process instance —
 think of the BPMN as a recipe and the process instance as one specific meal being cooked from that recipe. Each order has
 exactly one process instance running for it.

 From that point on, Camunda drives the order. Camunda doesn't do the actual work itself — it just keeps track of where the
 order is in the flow and tells our code "OK, now it's time to validate this order" or "now it's time to create the subscription."
 When that happens, our code does the work and tells Camunda the result. The pieces of our code that do the actual work are
 called workers. A worker is just a Java bean living inside our module that asks Camunda "anything for me to do?" on a loop,
 picks up tasks Camunda hands out, runs them, and reports the result back. We have 16 such workers in v1.0 — examples:
 order-validate checks the order is valid, order-create-subscription calls SUB-LM-01 to create the subscription,
 order-trigger-activation calls SUB-WF-ACTIVATE-01 to fire activation. The BPMN step where Camunda hands out
 work to a worker is called an external task (because the work happens outside Camunda's own process — in our module).
 When the recipe (BPMN) says "do validation here," Camunda creates an external task with topic order-validate; the
 worker subscribed to that topic picks it up, does the work, completes. Camunda then moves the recipe forward to the next
 step.

 Some steps in the flow need a human, not code. For those, the BPMN has a user task — a step that just sits there and waits
 for someone to claim it and finish it through a UI. In v1.0 we have 3 user tasks: KYC L1 supervisor approval, KYC Team
 Leader approval, Welcome Call agent task. Each user task carries an HTTP connector — a built-in Camunda feature that
 fires an HTTP POST when the task is created, so we can notify the responsible team that there's work waiting for them. (The
 connector calls back into our own module via NotificationHandlerResource, which then dispatches to
 email/SMS/Slack/Teams.)

 Some steps in the flow need to wait for an external thing to happen — a payment to be received, an install WO to be
 finalized. For those, the BPMN has a message catch event — a step that parks the process instance and goes to sleep until
 someone notifies Camunda "hey, the thing happened." The notification comes via Camunda's REST API (POST
 /engine-rest/message). Our code calls that endpoint when, for example, a Kafka consumer in our module sees
 PaymentApplied arrive on the bus — the consumer calls POST /engine-rest/message with
 messageName=PaymentReceived and the order's ID; Camunda finds the parked instance and wakes it up. We have 4
 such messages in v1.0: PaymentReceived, WorkOrderFinalized, WorkOrderCancelled,
 OrderCancellationRequested.

 Waiting can't be forever. So a message catch event is usually paired with a boundary timer — a side-step attached to the
 wait that fires after a configured duration (PT7D = 7 days, PT30D = 30 days, etc.). If the message arrives first, Camunda
 wakes the instance and proceeds normally; if the timer fires first, Camunda interrupts the wait and routes to a failure path
 (typically a mark-*-failed worker). v1.0 has 2 such timers: PT7D on payment wait (KE WIK), PT30D on install wait.

 Two more concepts. businessKey is how Camunda knows which order a process instance belongs to — we set
 businessKey = orderId when starting the instance, then we can look up the instance later by that key (e.g., when we
 need to send it a message). And Drools KJAR is a separate engine for decision rules — a .jar file holding business rules
 written in DRL (Drools Rule Language). We use it for operator-specific gateway decisions in the BPMN. The worker preceding
 a BPMN gateway calls Drools, gets back a decision (a process variable), and the BPMN gateway routes on that variable.
 Keeps operator-specific business rules out of code and out of BPMN, owned by business analysts.

 v1.0 ships the Wananchi Kenya shape: door-to-door capture + two-level KYC + pay-first + one install WO + activation. The
 architecture supports operator-specific BPMN compositions (different sequences for different operators) without code forks —
 see §2.2 for the architecture note. The condensed narrative in §2.1 walks the KE shape; each step satellite carries step-local

 The current operator scope is WIK, WUG, WTZ, YASSN. Adding a future operator: drop the operator's BPMN file, add a

 2.1 Wananchi Kenya shape — door-to-door, pay-first, two-level KYC
 The agent captures the customer's details on the Field Agent PWA and taps "Submit Order" at 09:00. The PWA POSTs to
 FUL-02 → STEP-CAPTURE: the row is written into customer_order, Camunda starts the process instance for the BPMN
 OrderCapture_WIK.

 The instance immediately advances to validation → STEP-VALIDATE: the order-validate worker (the Java code that
 checks whether the order can proceed — HomePass sellable, Package active, tech regions match, no duplicate subscription,
 customer eligible) runs the 5-check suite. All pass.

 Camunda routes to subscription creation → STEP-SUBSCRIPTION: the order-create-subscription worker (the Java
 code that asks SUB-LM-01 to create the actual subscription record) calls SUB-LM-01 POST /api/subscriptions, gets
 back sub_01HX...A.

 Then to payment computation and notification → STEP-PAYMENT: two workers run back-to-back. First
 order-compute-expected-payment (figures out how much the customer needs to pay — installation fee + first cycle
 prorate, looked up from BIL-CFG-01's BillableEvent catalog) resolves 15000 KES. Then
 order-notify-payment-instructions (just emits a Kafka event saying "this order is awaiting payment, the customer
 should be told how to pay") emits sophix.orders.awaiting-payment; DD_NOT-01 picks that event up and sends the
 customer the M-Pesa paybill instructions via SMS+email. The BPMN now parks at a wait-payment step (a message catch
 — a place the recipe goes to sleep until "payment received" arrives), guarded by a PT7D boundary timer (a 7-day fuse — if
 the customer hasn't paid by then, the BPMN routes to cancellation).

 At 11:23 the customer pays. BIL-01-PAY-01 (the billing module's payment application service) emits PaymentApplied on
 Kafka. PaymentAppliedConsumer (our module's Kafka consumer for that event — Java code subscribed to the topic, runs
 in our module) sees the event, looks up which order it belongs to (by subscription_id), then calls Camunda's POST
 /engine-rest/message to wake the parked instance with message name PaymentReceived. Camunda wakes the
 BPMN.

 The BPMN advances to the first KYC user task → STEP-KYC: a user task is a step that waits for a human. Camunda creates
 kyc-l1-supervisor-approval and fires its HTTP connector (the built-in Camunda feature for notifying when a user task
 appears — see §1) at our NotificationHandlerResource endpoint, which dispatches an email/SMS/Slack to the L1
 supervisor (candidate group kenya-l1-kyc in FOUNDATION_AUTH). The supervisor opens BO UI, reviews, clicks
 Approve; BO UI calls our completion endpoint which forwards the completion to Camunda. The BPMN advances to the next
 user task kyc-team-leader-approval, dispatched to kenya-kyc-leaders. Same flow. KYC complete.

 Camunda routes to install WO creation → STEP-INSTALL: the order-create-install-wo worker (Java code that
 resolves equipment requirements via PLM-CFG-01 — for this triple-play package: GPON_ONT + ATA — then asks the WO
 module to create the install Work Order; v1.0 uses an install_wo_stub table because the WO module DD isn't built yet)
 creates the install WO, emits OrderInstallDispatched. The BPMN parks at wait-install-finalize (another
 message catch) with a PT30D boundary (30-day fuse). Three hours later the contractor finalizes the install; the WO module
 emits WorkOrderFinalized on Kafka; WorkOrderFinalizedConsumer (the matching Kafka consumer in our module)
 wakes the BPMN by calling Camunda's /engine-rest/message.

 Camunda routes to activation → STEP-ACTIVATION: the order-trigger-activation worker calls
 SUB-WF-ACTIVATE-01 to start activation and receives an operation id quickly. FUL-02 must not hold an HTTP call open
 while the full activation saga runs. The BPMN waits for the activation completed/failed event correlated by order id,
 subscription id, and operation id. After completion, the order-notify-success worker sets current_phase =
 ACTIVATED, emits sophix.orders.activated; DD_NOT-01 sends the customer the "service is live" SMS+email.
 Camunda closes the process instance.

 Total elapsed: 5h 25min. Active worker + Camunda time: under 30s — the rest is the customer paying (2h) + install dispatch
 wait (3h).

 2.2 Architecture note — other operator shapes are supportable
 v1.0 ships the KE WIK shape (§2.1). The architecture is deliberately operator-agnostic at the worker level: workers are
 primitives (e.g., order-validate, order-create-subscription, order-compute-expected-payment,
 order-create-install-wo, order-trigger-activation) that don't know what shape they're running in — they read
 process variables, do their work, report back. The shape comes from the BPMN.

 A different operator could therefore compose the same primitives differently — for example, a deployment that wants a
 welcome-call qualification step before payment, or one that wants to defer subscription creation until a feasibility survey
 confirms the install can happen. Such a deployment would (a) write its own OrderCapture_{OPERATOR}.bpmn, (b)
 potentially add new worker types or user-task user-task types as new step satellites, (c) add operator-specific candidate


SOPHIX BSS Design Documents                                                                                                    Page 6
 groups in FOUNDATION_AUTH. The existing workers stay unchanged.

 v1.0 does NOT ship any of those alternative shapes. They are mentioned only to confirm the architecture supports them as
 future work, without that future work requiring rewrites of FUL-02's existing v1.0 deliverables.

 2.3 Cancellation applies across the journey
 A cancellation may be requested at any phase before ACTIVATED → STEP-CANCELLATION: when the cancel API is hit (or
 the PT7D payment timer fires), Camunda gets a message and the BPMN's top-level interrupting boundary event fires — a
 fancy way of saying the recipe has an emergency stop attached to the whole flow. It interrupts whatever step was running.
 Camunda then routes to order-cascade-cancellation (a worker that reads what state the order reached and undoes
 downstream things one by one: terminate the subscription if one was created, cancel the install WO if it exists, emit a refund
 request if money was received).

 Cross-step mechanisms — Camunda primitives, the cancellation pattern, phase projection, per-operator BPMN composition
 rules, the notification handler endpoint contract, the shared schemas — live in the FRAMEWORK satellite.

 Workshop sources: Customer Management deep dive (2026-04-27 / 2026-04-28); Provisioning deep dive (2026-04-30).

 Order capture workflow Wananchi Kenya needs:

     Wananchi Team Leader. Future IPRS integration for OCR-driven automation.

   - Pay-first invariant: contractor not dispatched until customer payment is received.

   - Work Order machinery (workshop verbatim — what Wananchi KE operationally needs):

   - One WO per assignment event — created systematically.

   - Equipment-delta rule: no equipment delta = audit-trail-only WO; delta ≠ 0 = contractor WO.

   - WO routing: BO → Contractor Slot (auto-assigned by Tech Region from HomePass + WO scope + availability) → Team
     Slot (contractor picks own team) → contractor Dispatcher FINALIZES → commands pushed to network through NMS.

   - Basic WO catalog (clone-extendable): Activation, Change of Service, Change Bill Cycle, Installation, Follow-Up.

   - Equipment follows the WO: same region/tech → equipment kept; otherwise re-attached to customer at FINALIZE.

   - Multi-DB observation from workshop (verbatim): same client supports multiple operator databases ("Database: Sibanand
     Trading alongside Zuku Kenya"). Open workshop question (verbatim): *"relationships with other fiber operators in the
