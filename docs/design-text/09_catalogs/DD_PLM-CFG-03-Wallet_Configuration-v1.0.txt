 1. What this process is about
 A Wallet is a deployment-configurable category of monetary-equivalent value held by the customer. Every wallet's balance is
 denominated in a currency (or in points convertible to a currency at a configured rate) and is used at charging time to settle
 the customer's obligations. The catalog tells downstream modules what wallets EXIST, how they BEHAVE (refill, expiry,
 negative-balance allowance, charging precedence, points-to-currency conversion where applicable), and what they
 REPRESENT in finance terms. The actual per-customer balances (the ledger) live in a separate billing sub-module (future
 BIL-06 / WAL-OP), out of scope here.

 The value held in a wallet originates from one of several sources, each with distinct finance and operational semantics:

   - Customer top-up — money the customer paid in (cash, card, mobile money, bank transfer). The "real money" balance.

   - Operator-granted bonus — money the operator gifted as a goodwill or retention credit. Spent like money but tracked
     separately for finance reconciliation.

   - Promotional credit — one-shot, time-limited grants (welcome bonus, referral reward, campaign credit). Typically charged
     against first because they expire.

   - Refundable deposit — money held at install against contract termination or equipment damage. Cannot be spent by the
     customer; only the operator moves funds in or out. Finance treats this as a balance-sheet liability.

   - Loyalty points — earned through activity (longevity, payments, referrals), stored as points internally and converted to
     currency at charging time via a per-wallet conversion rate.

   - SLA-driven service credit — operator-issued compensation for service-level breaches. Tracked separately to
     demonstrate SLA compliance and to keep it out of normal bonus/promo accounting.

   - Hardware buyback credit — issued when a customer returns equipment in good condition at contract end. Redeemable
     against future purchases or refundable.

 The wallet does NOT hold data MB, voice minutes, or SMS counts. Those are bucket-style allowances, modeled separately
 (deferred to a future DD). The model here is intentionally money-only — one numeric balance per (customer, wallet) used at
 charging time.

 The wallet is the unit of value the charging path uses. When a Service or charge runs, fulfillment / billing picks the right wallet
 from the catalog by reference (walletRef), reads the customer's current balance from BIL-06's ledger, and applies the rules
 defined in PLM-CFG-03 (can balance go negative, precedence among multiple eligible wallets, expiry behavior, refill-from
 rules). The catalog is therefore the source of truth for "what wallets does the deployment offer and how do they behave".

 PLM-CFG-03 scope. Wallet catalog admin: create, read, update, soft-delete, plus audit and lifecycle (DRAFT → ACTIVE →
 RETIRED). No workflow, no maker-checker, no Camunda. Pure catalog CRUD with DRL rules at every state transition.
 Wallet types are themselves a sub-catalog — admins seed and extend per deployment, identical pattern to
 homepass_status_code in RLM-CFG-01.

 implementation. Each rule has an ID; failures return BUSINESS_RULE_ERROR with the rule ID in the response.

 All defaults are monetary-equivalent. The unit is currency in all cases except LOYALTY_POINTS, where the unit is points
 and a per-wallet conversion rate (R-W-15) translates points to currency at charging time.

 The applicability defaults reflect a natural separation: top-up wallets (MONEY, BONUS, PROMO) are inherent to the
 prepaid model — a postpaid customer doesn't top up because the operator extends credit instead. Ancillary wallets
 (DEPOSIT, LOYALTY_POINTS, SERVICE_CREDIT, BUYBACK_CREDIT) apply equally to both billing modes — a customer's
 deposit is held regardless of mode; loyalty points are earned by anyone; SLA service credit is issued to anyone; buyback
 credit is issued to anyone returning equipment.

 A deployment may seed fewer types (e.g. only MONEY and DEPOSIT for an operator that doesn't run promos or loyalty), or
 add types unique to its product mix. Common future additions:

   - WHOLESALE (typically PREPAID_ONLY) — for B2B reseller prepaid balances if Wananchi enters the wholesale market

   - A postpaid-specific goodwill credit (typically POSTPAID_ONLY) — for operators that want to issue corporate goodwill that
     should never affect prepaid charging

   - Other operator-specific credit categories (e.g., EARLY_TERMINATION_FEE_WAIVER, REFERRAL_BONUS split from
     generic PROMO)

 The catalog is admin-managed; new types and applicability rules do not require a code release.

 B — Current TZ
 TZ Sophix has no Wallet entity at all. The TZ system is fundamentally postpaid: it issues PRO FORMA invoices at the cycle
 close (per BIL-01 / QuartzGenerateCycle), runs Quartz-driven dunning waves (BIL-03 / BIL-04) for unpaid invoices,
 and ultimately suspends customers via AAA when dunning escalates. No prepaid funding, no wallet ledger, no balance-based
 suspension.

 The wallet concept is not in the TZ codebase. Sources:

   - The Sophix V3 Format GAP analysis (G-04-1) explicitly classifies the wallet module as an XL net-new effort: *"Module
     structurant et nouveau. Nécessite un nouveau microservice (sofxWallet) ou une extension lourde de sofxInvoicing. Gère
     le ledger source-of-truth, la concurrence, les buckets, l'audit trail."* 8 sprints estimated, priority P1.

   - The same GAP analysis states the structural gap as: *"Le modèle prépayé wallet TVD de Wananchi (auto-debit,
     auto-settle, pas de dunning postpaid) est radicalement différent du modèle Sophix TZ qui est principalement postpaid
     (PRO FORMA invoice, dunning B2C/B2B avec waves Quartz, suspension AAA). C'est l'écart structurant qui définit la
     majeure partie de l'effort."*

   - The wallet taxonomy (TVD for Internet/TV, Phone for Voice) comes from Broadhub (BH) / Wananchi Kenya, not from TZ.
     It's documented in the BH business-process module (APPFREESN-Module_Billing) and the eTOM business-process
     review for Wananchi, both describing the *target* environment.

 So the V3 effort is not "modify the TZ wallet" — it's "introduce a wallet catalog and engine that doesn't yet exist in the
 codebase, drawing the model from Wananchi's existing Broadhub patterns and generalizing it for multi-deployment use".

 What does exist in TZ Sophix today that is adjacent:

   - sofxInvoicing owns the postpaid invoice lifecycle: PRO FORMA generation, payment intake, dunning. Reusable as the
     postpaid path going forward (separate DDs).

   - PaymentResource with callback handling (Mixx by Yas and generic webhooks) for inbound payments — reusable for the
     prepaid recharge intake once it's repurposed to credit a wallet instead of settle an invoice (per GAP G-05-1).

   - Cash Drawer module for shop / cash payments — reusable.

   - No wallet entity, no wallet ledger, no recharge-to-balance flow, no auto-settle-from-wallet flow.

 The Wananchi target is documented in the Broadhub materials:

   - Two operational wallets per customer in BH/KE today: TVD (Internet + TV settlement at cycle close) and Phone (Voice
     usage-based debit). The Voice wallet drains as the VoIP switch rates calls; the Internet/TV wallet drains at bill cycle close.

   - Refund mechanics via "ADJ" (adjustment) entries on the customer ledger — credits posted with mandatory notes,
     thresholds requiring approval. The Wananchi GAP documents a negative wallet ADJ avec note obligatoire
     pattern for refund debit-notes (BP-06), but this is a ledger entry sign convention (credit positive, debit-note negative),
     NOT a "wallet that can go below zero". The wallet balance itself is always non-negative; debit-notes net out
     previously-posted credits and the wallet is recomputed.

   - No applicability distinction in BH today — wallets are implicitly prepaid because BH/Wananchi operates a
     pure-prepaid model. V3 generalizes by adding applicability so the same catalog can serve future deployments that
     also need postpaid (e.g., a future B2B segment with corporate billing terms).

 V3 builds the wallet catalog from scratch as an extension of the plm module, generalizing the BH patterns and supporting
 both billing modes via the applicability field. Postpaid AR / dunning / invoicing concerns are handled by separate DDs
 (existing TZ sofxInvoicing + BIL-04 dunning, generalized as needed) — not by this DD.

 Migration approach
 TZ Sophix Services carry free-text wallet values that conflated allowance-buckets and money pools. V3 separates the two
 concerns: this DD handles only the monetary wallets; non-monetary allowances (data MB, voice minutes, SMS count) are
 deferred to a future Bucket DD. V3 migration for the wallet half:

   1. Seed wallet_type with the default 7 monetary types (MONEY, BONUS, PROMO, DEPOSIT, LOYALTY_POINTS,
     SERVICE_CREDIT, BUYBACK_CREDIT).

   2. Audit TZ wallet field values across Service defs. Classify each value as either (a) a monetary-equivalent pool that
     maps to a V3 wallet, or (b) an allowance bucket deferred to the future Bucket DD. Common monetary mappings: TZ
     free-text balance/credit fields → V3 MONEY_<currency>, deposit fields → V3 DEPOSIT_<currency>.

   3. Seed wallet with one entry per (monetary type, currency) pair the deployment needs (e.g., MONEY_KES, BONUS_KES,
     PROMO_KES, DEPOSIT_KES, LOYALTY_POINTS_KES for a single-currency KE deployment).

   4. Rewrite Service defaultWallet values from the free-text strings to the new wallet code references (handled in
     PLM-CFG-01's migration, not here).

   5. Set sensible defaults on each wallet: MONEY / BONUS / PROMO get applicability = PREPAID_ONLY and
     refillable = true. PROMO gets expires = true with a deployment-specific period and lower precedence (e.g. 50)
     so it's spent first. DEPOSIT / LOYALTY_POINTS / SERVICE_CREDIT / BUYBACK_CREDIT get applicability = ANY.
     LOYALTY_POINTS gets pointsToCurrencyRate per the loyalty programme design. No wallet has a negative-balance
     configuration — wallet balances are always non-negative.

   6. Per-currency wallet split: a deployment offering multiple currencies seeds one wallet per (type, currency) pair
     (MONEY_KES, MONEY_TZS, ...). The wallet code carries the currency suffix by convention.

 The migration runs once at V3 cutover; thereafter, the catalog is admin-managed.

 What's NEW in V3 / not in TZ Sophix
   1. First-class wallet catalog with a full DRAFT → ACTIVE → RETIRED lifecycle, replacing TZ's implicit string field.

   2. Configurable wallet_type sub-catalog — admins seed and extend; no code release to add new types.

   3. Per-wallet ISO 4217 currency — multi-currency deployments seed one wallet per (type, currency) pair.

   4. Per-wallet operational rules (applicability, expires, expiry_period_days, refillable,
     charging_precedence, points_to_currency_rate) — replaces hardcoded billing logic with configurable catalog
     data. Wallet balance is always non-negative by design; the V3 target BSS does NOT model wallets that can go below
     zero.

   5. Code immutability once referenced — Services / Packages / Discounts cross-reference by walletRef; changing a
     wallet code would break those refs, so once referenced, code is locked.

   6. Standard Kafka events for every catalog state change — downstream caches stay coherent without coupling.

   7. Rule-based validation — every catalog operation runs DRL rules; failed rules return structured
     BUSINESS_RULE_ERROR responses with rule IDs.

   8. Wallet-only model (no Bucket entity) — V3 V3 keeps it simple: the wallet has a single monetary balance used at
     charging time. If a future deployment needs the Bucket allocation pattern (free vs purchased vs promotional within one
     wallet), a separate DD adds it without changing this one.
