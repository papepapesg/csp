 1. What this module is
 OSR-RMA-01 is the operator's home for every workflow where a serialized piece of equipment moves OUT of a customer's
 premises — whether it's being replaced (HFC swap), unbound remotely and reused (GPON remote swap), retrieved
 end-of-life (EQP for termination), or upgraded (EQU tech upgrade). The module sits on top of OSR-INSTANCE-01 (instance
 lifecycle) and OSR-01 (SKU+qty stock), orchestrating the per-instance state transitions and the contractor-routing of
 recovered units that those modules can't decide on their own.

 The defining design constraint is that the four flows look 80% the same operationally — same Camunda primitives, same
 eligibility checks, same notification fanouts, same contractor-stock routing — but diverge sharply in their technology-specific
 provisioning (Broadhub slot/port preservation for HFC vs NMS remote unassign for GPON) and in their customer-facing intent
 (defect swap vs termination retrieval vs upgrade). The module split into framework + four satellites reflects that: shared
 infrastructure in one place, per-flow specifics each in their own document so a sprint team can pick up SWAP-HFC without
 dragging the full module weight into their context.

 The module also solves a specific, documented operational pain: ~40+ stale equipment items in Wananchi KE today because
 unassigned recovered equipment auto-routes to the main warehouse instead of the contractor team's warehouse that
 physically retrieved it (workshop 2026-04-30, Customer Management deep dive). OSR-RMA-01 closes this gap by recording
 the recovering contractor on the swap-request AND on the per-instance lifecycle event, then routing the recovered unit back

 to that contractor's van. The routing-decision-recovered-instance-routes-to-recovering-contractor
 Drools rule in the framework is the explicit codification.

 What this module does
   1. Orchestrates four distinct swap flows — SWAP-HFC, SWAP-GPON, EQP (Equipment Pickup), EQU (Equipment
     Upgrade). Each is a Camunda BPMN process with technology-specific service tasks, user tasks, and message catches.
     Per-flow BPMN definitions live in the satellite DDs; the framework provides the shared workers + Drools.

   2. Validates eligibility before committing field resources — warranty status, customer billing state, subscription state,
     source/target SKU compatibility. Failed eligibility transitions the swap-request to FAILED with a specific failure code; no
     slot is reserved, no WO is created, no truck rolls.

   3. Reserves contractor capacity atomically — calls EM-02 POST /api/contractor-slot-commitments with the
     resolved contractor for the customer's tech region. Slot is released on cancellation; capacity is freed.

   4. Creates and tracks Work Orders for field visits — through WO-01 with new job types EQUIPMENT_SWAP,
     EQUIPMENT_PICKUP, EQUIPMENT_UPGRADE. WO finalization fires a message back into the swap-request BPMN.

   5. Drives per-instance lifecycle transitions — every state change (source recovered, target placed, RMA shipped) calls
     OSR-INSTANCE-01 POST /api/equipment-instances/{id}/lifecycle-events. The contractor_id is carried
     on every recovery event.

   6. Routes recovered units to the recovering contractor's warehouse — closes the documented 40+ stale-equipment
     gap. The contractor-stock-route worker reads recovery_contractor_id and writes both an OSR-01
     stock_movement (SKU+qty) and an OSR-INSTANCE-01 lifecycle event (per-serial) in the same transaction.

   7. Calls provisioning adapters for OSS configuration — HFC: Broadhub serial unbind/rebind with slot/port preservation
     (UC-PR4). GPON: NMS ONT unassign / bind. Adapters are operator-configurable stubs in v1.0; real OSS integration
     deferred.

   8. Applies charges or refunds via BIL-01 — chargeable swaps (out-of-warranty, customer-caused damage, upgrade fees)
     call BIL-01 on completion. EQP termination triggers deposit refund (or forfeiture in EQR case).

   9. Notifies customer and internal staff — NOT-01 for customer-facing messages (appointment confirmation, completion,
     EQR equipment-return-required reminder); ICN-01 for internal candidate groups (swap-dispatchers, field-techs,
     noc-team).

   10. Captures vendor-RMA handoff metadata — v1.0 STUB. When defective units are batched and shipped to vendor, the
     vendor_rma_stub row records the handoff. Per-vendor SLA tracking and return-batch matching are deferred to a future
     expansion.

 What this module does NOT do
   - Doesn't orchestrate initial installation. Installation is FUL-02's responsibility. OSR-RMA-01 takes over only when
     equipment is leaving the customer (or being upgraded in place).

   - Doesn't handle Trouble Tickets. A ticket may trigger a swap (customer reports defect → ticket → ticket triage decides
     swap needed → ticket creates swap-request), but the ticket workflow lives in ASR-01 (pending). OSR-RMA-01 only
     handles the swap itself.

   - Doesn't make warranty decisions. Warranty status comes from PLM-CFG-06 (SKU + warranty period) + the source
     instance's created_at / current_state history. The eligibility worker reads these and resolves to a chargeable-or-not
     flag; the actual charge code is from BIL-01's catalog. OSR-RMA-01 doesn't define warranty policy.

   - Doesn't run vendor portals. The vendor_rma_stub is a back-office UI for ops to record what they shipped. Real-time
     vendor portal integration (vendor-issued reference numbers, vendor-side status updates, vendor-promised return dates) is
     deferred.

   - Doesn't allocate inventory. When a swap needs a target instance, the swap-request's source caller (e.g., the satellite's
     POST endpoint) is responsible for resolving an available unit from OSR-INSTANCE-01 (filter
     current_state=IN_CONTRACTOR_STOCK for the recovery contractor, or IN_MAIN_WAREHOUSE for cross-contractor
     swaps). OSR-RMA-01 then sets that instance's state to RESERVED_FOR_WO. The allocation strategy (FIFO? LIFO?
     closest van?) is owned upstream.

   - Doesn't span operators. A swap is operator-scoped. Cross-operator transfers (an instance moves from WIK to WUG
     warehouse) are out of v1.0 scope.

 3. Per-flow condensed narratives
 3.1 SWAP-HFC — HFC field-pickup swap
 When: Customer reports defect with HFC equipment (cable modem, MTA, STB, smart card), OR scheduled tech upgrade
 within HFC, OR proactive replacement by NOC.

 Trigger: NOC agent / customer-care agent creates swap-request via satellite's POST /api/swap-requests/hfc. Source
 instance MUST be HFC-family (equipment_kind IN (CABLE_MODEM, MTA, STB, SMART_CARD)); target instance
 pre-resolved by caller.

 Flow:

   1. Eligibility check — warranty status, customer billing state, source instance currently IN_FIELD_ACTIVE or
     IN_FIELD_DEFECTIVE, target instance currently IN_CONTRACTOR_STOCK for the resolved contractor (or
     IN_MAIN_WAREHOUSE for cross-contractor). HFC-specific: source's network_slot_metadata.{cmts, slot,
     port} MUST be present; copied to swap-request flow_payload. Eligibility worker resolves chargeable flag +
     charge_code + customer_charge_amount (chargeable when warranty void / customer-caused damage).

   2. Pay-first gate (chargeable only) — if chargeable=TRUE, worker bil01-charge-pre-authorize creates BIL-01
     billable event; swap-request transitions to AWAITING_PAYMENT. Customer notified by NOT-01 with payment link. No slot
     reserved, no contractor dispatched until BIL-01 emits BillableEventPaid (Wananchi "wallet funding gate" —
     workshop 2026-04-28). Payment timeout (default 7 days) cancels the swap. Free swaps (warranty / system fault) skip this
     step.

   3. Slot reservation — call EM-02 to reserve a contractor slot in the customer's tech region. recovery_contractor_id +
     slot_commitment_id populated.

   4. WO creation — call WO-01 POST /api/work-orders with wo_kind=EQUIPMENT_SWAP_HFC,
     origin_ref=swap_request_id. WO is dispatched per WO-01-FLOW-INSTALLATION-like pattern (claim → dispatch
     → assign tech).

   5. Customer appointment confirmation — NOT-01 sends customer SMS / email with appointment slot. Customer reply
     (accepted / rejected) routes via inbound webhook to the BPMN message catch.

   6. Field visit in progress — tech arrives, calls tech-confirm-defect user task. Confirms defect; advances
     swap-request to FIELD_VISIT_IN_PROGRESS.

   7. Source recovery — tech removes the old modem. Worker instance-state-transition advances source instance
     IN_FIELD_ACTIVE → RECOVERED_BY_CONTRACTOR with contractor_id set. Worker
     contractor-stock-route writes the stock_movement (van location) and per-instance lifecycle. THE ROUTING FIX
     HAPPENS HERE.

   8. Target placement — tech installs the new modem on the SAME slot/port (UC-PR4). Worker advances target instance
     RESERVED_FOR_WO → IN_FIELD_ACTIVE bound to customer.

   9. Provisioning — Broadhub serial rebind — worker serial-rebind-broadhub-stub calls the Broadhub adapter:
     unbind old CM-MAC (+ MTA-MAC if hybrid chassis), bind new CM-MAC at the same {cmts, slot, port}. For
     static-IP packages, double-config (Broadhub + Clearcable NOMS) — adapter handles both calls.

   10. Completion — swap-request advances to COMPLETED. Payment has already been collected at step 2 (if chargeable).
     NOT-01 sends customer "swap complete" notification. WO finalized.

 Failure paths: Broadhub rebind fails 3 attempts → FAILED, source rolled back to van (IN_CONTRACTOR_STOCK), target
 rolled back to van. Customer rejects appointment 3 times → FAILED with reason. Tech reports source not present at
 premises (customer already moved / damaged unrecoverably) → manual triage path.

 Detail: see DD_OSR-RMA-01-FLOW-SWAP-HFC-v1.0.md.

 3.2 SWAP-GPON — GPON swap (remote-first, field fallback)
 When: Customer reports defect with GPON ONT, OR scheduled tech upgrade within GPON, OR proactive replacement.

 Trigger: Same as HFC but on GPON-family source. Caller creates via satellite's POST /api/swap-requests/gpon.

 Flow (remote-first happy path):

   1. Eligibility check — same primitives as HFC, except no slot/port preservation requirement (GPON uses OLT
     auto-discovery, ONT serial is the only authentication signal). Source's network_slot_metadata.{olt, frame,
     slot, port} copied to flow_payload for traceability. Eligibility resolves chargeable + charge_code.

   2. Pay-first gate (chargeable only) — same as SWAP-HFC step 2. AWAITING_PAYMENT → AWAITING_SLOT on
     BillableEventPaid.

   3. Remote unassign attempt — worker nms-remote-unassign-stub calls the NMS adapter. If success, advance to
     SOURCE_RECOVERED (source instance IN_FIELD_ACTIVE → IN_FIELD_DEFECTIVE since the unit is physically still
     at premises but no longer in service). NOC user task noc-confirm-remote-success asks NOC to confirm customer
     plan for self-swap.

   4. Customer self-swap — NOT-01 sends customer instructions + appointment for new ONT pickup at shop / courier
     delivery. Customer picks up new ONT and self-installs. Worker nms-remote-bind-stub binds the new ONT serial in
     NMS once customer reports it online.

   5. HomePass network-path update — worker homepass-network-path-update calls HomePass-CFG PATCH
     /api/homepasses/{id}/network-path/ports updating the terminal ONT node's code from old serial to new ONT
     serial. Mandatory for GPON swaps (the HomePass.network_path terminal node is the system-of-record for which ONT
     serves the address).

   6. Old ONT recovery — at next shop visit or courier pickup, old ONT collected. Worker contractor-stock-route runs
     with recovery_contractor_id set (the contractor who collected the old unit, even via shop). Source instance
     IN_FIELD_DEFECTIVE → RECOVERED_BY_CONTRACTOR → IN_CONTRACTOR_STOCK. Target RESERVED_FOR_WO
     → IN_FIELD_ACTIVE bound to customer.

   7. Completion — same as HFC.

 Flow (field fallback path): If customer can't / won't self-swap (NOC user task receives
 customerSelfSwapConfirmed=false):

   - Advance to SLOT_RESERVED → WO_CREATED → FIELD_VISIT_IN_PROGRESS, same as HFC pattern thereafter.

   - The remote-attempt timer + retry logic is in the BPMN; if 3 remote-attempt failures, automatic field fallback.

 Detail: see DD_OSR-RMA-01-FLOW-SWAP-GPON-v1.0.md.

   1. Eligibility check — source instance IN_FIELD_ACTIVE or IN_FIELD_DEFECTIVE, subscription

 3.4 EQU — Equipment Upgrade
 When: Customer-initiated tech upgrade (DOCSIS 3.0 → 3.1, ONT v1 → v2, STB → STB-4K), OR operator-initiated (e.g.,
 end-of-life of an SKU forces mandatory replacement campaign).

 Trigger: Sales / customer-care agent creates via POST /api/swap-requests/equ. Caller specifies upgrade_from_sku
 and upgrade_to_sku in flow_payload. Source = customer's current device; target = a pre-allocated upgrade unit from
 contractor stock.

 Flow:

   1. Eligibility check — source SKU compatible with upgrade-to SKU (PLM-CFG-06 cross-check via equipment_kind and
     operator-configured upgrade paths), customer billing state ACTIVE, no outstanding upgrade-fee unpaid, upgrade-fee
     resolved via BIL-01 catalog. Always chargeable: chargeable=TRUE, charge_code = upgrade-fee code,
     customer_charge_amount = upgrade fee + deposit delta (if any).

   2. Pay-first gate — mandatory for EQU. Worker bil01-charge-pre-authorize creates BIL-01 billable event covering
     upgrade fee + deposit delta. Customer-care confirms with customer; customer pays via configured channels.
     AWAITING_PAYMENT → AWAITING_SLOT on BillableEventPaid. This codifies the Wananchi upgrade flow
     (workshop 2026-04-28): CC quotes price → customer pays → BO operates the change → WO scheduled.

   3. Slot reservation + WO creation — same field-visit pattern with wo_kind=EQUIPMENT_UPGRADE.

   4. Field visit — tech swaps old for new. Worker advances both instances; routing-back via contractor-stock-route.
     The OLD instance is NOT necessarily defective — typically returned to main warehouse for re-deployment after
     inspection.

   5. Provisioning — same per-tech path (HFC: Broadhub rebind, slot/port preservation per UC-PR4 if HFC upgrade-to is
     HFC; GPON: NMS unassign + bind, plus HomePass network_path terminal-node update for GPON upgrades).

   6. Completion — customer notified. Source instance returns to main warehouse for inspection; if good, re-enters
     IN_MAIN_WAREHOUSE pool.
