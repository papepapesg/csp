 1. Purpose
 This HLD replaces the older SOPHIX V3 high-level design that was written before the DDs were finalized.

 The previous replacement was intentionally compact. This version is the fuller HLD: it shows the module landscape, explains
 why the main design choices exist, and illustrates how modules work together to deliver BSS features.

 Use this document as the entry point for:

   - architects checking module boundaries;

   - developers deciding which DD/API owns a behavior;

   - frontend teams designing backoffice, CRM, sales, contractor, and self-care features;

   - operations teams sizing and monitoring the platform;

   - product owners reviewing end-to-end feature behavior.

 Process detail remains in the individual DDs and their developer implementation guides. This HLD explains how those DDs fit
 together.

 Recommended reading order:

   1. This HLD.

   2. APPFREESN-PROCESS_MODULE_MAP-DD_ALIGNED-20260528.

   3. Foundation DDs.

   4. The specific module/process DD and DEV_IMPL_GUIDE for implementation.


 2. Executive View
 SOPHIX V3 is a modular BSS. Each business capability owns its data, APIs, workflows, events, and UI responsibilities.
 Long-running operations are orchestrated by Camunda. Policy decisions that vary by operator or product are externalized to
 Drools. Business state is stored in PostgreSQL. Kafka carries facts after they are committed. Redis is a non-authoritative
 cache only.

 2.1 Module Communication And Performance Position
 The system has many modules, but it is not designed as all-to-all synchronous communication. Each user journey has one
 command owner and a small number of supporting reads. The communication model is:

  Communication type                         Used for                                                Performance rule

  REST/internal API                          Commands and current state reads from the owning        Keep synchronous chains short. A command should
                                             module.                                                 not call many modules in a deep chain.

  Kafka events                               Facts after commit, reporting feeds, cache              Use outbox/inbox and idempotent consumers. Do
                                             invalidation, downstream reactions.                     not use Kafka as a hidden command bus.

  Redis/cache                                Reference/catalog reads, session data,                  Cache is not source of truth. State-changing
                                             read-through acceleration.                              decisions must revalidate against the owning
                                                                                                     module.

  REP-01 reporting mart                      Dashboards, exports, cross-module metrics,              Do not fan out reporting screens to operational
                                             management views.                                       modules.

  BFF/read aggregator                        Customer 360 and dense backoffice screens if            Aggregates reads only; does not own business
                                             latency becomes high.                                   state.


 Practical implication: a Backoffice Customer 360 screen may show data from ILM, SUB, BIL, TCK, WO, OSR, and NOT, but
 those calls should be panelized, timeout-protected, and optionally served by a read aggregator. A payment command,
 activation command, ticket command, or stock command still goes to the owning module only.

 The main performance risks are not the number of DDs. They are:

   - long synchronous call chains inside commands;

   - dashboards querying operational modules instead of REP-01;

   - reading another module database directly instead of using APIs/events/read models;

   - treating every worker topic as a separate pod;

   - using Camunda or Drools for simple deterministic logic.

 The mitigation is explicit in the DD set: one write owner per business object, outbox/inbox events, consolidated worker pools
 for low-volume tasks, REP-01 for analytics, cache only for non-authoritative acceleration, and BFF/read aggregation only for
 frontend read composition.

 6. Core Design Choices
 6.1 Why ILM Owns Customer
 Customer data is required by billing, subscription, fulfillment, work order, notification, and CRM-style screens. If billing owns
 customer, every non-billing domain becomes financially coupled. ILM Customer Service is therefore the customer/account
 source of truth.
 Implications:

   - Billing reads customer/account by ILM API or approved client wrapper.



SOPHIX BSS Design Documents                                                                                                                        Page 4
   - SUB-LM stores account_id as the operational anchor and customer_id as denormalized identity/search context,
     without cross-module foreign keys.

   - Billing invoices, payments, dunning, work orders, and equipment bindings use account_id for operational partitioning.

   - Customer 360 assembles data from ILM, TCK, SUB-LM, BIL, FUL, WO, OSR, and NOT APIs.

 6.2 Why SUB-LM And SUB-WF Are Separate
 SUB-LM is the subscription source of truth. SUB-WF is the operation framework that starts and tracks lifecycle/MACD
 workflows.

 This separation prevents workflow complexity from corrupting master data ownership.

 SUB-LM owns:

   - subscription row;

   - subscription status fields;

   - cycle fields;

   - master fields;

   - restrictions catalog and active restrictions;

   - low-level subscription events.

 SUB-WF owns:

   - operation row;

   - idempotency key and request hash;

   - in-flight operation checks;

   - operation history and status;

   - Camunda process instance id;

   - cancel/interrupt handling;

   - operation-level success/failure events.

 6.3 Why FUL Owns Order Capture
 New customer acquisition touches customer capture, package eligibility, HomePass, KYC, payment, installation, subscription
 creation, and activation. It is not just a subscription operation.

 FUL-02 owns the onboarding/order orchestration because it coordinates fulfillment readiness before activation. Once
 onboarding finishes:

   - ILM owns customer/account;

   - SUB-LM owns subscription;

   - BIL owns payment/invoice state;

   - WO owns field execution history;

   - OSR owns equipment;

   - FUL owns fulfillment execution records.

 6.4 Why WO And OSR Are Separate
 Work orders answer: who went where, when, did what, and with what outcome?

 OSR answers: where is the equipment, what serial is it, what state is it in, and who is responsible for it?

 Keeping them separate avoids mixing field workflow state with inventory/accounting-grade equipment state.

 6.7 Why TCK Owns Tickets
 Customer Service interactions and notes are not enough for support operations. A ticket is an accountable work item: it has a
 category, priority, SLA, owner, assignment queue, linked entities, attachments, comments, status, timeline, and resolution. It
 may also create a Work Order when field intervention is needed.

SOPHIX BSS Design Documents                                                                                                Page 5
 TCK owns the case lifecycle. WO owns field execution. A technical ticket can call WO-01 POST /api/work-orders, then
 TCK waits for WO events such as WorkOrderFinalized before resolving or reviewing the ticket.

 This keeps the helpdesk/customer-care process separate from the field execution process while linking them through explicit
 APIs and events.

 6.5 Why Camunda And Drools Are Both Used
 Camunda is for process orchestration:

   - timers;

   - human tasks;

   - compensation;

   - message catches;

   - retryable worker tasks;

   - long-running multi-module workflows.

 Drools is for decisions:

   - eligibility;

   - operator-specific policy;

   - dunning stage decisions;

   - tax/fee/discount applicability;

   - flow branching decisions.

 Drools rules must be side-effect free. They receive facts and return decisions. They do not call HTTP APIs, query databases,
 publish Kafka, or write files.

 6.6 Why Outbox/Inbox Is Required
 A domain event is only true after the business state commits. Publishing directly to Kafka inside business code creates a
 failure window where the database commit and Kafka publish disagree.

 SOPHIX uses:

   - producer outbox: business row and event envelope are inserted in the same local database transaction;

   - outbox dispatcher: publishes committed outbox rows to Kafka;

   - consumer inbox: deduplicates received events before processing;

   - idempotent handlers: protect against retries and replay.

 Narrative:

   1. The sales/franchise app captures prospect, HomePass, package, documents, and contact data.

   2. FUL-02 creates the order and starts its Camunda process.

   3. ILM creates or updates the customer/account and KYC references.

 8. Feature Delivery Flow - Subscription Operations
 Figure 4 shows the common runtime pattern for activate, pause, resume, terminate, upgrade, downgrade, restrict, suspend
 non-payment, relocation, and migration.

 Figure 4 - Subscription operation runtime pattern




SOPHIX BSS Design Documents                                                                                                Page 7
 Common rules:

   - The public endpoint belongs to the operation DD, for example POST
     /api/subscriptions/{subscription_id}/pause.

   - The operation API checks auth, request shape, idempotency, and current state.

   - Drools decides whether the operation is allowed and which branch/config applies.

   - SUB-WF creates the operation row and starts Camunda.

   - Camunda external-task topics call SUB-LM, BIL, FUL, OSR, and NOT through approved APIs.

   - Final business events are emitted through outbox after state commits.

 Idempotency behavior:
  Condition                                                        Behavior

  Same key, same request hash                                      Return existing operation/result.

  Same key, different request hash                                 Return 409 IDEMPOTENCY_KEY_REUSED.

  New key                                                          Reserve/insert operation before side effects.


 Design choice: the operation row is created before Camunda starts. If Camunda start fails, the operation is marked failed with
 a controlled reason. This is easier to repair than having an untracked workflow attempt.

 11. Event Consistency Pattern
 Figure 7 shows how every module publishes and consumes events.

 Figure 7 - Outbox and inbox consistency




 Producer rules:

   - Write the business mutation and outbox row in the same transaction.

   - Use a stable event id.

   - Use a stable aggregate key so event order is preserved per aggregate.

   - Do not wait for Kafka publish before returning the API response unless a DD explicitly says otherwise.

 Consumer rules:

   - Write to inbox before processing.

   - Deduplicate by event id.

   - Make the handler idempotent.

   - Keep failed inbox rows visible and retryable.

   - Do not use a cache update as proof that business state changed.

 11A.2 Caching Guidance
 Use cache for:

   - package/catalog/HomePass/reference lookups;

   - auth/runtime configuration;

   - USSD/session and frontend convenience state;

   - short-lived Customer 360 panel acceleration where freshness is labelled;

   - cache invalidation based on catalog/config events.

 Do not use cache as final truth for:

   - balances and payments;

   - subscription status transitions;

   - work order finalization;

   - equipment serial ownership;

   - ticket status;

   - approval decisions that commit money, stock, or service state.

 18. Implementation Guidance
 Recommended build order:

   1. Foundations: auth, DB, Kafka, cache, Camunda, Drools, file storage.

   2. ILM Customer Service, catalogs, package management, HomePass config, tech region registry.

   3. SUB-LM before SUB-WF.

   4. SUB-WF framework and worker catalog before lifecycle flows.

   5. Billing payment/charging/invoice basics before dunning/cycle close automation.

   6. WO framework and EM registry before FUL installation steps.

   7. OSR stock/equipment instance basics before equipment swap/RMA.

   8. FUL-02 order capture after ILM, package/HomePass, SUB-LM, payment, and WO basics exist.

   9. Subscription activation first, then pause/resume/terminate, then MACD workflows.

   10. TCK early enough that Backoffice CRM/ticketing and ticket-to-WO flows do not use notes as a fake ticket system.

   11. NOT/ICN early enough that workflows can notify customers and staff without local stubs.

   12. REP-01 before management dashboards and exports; do not use operational modules as a reporting backend.

   13. PAY-GW, PROV-INT, MED/RAT, OSR procurement/audit, ASR, CVM, and USSD according to the process map and
     implementation wave.

 The old HLD should no longer be used for ownership decisions where it conflicts with this DD-aligned HLD.
