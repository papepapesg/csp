 1. Purpose
 ASR-01 defines the technical trouble process for customer-reported service faults.

 Examples:

   - no internet;

   - slow internet;

   - intermittent connection;

   - no voice service;

   - TV/IPTV not working;

   - equipment suspected faulty;

   - repeated technical issue after recent work order;

   - area outage affecting multiple customers.

 This DD does not create a new ticketing engine. Technical trouble is implemented as a configured TECHNICAL_SUPPORT
 ticket type in TCK-01, with ASR-specific category rules, diagnostics, work-order triggers, outage handling, and optional
 billing-credit hooks.

 9. Work Order Rules
 ASR may request a support WO only when:

   - ticket type is TECHNICAL_SUPPORT;

   - category config has wo_policy != NONE;

   - required diagnostics are captured unless category has AUTO_CREATE;

   - no active linked support WO already exists, unless repeat WO is explicitly allowed;

   - customer/subscription/HomePass references are present where required;

   - user has ticket.workorder.create or equivalent permission from EM-CFG-03.

 After WO finalization:

  WO result                                                          Ticket action

  Fixed/resolved                                                     Move ticket to UNDER_REVIEW or RESOLVED based on category policy.

  Customer unavailable                                               Move ticket to WAITING_CUSTOMER.

  Network construction needed                                        Keep WAITING_INTERNAL and optionally create escalation ticket/WO.

  No fault found                                                     Move UNDER_REVIEW; customer care decides closure.

  Repeat fault flagged                                               Reopen/escalate as REPEAT_FAULT.




 10. Compensation Rules
 Compensation is optional and policy-driven.

 ASR may recommend compensation when:

   - trouble is verified as operator/network fault;

   - service impact duration exceeds configured threshold;

   - issue affected a billable active subscription;

   - ticket/WO evidence supports the claim;

   - no previous compensation was granted for the same outage period.

 ASR calls BIL-02-ADJ-01 only to create an adjustment request. BIL owns approval and credit-note generation.

 Example adjustment request context:
              {
                  "sourceModule": "ASR-01",
                  "sourceRefId": "tck-001",
                  "customerId": "CUS-100045",
                  "subscriptionId": "SUB-700045",
                  "adjustmentKind": "CREDIT_NOTE",
                  "reasonCode": "SERVICE_OUTAGE_VERIFIED",
                  "amount": 250.00,
                  "currency": "KES",
                  "scope": "AMOUNT",
                  "notes": "ASR verified 10-hour internet outage."
              }

 Self-care can expose a simplified technical support request:

 12. Infra Recommendation
 ASR-01 should run inside the TCK service/module. No separate ASR pod is required for medium budget deployment.

 Recommended deployment:

  Component                                                           Recommendation

  API                                                                 Existing TCK API pods.

  DB                                                                  Existing TCK schema with ASR config tables.

  Workers                                                             Existing TCK workers for ticket events and WO event consumers.

  Cache                                                               Optional cache for category/diagnostic config.


 AWS deployment:

   - Same ECS/EKS service as TCK.

   - Same RDS schema as TCK.

   - Same Kafka/MSK event infrastructure.

   - CloudWatch alarms for diagnostic failures, WO creation failures, and ASR SLA breach counts.



 13. Testing Requirements
 13.1 Unit Tests
   - Technical trouble category config resolves diagnostic profile.

   - Required diagnostic missing blocks WO creation.

   - Known outage link moves ticket to correct status.

   - Repeat fault detection identifies prior resolved ticket within window.

   - Compensation recommendation does not create credit directly.

 13.2 Integration Tests
   - Create NO_INTERNET ticket.

   - Capture diagnostic results.

   - Create support WO through TCK.

   - Consume WorkOrderFinalized and update ticket.

 13.3 End To End Tests
   - Call center creates no-internet ticket, diagnostic fails ONT check, WO is created, technician fixes issue, ticket resolves.

   - Customer creates self-care trouble ticket, care team links it to known outage, customer sees outage-safe status.

   - Repeat fault within 30 days is escalated as REPEAT_FAULT.



 14. Definition Of Done
 ASR-01 is complete when:

   - Technical trouble categories are seeded in TCK.

   - ASR category config and diagnostic profiles exist.

   - Diagnostic capture APIs work.

   - WO creation is gated by ASR rules.

   - WO events update the ticket timeline and status.

   - Known outage linking works.

   - Compensation recommendation can create a BIL adjustment request without directly crediting customer.

   - Customer timeline receives ASR/TCK events.

   - Backoffice can execute the full trouble flow.
