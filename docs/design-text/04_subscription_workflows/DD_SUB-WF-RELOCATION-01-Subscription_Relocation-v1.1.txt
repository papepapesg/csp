 1. What this is
 The relocation operation. Triggered by: a customer requesting an address change while keeping their current Package
 (CUSTOMER_REQUESTED_RELOCATION), or an admin override for ops scenarios (ADMIN_RELOCATION).

 Outcomes (at actual commit time): subscription homepass_id updated to target HomePass, previous_homepass_id
 snapshot retained, optional relocation fee charged per BIL-CFG-01 BillableEvent, physical work completed at both source
 and target via WO-01 SHIFTING flow (or self-move), FUL-07 bookkeeping updated on both HomePasses, source HomePass
 network-side de-provisioned (FUL-04), target HomePass provisioned for the current Package (FUL-03),
 last_relocated_at master field updated, customer notified.

 For non-IMMEDIATE effectiveTiming, the subscription remains ACTIVE on source during the wait. A second
 pending-future relocation is rejected; any state-affecting operation during the wait cancels the pending relocation.

 What this DD owns
   1. subscription_relocation_config table — per-operator config.

   2. Trigger taxonomy — 2 triggers with role gating.

   3. Target-HomePass validation rules — sellable, service-family compatibility for current Package, port-provisioned, status
     active.

   4. equipmentPath taxonomy + auto-inference rules.

   5. disconnectMode taxonomy + resolution rules.

   6. effectiveTiming taxonomy + non-IMMEDIATE timer + cancellation paths.

   7. WO-01 SHIFTING integration sequencing — when to create the WO, what context to pass, which events to park on.

   8. Trigger + cancel REST endpoints.

   9. Domain Kafka events — SubscriptionRelocationScheduled, SubscriptionRelocated,
     SubscriptionRelocationRejected, SubscriptionRelocationCancelled.

 What this DD does NOT own
   - BPMN files — per-operator satellites.

   - Worker implementations — DD_SUB-WF-FRAMEWORK-01-WORKERS.

   - Subscription state machine — SUB-LM-01.

   - Package catalog — SIP-01.

   - Service catalog — PLM-CFG-01.

   - HomePass row mutations — RLM-CFG-01. Read-only.

   - WO state machine, BPMN, contractor model, finalization mechanics — WO-01-FRAMEWORK +
     WO-01-FLOW-SHIFTING.

   - Equipment binding mutations — handled internally by WO-01 SHIFTING flow (for tech-dispatch path) or remain
     unchanged (for self-move path).

   - Relocation-fee math + BillableEvent definitions — BIL-01 + BIL-CFG-01.

   - Source-side service teardown + target-side activation + per-service-class provisioner fan-out — FUL-03 + FUL-04.

 4. Rules
 4.1 State precondition + transition
  Rule                                                                     Description

  R-SUB-WF-RELOCATION-01-S-1                                               Relocation requires subscription's status_code = ACTIVE at request time
                                                                           AND at commit time. Other statuses return 409
                                                                           INVALID_STATE_FOR_RELOCATION. For scheduled-future, commit-time
                                                                           re-validation may fail if the subscription was paused or terminated during the
                                                                           wait (per R-EF-5).

  R-SUB-WF-RELOCATION-01-S-2                                               The transition at commit is ACTIVE → PENDING_RELOCATION → ACTIVE.
                                                                           PENDING_RELOCATION is entered only during the commit window. For
                                                                           scheduled-future, subscription stays ACTIVE during the wait —
                                                                           PENDING_RELOCATION entered when timer fires.

  R-SUB-WF-RELOCATION-01-S-3                                               Per framework R-FW-1, relocation COMMIT is mutually exclusive with other
                                                                           state-affecting operations. A scheduled-future relocation in wait state DOES
                                                                           allow other operations to fire (which cancel the pending relocation per R-EF-5).

  R-SUB-WF-RELOCATION-01-S-4                                               The subscription's current_transition_type is set to RELOCATION during
                                                                           PENDING_RELOCATION. current_transition_reason_code is set to
                                                                           relocationTrigger. NOT set during scheduled-future wait.

  R-SUB-WF-RELOCATION-01-S-5                                               Restrictions on the subscription (active_restrictions[]) are preserved
                                                                           post-relocation. The new HomePass inherits the restriction set. Operator policy
                                                                           may decide to clear or re-evaluate; this DD does not.

  R-SUB-WF-RELOCATION-01-S-6                                               At most one pending-future relocation per subscription. A second
                                                                           non-IMMEDIATE request returns 409
                                                                           PENDING_RELOCATION_ALREADY_SCHEDULED. An IMMEDIATE request
                                                                           while a pending-future exists returns 409 (caller must cancel pending one first).

 4.4 Equipment path resolution
  Rule                            Description

  R-SUB-WF-RELOCATION-01-EQ-1     equipmentPath ∈ {KEEP_EXISTING, NEW_INSTALL}. If the request supplies
                                  a value, Drools validates it; otherwise Drools auto-infers from network-tech
                                  compatibility.

  R-SUB-WF-RELOCATION-01-EQ-2     Auto-inference: if sourceHomepass.networkPath.rootNodeType ==
                                  targetHomepass.networkPath.rootNodeType (same network tech),
                                  inferred = KEEP_EXISTING. Otherwise inferred = NEW_INSTALL. The
                                  operator's compatibility matrix in Drools may declare additional
                                  same-tech-but-incompatible pairs → forced to NEW_INSTALL.

  R-SUB-WF-RELOCATION-01-EQ-3     Request override: if the request supplies equipmentPath, Drools validates
                                  compatibility. Request KEEP_EXISTING with incompatible network-tech returns
                                  400 EQUIPMENT_INCOMPATIBLE_WITH_TARGET. Request NEW_INSTALL
                                  always accepted.

  R-SUB-WF-RELOCATION-01-EQ-4     The resolved equipmentPath is carried in flowContext to WO-01 at WO
                                  creation. The SHIFTING flow uses it to drive its internal equipment-handling
                                  logic (KEEP_EXISTING → tech transports existing equipment; NEW_INSTALL
                                  → tech recovers old + installs new). Equipment binding mutations happen
                                  inside WO-01.

  R-SUB-WF-RELOCATION-01-EQ-5     The resolved equipmentPath is persisted to the Kafka event payload + the
                                  framework's subscription_operation audit row.



 4.5 Disconnect mode resolution
  Rule                            Description

  R-SUB-WF-RELOCATION-01-DM-1     disconnectMode ∈ {TECH_DISPATCH, CUSTOMER_SELF_MOVE}. Resolution:
                                  (a) if equipmentPath = NEW_INSTALL, force TECH_DISPATCH; (b) if
                                  equipmentPath = KEEP_EXISTING and request supplies, use it; (c) if
                                  request omits, default from subscription_relocation_config.default
                                  _disconnect_mode_keep_existing. Request CUSTOMER_SELF_MOVE
                                  with NEW_INSTALL returns 400
                                  DISCONNECT_MODE_INCOMPATIBLE_WITH_EQUIPMENT_PATH.

  R-SUB-WF-RELOCATION-01-DM-2     When disconnectMode = TECH_DISPATCH: the workflow creates a
                                  SHIFTING WO via WO-01's POST /api/work-orders (per
                                  DD_WO-01-CONTRACT-FOR-SUB-WF §1.3), then parks on
                                  WorkOrderFinalized (per §1.2 of that contract). The SHIFTING flow
                                  internally handles disconnect-then-reconnect, equipment recovery, topology
                                  resolution, account sub-status updates.

  R-SUB-WF-RELOCATION-01-DM-3     When disconnectMode = CUSTOMER_SELF_MOVE: NO SHIFTING WO is
                                  created. The workflow logs a self-move acknowledgement step (no field
                                  intervention). The customer disconnects, transports, and reconnects their own
                                  equipment at the target. Equipment bindings remain unchanged on the
                                  subscription. KE WIK v1.1: path enabled but conservative defaults route most
                                  customers through TECH_DISPATCH.

  R-SUB-WF-RELOCATION-01-DM-4     The resolved disconnectMode is persisted to the Kafka event payload + the
                                  framework's subscription_operation audit row.

  Rule                          Description

                                SUSPEND_SERVICE at source HomePass — deactivate per-service-class
                                provisioning; (b) FUL-07 RELEASE on source HomePass — close
                                homepass_subscription_binding, decrement ATP, release port bindings
                                if AT_INSTALLATION; (c) physical work — if disconnectMode =
                                TECH_DISPATCH: create SHIFTING WO via POST /api/work-orders with
                                flowContext={equipmentPath, disconnectMode,
                                sourceHomepassId, targetHomepassId}, park on
                                WorkOrderFinalized; if CUSTOMER_SELF_MOVE: log self-move
                                acknowledgement and proceed; (d) FUL-03 ACTIVATE_SERVICE at target
                                HomePass with equipment bindings (from
                                WorkOrderFinalized.finalEquipmentBindings for tech-dispatch; from
                                pre-existing bindings for self-move); (e) FUL-07 CLAIM on target HomePass —
                                open new homepass_subscription_binding, increment ATP, capture port
                                bindings if AT_INSTALLATION; (f) commit master fields (homepass_id,
                                previous_homepass_id, last_relocated_at).

  R-SUB-WF-RELOCATION-01-F-2    Atomic-switch: subscription stays ACTIVE on source HomePass until step (d)
                                succeeds. If any step before (e) fails, the workflow reverts: FUL-04
                                RESUME_SERVICE at source (best-effort), FUL-07 CLAIM back on source
                                (best-effort if previously RELEASED), revert state to ACTIVE, emit
                                SubscriptionRelocationRejected. For TECH_DISPATCH path, if the
                                SHIFTING WO already partially completed (disconnect-phase done,
                                reconnect-phase failed), operations alert fires for manual recovery — equipment
                                is in tech custody or installed at target without subscription activation.

  R-SUB-WF-RELOCATION-01-F-3    WO timeout: handled by WO-01 framework
                                (wo_kind_config(kind=SHIFTING).default_timeout_days). On
                                timeout, WO-01 emits WorkOrderTimedOut. The workflow's catch fires; runs
                                F-2 compensation; emits SubscriptionRelocationRejected with
                                rejectionReasonCode = WO_TIMEOUT.

  R-SUB-WF-RELOCATION-01-F-4    WO cancellation: if the dispatcher cancels the SHIFTING WO mid-flow
                                (operations intervention), WO-01 emits WorkOrderCancelled. The
                                workflow's catch fires; runs F-2 compensation; emits
                                SubscriptionRelocationRejected with rejectionReasonCode =
                                WO_CANCELLED_BY_DISPATCHER.

  R-SUB-WF-RELOCATION-01-F-5    HomePass row is NOT mutated by this workflow. RLM-CFG-01 is read-only
                                from this workflow's perspective. WO-01 (SHIFTING flow) and FUL-07 own their
                                respective mutations independently.
